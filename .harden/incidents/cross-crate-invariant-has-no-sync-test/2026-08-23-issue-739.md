# Incident: cross-crate-invariant-has-no-sync-test

**Date:** 2026-08-23
**Topic:** cross-crate-invariant-has-no-sync-test
**Verdict:** pending (singleton — batch threshold not met, counter seed only)

## Symptom

Batch pass over `.harden/findings/issue-739.jsonl` (2 findings, 1 review
round). One finding: two independent functions in two different crates
(`pycc_mir::exception::resolve_exception_tag` and
`pycc_hir::exception::is_flat_builtin_exception_class`) each encode their own
notion of "the same fixed set of names" — an invariant the design explicitly
requires to hold, documented in prose in both functions' doc comments — but
no test asserted the two functions actually agree with each other. Each
function had tests of its own hardcoded expectations in isolation; neither
was tested against the other's output.

## Root cause

When two crates each independently re-derive a value that is supposed to be
identical, unit tests inside each crate naturally test "does this function
match its own author's expectation," not "do these two functions match each
other" — the second question requires a test that imports both crates and
compares outputs directly, which is a different (and easy to skip) test to
write than either crate's own local suite. The doc comments stated the
invariant; no executable check enforced it.

## Termination point

Not escalated — singleton, caught by the existing pinned review loop before
merge, fixed by adding the missing cross-crate comparison test directly. No
artefact proposed at this occurrence.

## Fixture / artifact / verify

None — threshold not met (class size 1, no journal match at time of
recording). This entry is the counter: a second occurrence of this pattern
(a cross-crate invariant stated in docs on both sides but asserted by
neither) should escalate — e.g. to a lint/rule reminding reviewers to check
for a same-invariant sync test whenever a change touches two independently
re-derived tables — rather than being logged as a third isolated singleton.
