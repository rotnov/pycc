Third occurrence, found by the pinned reviewer during the #695 D-185
partial decomposition of `crates/pycc_types/src/tests.rs`. Inserting
`mod constraints;` at the head of the existing `mod` block put it directly
beneath a `//` run that named only the #934 protocol-return split, so the
comment read as describing the new module.

What this occurrence adds to the class, and why it widens the tracked gate's
required shape a second time:

1. **The run is `//`, not `///`.** Both earlier entries are doc-comment
   (`///`) runs. A matcher keyed on `///` would not see this one. The class
   is "a comment run immediately above an item", not "a rustdoc run".
2. **The retargeted item is a `mod` declaration, not a function.** The gate's
   item grammar has to cover declaration lists, where an insertion is
   *expected* (alphabetical ordering) and therefore especially likely.
3. **It is insertion-caused**, unlike the topic's second entry -- so the
   first entry's diff-shaped proposal ("flag a newly-added item whose
   immediately preceding comment run is unchanged context") *would* have
   caught it, once widened per (1) and (2). That is the first positive
   evidence that the diff-shaped rung is the right one for at least part of
   the class.

Fixed inline here rather than routed to a follow-up, which is the opposite
of the second entry's disposition and deliberately so: there the correction
would have contaminated a pure-relocation diff whose whole reviewability
rested on byte-identity of the moved range; here the mis-targeted run is on
a line this change already edits (the insertion point itself), so
generalizing it is part of the same edit rather than an unrelated one.

Not built here, for the reason the first entry gives and #677 still tracks:
the matcher core needs its own unit tests under this repository's 100%
line/region coverage invariant, which makes it its own tracked change.
