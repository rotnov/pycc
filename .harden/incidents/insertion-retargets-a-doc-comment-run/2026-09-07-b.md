What it adds to the class, and why it widens the tracked gate's shape a third
time:

1. **The cause is deletion, not insertion.** Every earlier entry is an
   insertion placing a new item under someone else's comment run, or an edit
   changing an item under its own run. Here the *item was removed* and the run
   stayed behind, so the run silently re-bound to the next item in the file.
   The topic slug ("insertion-retargets") names only half the class; the
   general shape is "an edit changes which item a comment run precedes".
2. **It has a symmetric second half the earlier entries do not.** The moved
   test arrives in the child file stripped of the run that described it, so a
   detector that only guards the *source* file reports half the defect. A
   relocation has to carry the immediately-preceding comment run with the item.
3. **It is invisible to line-multiset identity.** The pure-move oracle this
   pull request leaned on (the moved range's line multiset is unchanged) holds
   exactly as well with the runs left behind as with them moved, because the
   runs never entered the moved range. A move-verification gate cannot be built
   on multiset identity alone; item-to-preceding-comment adjacency is a
   separate invariant.
