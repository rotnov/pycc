# Incident: new-case-misses-branching-sites (file 5, #1006)

**Batch:** `.harden/findings/issue-1006.jsonl`, rows 1 and 2 (both `fixed`).

## What happened

Two validation sites in the new status-snapshot code were written weaker
than an established sibling in the same module. Row 1: the collector typed
the check-runs payload as a list but not per element, so a null entry raised
`AttributeError` instead of taking the `Unavailable` path that the adjacent
`merged_pull_request` guard already implements with an `isinstance` check.
Row 2: the validator's one-parent invariant was `parent_count != 1`, which
`True` and `1.0` satisfy, while the sibling `run_id` / `number` checks in the
same function already required a real int that is not a bool. Both were
caught by `ievo:deep-reviewer` (rounds 1 and 2) and fixed by copying the
sibling predicate.

## Why it was not caught

Each guard was written fresh instead of by reading the module's existing
predicates; the plan (item 4) said "any error → `unavailable`" without naming
a per-element shape, and the module's own sibling checks were the only
statement of the stronger rule. Same mechanism as the topic's file 1 ("two
sibling rejection arms normalized asymmetrically"). Row 1 also fits
`out-of-model-input-lands-on-wrong-failure-tier` (an out-of-model shape
reached an interpreter exception rather than the fail-closed tier); it is
landed here because the earliest point in the pipeline that could have
prevented it is the sibling-asymmetry read, and cross-referenced there.
Gap type: content (plan) plus convention (module). Intra-batch count: 2.
Prior topic files: 4 (the topic's `rule` artefact in `issue-to-plan` step 3
targets dispatch sites named by a document, not sibling predicates inside a
module, so this occurrence is the same class at a different grain, not a
failure of that artefact).

## Artefact and why this type

Build nothing: review is the right rung. Both defects are semantic — which
element shape counts as unavailable, and whether a bool is an int — and no
grep separates `!= 1` from a correct comparison. The fixes' own subTest
mutations (`None` entry; `True`, `1.0`, `"1"`) are the guard for these two
sites. The topic's `incident.md` verdict (`no baseline (twice)`) stands; this
file is a counter, not a re-run.
