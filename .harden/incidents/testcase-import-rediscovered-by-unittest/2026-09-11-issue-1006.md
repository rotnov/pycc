# Incident: testcase-import-rediscovered-by-unittest (counter seed, #1006)

**Batch:** `.harden/findings/issue-1006.jsonl`, row 4 (`fixed` in `48d9b813`).

## What happened

`scripts/test_site_status_wiring.py` imported a `TestCase` subclass by name
(`from test_site_execution_wiring import ExecutionEvidenceWiringTests`) at
module scope. `unittest` discovery collects class objects per module, so the
six tests of that class ran twice under
`python3 -B -m unittest discover -s scripts -p 'test_*.py'`. Fixed by a
qualified module import; the collected count dropped from 1182 to 1176.

## Why it was not caught

Import style, not test logic: every test still passed, twice. Nothing in the
`scripts/` suite asserts that discovered test ids are unique. Gap type:
absence. Intra-batch count: 1. No existing topic fits
(`history-dependent-tests-in-shallow-discovery` is discovery-adjacent but a
different cause), so this is a new topic seed.

## Artefact and why this type

Mechanically detectable: the smallest static check is a `scripts/test_*.py`
wiring test asserting that `unittest.defaultTestLoader.discover("scripts",
"test_*.py")` yields no duplicate test ids, or a grep gate on
`^from test_\w+ import \w+` in `scripts/test_*.py` (zero hits after the fix).
Not built: under D-192's filing bar a doubled suite can neither cause an
incorrect merge decision nor hide a compiler defect; it only costs runtime.
Counter only — a second occurrence is the point at which the wiring test
becomes worth its maintenance.
