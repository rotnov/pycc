# Recurrence 2: findings pile committed without the mandated read-back

**Date:** 2026-09-04
**Topic:** process-record-written-without-read-back
**Verdict:** profit — the existing precommit artefact fired
**Source:** `/harden batch .harden/findings/issue-923.jsonl`, process finding raised by the batch itself

## Symptom

`f71a2f71` committed `.harden/findings/issue-923.jsonl` carrying the non-schema key
`outcome` instead of `disposition`, and no `fix_commit` on the `fixed` row. Branch
`autopilot/iter-2026-09-04-07` was CI-red from that commit until this batch:
`.github/workflows/ci.yml:87` runs `python3 -B -m unittest discover -s scripts`, which
discovers `scripts/test_check_harden_findings.py::test_real_repository_piles_conform`,
which walks every pile in `.harden/findings/`.

`.claude/skills/issue-implement/SKILL.md` §5.5 names the exact command that would have
caught this before the commit, inside the procedure that was running:
`python3 scripts/check_harden_findings.py .harden/findings/issue-<N>.jsonl`. It was not
run.

## Gap type

**Compliance.** Not a trigger gap in disguise: the instruction sits in the running
procedure and explains both failure modes it covers. The guard is maximally reachable —
it binds every harness and every human through CI — it was simply not invoked.

## The other half of the same checker: the machine-local exclude

`/Users/denis/projects/pycc-proto/.git/info/exclude:21` contains `.harden/`. It cannot
hide an already-tracked pile, but it silently swallows every new one from `git add -A`,
leaving `git status` clean. `.harden/findings/issue-910.jsonl` exists in no ref
(`git log --all --diff-filter=A` returns nothing) although #910 ran the identical loop
and merged as `12650781` via PR #924 — that pile was lost silently.

`check_harden_findings.py:67` (`git ls-files --error-unmatch`) is the guard for exactly
this, which is why §5.5 puts the invocation inside the procedure: **no gate can fire on
a record that does not exist.** The exclude file is machine-local and untracked, so a
tracked governance surface can detect the condition but can never remove it.

Every file this batch wrote under `.harden/` was staged with `git add -f` and confirmed
present in `git diff --cached --name-only` before committing, for that reason.

## Artefact

**Type:** precommit — already built, not rebuilt.
`scripts/check_harden_findings.py`, paired with `scripts/test_check_harden_findings.py`
and run by CI. Recurrence 1 (`2026-09-02-issue-729.md`) already settled the rung:
"the existing checker and its CI-run test are the right rung and reach every harness; a
second textual reminder would be the weaker artefact the ladder rejects." That holds.
`incident.md` further predicted this exact occurrence — the exclude entry "will repeat
for every `git add -A` in every worktree of that checkout until the entry is removed."

The fix this occurrence landed is the record repair itself, commit `1e1bb8c3`:
`disposition` and `fix_commit` added to all four rows, original `outcome` values kept
alongside.

## Residual hole, left open

An *absent* pile is invisible to a checker that only validates piles that exist.
Detecting absence is possible only on the writing side — which is the instruction that
was ignored here. Per step 6.2 (stop after two escalations), this is recorded rather
than escalated to a third rung: absence-detection stays open.

## Schema limitation observed

The pile schema's two dispositions (`fixed`, `refuted`) cannot express
accepted-but-out-of-scope. `reviewer-hypothesis-refuted-on-verification/2026-08-22-issue-719.md`
recorded the same expressive gap. Finding 1 was therefore encoded as `refuted` with the
loss called out in its note and the true verdict preserved in the non-schema `outcome`
key, rather than silently logging a reviewer error that did not happen. Adding a third
disposition value is identified and not built: it would diverge the tracked checker from
the vendored skill's own schema inside the pull request whose review surfaced it.
