Current implementation

The frontend and native backend cover v0.1 through v0.3, released as v0.3.0.

pycc check runs the parser → HIR → strict type checker without entering code generation. The build/run path lowers the same implemented language surface through MIR, LLVM object generation, host linking, and execution of a native binary.

Frontend language surface Implemented v0.1 subset

Arithmetic, comparisons, assignments, calls, recursion, if/while/for with range, booleans, floats, strings and basic f-strings are parsed and checked.

Compiler driver Build, run, check, init, explain, version

check emits validated human and JSON diagnostics; build and run compile the implemented surface; init and explain are implemented too.

Type system Strict checking and inference

Public annotations are required, Any is rejected, and monomorphic private-helper signatures are inferred and materialized before MIR.

Diagnostics Validated frontend codes

Parser failures use L0001; byte-exact CLI snapshots cover T0001, T0002, T0021, T0022, T0023, and T0024. An unknown module-level future feature reports L0001 with CPython's wording; import math as m compiles.

In the module prologue, from __future__ import annotations is accepted as a compile-time no-op and binds no feature name. The PEP 563 subset proves that this directive leaves supported own-class method annotations and already-defined-class function annotations working. Later-defined forward references, string annotations, and runtime __annotations__ introspection remain unsupported. This is partial evidence, not whole-PEP acceptance. The language support map links the directive's contract and evidence.

Quality 100% lines and regions

Pull requests must keep the Rust implementation at 100% line and region coverage before the protected branch can merge; the published llms.txt context is bounded by per-resource byte budgets within a reviewed 272 KiB ceiling.

Collections and generics v0.2 acceptance criteria met

list, dict, set, tuple, comprehensions, slicing, methods and generics match pinned CPython output on all five Tier-1 targets; --release clears its nbody speedup floor on every target.

Class model and pattern matching v0.3 acceptance criteria met

Classes, instantiation, attributes and methods, inheritance with C3 linearization, @property, dataclasses, enums, protocols, and structural pattern matching (match) with exhaustiveness all match pinned CPython output. Exceptions (try/except/finally, chaining, except*, parenthesis-free multi-type handlers) are implemented, and a user class can inherit from a builtin exception class, raise it, and have it caught. A bare X = 1 in a class body is the same class attribute as X: int = 1, type inferred from the literal; in a @dataclass body it stays rejected.

Scope boundary

pycc still has explicit implementation gaps.

The backend rejects bigint comparisons, several bigint arithmetic operations and float formatting outside the accepted v0.1 range. Unary operators are rejected earlier by HIR lowering with a spanned C0001 capability diagnostic, including under pycc check. Printing a class instance other than a @dataclass or a caught builtin exception, or a protocol-typed value, is C0001 (D-237). Strings, list, dict, set and class instances follow a leak-only policy until ownership analysis lands (D-107/D-124, D-154). set[int] has no membership test; tuple[...] slicing is deferred (D-118). Optional[T] and is/is not None have landed (D-197) with top-level narrowing only (D-199). Type diagnostics still use the line-1/column-1 placeholder span (D-043).

Do not use pycc in production.

Type diagnostics still use placeholder positions, safe help suggestions are not populated, and landing-page examples outside the implemented surface remain design targets.

Known correctness defects in the named v0.1 surface.

Unlike the deliberate scope limits above, these are open defects inside the named surface — programs that pass pycc check or pycc run but produce wrong results or abort where CPython succeeds:

  • #118: pycc check exits 0 for a name assigned only under if False and then read (CPython raises NameError).
  • #123: pycc check rejects "ab" * 3 with T0021 (valid standard Python; CPython prints ababab).
  • #145: multi-argument print evaluates arguments in a different order than CPython.
  • #146: supported bigint add/sub in a constant-magnitude loop leaks native memory linearly.
  • #147: pycc run aborts (exit 101) for bigint-valued range instead of raising a user-level exception.
  • #148: pycc run aborts with a codegen panic for large integer literals like 2**62.
  • #150: pycc run aborts with a Rust panic for range(..., step=0) instead of raising ValueError.

Not exhaustive: milestone acceptance proves the binary gates are green, not every combination inside a feature label.

Planned next

v0.4 — multi-file projects and incremental compilation — is in progress.

v0.1, v0.2, and v0.3's acceptance criteria are all met, and v0.3 is released as the v0.3.0 tag. The conformance matrix has 39 evidence-backed PYTHON_STANDARDS.md rows (2 whole-PEP acceptances, 37 tested subsets, 40 distinct PEPs); the v0.3 floors of 37 rows and 39 PEPs remain met without establishing full Python compatibility — see the roadmap's v0.3 section.

v0.4 — multi-file projects, imports, namespace packages, an incremental compilation cache, parallel codegen, and native os/pathlib/json/datetime support — is in progress on the delivery plan. v0.4 is in progress. Cross-file project from imports have landed. Bare/submodule imports, namespace handling, broader project CLI behavior, and incremental compilation remain incomplete. Its acceptance criteria: a Tier-2 corpus (black, isort, attrs, click) compiling at 80% or more of files, an incremental rebuild of 10k LOC under 200 ms, and a mac-to-Windows cross-compile demo in the README. The full multi-version conformance matrix, differential fuzzing, and corpus testing beyond the v0.3 floor remain planned test-depth work tracked alongside v0.4.

The 100% line/region coverage gate and the required frontend-perf-gate (currently a greater-than-7.0% regression floor, enforced by a paired predecessor/candidate measurement — see the roadmap) stay required through all of this work. The implementation gaps listed above are accepted boundaries the met milestones' acceptance criteria never required closing, not outstanding blockers.
