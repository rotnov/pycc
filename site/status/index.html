What pycc can do today.

pycc is a pre-alpha ahead-of-time compiler for typed Python 3.14. This page separates working, repository-tested behavior from the larger design contract. It is not a release announcement.

Current implementation

The frontend is broader than the native backend.

pycc check runs the broadened parser → HIR → strict type checker without entering code generation. Separately, the repository retains a working vertical slice from Python source through MIR, LLVM object generation, host linking, and execution of a native binary.

Frontend language surface Full v0.1 grammar

Arithmetic, comparisons, assignments, calls and returns, recursion, if/while/for with range, booleans, floats, strings, and basic f-strings are parsed and checked.

Compiler driver Build, run, check, version

check supports validated human and JSON diagnostics. build and run retain their slice-level paths; other documented commands remain planned.

Type system Strict checking and inference

Public annotations are required, Any is rejected, and monomorphic private-helper signatures are inferred and materialized before MIR.

Diagnostics Validated frontend codes

Parser failures use L0001; byte-exact CLI snapshots cover T0001, T0002, T0021, T0022, T0023, and T0024.

Portability Five native CI targets

Linux x64/arm64, macOS x64/arm64, and Windows x64 build and test in CI. A macOS arm64-to-x64 cross-host path is verified.

Quality 100% lines and regions

Pull requests must keep the current Rust slice at 100% line and region coverage before the protected branch can merge.

Scope boundary

Native code generation remains slice-only.

pycc build and pycc run still lower only module-level print(<i64 literal>), zero-argument function definitions, and explicit zero-argument calls. New frontend constructs reach an explicit backend boundary until the v0.1 MIR, code generation, and runtime work lands. Containers, Optional, and narrowing are also outside the current frontend grammar.

Do not use pycc in production.

HIR and type diagnostics still use placeholder source positions, safe help suggestions are not populated, and unsupported backend constructs still fail at the explicit pre-alpha boundary. Landing-page build examples remain design targets unless marked as implemented.

Planned next

Code generation and runtime breadth are next.

The next compiler slice lowers the implemented v0.1 frontend constructs through MIR and LLVM, then expands the runtime for integers, floats, strings, booleans, control flow, recursion, and basic f-strings. D-048's performance transition runs independently of that compiler sequence: the tracked CI workflow tells whether exact-head activation is pending, the required frontend measurement and greater-than-2% regression gate are seeding their first main-owned baseline, or the gate is in bootstrap-free steady state. The conformance testkit, named demos, and final v0.1 acceptance pass follow the code-generation and runtime work.
