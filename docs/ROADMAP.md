**Follow-up (untracked by any issue yet, per D-116's own correction note):** D-116 point 4 originally claimed tuple's function-argument/return pass-through "ships now since the representation makes it free." That is true only at the `pycc_codegen` layer (`build_call_to`, `MirStmt::Return`, and `emit_assign` all accept `Scalar::Tuple` with a plain pass-through arm, unit-tested directly against hand-built MIR). It is not reachable from real, unannotated Python source today: `pycc_types`' private-helper signature-inference solver (`infer_function_signatures_with_solver`) has no unification-friendly representation for any container literal, so `collect_expr_constraints` produces no term for `TupleLiteral`, `ListLiteral`, `DictLiteral`, or `SetLiteral` alike — an entirely unannotated (`_`-prefixed) private helper can never have a container-typed parameter or return type inferred. This is a pre-existing gap shared identically by `list[int]`/`dict[str, int]`/`set[int]`, not something PR-11b introduced or was scoped to fix; confirmed empirically for all four container types, including one actively misleading diagnostic (`def _h(): t = (10, 20); return t` reports "local name `t` is not bound before this use" even though `t` is assigned on the preceding line, because a container-literal assignment's target never receives a solver binding at all). Closing this gap needs **two** independent fixes, not one: (a) `pycc_types` needs to give container-typed terms a real unification representation (or a narrower, container-aware fallback path distinct from today's scalar-only solver); and (b) even with (a) fixed, `pycc_codegen`'s own `emit_expr` function has no dedicated `MirExpr::Call` result-dispatch arm for `Ty::List`/`Ty::Dict`/`Ty::Set`/`Ty::Tuple` either — its catch-all arm panics with a message naming the specific type ("a `{ty}`-typed call result is not supported yet") for all four container types today, so a hypothetically-now-inferrable `p = make_pair()` would still panic, just one layer later, in codegen instead of type-checking. A future PR closing this gap needs both (a) and (b) before any of the four containers can genuinely cross a function boundary from real source.
