Milestone = shippable + demo-able. Acceptance criteria are binary; a milestone isn't done until they're green on **all Tier-1 platforms** (Linux x64/arm64, macOS x64/arm64, Windows x64).

| Type system | Real v0.1 frontend subset | [`pycc_types::check_and_resolve`](../crates/pycc_types/src/lib.rs) enforces public annotations (`T0001`), rejects `Any` (`T0002`), infers and materializes local/private-helper signatures over the v0.1 primitive subset before MIR, classifies parameters plus nested assignment/`for` targets as function-local before resolving reads, applies Python true-division and `bool`-as-`int` rules, validates call/range/assignment compatibility, and rejects non-`None` functions when the conservative v0.1 control-flow analysis finds a fallthrough path. An initialized scalar-annotated local with no earlier representation binding uses the declaration type for its own solver binding without retagging the initializer's independently inferred type; compatible re-declarations retain the first binding. Scalar declaration bounds are aggregated per inference root and applied only as order-independent fallbacks when harder call/operator evidence leaves the source unresolved ([#241](https://github.com/rotnov/pycc/issues/241)). Non-scalar annotated targets instead receive local-only unresolved solver bindings; an inference root joined to one cannot resolve an otherwise-inferred private parameter or return as a container, even through hard call evidence, while existing container inference from explicit function-signature evidence remains unchanged. This type-inference correction remains separate from the now-fixed runtime identity issue [#240](https://github.com/rotnov/pycc/issues/240) (D-141); value-less annotation state remains tracked by [#245](https://github.com/rotnov/pycc/issues/245). Function locals never fall back to same-named module globals before binding; the validation pass tracks definite-assignment joins across `if`/`while`/`for` control flow (T0041, [#360](https://github.com/rotnov/pycc/pull/360), D-147) and the private-helper constraint solver now mirrors that tracking with a `maybe_bindings` side-table on `ConstraintEnvironment` ([#359](https://github.com/rotnov/pycc/issues/359)): a name assigned in only one `if` branch (no `else`), only in a loop body, or introduced as a `for` loop variable is marked maybe-bound and skipped during `collect_expr_constraints`'s `Name` unification, so the solver does not infer a private-helper return type from a value that may not exist. A call target resolves through the active value binding before any builtin or function-registry fallback ([#133](https://github.com/rotnov/pycc/issues/133)): a module-level `helper = 1` makes every later `helper()` -- at top level (source order, pass 2) and in any function body (checked against the final module environment per D-041) -- a `T0021` non-callable rejection in both the final-validation and private-helper-inference paths, while a top-level call *before* the shadowing assignment still resolves the function and a later `def` rebinds its own name over an earlier value binding (the gate always tests the net source-order binding, while D-040's representation stickiness survives the `def`, so an incompatible value reassignment after it still fails `T0023`), keeping [#22](https://github.com/rotnov/pycc/issues/22)'s execution-order questions separate; D-110 records the rule and its three deliberate ordering consequences (final-environment body rejection of later-rebind programs, callee-before-argument diagnostic order, accurate non-callable messages for bindings that shadow nothing). Equality (`==`/`!=`) requires operand-type compatibility like every other typed operation, and numeric widening (`int` where `float` is annotated) requires an explicit conversion rather than an implicit one — both deliberate, `mypy --strict`-or-stricter choices recorded in D-086. The numeric-widening conversion now has a usable remedy for the `int`-to-`float` case: `float(x)` for `x: int | float | bool` is a real, callable builtin ([#181](https://github.com/rotnov/pycc/issues/181)), hand-recognized the same way `len()` is, reusing the existing `int_to_float`/`to_float` runtime conversion, and correctly deferring to a user-defined `float` of the same name when one is declared. `int(...)`/`bool(...)`/`str(...)` conversions remain unimplemented; a bigint-valued `int` argument to `float(...)` aborts, the same pre-existing limitation every other numeric promotion to `float` already has. String repetition (`str * int` / `int * str`, `bool` count included) now type-checks to `str` in both the validation pass and private-helper constraint inference ([#574](https://github.com/rotnov/pycc/issues/574), Part 1 of [#123](https://github.com/rotnov/pycc/issues/123)); native execution followed in [#575](https://github.com/rotnov/pycc/issues/575) (Part 2 of the same issue), so `pycc build`/`run` now lower it through `pycc_rt_str_repeat` instead of stopping at the retired D-072 exit-`101` boundary. **[#432](https://github.com/rotnov/pycc/issues/432) — Inheritance, C3 MRO, and `@override` (PR-16 Part 1):** implemented the foundational inheritance machinery. `class Derived(Base):` parses base class names from the class definition's argument list, computes the C3 linearization (MRO) at compile time, and stores it in `HirClassDef.mro`. Validation rejects unknown base classes, circular inheritance, duplicate bases, inheriting from generic classes, and inconsistent C3 linearizations, all with `C0001`. Method, attribute, and property resolution walks the MRO (most-derived-first) in the type checker (`resolve_method_call`, `resolve_attr_get`, `check_attr_set`) and the MIR lowering (`lower_expr`'s `AttrGet`/`MethodCall` arms, `lower_stmt`'s `AttrSet` arm), so a method or attribute declared in a base class is found when accessed on a derived instance, and a subclass method shadows a base class method of the same name. The instance's flat attribute-slot layout is computed from the MRO (`mro_attrs`/`mro_attr_count`), with each unique attribute across the MRO getting one slot and the most-derived class's declaration winning on name conflicts. `@override` (PEP 698) is recognized as a method decorator and validated at HIR-lowering time: if the decorated method does not override a same-named method or property in any base class (walking the MRO, excluding the current class), `T0031` is emitted. **[#433](https://github.com/rotnov/pycc/issues/433) — `super()` and base class initialization (PR-16 Part 2):** implemented zero-argument `super()` (PEP 3135) and base class `__init__` calls using static dispatch (D-160). `super().__init__(args)` and `super().method(args)` are recognized at HIR-lowering time in `pycc_hir::expr::lower_expr`'s `Expr::Call` and `Expr::Attribute` arms, lowering to `HirExpr::MethodCall { base: HirExpr::Super, ... }` and `HirExpr::AttrGet { base: HirExpr::Super, ... }` respectively. A bare `super()` or `super()` outside a method body is rejected with `C0001`. The type checker (`pycc_types::class::resolve_super_method_call`, `resolve_super_attr_get`) resolves the target starting from the next class after the current class in the MRO, with `self` (the most-derived instance) as the implicit first argument. The MIR lowering (`pycc_mir::lower_expr`'s `Super`-base handling in `MethodCall`/`AttrGet` arms) emits a direct `MirExpr::Call` to the resolved base method's mangled name with `self` prepended, or, for a property read, a direct call to the base class's getter with `self` as its argument — no vtable, no runtime dispatch (D-006 static-dispatch framing). A 3-level `super()` chain (`C` → `B` → `A`) works correctly. Cooperative multiple inheritance (diamond pattern where `super()` in a middle class should skip to the next class in the *caller's* MRO, not the defining class's own MRO) is an accepted limitation of the static-dispatch model, documented in D-160. `super().attr` resolves only the class-level members a CPython `super` object actually proxies along the MRO: a base class `@property` is such a member, so `super().attr` lowers to a call to the base class's getter. An *instance* attribute is not proxied, and `super().<instance attr>` is rejected with `T0047` (#587) rather than lowering to a slot read against `self`, matching CPython's `AttributeError: 'super' object has no attribute '<attr>'`; the equivalent read is spelled `self.<attr>`. `super().attr = value` is rejected with `C0001` (attribute assignment through `super()` is not yet implemented). End-to-end integration tests: `tests/issue_433_super.rs`. HIR and MIR unit tests cover `super()` lowering and direct-call resolution.

**[#436](https://github.com/rotnov/pycc/issues/436) — `@classmethod` and `@staticmethod` (PR-16 Part 3):** implemented `@classmethod` and `@staticmethod` decorators with static dispatch. `@classmethod`-decorated methods receive an implicit `cls` parameter typed as the defining class's instance type, lowered to `MethodKind::ClassMethod` with a distinct mangled name (`<ClassName>.<method>.classmethod`); `@staticmethod`-decorated methods have no implicit `self`/`cls` parameter, lowered to `MethodKind::StaticMethod` with a distinct mangled name (`<ClassName>.<method>.static`). Both are callable through class syntax (`ClassName.method(...)`) and instance syntax (`instance.method(...)`), dispatched statically — no vtable. Inherited static and class methods are resolved via the MRO. `NullInstance` is used for class-level classmethod dispatch in codegen. Same-name collisions between static/class methods and regular methods, properties, or the opposite decorated kind are rejected with `C0001` in both definition-order directions. Decorating `__init__` with `@classmethod` or `@staticmethod` is rejected with `C0001`. The first classmethod parameter must be named `cls`. End-to-end integration tests: `tests/issue_436_classmethod_staticmethod.rs`. HIR unit tests cover collision detection paths.

**[#378](https://github.com/rotnov/pycc/issues/378) — Dataclasses (PEP 557), `dataclass_transform` (PEP 681), and class decorators (PEP 3129):** implemented a narrow, statically dispatched dataclass feature. `@dataclass` (bare) and `@dataclass_transform()` (bare, keyword arguments accepted but ignored) trigger auto-generation of `__init__` (one required parameter per annotated field, in declaration order), `__eq__` (field-by-field equality returning `bool`), and `__repr__` (producing `ClassName(field=value, ...)`). Class-level annotated assignments (`x: int`) are accepted as dataclass fields; all other class-body statements are rejected with `C0001`. Field defaults, `field(default=...)`, `field(default_factory=...)`, and `@dataclass(frozen=True)` or any other option-bearing form are rejected with `C0001`. Dataclass inheritance merges parent fields (via MRO, parent-before-child order, deduplicating redeclared fields) with the child's own fields; a dataclass inheriting from a non-dataclass base is rejected with `C0001`. Explicit `__init__`, `__eq__`, or `__repr__` definitions in a `@dataclass` body are rejected with `C0001`. `__ne__` is lowered at the MIR level as the negation of the generated `__eq__` call (no separate method is synthesized). `print()` and f-string interpolation of a dataclass instance are rewritten at the MIR level to call the generated `__repr__`. Same-class `==`/`!=` comparisons between dataclass instances are accepted (the synthesized `__eq__` has a known-correct signature); ordering operators (`<`, `<=`, `>`, `>=`) between instances and `==`/`!=` between non-dataclass instances produce `T0021` (pycc has no general dunder dispatch). Incompatible class comparisons also produce `T0021`. PEP 3129 class-decorator syntax is supported as the vehicle for `@dataclass`/`@dataclass_transform()`; other class decorators are rejected with `C0001`. General function-decorator syntax remains unsupported. `HirClassDef` carries `is_dataclass: bool` and `dataclass_fields: Vec<(String, Ty)>` through the pipeline. Conformance fixtures: `pep_0557_dataclasses.py`, `pep_0681_dc_transform.py`, `pep_3129_class_deco.py`. End-to-end integration tests: `tests/issue_378_dataclasses.rs`. **[#435](https://github.com/rotnov/pycc/issues/435) — `isinstance`/`issubclass`, `__init_subclass__`, `__set_name__`, `__class_getitem__`:** implemented compile-time evaluation of `isinstance` and `issubclass` using pycc's static dispatch model (D-006 — every variable's runtime type is exactly its declared type, so both builtins are always evaluable at compile time). Both are intercepted before generic call inference in `pycc_types::infer_expr_in` and `collect_expr_constraints`, and before generic arg lowering in `pycc_mir::lower_expr`. The class arguments (bare names or tuples of bare names) are never lowered as runtime values. The MIR emits `MirExpr::BoolLiteral(result)` — no runtime RTTI or type tags. Tuple targets are supported. Wrong arg counts produce `T0021`; unknown class names produce `T0001`; non-class arguments produce `T0021`. Shared evaluation helpers (`eval_isinstance_single`, `eval_issubclass_single`, `extract_class_names`, `is_builtin_type_name`) live in `pycc_hir` and are consumed by both `pycc_types` and `pycc_mir`. `__init_subclass__` (PEP 487) is recognized as a regular method; if a base class defines it, a subclass's own `__init_subclass__` must be statically evaluable (only `pass` or a docstring body is accepted — side-effecting statements are rejected with `C0001`). `__set_name__` (PEP 487) is accepted as a valid method name (not triggerable yet because class-level attribute assignments are unsupported). `__class_getitem__` (PEP 560) is accepted as a static method and enables `ClassName[type_arg]` subscript syntax in type annotations, resolving to `Ty::Instance(ClassName)` and ignoring the type argument; [#611](https://github.com/rotnov/pycc/issues/611) later gated that annotation form on the class actually being subscriptable: the class must define `__class_getitem__` somewhere in its MRO, in either the `@staticmethod` or the `@classmethod` spelling, or be a PEP 695 generic class (`class C[T]:`), which CPython makes implicitly subscriptable through `Generic`. Any other known class name in `ClassName[type_arg]` annotation position is rejected with `T0044`, the same code the value position uses; a name that is not a known class resolves as before. `Stmt::Pass` is now filtered as a no-op in `lower_body` (previously rejected with `C0001`). **[#379](https://github.com/rotnov/pycc/issues/379) — Enums (PEP 435, PR-19):** implemented scoped `class C(Enum):` with integer-literal member values. A class whose sole base is the bare name `Enum` is detected at HIR-lowering time as an enum class: `Enum` is consumed as a marker (not registered as a real base), the class has no `__init__`, no methods, and no items, and its members are stored in `HirClassDef.enum_members: Vec<(String, i64)>` preserving the actual integer literal from the source. **[#380](https://github.com/rotnov/pycc/issues/380) — PEP 544 protocols and structural typing (PR-20):** implemented compile-time-only structural protocols with no runtime vtable or protocol object (D-166). `class P(Protocol):` with method declarations (`...`/`pass` bodies) and attribute annotations is lowered at HIR time into `HirClassDef` with `is_protocol: true` and `protocol_members: Vec<ProtocolMember>` — protocol methods are not lowered to `HirItem::Function`s. ## v0.7 — transparent CPython interop

This milestone is planned and **not implemented** in the current compiler.
Ordinary standard-Python imports such as `import numpy as np` automatically
classify CPython-backed packages and bundle a pinned CPython 3.14/package/native
dependency closure without requiring pycc-specific source rewrites. The
planned `auto` (default), `allowlist`, and `deny` policies plus `--pure` provide
deployment control; the typed `I04xx` boundary, `unittest`/`logging`/`argparse`,
and an optional low-level `pycc.interop.cpython` API remain part of the
milestone (D-128).

**Accept:** an unchanged CPython-compatible app using `import numpy as np`
builds and runs on all Tier-1 targets without a separately installed Python;
the package/runtime closure is pinned and reproducible; `auto` succeeds without
per-package approval; `allowlist` accepts an allowed import root and rejects an
otherwise-resolvable unlisted root with `I0402`; both `deny` and `--pure`
reject a CPython-backed fixture, while a separate native-only fixture builds
successfully under both modes and its artifact has no CPython/libpython
dependency; and a published boundary-cost benchmark reports copied versus
zero-copy transfers.

## v1.x — Python 3.15 adoption

Starts only after both pycc v1.0 and upstream Python 3.15.0 final. Add the 3.15
grammar, typing rules, import behavior, builtins, and stdlib surface listed in
the preview matrix while preserving Python 3.14 compatibility.

The gate-opening change must introduce a machine-readable supported-language
registry consumed by project-configuration validation and conformance CI. For
each supported level, that registry binds the accepted configuration value,
cumulative fixture range, and pinned CPython oracle; CI must verify that the
documented matrix and executable conformance jobs agree with it. Until that
change lands, the 3.15 rows remain planning inputs rather than
supported-language claims.

**Accept:** every Python 3.15 matrix row is ✅ or explicitly
`rejected-by-design` with a negative test; differential conformance runs
the cumulative Python 3.0–3.15 fixture set against a pinned current Python 3.15
patch on all Tier-1 targets; the independent Python 3.14 configuration keeps
the complete Python 3.0–3.14 suite green; a new ADR supersedes D-012 and
records the supported-version policy; the supported-language registry and its
matrix/oracle consistency check are required and green.
