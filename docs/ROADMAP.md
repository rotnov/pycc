| Type system | Real v0.1 frontend subset | [`pycc_types::check_and_resolve`](../crates/pycc_types/src/lib.rs) enforces public annotations (`T0001`), rejects `Any` (`T0002`), infers and materializes local/private-helper signatures over the v0.1 primitive subset before MIR, classifies parameters plus nested assignment/`for` targets as function-local before resolving reads, applies Python true-division and `bool`-as-`int` rules, validates call/range/assignment compatibility, and rejects non-`None` functions when the conservative v0.1 control-flow analysis finds a fallthrough path. An initialized scalar-annotated local with no earlier representation binding uses the declaration type for its own solver binding without retagging the initializer's independently inferred type; compatible re-declarations retain the first binding. Scalar declaration bounds are aggregated per inference root and applied only as order-independent fallbacks when harder call/operator evidence leaves the source unresolved ([#241](https://github.com/rotnov/pycc/issues/241)). Non-scalar annotated targets instead receive local-only unresolved solver bindings; an inference root joined to one cannot resolve an otherwise-inferred private parameter or return as a container, even through hard call evidence, while existing container inference from explicit function-signature evidence remains unchanged. This type-inference correction remains separate from the now-fixed runtime identity issue [#240](https://github.com/rotnov/pycc/issues/240) (D-141); value-less annotation state remains tracked by [#245](https://github.com/rotnov/pycc/issues/245). Function locals never fall back to same-named module globals before binding; the validation pass tracks definite-assignment joins across `if`/`while`/`for` control flow (T0041, [#360](https://github.com/rotnov/pycc/pull/360), D-147) and the private-helper constraint solver now mirrors that tracking with a `maybe_bindings` side-table on `ConstraintEnvironment` ([#359](https://github.com/rotnov/pycc/issues/359)): a name assigned in only one `if` branch (no `else`), only in a loop body, or introduced as a `for` loop variable is marked maybe-bound and skipped during `collect_expr_constraints`'s `Name` unification, so the solver does not infer a private-helper return type from a value that may not exist. A call target resolves through the active value binding before any builtin or function-registry fallback ([#133](https://github.com/rotnov/pycc/issues/133)): a module-level `helper = 1` makes every later `helper()` -- at top level (source order, pass 2) and in any function body (checked against the final module environment per D-041) -- a `T0021` non-callable rejection in both the final-validation and private-helper-inference paths, while a top-level call *before* the shadowing assignment still resolves the function and a later `def` rebinds its own name over an earlier value binding (the gate always tests the net source-order binding, while D-040's representation stickiness survives the `def`, so an incompatible value reassignment after it still fails `T0023`), keeping [#22](https://github.com/rotnov/pycc/issues/22)'s execution-order questions separate; D-110 records the rule and its three deliberate ordering consequences (final-environment body rejection of later-rebind programs, callee-before-argument diagnostic order, accurate non-callable messages for bindings that shadow nothing). Equality (`==`/`!=`) requires operand-type compatibility like every other typed operation, and numeric widening (`int` where `float` is annotated) requires an explicit conversion rather than an implicit one — both deliberate, `mypy --strict`-or-stricter choices recorded in D-086. Later-language features such as containers, `Optional`, and narrowing have no grammar surface yet. |

This is a pre-existing gap shared identically by `list[int]`/`dict[str, int]`/`set[int]`, not something PR-11b introduced or was scoped to fix; confirmed empirically for all four container types, including one actively misleading diagnostic (`def _h(): t = (10, 20); return t` reports "local name `t` is not bound before this use" even though `t` is assigned on the preceding line, because a container-literal assignment's target never receives a solver binding at all). **D-146 (#239) narrowed this gap for `list` specifically:** `collect_expr_constraints`'s `ListLiteral`/`Subscript`/`ListPop` arms now represent `Ty::List` as a destructured element-type carrier for homogeneous scalar-element lists, enabling scalar return-type inference for `def _first(): xs = [1]; return xs[0]` and `def _pop(): xs = [1, 2]; y = xs.pop(); return y` (return type `int`, no codegen change). The carrier is destructured, never unified — `unify_terms`/`merge_inferred_types` are unchanged — and `dict`/`set`/`tuple` remain in the scalar-only gap. The broader gap — a container-typed *parameter or return* crossing a function boundary — still needs **two** independent fixes: (a) `pycc_types` needs to give container-typed terms a real unification representation (or a narrower, container-aware fallback path distinct from today's scalar-only solver); and (b) even with (a) fixed, `pycc_codegen`'s own `emit_expr` function has no dedicated `MirExpr::Call` result-dispatch arm for `Ty::List`/`Ty::Dict`/`Ty::Set`/`Ty::Tuple` either — its catch-all arm panics with a message naming the specific type ("a `{ty}`-typed call result is not supported yet") for all four container types today, so a hypothetically-now-inferrable `p = make_pair()` would still panic, just one layer later, in codegen instead of type-checking. A future PR closing the broader gap needs both (a) and (b) before any of the four containers can genuinely cross a function boundary from real source.

**Follow-up (untracked by any issue yet, per D-116 point 3):** `for x in t:` iteration over a tuple is deferred — it needs per-position codegen for a heterogeneous tuple, a materially different problem than `ForList`/`ForDict`/`ForSet`'s homogeneous-element loops, since each position may have its own element type.

**Follow-up (untracked by any issue yet, per D-116 point 3):** tuple-unpacking assignment (`a, b = t`) is deferred — it is a new multi-target assignment form nothing in `HirStmt::Assign`'s current shape supports today, unlike a single-name target.

**Follow-up (untracked by any issue yet, per D-116 point 3):** a `tuple[...]` annotation syntax (e.g. `def f(t: tuple[int, int])`) is deferred, mirroring D-105 cut 1's identical deferral for `list[T]` — today a tuple's type can only ever be established structurally (literal construction or, once the gap above closes, call-site inference), never written directly in an annotation.

Part 1 threads the class name into `annotation_to_ty` so `Self` resolves to `Ty::Instance(class_name)` at HIR-lowering time. Part 2 makes the class name resolvable as a type annotation within the class's own method bodies (self-referential annotations), mirroring PEP 649/749's deferred-evaluation semantics for the class-model scope. Part 3 adds `class C[T]:` with a single type parameter and scalar-only instantiation (`C[int](args)`): a new `HirExpr::GenericClassInstantiate` variant is lowered at HIR time, `pycc_types::monomorphize` pre-scans for all instantiations and produces specialized methods + class definitions (substituting `T` with the concrete scalar type and rewriting `Ty::Instance("C")` to `Ty::Instance("0gen_C__T_int")`), and `is_assignable` accepts `Ty::Param` as matching any concrete scalar during type checking. Conformance fixtures: `pep_0673_self.py`, `pep_0649_deferred_ann.py`, `pep_0695_generic_classes.py`. Per D-102, `PYTHON_STANDARDS.md` rows stay `☐` until CI-observed green on all 5 Tier-1 targets.

**[#377](https://github.com/rotnov/pycc/issues/377) — `@property` getter and setter:** implemented as an HIR-level transformation that reuses the existing method-call infrastructure with no new MIR or codegen variant. A `@property`-decorated method is lowered into a `PropertyDef` entry on `HirClassDef` (not the methods table), and `@<name>.setter` decorates a companion setter method. At the type-checking level, `resolve_attr_get` checks the property table before the regular attribute slot table (matching CPython's descriptor protocol precedence), returning the getter's return type for `base.attr`; `check_attr_set` redirects `base.attr = value` to the setter's parameter type, rejecting a read-only property (no setter) with `T0044` and a type mismatch with `T0021`. At the MIR level, `lower_expr`'s `AttrGet` arm rewrites `base.attr` to `MirExpr::Call { callee: getter, args: [base] }`, and `lower_stmt`'s `AttrSet` arm rewrites `base.attr = value` to `MirStmt::ExprStmt(MirExpr::Call { callee: setter, args: [base, value] })`. Conformance fixtures: `property_basic.py`, `property_setter.py`. End-to-end integration tests: `tests/issue_377_property.rs`. Per D-102, `PYTHON_STANDARDS.md` rows stay `☐` until CI-observed green on all 5 Tier-1 targets.

**[#432](https://github.com/rotnov/pycc/issues/432) — Inheritance, C3 MRO, and `@override` (PR-16 Part 1):** implemented the foundational inheritance machinery. `class Derived(Base):` parses base class names from the class definition's argument list, computes the C3 linearization (MRO) at compile time, and stores it in `HirClassDef.mro`. Validation rejects unknown base classes, circular inheritance, duplicate bases, inheriting from generic classes, and inconsistent C3 linearizations, all with `C0001`. Method, attribute, and property resolution walks the MRO (most-derived-first) in the type checker (`resolve_method_call`, `resolve_attr_get`, `check_attr_set`) and the MIR lowering (`lower_expr`'s `AttrGet`/`MethodCall` arms, `lower_stmt`'s `AttrSet` arm), so a method or attribute declared in a base class is found when accessed on a derived instance, and a subclass method shadows a base class method of the same name. A derived class without its own `__init__` inherits the base class's constructor, resolved via the MRO at instantiation time in both the type checker (`resolve_instantiation`) and the MIR lowering (`Instantiate`'s `ctor` field). The instance's flat attribute-slot layout is computed from the MRO (`mro_attrs`/`mro_attr_count`), with each unique attribute across the MRO getting one slot and the most-derived class's declaration winning on name conflicts. `@override` (PEP 698) is recognized as a method decorator and validated at HIR-lowering time: if the decorated method does not override a same-named method or property in any base class (walking the MRO, excluding the current class), `T0031` is emitted. Conformance fixtures: `inheritance_basic.py`, `pep_0698_override.py`. End-to-end integration tests: `tests/issue_432_inheritance.rs`. HIR unit tests and type checker unit tests cover MRO computation, `@override` validation, inherited `__init__`, and MRO-aware resolution. Per D-102, `PYTHON_STANDARDS.md` row for PEP 698 stays `☐` until CI-observed green on all 5 Tier-1 targets.

**[#433](https://github.com/rotnov/pycc/issues/433) — `super()` and base class initialization (PR-16 Part 2):** implemented zero-argument `super()` (PEP 3135) and base class `__init__` calls using static dispatch (D-160). `super().__init__(args)` and `super().method(args)` are recognized at HIR-lowering time in `pycc_hir::expr::lower_expr`'s `Expr::Call` and `Expr::Attribute` arms, lowering to `HirExpr::MethodCall { base: HirExpr::Super, ... }` and `HirExpr::AttrGet { base: HirExpr::Super, ... }` respectively. A bare `super()` or `super()` outside a method body is rejected with `C0001`. The type checker (`pycc_types::class::resolve_super_method_call`, `resolve_super_attr_get`) resolves the target starting from the next class after the current class in the MRO, with `self` (the most-derived instance) as the implicit first argument. The MIR lowering (`pycc_mir::lower_expr`'s `Super`-base handling in `MethodCall`/`AttrGet` arms) emits a direct `MirExpr::Call` to the resolved base method's mangled name with `self` prepended, or a `MirExpr::AttrGet` with `self` as the base — no vtable, no runtime dispatch (D-006 static-dispatch framing). A 3-level `super()` chain (`C` → `B` → `A`) works correctly. Cooperative multiple inheritance (diamond pattern where `super()` in a middle class should skip to the next class in the *caller's* MRO, not the defining class's own MRO) is an accepted limitation of the static-dispatch model, documented in D-160. `super().attr` is rejected with `T0021` when an intervening class in the MRO redeclares the attribute with a different type (shared-slot type-safety restriction). `super().attr = value` is rejected with `C0001` (attribute assignment through `super()` is not yet implemented). End-to-end integration tests: `tests/issue_433_super.rs`. HIR and MIR unit tests cover `super()` lowering and direct-call resolution.

**[#436](https://github.com/rotnov/pycc/issues/436) — `@classmethod` and `@staticmethod` (PR-16 Part 3):** implemented `@classmethod` and `@staticmethod` decorators with static dispatch. `@classmethod`-decorated methods receive an implicit `cls` parameter typed as the defining class's instance type, lowered to `MethodKind::ClassMethod` with a distinct mangled name (`<ClassName>.<method>.classmethod`); `@staticmethod`-decorated methods have no implicit `self`/`cls` parameter, lowered to `MethodKind::StaticMethod` with a distinct mangled name (`<ClassName>.<method>.static`). Both are callable through class syntax (`ClassName.method(...)`) and instance syntax (`instance.method(...)`), dispatched statically — no vtable. Inherited static and class methods are resolved via the MRO. `NullInstance` is used for class-level classmethod dispatch in codegen. Same-name collisions between static/class methods and regular methods, properties, or the opposite decorated kind are rejected with `C0001` in both definition-order directions. Decorating `__init__` with `@classmethod` or `@staticmethod` is rejected with `C0001`. The first classmethod parameter must be named `cls`. End-to-end integration tests: `tests/issue_436_classmethod_staticmethod.rs`. HIR unit tests cover collision detection paths.

**[#435](https://github.com/rotnov/pycc/issues/435) — `isinstance`/`issubclass`, `__init_subclass__`, `__set_name__`, `__class_getitem__`:** implemented compile-time evaluation of `isinstance` and `issubclass` using pycc's static dispatch model (D-006 — every variable's runtime type is exactly its declared type, so both builtins are always evaluable at compile time). Both are intercepted before generic call inference in `pycc_types::infer_expr_in` and `collect_expr_constraints`, and before generic arg lowering in `pycc_mir::lower_expr`. The class arguments (bare names or tuples of bare names) are never lowered as runtime values. The MIR emits `MirExpr::BoolLiteral(result)` — no runtime RTTI or type tags. For user classes, the result is computed via MRO membership; for builtin types, `bool` is a subtype of `int` (`isinstance(True, int)` and `issubclass(bool, int)` are `True`). Tuple targets are supported. Wrong arg counts produce `T0021`; unknown class names produce `T0001`; non-class arguments produce `T0021`. Shared evaluation helpers (`eval_isinstance_single`, `eval_issubclass_single`, `extract_class_names`, `is_builtin_type_name`) live in `pycc_hir` and are consumed by both `pycc_types` and `pycc_mir`. `__init_subclass__` (PEP 487) is recognized as a regular method; if a base class defines it, a subclass's own `__init_subclass__` must be statically evaluable (only `pass` or a docstring body is accepted — side-effecting statements are rejected with `C0001`). `__set_name__` (PEP 487) is accepted as a valid method name (not triggerable yet because class-level attribute assignments are unsupported). `__class_getitem__` (PEP 560) is accepted as a static method and enables `ClassName[type_arg]` subscript syntax in type annotations, resolving to `Ty::Instance(ClassName)` and ignoring the type argument. `Stmt::Pass` is now filtered as a no-op in `lower_body` (previously rejected with `C0001`). End-to-end integration tests: `tests/issue_435_isinstance_issubclass.rs`. Per D-102, `PYTHON_STANDARDS.md` rows stay `☐` until CI-observed green on all 5 Tier-1 targets.
