## D-014: 100% test coverage requirement

- Status: accepted (PR-1/PR-2 wires the CI gate this depends on)
- Context: pycc is a compiler — silent gaps in its own test suite are exactly the kind of bug that surfaces as a miscompile in someone else's code, far from where the gap was introduced. The project needs a binary, CI-enforced floor, not an aspirational target. Verified on the pinned toolchain (rustc 1.97.1) before adopting: `#[coverage(off)]` is still gated behind `#![feature(coverage_attribute)]` (rust-lang/rust#84605) and unavailable on stable — so any exemption mechanism must not depend on it.
- Decision: `cargo llvm-cov` (wraps `-C instrument-coverage`; a separately distributed cargo subcommand that *drives* the `llvm-tools-preview` rustup component at runtime — the two are installed separately, caught by repo audit issue #13 after an earlier draft of this entry conflated them — independent of the Homebrew LLVM 22.1.1 used for `inkwell` codegen, no version coupling between the two) gates every PR at `--fail-under-lines 100 --fail-under-regions 100`. Branch coverage is reported when available but not gated — it requires a nightly toolchain, and this project has no other reason to leave the stable channel (`rust-toolchain.toml` pins stable 1.97.1; introducing a nightly dependency just for one coverage sub-metric would be its own separate, unwarranted decision). The only exemption granularity is whole-file, via `--ignore-filename-regex`, because per-function exemption has no stable mechanism — this is a feature, not a limitation: it keeps platform-conditional or otherwise-unreachable code in its own file rather than letting an exemption hide inside an otherwise-normal one. Test code itself (`tests/`, `*_tests.rs`, `tests.rs`) is excluded from the denominator by cargo-llvm-cov by default, so coverage measures product code exercised by tests, not tests covering themselves.
- Alternatives: `grcov`/`tarpaulin` (older, less precise than LLVM source-based coverage now that `cargo llvm-cov` exists and the project already standardizes on LLVM tooling); a percentage target below 100% (rejected — a threshold like 95% lets the uncovered 5% drift to wherever it's least inconvenient to test, which is usually exactly the error-handling and edge-case code that matters most for a compiler); no gate at all (rejected outright, contradicts D-013's premise that specs and quality bars must be mechanically checkable).
- Consequences: every new file needs tests before merge, including CI/tooling glue where that's checked into a coverable crate. Genuinely untestable code (OS-specific branches exercised only on a different Tier-1 target, for instance) must live in its own file and get a named, justified entry in the exemption list in TESTING.md — an undocumented exemption is a review-blocking finding, same as an undocumented CPython deviation elsewhere in the spec. Wired into CI starting PR-1 (see DELIVERY_PLAN.md), not retrofitted later, so no crate ever accumulates an uncovered backlog.

## D-015: LLVM/inkwell version pin

- Status: accepted (PR-1/PR-2 is the PR that depends on it)
- Context: ARCHITECTURE.md/D-002 specify "LLVM (inkwell)" without a version. `pycc_codegen` needs one concrete pin to build against at all. Checked empirically on the dev host rather than picked from memory: only one real LLVM install exists (`llvm@17` through `llvm@22` under `/opt/homebrew/opt/` all resolve to the same single Cellar keg, `llvm/22.1.1` — not five distinct installs).
- Decision: LLVM `22.1.1`, `inkwell = "0.9"` (latest at pin time) with `default-features = false, features = ["llvm22-1"]`. `inkwell` 0.9.0's feature list was checked directly (crates.io version metadata) to confirm `llvm22-1` exists before committing to it — it does, alongside `llvm19-1`/`llvm20-1`/`llvm21-1`.
- Alternatives: none genuinely competing — this isn't a preference call between installed options, only one LLVM was actually present. The alternative considered was installing an older/different LLVM version to chase a "more battle-tested" inkwell feature; rejected as unnecessary extra setup work for no concrete benefit given `llvm22-1` already exists and matches what's on the machine.
- Consequences: `pycc_codegen/Cargo.toml`'s `inkwell` feature and CI's `LLVM_SYS_221_PREFIX` (or whatever exact env var `llvm-sys` reports needing — confirm per-build, don't assume the number matches the LLVM minor version) must be changed together if this ever bumps; a version bump is a new ADR, not an edit to this one.

## D-016: Vendored parser version pin

- Status: accepted (PR-1/PR-2 is the PR that depends on it)
- Context: D-003 already decided *that* pycc vendors `ruff_python_parser` through v0.5; it didn't pin *which* version. `ruff_python_parser`/`ruff_python_ast` are published to crates.io infrequently (6 total versions as of this pin) rather than continuously, so drift between what a contributor's local `Cargo.lock` resolves and what CI resolves is a real risk without an explicit pin.
- Decision: `ruff_python_parser = "0.0.6"`, `ruff_python_ast = "0.0.6"` — the newest versions on crates.io when PR-1 was built, verified via the crates.io API rather than assumed from training data.
- Alternatives: pinning to a specific git commit of `astral-sh/ruff` directly (rejected for v0.1 — crates.io releases are simpler to audit and update than a floating git dependency, and the project isn't blocked on any unreleased fix yet).
- Consequences: `pycc_ast`/`pycc_parser`'s `Cargo.toml` pins these exactly; bumping either is a new ADR entry (or an amendment noted here), not a silent `cargo update`.

## D-017: No separate `pycc_lexer` crate for v0.1

- Status: accepted (PR-1/PR-2 is the PR that depends on it)
- Context: ARCHITECTURE.md's crate table lists `pycc_lexer`/`pycc_parser`/`pycc_ast` as three crates, describing the end state after D-003 resolves (pycc's own hand-written lexer and parser, v0.6). During the vendored-parser bootstrap phase, `ruff_python_parser` performs lexing internally and does not expose a standalone token stream pycc could wrap even if it wanted to, and nothing downstream in the v0.1 pipeline (`pycc_hir` onward) consumes tokens directly — only the parsed AST.
- Decision: v0.1 creates `pycc_ast` (a thin, stable re-export boundary over `ruff_python_ast`) and `pycc_parser` (wraps `ruff_python_parser::parse_module`), but not `pycc_lexer`.
- Alternatives: an empty pass-through `pycc_lexer` crate now, for table-completeness with ARCHITECTURE.md (rejected as YAGNI — nothing would depend on it, and an empty crate that exists only to match a table is exactly the kind of unnecessary abstraction the project's own engineering conventions warn against).
- Consequences: `pycc_lexer` gets created in v0.6 when D-003's own-parser work gives it a real reason to exist (a token stream something actually consumes); until then, ARCHITECTURE.md's crate table describes a target state, not every crate's exact creation date.

## D-018: `pycc_testkit` deferred past PR-1/PR-2

- Status: proposed (graduates to accepted when `pycc_testkit` is actually created)
- Context: DELIVERY_PLAN.md's original "v0.1 crate scope" and "Testing scope for v0.1" sections listed `pycc_testkit` as built alongside the other 8 crates, with Layer 2 (the conformance harness) starting "as early as slice 0" -- but PR-1/PR-2 never created it (flagged by repo audit as an undocumented deviation, unlike `pycc_lexer`'s reasoned D-017). TESTING.md's actual spec for `pycc_testkit` is a real harness: `.py` fixtures under `tests/conformance/pyXY/` with PEP/category/milestone header comments, diffed against a pinned CPython 3.14 reference output, flipping ✅ marks in PYTHON_STANDARDS.md. None of that exists yet -- PYTHON_STANDARDS.md's matrix is still 100% unstarted (☐), so there is no PEP-level conformance tracking for a harness to drive yet.
- Decision: PR-1/PR-2 use a hand-written `tests/slice0.rs` integration test instead -- it compiles fixtures through the real `pycc` binary and asserts exact stdout, which is a genuine (if narrow) proof that the pipeline works end to end, but it is not TESTING.md's Layer 2 harness. `pycc_testkit` gets built for real once PR-4/PR-6 gives it PEPs to actually track (PR-6 is where DELIVERY_PLAN.md already schedules the first real conformance run: fib + mandelbrot-ascii vs. CPython on all 5 targets).
- Alternatives: scaffold a minimal `pycc_testkit` crate now, even with nothing real for it to do (rejected as premature -- there's no PEP matrix yet for it to check against, so it would be structure without function, the same YAGNI concern D-017 raised about `pycc_lexer`); keep DELIVERY_PLAN.md's "as early as slice 0" wording as-is and treat `tests/slice0.rs` as satisfying it (rejected -- that wording specifically promises TESTING.md's Layer 2 shape, which `tests/slice0.rs` doesn't have, and leaving the mismatch undocumented is exactly the kind of thing this decisions log exists to prevent).
- Consequences: DELIVERY_PLAN.md's "Testing scope for v0.1" section is corrected to say Layer 2 starts at PR-4/PR-6, not slice 0. `tests/slice0.rs` stays as ad hoc coverage for the two named PR-2 fixtures specifically, not a stand-in for the conformance harness.

## D-019: Codex and Claude Code are equal agent surfaces

- Status: accepted
- Context: pycc development uses both OpenAI Codex and Claude Code. Letting repository-owned automation exist on only one surface would make the effective development contract depend on which client happened to open a task, while copying complete instruction files per client would let them drift.
- Decision: `AGENTS.md` is the canonical shared repository instruction source and `CLAUDE.md` imports it. Every new or changed repository-owned agent or skill ships discoverable entrypoints and equivalent behavior, safety gates, inputs, and outputs for both Codex and Claude Code in the same pull request. Platform-specific adapters may differ, but they remain thin and share the underlying implementation where practical.
- Alternatives: choose one agent platform (rejected because both are active development surfaces); duplicate all rules and implementations independently (rejected because parity would be unverifiable and drift-prone); permit silent single-platform gaps (rejected because task behavior would become client-dependent).
- Consequences: agent/skill changes are incomplete until discovery plus primary success and failure paths work on both surfaces. A platform API gap needs a safe documented fallback, not an implicit reduction in support.

## D-020: Pull-request CI is an untrusted execution boundary

- Status: accepted
- Context: workflows may execute scripts and definitions controlled by a pull request, including same-repository branches. Workflow-level write permissions, OIDC, secrets, environments, or inherited state can therefore expose deployment and repository authority before review. A checker executed only from the pull-request revision cannot be its own trust anchor because that revision can change the checker too.
- Decision: every workflow declares an explicit workflow-level read/none permission baseline. Jobs that execute or consume untrusted pull-request state receive no elevated capability beyond a minimally scoped read-only `GITHUB_TOKEN`. Every privileged job, including one in a push-only or reusable workflow, is isolated behind the exact `push` plus `refs/heads/main` guard. The semantic policy checker provides normal CI feedback, while a separate read-only `pull_request_target` workflow runs the checker from the trusted base commit and downloads only head-revision workflow YAML as non-executable data. The checker also requires the trust-anchor workflow itself to match an independently reviewed SHA-256 allowlist.
- Alternatives: rely on repository permission defaults (rejected because they are mutable and implicit); trust an in-branch grep checker (rejected because YAML spellings bypass text matching and the PR can modify its own checker); grant workflow-level credentials and skip only the deploy step (rejected because credentials exist before step conditions contain their use).
- Consequences: after the one-time manually reviewed bootstrap PR introduces the trust anchor, workflow changes must pass the trusted `Workflow policy` check from their base revision. Cross-job artifacts, caches, outputs, reusable workflows, secrets, and environments remain explicit review boundaries even when the static checker accepts the YAML.

## D-021: PR-3's cross-compilation proof is same-OS cross-arch, not cross-OS

- Status: accepted (PR-3 is the PR that depends on it)
- Context: D-011/README.md/ARCHITECTURE.md/CLI_SPEC.md require `pycc build --target <triple>` cross-compilation from v0.1, "bundled lld, no system linker needed." Checked empirically before committing to a design: `cc -target x86_64-unknown-linux-gnu` on this macOS host fails immediately (`stdio.h` file not found) -- cross-compiling to a *different OS* needs that OS's actual sysroot (headers, libc, CRT startup objects) physically present on the build host, which "bundle a linker" does not provide by itself; tools that do this for real (`cross-rs`, Zig) bundle or download full target sysroots, a substantially bigger undertaking than wiring up an existing capability. By contrast, `cc -target x86_64-apple-macos12` on this same arm64 host succeeded immediately and produced a genuinely running x86_64 Mach-O binary (verified via Rosetta 2) -- macOS's own SDK already covers both Tier-1 Mac architectures, and Rust's own target support cross-builds `pycc_rt` for `x86_64-apple-darwin` from an `aarch64-apple-darwin` host cleanly via plain `rustup target add` + `cargo build --target`.
- Decision: PR-3's "at least one cross-compiled build" is same-OS, cross-architecture: build for `x86_64-apple-darwin` from the `macos-14` (arm64) CI runner (or the reverse), execute the result on the matching native runner (`macos-13`). This is genuine cross-compilation (a different `--target` than the host, a real architecture-mismatched binary, executed and verified on its own native hardware) using exactly the mechanism the spec describes (`pycc build --target <triple>`), just scoped to the pair of targets where "no system linker needed" is actually true today. `pycc_codegen::compile_to_object` itself is not scoped to any OS pair -- it accepts any target triple LLVM knows about (`Target::initialize_all` covers whatever the LLVM build supports) -- so extending to cross-OS later is a linking/sysroot problem, not a codegen rewrite.
- Alternatives: attempt full cross-OS compilation now with a hand-rolled minimal sysroot (rejected -- fragile, would need maintaining libc/CRT stubs per target, and is exactly the kind of "half-working hack" this project's own conventions warn against); skip the cross-compilation requirement entirely for PR-3 and defer all of it (rejected -- issue #9 exists specifically because a previous draft of this plan silently dropped this requirement; the same-arch proof is a real, honest partial fix, not another silent drop).
- Consequences: Windows MSVC and Linux cross-compilation (from a macOS or from each other) remain a real gap for a specific future PR, once sysroot bundling/downloading is designed properly -- tracked as a known gap here, not silently reintroduced. The CI matrix's other 3 targets (Linux x64/arm64, Windows) still build+test natively on their own runners in PR-3; only the *cross*-compiled proof is scoped to the Mac pair.

## D-022: Windows build needs a real `libxml2`, supplied via vcpkg

- Status: accepted (PR-3 is the PR that depends on it)
- Context: `native-build-test (windows-latest)` failed `cargo build --workspace` with `LINK : fatal error LNK1181: cannot open input file 'xml2s.lib'`, after the LLVM install and path-handling itself succeeded. Traced to `llvm-sys-221.0.1/build.rs`'s `get_system_libraries` (around line 298), which runs the downloaded release's own `llvm-config --system-libs` and emits a `cargo:rustc-link-lib=...` for every name it returns -- `xml2s` is one of them, because LLVM's official prebuilt Windows 22.1.1 archive was itself built with libxml2 support. This is a property of the official binary, not something `llvm-sys` or this project chose; there is no Cargo feature to opt the dependency away, and rebuilding LLVM from source without it is a categorically bigger undertaking than the whole rest of PR-3.
- Decision: install a real `libxml2` on the Windows runner via vcpkg (preinstalled on GitHub-hosted runners, path given by the `VCPKG_INSTALLATION_ROOT` env var -- not hardcoded, since it differs across runner-image versions), using the `x64-windows-static-md` triplet: a static `.lib` (not a DLL) built against the *dynamic* MSVC CRT, matching Rust's own default linkage for `x86_64-pc-windows-msvc` (which links the release, dynamic CRT regardless of `cargo build` vs `cargo build --release`). The resulting `libxml2.lib` is copied to `xml2s.lib` in the same directory (whatever exact name the port produces -- matched via a glob rather than hardcoded, since vcpkg's own file naming wasn't going to be verified against a live Windows host before pushing) and that directory is appended to the `LIB` environment variable, which `link.exe` reads natively for extra search paths -- no rustflags or `.cargo/config.toml` needed.
- Alternatives: ship an empty stub `xml2s.lib` (just enough to satisfy the linker's ability to *open* the file) -- rejected as too likely to just trade this error for a less obvious "unresolved external symbol xmlXXXX" one further down the same link, if any actually-linked LLVM object genuinely calls into libxml2, costing another full CI round-trip to re-diagnose; a real, fully-functional library resolves either way. Building LLVM from source with `LLVM_ENABLE_LIBXML2=OFF` -- rejected, hours-scale effort for a one-line dependency. Dropping Windows from the CI matrix -- rejected outright: D-011 makes Windows/MSVC Tier-1 from v0.1, non-negotiable.
- Consequences: adds one more external package install to the Windows leg of `native-build-test`, and one more platform-specific quirk to maintain alongside the Linux Polly and Windows path-mangling fixes already in `ci.yml`. If a future LLVM/inkwell version bump ships a Windows release built *without* libxml2, this step becomes a harmless no-op dependency rather than a hard requirement -- worth rechecking whenever D-015 is next touched.

## D-023: Windows has no system `cc`, and clang's bare-invocation default target is unreliable

- Status: accepted (PR-3 is the PR that depends on it)
- Context: with D-022 resolved, `cargo build --workspace` passed on Windows but `cargo test --workspace` failed most of `tests/slice0.rs`'s integration tests -- every one that runs `pycc build`/`pycc run` end-to-end -- and, discovered a CI round later after the first fix below landed, four unit tests inside `pycc_codegen`'s own `#[cfg(test)] mod tests` kept failing with the identical symptom. Several distinct, real bugs surfaced across multiple CI round-trips, not test flakiness, each verified directly rather than guessed at:
  1. `try_build` (`src/main.rs`) hardcoded `Command::new("cc")` to invoke the second-stage linker (object file + `pycc_rt` → native binary). Windows has no `cc` by default -- that is a Unix convention; MSVC's own tools are `cl.exe`/`link.exe`. Confirmed this was the *only* new problem at this step by checking that `native-build-test` already passes on both Linux architectures and macOS, i.e. `cc` genuinely already works everywhere else.
  2. `find_pycc_rt_lib_dir_in` hardcoded the expected static-lib filename as `libpycc_rt.a`. Rust's `staticlib` crate-type output naming is platform-specific -- confirmed empirically by cross-building `pycc_rt` for `x86_64-pc-windows-msvc` locally and inspecting the result directly: `target/x86_64-pc-windows-msvc/debug/pycc_rt.lib`, not `libpycc_rt.a` -- no `lib` prefix, `.lib` extension, COFF format.
  3. Even after fixing (1) and (2) plus adding the Windows system-libs list below, a bare `clang.exe` invocation with no explicit `-target` flag resolved inconsistently across otherwise byte-identical command lines in the same job: some invocations correctly selected MSVC's `lld-link`, others silently fell back to a MinGW/GCC toolchain discovered on `PATH` (`C:\mingw64`) -- which cannot link `pycc_rt.lib`'s MSVC-ABI symbols (`__imp_closesocket`, `__chkstk`, the MSVC RTTI vtable), producing a wall of GNU `ld`/`collect2` "undefined reference" errors instead of a normal MSVC link. Confirmed directly via clang's own `-v` verbose output, which showed "Target: x86_64-pc-windows-msvc" and a correct, complete `lld-link` invocation for every test once `-target` was forced explicitly.
  4. Separately, `pycc_codegen/src/lib.rs`'s own test-only `link_object_with_runtime` helper (added so that crate's tests can prove its object-file output actually links and runs, without a dependency cycle on the `pycc` binary crate) duplicated a minimal linking step and *also* hardcoded `Command::new("cc")`, with none of (1)-(3)'s fixes applied -- a second, independent call site the first round of fixes never touched, which is exactly why 4 tests kept failing with (1)'s original symptom one full CI round after `src/main.rs` had already been fixed.
  5. Even with (1) fixed, `clang.exe`'s bundled `lld-link` initially failed with `cannot open libcmt.lib`/`oldnames.lib`: `rustc`'s own link step auto-discovers the MSVC toolset (`LIB`/`INCLUDE`/CRT search paths) internally, but a direct `clang.exe` invocation outside any MSVC Developer Command Prompt does not.
- Decision: `#[cfg(windows)]`/`#[cfg(not(windows))]`-gated (compile-time conditional compilation, not a `cfg!()` runtime check, for the same D-014 coverage-gate reason as everywhere else in this arc) at both call sites:
  - The linker binary: bundled `<LLVM_SYS_221_PREFIX>/bin/clang.exe` on Windows, `cc` elsewhere -- the same official LLVM release D-022 already requires, not a new dependency.
  - Both call sites now always pass an explicit `-target x86_64-pc-windows-msvc` on Windows rather than relying on clang's bare-invocation default, since (3) showed that default is not reliable.
  - The expected static-lib filename is a `#[cfg]`-gated constant: `pycc_rt.lib` on Windows, `libpycc_rt.a` elsewhere.
  - Both call sites pass the same explicit Windows system-libs list (`ws2_32`, `ntdll`, `userenv`, `advapi32`, `shell32`, `ole32`, `uuid`, `psapi`, `dbghelp`, `kernel32`, `legacy_stdio_definitions`), sourced from rustc's own captured link-invocation log for `pycc.exe` on the same CI runner, not guessed -- needed because linking directly via a compiler driver, rather than through `cargo`/`rustc`'s own link step, doesn't get Rust std's transitively-required Windows libraries for free.
  - For (5): the `native-build-test` job sets up an MSVC Developer Command Prompt environment (`ilammy/msvc-dev-cmd@v1`, the standard action for this) before the LLVM install steps, giving the bundled `clang.exe`/`lld-link` the same `LIB`/`INCLUDE` environment `vcvarsall.bat` would.
- Alternatives: hand-roll a direct `lld-link`/`ld.lld`/`ld64.lld` invocation on every platform, matching ARCHITECTURE.md's literal "LLVM IR → object code → lld → native binary" diagram and D-011's "bundled lld" wording exactly -- rejected for *this* PR: it would mean reconstructing, per OS, all the default libraries/CRT-startup-object/entry-point arguments a compiler driver normally supplies for free (verified none of the three LLVM distributions this project already installs actually bundle an `lld`/`ld64.lld`/`ld.lld` *binary* -- Homebrew's `llvm` formula ships `lldb`, the debugger, not the linker), which is a substantially bigger undertaking than the rest of PR-3 combined. Sharing one linking helper between `pycc` (the binary crate) and `pycc_codegen`'s own tests, to avoid (4)'s duplication -- rejected, same as when `link_object_with_runtime` was first written: it would invert the crate dependency graph (`pycc` depends on `pycc_codegen`, not the reverse). Given that constraint, duplicating the now four-part Windows-specific linking logic a second time is an accepted cost, not an oversight -- but it is exactly why the second call site was missed for a full CI round, since nothing enforces the two copies stay in sync.
- Consequences: `pycc`'s own linking step still depends on a driver-plus-toolchain (system `cc` on macOS/Linux, bundled `clang` calling system `link.exe` on Windows) rather than the fully self-contained "bundled lld, no system toolchain required" end state D-011/ARCHITECTURE.md describe -- a real, tracked gap (same honesty pattern as D-021's cross-OS scoping), not silently declared done. Revisit when a PR specifically targets toolchain-independent linking. Additionally: any future change to Windows linking arguments (system libs, target, toolchain path) must be applied at both `src/main.rs`'s `try_build` and `pycc_codegen/src/lib.rs`'s `link_object_with_runtime` -- nothing currently enforces this stays in sync, a known follow-up risk worth revisiting if a third call site is ever added.

## D-024: LLVM's `LLVMDisposeMessage` crashes on Windows for the official prebuilt 22.1.1 release

- Status: accepted (PR-3 is the PR that depends on it)
- Context: with D-023's first two fixes in place, `native-build-test (windows-latest)` still failed `cargo test --workspace` -- the same integration tests, with the same signature: the spawned `pycc.exe` exits with code `-1073741819` (`0xC0000005`, `STATUS_ACCESS_VIOLATION` -- a genuine native crash, not a clean error or a Rust panic). Localized by instrumenting `compile_to_object` with unbuffered `eprintln!` checkpoints bracketing every call from the end of IR building through object emission, then reading the actual CI log: every failing run printed the checkpoint immediately before `module.verify()` and never the one immediately after. Fixing that (see Decision below) eliminated the crash for every test *except* `an_unknown_target_triple_is_a_clean_build_error`, which still crashed identically -- revealing this was never really "one bug at `verify()`," but one underlying defect (`inkwell::support::LLVMString`'s `Drop` impl calls `LLVMDisposeMessage`, which faults on this platform/LLVM-release combination) surfacing at whichever call happened to be the first to construct and drop an `LLVMString` on a given code path:
  1. `module.verify()` itself doesn't return an `LLVMString`, but every test that reaches it also constructs a `TargetTriple` (whose `triple` field is an owned `LLVMString`) shortly afterward; checkpoint evidence pointed at `verify()` as the crash site specifically, since it consistently ran last among printed checkpoints.
  2. `TargetTriple::create`/`TargetMachine::get_default_triple`'s returned `TargetTriple` owns an `LLVMString` whose `Drop` runs when the triple goes out of scope at the end of `compile_to_object` -- still crashed even with `verify()` skipped, since skipping `verify()` fixed its own call site but not the real underlying `Drop` defect.
  3. `Target::from_triple`'s `Err` branch separately returns its own `LLVMString` (`Err(LLVMString::new(...))`), and `TargetMachine::write_to_file`'s `Err` is likewise `LLVMString` -- two more values of the exact same type crossing into this crate's error paths, each hit only by a test that actually exercises that specific error branch (`an_unknown_target_triple_is_a_clean_build_error`, specifically, for (3)'s first half).
- Decision: a `#[cfg(windows)]`/`#[cfg(not(windows))]`-gated `verify_module()` helper (no-op on Windows; the original `.expect()`-wrapped `verify()` call elsewhere) for (1) -- a targeted skip of a *pure internal sanity check*, not a change to what gets compiled: the call's own message already says a failure here means a `pycc_codegen` bug, never a rejection of legitimate user code. `std::mem::ManuallyDrop::new(...)` at the point `TargetTriple` is created, covering every exit path including early `?` returns, for (2). A general `llvm_string_to_owned(message: LLVMString) -> String` helper (`.to_string()` then `std::mem::forget()`, rather than patching each call site's error-conversion by hand) applied at both `Target::from_triple`'s and `write_to_file`'s `.map_err(...)`, for (3) -- chosen over fixing each call site individually specifically so a *future* `LLVMString`-typed value crossing into this crate's error paths doesn't reintroduce the same crash silently.
- Alternatives: root-causing the crash inside LLVM's own compiled `LLVMDisposeMessage` -- rejected as open-ended with no reachable next step from this environment (no Windows debugger available to get an exact fault address). An alternate verification API for (1) specifically (per-function `LLVMVerifyFunction`, or a raw non-inkwell `llvm-sys` call bypassing inkwell's wrapper) -- rejected once (2) and (3) showed the *real* defect was `Drop`/`LLVMDisposeMessage`, not `verify()`'s own logic, making an alternate verify API beside the point.
- Consequences: Windows CI no longer gets `pycc_codegen`'s own well-formed-IR self-check from (1) -- a real, narrow, tracked gap. The compensating fact: IR-building has zero platform-conditional logic anywhere in this crate, and the identical code stays verified on macOS/Linux every commit, so a bug that only produces malformed IR on Windows would require Windows-specific codegen logic that doesn't exist yet. Any future `LLVMString`-returning API this crate starts calling must route its error conversion through `llvm_string_to_owned` (or wrap owned values in `ManuallyDrop`, if kept alive rather than immediately converted) on Windows, or risk reintroducing this exact crash silently -- revisit if a future LLVM/inkwell version fixes the underlying `LLVMDisposeMessage` defect, at which point all three workarounds could potentially be reverted together.

## D-025: CI steps must not force `shell: bash` on Windows without a reason

- Status: accepted (PR-3 is the PR that depends on it)
- Context: with D-023 and D-024 resolved, every actual `pycc`/`pycc_codegen` test passed on Windows for the first time in this arc -- but `cargo clippy --workspace --all-targets -- -D warnings` still failed, compiling an unrelated transitive proc-macro dependency (`manyhow-macros`), with `error: linking with \`link.exe\` failed` / `/usr/bin/link: extra operand ...` / `Try '/usr/bin/link --help' for more information` -- not an MSVC `link.exe` error message at all. Root cause: this step forced `shell: bash`; on Windows that's Git Bash, whose own startup reorders `PATH` such that its bundled coreutils `link.exe` (the Unix hardlink tool, at `C:\Program Files\Git\usr\bin\link.exe`) shadows MSVC's real linker that `ilammy/msvc-dev-cmd@v1` had already put on `PATH` correctly earlier in the same job -- a known Windows CI gotcha, confirmed directly by the error text itself (coreutils' own `link --help` message, not MSVC's).
- Decision: drop the explicit `shell: bash` override for this step. `cargo build`/`cargo test` already ran correctly on Windows earlier in the same job using pwsh (the OS's own default, no override needed), and this step's two commands (`rustup component add clippy`, `cargo clippy ...`) have no bash-specific syntax -- nothing is lost by letting each OS use its own default shell instead (bash on Linux/macOS, unchanged; pwsh on Windows, fixed).
- Alternatives: keep `shell: bash` and explicitly fix `PATH` ordering (e.g. removing/renaming Git's own `link.exe`, or setting a target-specific linker override to bypass `PATH` search entirely) -- rejected as more moving parts than simply not forcing a shell this step never needed bash syntax for in the first place.
- Consequences: none of the other `native-build-test` steps specify `shell:`, so this brings the clippy step in line with that existing pattern rather than introducing a new one. If a future step's script genuinely needs bash-specific syntax on Windows, this same PATH-shadowing risk applies and needs to be checked for explicitly, not assumed away.
