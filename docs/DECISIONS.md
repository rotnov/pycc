## D-014: 100% test coverage requirement

- Status: accepted (PR-1/PR-2 wires the CI gate this depends on)
- Context: pycc is a compiler — silent gaps in its own test suite are exactly the kind of bug that surfaces as a miscompile in someone else's code, far from where the gap was introduced. The project needs a binary, CI-enforced floor, not an aspirational target. Verified on the pinned toolchain (rustc 1.97.1) before adopting: `#[coverage(off)]` is still gated behind `#![feature(coverage_attribute)]` (rust-lang/rust#84605) and unavailable on stable — so any exemption mechanism must not depend on it.
- Decision: `cargo llvm-cov` (wraps `-C instrument-coverage`; a separately distributed cargo subcommand that *drives* the `llvm-tools-preview` rustup component at runtime — the two are installed separately, caught by repo audit issue #13 after an earlier draft of this entry conflated them — independent of the Homebrew LLVM 22.1.1 used for `inkwell` codegen, no version coupling between the two) gates every PR at `--fail-under-lines 100 --fail-under-regions 100`. Branch coverage is reported when available but not gated — it requires a nightly toolchain, and this project has no other reason to leave the stable channel (`rust-toolchain.toml` pins stable 1.97.1; introducing a nightly dependency just for one coverage sub-metric would be its own separate, unwarranted decision). The only exemption granularity is whole-file, via `--ignore-filename-regex`, because per-function exemption has no stable mechanism — this is a feature, not a limitation: it keeps platform-conditional or otherwise-unreachable code in its own file rather than letting an exemption hide inside an otherwise-normal one. Test code itself (`tests/`, `*_tests.rs`, `tests.rs`) is excluded from the denominator by cargo-llvm-cov by default, so coverage measures product code exercised by tests, not tests covering themselves.
- Alternatives: `grcov`/`tarpaulin` (older, less precise than LLVM source-based coverage now that `cargo llvm-cov` exists and the project already standardizes on LLVM tooling); a percentage target below 100% (rejected — a threshold like 95% lets the uncovered 5% drift to wherever it's least inconvenient to test, which is usually exactly the error-handling and edge-case code that matters most for a compiler); no gate at all (rejected outright, contradicts D-013's premise that specs and quality bars must be mechanically checkable).
- Consequences: every new file needs tests before merge, including CI/tooling glue where that's checked into a coverable crate. Genuinely untestable code (OS-specific branches exercised only on a different Tier-1 target, for instance) must live in its own file and get a named, justified entry in the exemption list in TESTING.md — an undocumented exemption is a review-blocking finding, same as an undocumented CPython deviation elsewhere in the spec. Wired into CI starting PR-1 (see DELIVERY_PLAN.md), not retrofitted later, so no crate ever accumulates an uncovered backlog.

## D-015: LLVM/inkwell version pin

- Status: accepted (PR-1/PR-2 is the PR that depends on it)
- Context: ARCHITECTURE.md/D-002 specify "LLVM (inkwell)" without a version. `pycc_codegen` needs one concrete pin to build against at all. Checked empirically on the dev host rather than picked from memory: only one real LLVM install exists (`llvm@17` through `llvm@22` under `/opt/homebrew/opt/` all resolve to the same single Cellar keg, `llvm/22.1.1` — not five distinct installs).
- Decision: LLVM `22.1.1`, `inkwell = "0.9"` (latest at pin time) with `default-features = false, features = ["llvm22-1"]`. `inkwell` 0.9.0's feature list was checked directly (crates.io version metadata) to confirm `llvm22-1` exists before committing to it — it does, alongside `llvm19-1`/`llvm20-1`/`llvm21-1`.
- Alternatives: none genuinely competing — this isn't a preference call between installed options, only one LLVM was actually present. The alternative considered was installing an older/different LLVM version to chase a "more battle-tested" inkwell feature; rejected as unnecessary extra setup work for no concrete benefit given `llvm22-1` already exists and matches what's on the machine.
- Consequences: `pycc_codegen/Cargo.toml`'s `inkwell` feature and CI's `LLVM_SYS_221_PREFIX` (or whatever exact env var `llvm-sys` reports needing — confirm per-build, don't assume the number matches the LLVM minor version) must be changed together if this ever bumps; a version bump is a new ADR, not an edit to this one.

## D-016: Vendored parser version pin

- Status: accepted (PR-1/PR-2 is the PR that depends on it)
- Context: D-003 already decided *that* pycc vendors `ruff_python_parser` through v0.5; it didn't pin *which* version. `ruff_python_parser`/`ruff_python_ast` are published to crates.io infrequently (6 total versions as of this pin) rather than continuously, so drift between what a contributor's local `Cargo.lock` resolves and what CI resolves is a real risk without an explicit pin.
- Decision: `ruff_python_parser = "0.0.6"`, `ruff_python_ast = "0.0.6"` — the newest versions on crates.io when PR-1 was built, verified via the crates.io API rather than assumed from training data.
- Alternatives: pinning to a specific git commit of `astral-sh/ruff` directly (rejected for v0.1 — crates.io releases are simpler to audit and update than a floating git dependency, and the project isn't blocked on any unreleased fix yet).
- Consequences: `pycc_ast`/`pycc_parser`'s `Cargo.toml` pins these exactly; bumping either is a new ADR entry (or an amendment noted here), not a silent `cargo update`.

## D-017: No separate `pycc_lexer` crate for v0.1

- Status: accepted (PR-1/PR-2 is the PR that depends on it)
- Context: ARCHITECTURE.md's crate table lists `pycc_lexer`/`pycc_parser`/`pycc_ast` as three crates, describing the end state after D-003 resolves (pycc's own hand-written lexer and parser, v0.6). During the vendored-parser bootstrap phase, `ruff_python_parser` performs lexing internally and does not expose a standalone token stream pycc could wrap even if it wanted to, and nothing downstream in the v0.1 pipeline (`pycc_hir` onward) consumes tokens directly — only the parsed AST.
- Decision: v0.1 creates `pycc_ast` (a thin, stable re-export boundary over `ruff_python_ast`) and `pycc_parser` (wraps `ruff_python_parser::parse_module`), but not `pycc_lexer`.
- Alternatives: an empty pass-through `pycc_lexer` crate now, for table-completeness with ARCHITECTURE.md (rejected as YAGNI — nothing would depend on it, and an empty crate that exists only to match a table is exactly the kind of unnecessary abstraction the project's own engineering conventions warn against).
- Consequences: `pycc_lexer` gets created in v0.6 when D-003's own-parser work gives it a real reason to exist (a token stream something actually consumes); until then, ARCHITECTURE.md's crate table describes a target state, not every crate's exact creation date.

## D-018: `pycc_testkit` deferred past PR-1/PR-2

- Status: proposed (graduates to accepted when `pycc_testkit` is actually created)
- Context: DELIVERY_PLAN.md's original "v0.1 crate scope" and "Testing scope for v0.1" sections listed `pycc_testkit` as built alongside the other 8 crates, with Layer 2 (the conformance harness) starting "as early as slice 0" -- but PR-1/PR-2 never created it (flagged by repo audit as an undocumented deviation, unlike `pycc_lexer`'s reasoned D-017). TESTING.md's actual spec for `pycc_testkit` is a real harness: `.py` fixtures under `tests/conformance/pyXY/` with PEP/category/milestone header comments, diffed against a pinned CPython 3.14 reference output, flipping ✅ marks in PYTHON_STANDARDS.md. None of that exists yet -- PYTHON_STANDARDS.md's matrix is still 100% unstarted (☐), so there is no PEP-level conformance tracking for a harness to drive yet.
- Decision: PR-1/PR-2 use a hand-written `tests/slice0.rs` integration test instead -- it compiles fixtures through the real `pycc` binary and asserts exact stdout, which is a genuine (if narrow) proof that the pipeline works end to end, but it is not TESTING.md's Layer 2 harness. `pycc_testkit` gets built for real once PR-4/PR-6 gives it PEPs to actually track (PR-6 is where DELIVERY_PLAN.md already schedules the first real conformance run: fib + mandelbrot-ascii vs. CPython on all 5 targets).

- Consequences: DELIVERY_PLAN.md's "Testing scope for v0.1" section is corrected to say Layer 2 starts at PR-4/PR-6, not slice 0. `tests/slice0.rs` stays as ad hoc coverage for the two named PR-2 fixtures specifically, not a stand-in for the conformance harness.

## D-019: Codex and Claude Code are equal agent surfaces

- Status: accepted
- Context: pycc development uses both OpenAI Codex and Claude Code. Letting repository-owned automation exist on only one surface would make the effective development contract depend on which client happened to open a task, while copying complete instruction files per client would let them drift.
- Decision: `AGENTS.md` is the canonical shared repository instruction source and `CLAUDE.md` imports it. Every new or changed repository-owned agent or skill ships discoverable entrypoints and equivalent behavior, safety gates, inputs, and outputs for both Codex and Claude Code in the same pull request. Platform-specific adapters may differ, but they remain thin and share the underlying implementation where practical.
- Alternatives: choose one agent platform (rejected because both are active development surfaces); duplicate all rules and implementations independently (rejected because parity would be unverifiable and drift-prone); permit silent single-platform gaps (rejected because task behavior would become client-dependent).
- Consequences: agent/skill changes are incomplete until discovery plus primary success and failure paths work on both surfaces. A platform API gap needs a safe documented fallback, not an implicit reduction in support.

## D-020: Pull-request CI is an untrusted execution boundary

- Status: accepted
- Context: workflows may execute scripts and definitions controlled by a pull request, including same-repository branches. Workflow-level write permissions, OIDC, secrets, environments, or inherited state can therefore expose deployment and repository authority before review. A checker executed only from the pull-request revision cannot be its own trust anchor because that revision can change the checker too.
- Decision: every workflow declares an explicit workflow-level read/none permission baseline. Jobs that execute or consume untrusted pull-request state receive no elevated capability beyond a minimally scoped read-only `GITHUB_TOKEN`. Every privileged job, including one in a push-only or reusable workflow, is isolated behind the exact `push` plus `refs/heads/main` guard. The semantic policy checker provides normal CI feedback, while a separate read-only `pull_request_target` workflow runs the checker from the trusted base commit and downloads only head-revision workflow YAML as non-executable data. The checker also requires the trust-anchor workflow itself to match an independently reviewed SHA-256 allowlist.
- Alternatives: rely on repository permission defaults (rejected because they are mutable and implicit); trust an in-branch grep checker (rejected because YAML spellings bypass text matching and the PR can modify its own checker); grant workflow-level credentials and skip only the deploy step (rejected because credentials exist before step conditions contain their use).
- Consequences: after the one-time manually reviewed bootstrap PR introduces the trust anchor, workflow changes must pass the trusted `Workflow policy` check from their base revision. Cross-job artifacts, caches, outputs, reusable workflows, secrets, and environments remain explicit review boundaries even when the static checker accepts the YAML.

## D-021: Agent task preflight and documentation refresh

- Status: accepted
- Context: this AI-first repository treats specifications and generated Rust API documentation as implementation inputs. Starting from a stale remote ref, stale rustdoc, or an unidentified dirty tree can make an otherwise-correct agent optimize against the wrong contract or overwrite user work.
- Decision: before a new task mutates the repository, the agent records status and HEAD, fetches/prunes without changing checked-out files, resolves the remote default branch, starts from that exact commit in a clean task branch/worktree, generates `cargo doc --workspace --no-deps`, and reads the specification/rustdoc that owns the affected area. Continuing dirty work is allowed only in place and only after comparing it with refreshed remote state; no implicit pull, merge, rebase, reset, or branch switch is authorized.

## D-026: PR-3's cross-compilation proof is same-OS cross-arch, not cross-OS

- Status: accepted (PR-3 is the PR that depends on it)
- Context: D-011/README.md/ARCHITECTURE.md/CLI_SPEC.md require `pycc build --target <triple>` cross-compilation from v0.1, "bundled lld, no system linker needed." Checked empirically before committing to a design: `cc -target x86_64-unknown-linux-gnu` on this macOS host fails immediately (`stdio.h` file not found) -- cross-compiling to a *different OS* needs that OS's actual sysroot (headers, libc, CRT startup objects) physically present on the build host, which "bundle a linker" does not provide by itself; tools that do this for real (`cross-rs`, Zig) bundle or download full target sysroots, a substantially bigger undertaking than wiring up an existing capability. - Alternatives: attempt full cross-OS compilation now with a hand-rolled minimal sysroot (rejected -- fragile, would need maintaining libc/CRT stubs per target, and is exactly the kind of "half-working hack" this project's own conventions warn against); skip the cross-compilation requirement entirely for PR-3 and defer all of it (rejected -- issue #9 exists specifically because a previous draft of this plan silently dropped this requirement; the same-arch proof is a real, honest partial fix, not another silent drop).
- Consequences: Windows MSVC and Linux cross-compilation (from a macOS or from each other) remain a real gap for a specific future PR, once sysroot bundling/downloading is designed properly -- tracked as a known gap here, not silently reintroduced. The CI matrix's other 3 targets (Linux x64/arm64, Windows) still build+test natively on their own runners in PR-3; only the *cross*-compiled proof is scoped to the Mac pair.

Building LLVM from source with `LLVM_ENABLE_LIBXML2=OFF` -- rejected, hours-scale effort for a one-line dependency. Dropping Windows from the CI matrix -- rejected outright: D-011 makes Windows/MSVC Tier-1 from v0.1, non-negotiable.
- Consequences: adds one more external package install to the Windows leg of `native-build-test`, and one more platform-specific quirk to maintain alongside the Linux Polly and Windows path-mangling fixes already in `ci.yml`. If a future LLVM/inkwell version bump ships a Windows release built *without* libxml2, this step becomes a harmless no-op dependency rather than a hard requirement -- worth rechecking whenever D-015 is next touched.

## D-028: Windows has no system `cc`, and clang's bare-invocation default target is unreliable

- Status: accepted (PR-3 is the PR that depends on it)
- Context: with D-027 resolved, `cargo build --workspace` passed on Windows but `cargo test --workspace` failed most of `tests/slice0.rs`'s integration tests -- every one that runs `pycc build`/`pycc run` end-to-end -- and, discovered a CI round later after the first fix below landed, four unit tests inside `pycc_codegen`'s own `#[cfg(test)] mod tests` kept failing with the identical symptom. Several distinct, real bugs surfaced across multiple CI round-trips, not test flakiness, each verified directly rather than guessed at:
  1. `try_build` (`src/main.rs`) hardcoded `Command::new("cc")` to invoke the second-stage linker (object file + `pycc_rt` → native binary). Windows has no `cc` by default -- that is a Unix convention; MSVC's own tools are `cl.exe`/`link.exe`. Confirmed this was the *only* new problem at this step by checking that `native-build-test` already passes on both Linux architectures and macOS, i.e. `cc` genuinely already works everywhere else.
  2. `find_pycc_rt_lib_dir_in` hardcoded the expected static-lib filename as `libpycc_rt.a`. Rust's `staticlib` crate-type output naming is platform-specific -- confirmed empirically by cross-building `pycc_rt` for `x86_64-pc-windows-msvc` locally and inspecting the result directly: `target/x86_64-pc-windows-msvc/debug/pycc_rt.lib`, not `libpycc_rt.a` -- no `lib` prefix, `.lib` extension, COFF format.
  3. Even after fixing (1) and (2) plus adding the Windows system-libs list below, a bare `clang.exe` invocation with no explicit `-target` flag resolved inconsistently across otherwise byte-identical command lines in the same job: some invocations correctly selected MSVC's `lld-link`, others silently fell back to a MinGW/GCC toolchain discovered on `PATH` (`C:\mingw64`) -- which cannot link `pycc_rt.lib`'s MSVC-ABI symbols (`__imp_closesocket`, `__chkstk`, the MSVC RTTI vtable), producing a wall of GNU `ld`/`collect2` "undefined reference" errors instead of a normal MSVC link. Confirmed directly via clang's own `-v` verbose output, which showed "Target: x86_64-pc-windows-msvc" and a correct, complete `lld-link` invocation for every test once `-target` was forced explicitly.
  4. Separately, `pycc_codegen/src/lib.rs`'s own test-only `link_object_with_runtime` helper (added so that crate's tests can prove its object-file output actually links and runs, without a dependency cycle on the `pycc` binary crate) duplicated a minimal linking step and *also* hardcoded `Command::new("cc")`, with none of (1)-(3)'s fixes applied -- a second, independent call site the first round of fixes never touched, which is exactly why 4 tests kept failing with (1)'s original symptom one full CI round after `src/main.rs` had already been fixed.
  5. Even with (1) fixed, `clang.exe`'s bundled `lld-link` initially failed with `cannot open libcmt.lib`/`oldnames.lib`: `rustc`'s own link step auto-discovers the MSVC toolset (`LIB`/`INCLUDE`/CRT search paths) internally, but a direct `clang.exe` invocation outside any MSVC Developer Command Prompt does not.
- Decision: `#[cfg(windows)]`/`#[cfg(not(windows))]`-gated (compile-time conditional compilation, not a `cfg!()` runtime check, for the same D-014 coverage-gate reason as everywhere else in this arc) at both call sites:
  - The linker binary: bundled `<LLVM_SYS_221_PREFIX>/bin/clang.exe` on Windows, `cc` elsewhere -- the same official LLVM release D-027 already requires, not a new dependency.
  - Both call sites now always pass an explicit `-target x86_64-pc-windows-msvc` on Windows rather than relying on clang's bare-invocation default, since (3) showed that default is not reliable.
  - The expected static-lib filename is keyed on the *requested* `--target` triple (`pycc_rt.lib` for an `-msvc` triple, `libpycc_rt.a` otherwise), not a host `#[cfg(windows)]` constant -- the first version used a host-keyed constant, which silently checked for the wrong filename whenever `--target` crossed OS families; caught and fixed in PR review before merge (D-031).
  - Both call sites pass the same explicit Windows system-libs list (`ws2_32`, `ntdll`, `userenv`, `advapi32`, `shell32`, `ole32`, `uuid`, `psapi`, `dbghelp`, `kernel32`, `legacy_stdio_definitions`), sourced from rustc's own captured link-invocation log for `pycc.exe` on the same CI runner, not guessed -- needed because linking directly via a compiler driver, rather than through `cargo`/`rustc`'s own link step, doesn't get Rust std's transitively-required Windows libraries for free.
  - For (5): the `native-build-test` job sets up an MSVC Developer Command Prompt environment (`ilammy/msvc-dev-cmd@v1`, the standard action for this) before the LLVM install steps, giving the bundled `clang.exe`/`lld-link` the same `LIB`/`INCLUDE` environment `vcvarsall.bat` would.
- Alternatives: hand-roll a direct `lld-link`/`ld.lld`/`ld64.lld` invocation on every platform, matching ARCHITECTURE.md's literal "LLVM IR → object code → lld → native binary" diagram and D-011's "bundled lld" wording exactly -- rejected for *this* PR: it would mean reconstructing, per OS, all the default libraries/CRT-startup-object/entry-point arguments a compiler driver normally supplies for free (verified none of the three LLVM distributions this project already installs actually bundle an `lld`/`ld64.lld`/`ld.lld` *binary* -- Homebrew's `llvm` formula ships `lldb`, the debugger, not the linker), which is a substantially bigger undertaking than the rest of PR-3 combined. Sharing one linking helper between `pycc` (the binary crate) and `pycc_codegen`'s own tests, to avoid (4)'s duplication -- rejected, same as when `link_object_with_runtime` was first written: it would invert the crate dependency graph (`pycc` depends on `pycc_codegen`, not the reverse). Given that constraint, duplicating the now four-part Windows-specific linking logic a second time is an accepted cost, not an oversight -- but it is exactly why the second call site was missed for a full CI round, since nothing enforces the two copies stay in sync.
- Consequences: `pycc`'s own linking step still depends on a driver-plus-toolchain (system `cc` on macOS/Linux, bundled `clang` calling system `link.exe` on Windows) rather than the fully self-contained "bundled lld, no system toolchain required" end state D-011/ARCHITECTURE.md describe -- a real, tracked gap (same honesty pattern as D-026's cross-OS scoping), not silently declared done. Revisit when a PR specifically targets toolchain-independent linking. Additionally: any future change to Windows linking arguments (system libs, target, toolchain path) must be applied at both `src/main.rs`'s `try_build` and `pycc_codegen/src/lib.rs`'s `link_object_with_runtime` -- nothing currently enforces this stays in sync, a known follow-up risk worth revisiting if a third call site is ever added.

## D-029: LLVM's `LLVMDisposeMessage` crashes on Windows for the official prebuilt 22.1.1 release

- Status: accepted (PR-3 is the PR that depends on it)
- Context: with D-028's first two fixes in place, `native-build-test (windows-latest)` still failed `cargo test --workspace` -- the same integration tests, with the same signature: the spawned `pycc.exe` exits with code `-1073741819` (`0xC0000005`, `STATUS_ACCESS_VIOLATION` -- a genuine native crash, not a clean error or a Rust panic). Localized by instrumenting `compile_to_object` with unbuffered `eprintln!` checkpoints bracketing every call from the end of IR building through object emission, then reading the actual CI log: every failing run printed the checkpoint immediately before `module.verify()` and never the one immediately after. Fixing that (see Decision below) eliminated the crash for every test *except* `an_unknown_target_triple_is_a_clean_build_error`, which still crashed identically -- revealing this was never really "one bug at `verify()`," but one underlying defect (`inkwell::support::LLVMString`'s `Drop` impl calls `LLVMDisposeMessage`, which faults on this platform/LLVM-release combination) surfacing at whichever call happened to be the first to construct and drop an `LLVMString` on a given code path:
  1. `module.verify()` itself doesn't return an `LLVMString`, but every test that reaches it also constructs a `TargetTriple` (whose `triple` field is an owned `LLVMString`) shortly afterward; checkpoint evidence pointed at `verify()` as the crash site specifically, since it consistently ran last among printed checkpoints.
  2. `TargetTriple::create`/`TargetMachine::get_default_triple`'s returned `TargetTriple` owns an `LLVMString` whose `Drop` runs when the triple goes out of scope at the end of `compile_to_object` -- still crashed even with `verify()` skipped, since skipping `verify()` fixed its own call site but not the real underlying `Drop` defect.
  3. `Target::from_triple`'s `Err` branch separately returns its own `LLVMString` (`Err(LLVMString::new(...))`), and `TargetMachine::write_to_file`'s `Err` is likewise `LLVMString` -- two more values of the exact same type crossing into this crate's error paths, each hit only by a test that actually exercises that specific error branch (`an_unknown_target_triple_is_a_clean_build_error`, specifically, for (3)'s first half).

A general `llvm_string_to_owned(message: LLVMString) -> String` helper (`.to_string()` then `std::mem::forget()`, rather than patching each call site's error-conversion by hand) applied at both `Target::from_triple`'s and `write_to_file`'s `.map_err(...)`, for (3) -- chosen over fixing each call site individually specifically so a *future* `LLVMString`-typed value crossing into this crate's error paths doesn't reintroduce the same crash silently.
- Alternatives: root-causing the crash inside LLVM's own compiled `LLVMDisposeMessage` -- rejected as open-ended with no reachable next step from this environment (no Windows debugger available to get an exact fault address). An alternate verification API for (1) specifically (per-function `LLVMVerifyFunction`, or a raw non-inkwell `llvm-sys` call bypassing inkwell's wrapper) -- rejected once (2) and (3) showed the *real* defect was `Drop`/`LLVMDisposeMessage`, not `verify()`'s own logic, making an alternate verify API beside the point.
- Consequences: Windows CI no longer gets `pycc_codegen`'s own well-formed-IR self-check from (1) -- a real, narrow, tracked gap. The compensating fact: IR-building has zero platform-conditional logic anywhere in this crate, and the identical code stays verified on macOS/Linux every commit, so a bug that only produces malformed IR on Windows would require Windows-specific codegen logic that doesn't exist yet. Any future `LLVMString`-returning API this crate starts calling must route its error conversion through `llvm_string_to_owned` (or wrap owned values in `ManuallyDrop`, if kept alive rather than immediately converted) on Windows, or risk reintroducing this exact crash silently -- revisit if a future LLVM/inkwell version fixes the underlying `LLVMDisposeMessage` defect, at which point all three workarounds could potentially be reverted together.

## D-030: CI steps must not force `shell: bash` on Windows without a reason

- Status: accepted (PR-3 is the PR that depends on it)
- Context: with D-028 and D-029 resolved, every actual `pycc`/`pycc_codegen` test passed on Windows for the first time in this arc -- but `cargo clippy --workspace --all-targets -- -D warnings` still failed, compiling an unrelated transitive proc-macro dependency (`manyhow-macros`), with `error: linking with \`link.exe\` failed` / `/usr/bin/link: extra operand ...` / `Try '/usr/bin/link --help' for more information` -- not an MSVC `link.exe` error message at all. ## D-039: Function signatures are pre-registered into the module `Environment` before body checks run

- Status: accepted (PR-4 Task 9, `pycc_types`)
- Context: Task 9's own plan snippet for `check()` calls `check_function(item)` for each `HirItem::Function`, and `check_function` binds the function's own signature into a brand-new, isolated `Environment` (needed so a function's parameters don't leak into sibling scopes, and so recursive self-calls resolve). That isolated environment is discarded once `check_function` returns -- it's never merged back into `check()`'s own module-level `env`. Implementing the plan exactly as written and then running the full workspace test suite surfaced a real regression: `tests/slice0.rs`'s `build_and_run_explicit_call_to_main` (`def main() -> None: ...\n\nmain()\n`) started failing with `T0021: call to undefined function `main``, because the top-level `main()` call is checked via `check_stmt(&mut env, stmt)`, using the module `env` that Task 9's `check_function` never populated.
- Decision: `check()` does a first pass over every `HirItem` in the module, registering each `HirItem::Function`'s signature into its own module-level `Environment` via `bind_function`, *before* the second pass that actually checks each item's statements/body. This matches ordinary Python semantics (a function can be called from code that runs after its own `def`, and forward references at module scope work once the module has finished executing top to bottom) for the one case current tests exercise: top-level code calling a previously-defined function.
- Alternatives: thread the module `env`'s function registry into `check_function` so sibling functions can also call each other (rejected for now -- no existing fixture or test exercises non-recursive function-to-function calls; adding it would be speculative surface area beyond what Task 9's own scope or test suite calls for, YAGNI); leave `check_function` fully isolated and only fix the specific failing test by special-casing top-level calls (rejected -- doesn't generalize, and the two-pass registration is the more honest fix for the actual gap: signatures need to exist before anything can reference them).
- Consequences: any top-level statement can call any module-level function regardless of where in the file that function is defined. A function body still cannot call a *sibling* function it doesn't already know about via its own self-registration (only recursion is proven to work, per the existing `recursion_is_supported_since_the_function_s_own_signature_is_in_scope` test) -- revisit if/when a fixture needs one function to call another, non-recursively.

## D-040: Function bodies resolve sibling calls against the module's shared function registry

- Status: accepted (PR-4 Task 9 follow-up, `pycc_types`) -- supersedes D-039's "Alternatives" deferral of sibling-to-sibling calls
- Context: D-039 deliberately deferred sibling function calls, reasoning that no fixture exercised the case. That reasoning didn't hold up: `def helper(x: int) -> int: return x + 1` plus `def main() -> None: print(helper(5))` plus `main()` is ordinary, valid Python -- and, verified directly against the built `pycc` binary, it was rejected with `T0021: call to undefined function `helper``. The root cause is exactly what D-039 flagged as a known gap: `check_function` (called from `check()` for every `HirItem::Function`) built its own `Environment::new()` from scratch, so only a function's *own* signature (self-registered for recursion) was ever visible inside its body -- a sibling's signature, even though already present in `check()`'s module-level `env`, was never threaded through. A compiler that rejects one ordinary function calling another is a correctness defect in a PR-4 headline feature (function definitions and calls), not a documented scope boundary.
- Decision: `check_function` is split into a thin public wrapper (unchanged signature, still seeds a fresh, self-only `Environment` -- so its own existing unit tests keep testing exactly what they tested before) and an internal `check_function_in(module_env: &Environment, function: &HirItem)`, which starts from `module_env.child_for_function()` -- a new environment with empty local bindings but the *module's full function registry* cloned in. `check()` now calls `check_function_in(&env, item)` (its own module-level `env`, already populated by D-039's pre-registration pass) instead of the old `check_function(item)`. `Environment::child_for_function` is a private helper (`bindings: HashMap::new(), functions: self.functions.clone()`) -- local variables never leak into a function body's scope (correct, since Python functions don't see their caller's or the module's locals without `global`/`nonlocal`, which v0.1 doesn't support), but the function registry does, in both directions (a function can call one defined earlier or later in the file, matching D-039's own forward-reference reasoning).
- Alternatives: keep `check_function` fully isolated and special-case `main`-only top-level calls (rejected -- this is exactly the "doesn't generalize" alternative D-039 already rejected, and it would leave the newly-confirmed sibling-call bug unfixed); thread the whole module `Environment` (including top-level bindings) into every function body (rejected -- would incorrectly let a function body read module-level variables as if they were closures, which isn't real Python scoping and isn't in TYPE_SYSTEM.md's rules).
- Consequences: any module-level function can now call any other module-level function, regardless of definition order, closing the gap D-039 left open. `check_function`'s public behavior (self-only visibility, used by its own pre-existing unit tests) is unchanged and covered by `check_function_the_public_api_still_has_no_sibling_visibility`. New regression tests `a_function_can_call_a_sibling_function_defined_before_it` and `a_function_can_call_a_sibling_function_defined_after_it` cover both directions at the `pycc_types` level; an end-to-end CLI test isn't added because D-035 keeps PR-4 frontend-only -- lowering a function body with a `Return(BinOp(...))` isn't wired up in `pycc_mir`/`pycc_codegen` until PR-5, so the fixture above type-checks cleanly but still panics at the documented "codegen lands in PR-5" boundary if actually built.

## D-041: Function bodies also resolve reads of module-level global variables

- Status: accepted (PR-4 Task 9 follow-up, `pycc_types`; D-055 supersedes the `UnboundLocalError` deferral recorded below) -- corrects a factually wrong claim in D-040's own "Alternatives" section, does not merely extend it
- Context: D-040's "Alternatives" paragraph rejected threading module-level bindings into function bodies, reasoning "Python functions don't see their caller's or the module's locals without `global`/`nonlocal`." That statement conflates two different things: a *caller's* locals (correctly never visible to a callee -- Python has no dynamic scoping) and the *module's* globals (visible for *reading* in any function with no declaration needed at all; `global`/`nonlocal` is only required to *rebind* a name from inside a nested scope, not to read one). Verified directly against the built `pycc` binary: `x = 5` at module level followed by `def f() -> int:\n    return x` -- ordinary, extremely common Python (any module-level constant used inside any function has this exact shape) -- was rejected with `T0021: name \`x\` is not defined`, the same class of defect D-040 itself had just fixed for sibling function calls. The root cause was identical in kind: `check_function_in`'s scope (then called `child_for_function`) reset `bindings` to an empty map, discarding every top-level assignment the module-level `env` had already accumulated.
- Decision: `Environment` gains `#[derive(Clone)]` and the dedicated `child_for_function` helper is removed in favor of a plain `module_env.clone()` -- there is no longer any field that should be reset when entering a function body, since both the function registry (D-040) and the global-variable bindings (this decision) are meant to carry over in full; only the function's own subsequent `bind` calls (its parameters, then any local assignments in its body) mutate the *clone*, never the original module `env`, so nothing leaks back out or across sibling function checks. `check()` is restructured from one interleaved pass into three: (1) register every function signature (D-039, unchanged), (2) check every `HirItem::TopLevelStmt` in source order, growing `env`'s bindings as module-level assignments are encountered -- preserving real top-to-bottom evaluation order for top-level code, so a genuine top-level forward reference to a not-yet-assigned name is still an error -- then (3) check every `HirItem::Function`'s body against a clone of `env` as it stands once *all* top-level statements have been processed, regardless of whether that function's own `def` appears before or after the global it reads. Pass 3's "regardless of position" rule mirrors D-039's own justification for function signatures: real Python only evaluates a function body when the function is *called*, and by the time any call machinery could plausibly run, the module has typically already finished executing top to bottom.
- Alternatives: interleave global-registration with function-body-checking in a single pass, exposing only globals whose `Assign` textually precedes the function's `def` (rejected -- weaker than real Python, which has no such positional restriction for a *called* function, and it would still incorrectly reject the "def appears before the global" direction, i.e. exactly `a_function_can_read_a_module_level_global_defined_after_it`); model Python's actual `UnboundLocalError` rule (a name assigned anywhere in a function body, without `global`, is local for the *entire* function scope, even before the assignment) precisely (rejected as speculative scope for this fix -- no fixture or planned v0.1 acceptance criterion needs it, and function-local `Assign` already correctly shadows a same-named global via ordinary last-write-wins `HashMap` semantics on the cloned, independent copy, which is all current tests require).
- Consequences: a function body can read any module-level global regardless of source-code order, matching real Python semantics for the common "module-level constant used inside a function" pattern. A function parameter (or a function-local `Assign`) of the same name still correctly shadows a same-named global, verified by `a_function_parameter_shadows_a_module_level_global_of_the_same_name`. New regression tests `a_function_can_read_a_module_level_global_defined_before_it` and `a_function_can_read_a_module_level_global_defined_after_it` cover both directions. Real Python's `UnboundLocalError` nuance (assigning to a name anywhere in a function body makes it local for the whole function, retroactively) is *not* modeled -- pycc is currently more permissive than CPython here; revisit if a fixture ever needs that exact error.

## D-042: Frontend performance gate is a hand-rolled regression check, informational-only in CI

- Status: accepted (PR-4 Task 14)
- Context: DELIVERY_PLAN.md's Performance gate section requires "every subsequent PR records a `pycc check` timing run... and fails if it regresses >2% against the previous PR's baseline," starting with PR-4 (the first PR with a non-trivial frontend to measure). The plan's own Task 14 draft flagged, but did not resolve, whether `criterion`'s CLI sets a failing exit code when it detects a regression via `--baseline`/`--save-baseline`. Verified directly against `criterion` 0.8.2's own source (`~/.cargo/registry/.../criterion-0.8.2/src/lib.rs` and `report.rs`): its only `std::process::exit(1)` calls are for CLI-argument-parsing errors (e.g. an unsupported flag combination under `cargo-criterion`, an invalid `--profile-time`); `ComparisonResult::Regressed` (`report.rs`) only changes the printed report's text/color, never the process exit code. A CI step that ran `cargo bench -- --baseline previous` and trusted its exit code would therefore never fail on a real regression -- silently not gating anything, while looking like it does.
- Decision: `scripts/check_perf_regression.rb` (matching the existing `scripts/check_ci_permissions.rb` convention: a small, directly-invokable Ruby script with its own `scripts/test_check_perf_regression.rb` unit-test file, `require_relative`'d, run via `ruby scripts/test_check_perf_regression.rb`) reads two criterion `estimates.json` files (`current`/`previous` baselines) directly, computes `(current.mean.point_estimate - previous.mean.point_estimate) / previous.mean.point_estimate * 100`, and exits 1 if that exceeds a 2% threshold (configurable via an optional third CLI argument), 0 otherwise, 2 on a usage/IO error. Both the regression-detected and within-threshold exit paths are exercised by real, passing unit tests (`test_exits_one_when_regression_exceeds_threshold`, `test_exits_zero_when_within_threshold`, plus an improvement case and a custom-threshold case) -- this is the part of the mechanism that is actually proven, independent of any live CI run. The new `frontend-perf-gate` CI job (`.github/workflows/ci.yml`) runs the benchmark every PR, restores the most recent prior run's `estimates.json` via `actions/cache/restore@v4` with a `run_id`-keyed cache entry and a `restore-keys` prefix fallback, invokes the script when a previous baseline exists, and always saves its own run's result via `actions/cache/save@v4` as the next run's fallback baseline.
- Alternatives: trust criterion's own `--baseline previous` comparison output/exit code directly (rejected -- confirmed above to never fail on a real regression); design and attempt to fully prove a canonical "always compare against `main`'s last baseline" cache lifecycle with a `push`-vs-`pull_request` split before merging this PR (rejected as scope creep for this task -- this sandboxed environment cannot execute a real, multi-run GitHub Actions round trip to confirm `actions/cache`'s restore-key fallback behavior across separate workflow runs; over-engineering an unverifiable design is worse than shipping the plan's own minimal sketch, informational-only, and promoting it once real CI history exists to check).
- Consequences: `frontend-perf-gate` is **not** added to `ci-gate`'s `needs:` list -- a regression cannot yet block a merge, only be visible in that PR's own CI run. The cache-based "compare against the immediately preceding run" lifecycle relies on GitHub's documented per-branch cache scoping (a `push`-to-`main` run's cache is visible as a fallback to PR branches based on it) but this specific restore/compare/save cycle has not been confirmed by an actual multi-run round trip -- this PR's own first run has no prior cache entry at all, so it can only exercise the "no previous baseline yet" path locally and in its own first CI run. Promote `frontend-perf-gate` into `ci-gate`'s required checks once a live round trip (e.g. two consecutive merged PRs) confirms the cycle behaves as designed.

## D-045: Private helpers use explicit, monomorphic inference variables

- Status: accepted (PR-4 review correction; completes D-038's promised v0.1 inference behavior)
- Context: D-038 makes underscore-prefixed functions eligible for the local inference required by TYPE_SYSTEM.md, but the initial implementation lowered every missing private parameter and return annotation to `Ty::None`. A single private helper cannot silently acquire unrelated concrete signatures at different call sites; code that needs polymorphism must use the later generic surface or explicit annotations once supported. `Ty::Infer` exists only in the unresolved lowering result; the typed driver path materializes concrete HIR before MIR/codegen.

## D-046: Only successful main pushes publish the frontend-performance baseline

- Status: accepted (PR-4 Codex review correction; supersedes D-042's per-run publication lifecycle)
- Context: GitHub Actions caches are scoped by ref. A `pull_request` run writes to its merge ref, and later runs of that pull request search that scope before the default branch. Publishing a baseline from every successful PR head would therefore make the next head compare with the same PR's previous head. Several individually sub-2% regressions could ratchet beyond 2% relative to the last merged code without any one comparison failing.
- Decision: split the gate into `frontend-perf-measure` and `frontend-perf-gate`. The measurement job executes PR code and uploads only Criterion's `estimates.json`. The gate job has no source build: it sparse-checks out only the Ruby comparator and its tests, verifies their reviewed SHA-256 digests, restores the `frontend-perf-main-v1-` namespace, downloads the measurement as untrusted JSON data, self-tests the comparator, and applies the threshold. Pull requests never promote or save; only a successful `push` on `refs/heads/main` may publish the next canonical baseline. Both jobs are explicit `ci-gate` dependencies. The first run before any canonical baseline exists remains the one permitted bootstrap: the PR reports no baseline, and the successful post-merge `main` run publishes it.
- Alternatives: let each PR head publish and compare incrementally (rejected because it weakens the cumulative merge threshold); use a privileged PR workflow to overwrite the `main` cache (rejected because low-trust PR code must not write trusted shared state); store baselines as repository artifacts or commits (deferred because the main-scoped cache already supplies the required canonical comparison without write credentials).
- Consequences: repeated updates to one PR always compare against the latest successfully published `main` measurement rather than a PR-local predecessor. Untrusted compiler/build code cannot modify the comparator that interprets its measurement. A failed comparison cannot advance either PR-local or canonical state. If the post-merge `main` run fails or is cancelled, it leaves the previous canonical baseline intact and the failure remains a release-blocking signal.

## D-055: Classify function-local bindings before resolving global reads

- Status: accepted (closes #120 and supersedes D-041's explicit `UnboundLocalError` deferral)
- Context: D-041 correctly made module globals readable inside functions, but its sequential clone-and-overwrite model treated a later local assignment as though it could not affect an earlier read. Python classifies bindings for the entire code block before execution: absent `global` or `nonlocal`, any assignment or `for` target makes that name local throughout the function. As a result, `x = 1; def f(): print(x); x = 2` deterministically raises `UnboundLocalError` in CPython, while pycc previously accepted it and resolved the read to the global. Private-helper constraint collection inherited the same incorrect fallback.
- Decision: construct each function's lexical-local list once from its parameters plus a recursive, deduplicating body scan for the remaining binding forms implemented by the v0.1 HIR: assignment targets and `for` targets under nested `if`, `while`, and `for` statements. The borrowed lists are reused by private-helper inference and final validation. A function environment starts from the completed module environment but removes every classified name before binding parameters and walking the body. Reads of a classified-but-not-yet-bound local produce `T0021` (“local name `<name>` is not bound before this use”) instead of consulting a same-named global. A call target is resolved as a name before its arguments, builtin handling, or function-registry lookup; a classified unbound target gets the same `T0021`, and a bound primitive value or parameter cannot fall through to a same-named callable. Until runtime exception preservation exists end to end, strict static rejection is the supported behavior.
- Alternatives: keep sequential last-write-wins shadowing (rejected because it silently changes deterministic Python behavior); emit code that raises `UnboundLocalError` at runtime (deferred because the current backend does not yet preserve this function-body case end to end); implement complete branch/loop definite-assignment joins here (rejected as conflating lexical classification with #118's separately tracked control-flow problem).
- Consequences: ordinary reads of globals that have no local binding form remain valid regardless of whether the module assignment appears before or after the function definition. A first local assignment establishes its own type without inheriting the global's representation, and a read in that assignment's right-hand side is correctly rejected. Nested binding forms affect the whole function, including a `for` target while its range operands are evaluated. Parameters remain bound at function entry. Calls cannot bypass local-value or parameter shadowing through the builtin or function registry. The checked CPython-differential source, exact human/JSON diagnostic snapshots, and direct call-target regressions lock this behavior; #118 remains responsible for whether a local bound on only some runtime paths is definitely available after a control-flow join.

## D-061: `int`'s fast-path `i64` slot is a low-bit-tagged 63-bit fixnum

- Status: accepted (PR-5 Task 3 is the task that depends on it; renumbered from this branch's original draft ID D-052 -- see D-071's own renumbering-record table row)
- Context: D-001 says "`i64` fast path, overflow promotes to heap bigint" without fixing a concrete bit-level representation. With `pycc_own` deferred to v0.5 (no escape/ownership analysis), codegen cannot statically distinguish an `int` value that will always stay small from one that might later overflow -- a loop accumulator or a function parameter is runtime-unknown either way. Every `int` value must therefore share one storage layout from the first codegen task that touches `int` at all, or a later task migrating the layout would have to rewrite every earlier task's `alloca`/parameter/return/print/compare codegen -- exactly the kind of silent representation drift this plan's own type-consistency self-review exists to catch. Two alternatives were weighed against this constraint (see Alternatives).
- Decision: represent every `Ty::Int` value, in every context (local `alloca`, function parameter, function return, a literal constant), as one LLVM `i64`. Its low bit is the discriminant: `1` means the remaining 63 bits (arithmetic-shift-recovered: `tagged >> 1`) are the real value (`tag_smallint(n) = (n << 1) | 1`); `0` means the full 64 bits are a real heap pointer to a `BigInt` (D-058), which Rust's global allocator guarantees is at least 2-byte aligned on every Tier-1 target, so a genuine heap pointer's low bit is always `0` -- disjoint from a tagged fixnum's low bit, which is always `1`. Every arithmetic/comparison/print operation on `int` is a call to a `pycc_rt` function taking/returning this exact tagged `i64` (never a raw untagged value) -- `pycc_codegen` itself never inspects the tag bit or constructs a `BigInt` pointer; all of that logic (and 100%-coverage-friendly unit testing of it) lives in `pycc_rt`. Task 9 (bigint promotion) only ever changes what these same functions do internally on overflow -- their signatures, and every call site this task (and Tasks 4/5/10) write, stay fixed.
- Alternatives: a 16-byte `{ tag: i64, payload: i64 }` struct passed by value -- rejected: this project has already hit real, expensive-to-diagnose cross-platform ABI mismatches for far simpler cases (D-027/D-028/D-029's ~3 CI round-trips over Windows linking alone), and Windows x64's C ABI passes aggregates larger than 8 bytes *by hidden reference* rather than in two registers, unlike System V -- a fresh source of exactly that kind of bug, for no benefit this project's stated v0.1 perf bar requires. Always-boxed (every `int`, even a small one, is a heap `BigInt` from the start) -- rejected: contradicts this plan's own header ("every scalar keeps its unboxed representation... until `int` overflows") and would require building the bigint runtime (Task 9's job) before Task 3 could emit any arithmetic at all, inverting this plan's dependency order for no correctness benefit. Emitting raw LLVM `add`/`sub`/`mul`/overflow-intrinsic instructions directly in `pycc_codegen` instead of calling `pycc_rt` functions -- rejected for v0.1 only: it avoids a function-call's overhead (irrelevant, since v0.1 has no generated-code speed requirement -- see TESTING.md Layer 7, a v0.2+ item) at the cost of moving all the tagging/overflow/floor-division-semantics logic into hand-built LLVM IR, which is far harder to get right and to unit-test in isolation than equivalent Rust code in `pycc_rt`; revisit once a real perf bar exists.
- Consequences: `RUNTIME.md`'s "scalars... unboxed, never touch the runtime" describes the eventual, optimized steady state (once direct-intrinsic codegen replaces these calls, a documented future item) -- v0.1's actual `int` fast path does call into `pycc_rt` for every arithmetic/comparison/print operation; `RUNTIME.md` is annotated to say so honestly rather than silently contradicted (see Task 11). `bool` gets its own, simpler, untagged `i8` representation (0/1) -- not folded into this tagging scheme, since Python `bool` never needs bigint promotion. A **known, load-bearing gap accepted for the rest of PR-5**: `pycc_rt_int_cmp` (and any future bigint-comparison need) explicitly panics if either operand's tag bit shows it's already a heap `BigInt` -- comparing a bigint-valued `int` is out of scope for v0.1 and stays an honest, named limitation (like D-026's cross-OS gap), not a silent wrong answer. `str`'s own refcounting (Task 7) follows the same honesty convention, and this entry's own first-draft wording of that gap (added alongside Task 7) understated its scope -- corrected here rather than left standing (see D-070, which similarly flags D-060's own overclaim): codegen inserts `incref`/`decref` calls only at codegen-time *binding sites* it can see in one static pass over the MIR -- an `Assign` target's slot, a `Call` argument/return, and a final top-level-locals completion pass right before `main` returns -- never via real control-flow- or lifetime-aware liveness tracking, which only `pycc_own` (v0.5) can provide. Two distinct, memory-safe (no double-free, no use-after-free), and potentially loop-unbounded leak classes follow from that scope, not just one: **(a) an unbound temporary** -- a `str` value that is produced but never bound to any name, e.g. a string literal or a comparison/concatenation/non-duplicate-`Call` result consumed directly as an `if`/`while` condition, as a comparison or concatenation operand, or as an intermediate concatenation result -- is never decremented at all, at any point; and **(b) a loop-body-first binding** -- a `str` local whose *first* assignment (within the function currently being compiled) lexically occurs inside a `while`/`for` body is not recognized as "already bound" by codegen's single static visit to that `Assign` statement, so `decref_old_str_if_reassigning` never fires for it and every loop iteration but the last leaks its predecessor's value (only the final iteration's value is later freed, by whichever exit mechanism applies -- the top-level completion pass, or case (c) below). The originally-documented gap is real but narrower than either of these: **(c) a function-scoped `str` local/parameter never reassigned before its function returns** is never decrefed at any of that function's `return` sites. All three are accepted for the rest of PR-5, closed only once `pycc_own` lands.

- Context: D-041/D-055 make module bindings available to function bodies regardless of declaration order while classifying every nested function assignment and `for` target as local from entry. The type checker also accepts `bool` wherever an `int` is required and fixes an inferred binding's representation at its first assignment. The original MIR/codegen walk was source-order and allocation-on-first-emission: functions could miss later globals, branch-local allocas did not dominate post-branch uses, and accepted `bool` values could reach an `i64` parameter, return, range, or existing binding as `i8`. A two-return `if` also left a synthetic merge block unterminated, and `None`-returning calls interpolated in f-strings reused an internal false placeholder instead of Python's text `None`.
- Decision: MIR registers functions, lowers top-level statements sequentially to preserve top-level forward-read errors, and lowers function bodies only after the module binding environment is complete. Codegen declares every supported module binding as an LLVM global before emitting bodies and seeds function name resolution from those globals. Every global and non-parameter local slot has an initialization flag: assignment sets the flag only after evaluating and storing its right-hand side, while an earlier read traps before an LLVM initializer, `undef`, or null can become a fabricated Python value. Parameters are initialized at entry and need no flag; #118 still owns earlier static rejection and structured definite-assignment diagnostics. Codegen recursively classifies each function's assignment and `for` targets and allocates all function-local slots in the entry block; parameters and local targets override same-named globals. A `for` uses hidden SSA induction state and writes the Python-visible target only on entry to a real iteration, so an empty range leaves a new target unbound, the post-loop target remains the last element, and body reassignment cannot alter iteration. The first binding type remains stable in MIR. At assignment, call-argument, return, and `range` boundaries, an accepted `bool` flowing to `int` is widened into the tagged D-061 representation. A synthetic `if` merge with no predecessor is terminated by `unreachable`, and a `None`-returning call in an f-string preserves the call side effect then materializes `None` text. General nested `None` values remain outside D-072.
- Alternatives: reject later module globals or accepted `bool`→`int` programs in the backend (rejected because `check` already promises they are valid); allocate on the first dynamically emitted assignment (rejected because an allocation inside one control-flow predecessor cannot safely serve other predecessors or a post-join read); add SSA and definite-assignment analysis now (rejected because D-057 deliberately keeps PR-5 MIR structural and #118 owns the later join analysis); store every scalar in one oversized tagged union (rejected because it discards the fixed representations that type checking exists to establish).
- Consequences: backend name resolution now matches D-041/D-055 without exposing a binding before execution initializes it, all local allocas dominate their uses, `for` target lifetime matches Python for empty, positive, negative, and body-reassignment paths, and `bool`→`int` compatibility has one representation-preserving realization across storage and ABI boundaries. Until Python exception objects land, an early global or local read is a deterministic process trap rather than a formatted `NameError`/`UnboundLocalError`; it cannot silently return a fabricated scalar or dereference a null string. Preallocating string slots also closes D-061/D-070's loop-body-first reassignment leak because every iteration can decref the slot's previous value. D-061/D-070 remain historical descriptions of the accepted PR-5 scope; D-074 supersedes only that loop-body-first leak. Unbound string temporaries and function-scoped string parameters/locals at return remain documented memory-safe leaks until `pycc_own`.

## D-075: Carry `None` parameters as a canonical zero unit

- Status: accepted (PR #132 Codex review found that the frontend accepted a `None`-typed parameter while codegen panicked merely declaring the function)
- Context: LLVM `void` is a return type, not a legal parameter or storage type. pycc's frontend nevertheless accepts the standard Python annotation `None` for a parameter, and a `None`-returning call or another `None` parameter can supply that argument. Rejecting the program only in codegen violates the checked-program contract and made even an unused `def f(value: None) -> None: return` crash during function declaration.
- Decision: keep `None` function returns as LLVM `void`, and use the canonical LLVM `i8 0` as the unit carrier whenever a `None` value crosses the v0.1 user-function parameter ABI or is held in that parameter's entry slot. MIR's static `Ty::None` is the semantic tag; the identical physical width of `bool` does not make the values interchangeable. Evaluating `return value` in a `None` function preserves expression side effects and emits a void return. Printing or interpolating a `None`-typed parameter materializes Python's `None` text. D-072's explicit rejection of using `print()` itself as a nested expression remains unchanged.
- Alternatives: reject `None` annotations on parameters during HIR lowering (rejected because the standard annotation and unit type are already part of the v0.1 frontend contract); use an empty LLVM struct (rejected because an internal aggregate adds target-ABI complexity without carrying information); implement a general tagged `None` object now (rejected because the singleton carries no payload and D-072 still deliberately excludes `print()`'s result from general expression flow).
- Consequences: every source program accepted solely because it declares or passes a `None` parameter now reaches codegen without a declaration-time panic, and the carrier has one deterministic representation across Tier-1 targets. The representation is an internal ABI detail, not a new user-visible value or a relaxation of D-072.

## D-076: Normalize unsuccessful `pycc run` children to exit 101

- Status: accepted (PR #132 Codex review found that a generated runtime panic terminated by signal and surfaced as exit 1 on Unix)
- Context: CLI_SPEC.md promises exit 101 for a compiled-program panic or uncaught runtime failure. `pycc run` previously converted the child's `ExitStatus::code()` directly and substituted 1 when no code existed. Unix reports signal termination with no code, while Windows can report an abort status outside the portable one-byte range, so the implementation leaked platform process details and contradicted the stable CLI contract.
- Decision: generated programs in the current CLI have no user-controlled non-zero exit status. `pycc run` therefore returns 0 only when the child succeeds and maps every other child termination to 101, regardless of whether the platform represents it as a normal non-zero code, signal, exception, or abort status. Build and invocation failures retain their existing compiler-owned exit codes because they occur before child execution.
- Alternatives: preserve ordinary child codes and special-case Unix signals (rejected because no current language surface can request those codes and the result would remain platform-dependent); map only missing codes to 101 (rejected because Windows abort statuses would still be truncated); make every runtime failure unwind back through the compiler process now (deferred until Python exception objects and runtime propagation exist).
- Consequences: `pycc run` now fulfills one cross-platform exit contract for runtime panics and traps; callers need not decode platform-specific child status. A future explicit `sys.exit(n)` feature must supersede this decision with a documented rule for user-requested statuses.

## D-077: Project-local iEvo hook lifecycle is symmetric

- Status: accepted (closes #34; implements D-023's local-hook rollback)
- Context: D-023 deliberately relocates iEvo's generated Claude hooks to ignored `.claude/settings.local.json`, but the paired iEvo disable workflow through v0.61.1 removed entries only from shared `.claude/settings.json` before deleting their scripts. The result was a configured local hook whose target no longer existed and exited 127 on every prompt. Upstream `ievo-ai/skills#446` was later resolved by tracked dispatcher shims in PR #455, but this repository's stricter D-023/D-025 policy still keeps generated hooks local; equivalent project-local Codex wiring belongs in `.codex/hooks.json`.
- Decision: `scripts/manage_ievo_hooks.py` is the repository-owned lifecycle boundary. After an iEvo enable or refresh, `localize` moves only the exact known iEvo Claude hook entries from shared to local settings, deduplicates them with refreshed shared metadata taking precedence over a stale local copy, preserves every unrelated setting and hook (including empty groups/events), restores `.ievo/hooks/` to the machine-local ignore policy if upstream added tracked-shim exceptions, and refuses missing or symlinked targets. It writes the local destination before removing shared entries so an interrupted relocation cannot lose the only hook record. `check --smoke` validates the shared/local split, both ignored client configurations, every generated target, and one synthetic zero-exit invocation per distinct hook script. `disable` first parses every present configuration, removes the exact iEvo entries from shared/local Claude and Codex configuration, and fails before mutation if any managed script remains referenced through an unsupported event or command form, including a separator, lexical, quoted, case-insensitive, or Unicode-prefixed alias of the managed directory; only then does it delete the three generated hook targets and companions plus their vendored fallback directory. It preserves the tracked `.ievo/evo-auto.flag`, because that file records repository-wide intent and disabling it requires a separate reviewed D-023 rollback. All three operations are idempotent; malformed or unsupported configuration fails before mutation.
- Alternatives: adopt upstream's tracked shims (rejected because D-025 requires a separately registered clean-clone contract and the project intentionally keeps hook execution local); teach contributors to hand-edit local JSON before every disable (rejected because it is neither symmetric nor testable); run generic disable and tolerate stale local entries (rejected because `UserPromptSubmit` turns the resulting exit 127 into a per-prompt failure).
- Consequences: `.claude/settings.local.json`, `.codex/hooks.json`, and `.ievo/hooks/` remain ignored and machine-local while `.ievo/evo-auto.flag` preserves shared corrections-only intent. The required `agent-policy` test discovery exercises a tracked-clean-clone enable/refresh → smoke → disable cycle, verifies that the tracked view returns clean, and covers exact preservation, malformed-input fail-closed behavior, safe relocation order, and repeated operations. Future iEvo hook names or event shapes require an explicit helper/test update rather than being removed by a broad heuristic.
