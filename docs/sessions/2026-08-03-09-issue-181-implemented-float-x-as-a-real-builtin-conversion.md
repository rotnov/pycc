`float(x)` for `x: int | float | bool` is now implemented as a hand-recognized builtin, mirroring `len()`'s existing three-crate dispatch pattern exactly (`pycc_types`'s `infer_expr_in` and `collect_expr_constraints`, `pycc_mir`'s `lower_expr`, `pycc_codegen`'s `emit_expr`, reusing the pre-existing `to_float`/`int_to_float` runtime conversion). Wrong arity or a non-numeric argument is rejected with the existing `T0021` code, deliberately not minting a new one. `docs/DECISIONS.md`'s D-086, `docs/TYPE_SYSTEM.md`, and `docs/ROADMAP.md` were updated to record that the `int`-to-`float` boundary now has a real in-language remedy.

**A genuine coverage-gate gap, found and fixed, not a false alarm:** the plan's own assumption that `len()`'s MIR/codegen dispatch arms have "no dedicated unit test, only e2e coverage" turned out to be wrong — both actually have direct unit-level tests in `pycc_mir` and `pycc_codegen` (`lowers_len_call_to_mir_with_int_type_without_panicking`, `dict_literal_construction_codegens_and_runs`-style tests) in addition to e2e coverage, and `float`'s own e2e-only tests left one MIR region and several codegen regions uncovered even though the CLI subprocess itself definitely executed that code — `cargo llvm-cov`'s workspace merge does not always unify coverage attributed to `pycc_mir`/`pycc_codegen`'s own unit-test binary versus the separately-linked `pycc` CLI binary for small, single-value regions. Confirmed via a baseline-vs-diff `cargo llvm-cov --json` comparison (stashing the diff and re-running coverage) before concluding this, not assumed. Fixed by adding `lowers_float_call_to_mir_with_float_type_without_panicking` (`pycc_mir`) and `float_call_codegens_and_runs` (`pycc_codegen`), both constructing MIR directly and running the compiled binary, mirroring `len`'s own sibling tests exactly. `cargo llvm-cov --workspace --fail-under-lines 100 --fail-under-regions 100` is green with this fix; recorded here as a real, reproducible gap for a future session to recognize immediately rather than re-diagnose from scratch.

`ievo:deep-reviewer`'s pinned D-068 loop found one real prose defect (D-086's own correction paragraph wrongly claimed `T0021` is "the same code every other hand-recognized-builtin argument-type mismatch already uses" — `len()` is the one exception, using the domain-specific `T0033`) and one cosmetic one (a new codegen comment under-listing `to_float`'s panic arms); both fixed, second round clean.

**Two real P1 findings from the GitHub-side automated review (`chatgpt-codex-connector`) after the PR opened, both confirmed and fixed, not dismissed:**

1. **A genuine shadowing regression.** Unlike `len`/`print`, which have been hand-recognized since before this compiler could compile user-declared functions at all, `float` was undefined until this issue — so `def float(x: int) -> int: return x + 1` was a valid, working program on `main` immediately before this PR (reproduced directly against a pristine checkout, printing `6`), and the original dispatch would have silently reinterpreted it as the builtin, producing `5.0` with no diagnostic. Fixed at all four dispatch sites (`pycc_types` × 2, `pycc_mir`, `pycc_codegen`) by checking for a registered user function first — `env.lookup_function`/`signatures.contains_key`/a `$fn:` scope check/`user_functions.contains_key`, respectively — and only falling through to the builtin when none exists. New regression tests at every layer (`pycc_types` × 2, `pycc_mir`, `pycc_codegen`, an e2e test in `tests/slice1_codegen_depth.rs`) plus a correction appended to `docs/DECISIONS.md`'s D-086.
2. **A documentation-precision gap, not a new code defect.** `float(<bigint>)` aborts via `require_smallint` — confirmed this is the exact same pre-existing "no bigint-to-float" limitation ordinary arithmetic promotion already has (`fib_iter(100) + 1.5` hits the identical abort on `main` before this PR), not something `float()` newly introduces. The finding was that the PR's own doc updates advertised `float(x)` for `x: int` without this caveat, which could read as overpromising given `int` is documented elsewhere as arbitrary-precision. Fixed by tightening `docs/DECISIONS.md`, `docs/TYPE_SYSTEM.md`, and `docs/ROADMAP.md`'s wording, and adding an executing rejection test (`a_float_call_on_a_bigint_argument_aborts_honestly`, mirroring the existing `list_append_bigint_aborts` D-106 precedent) rather than only documenting the gap.

Both fixes re-ran the full local gate set clean, including a fresh `cargo llvm-cov --workspace --fail-under-lines 100 --fail-under-regions 100` (100% again — the new tests were added at every layer from the start this time, not just e2e, applying the lesson from the coverage gap above).
