## What the change does

A class that declares no `__init__` **and** inherits none through its MRO used
to be rejected with `C0001` at HIR-lowering time. It is now given an implicit
zero-argument constructor, synthesized at the exact point the rejection used to
fire. `class Config:` with only #911/D-224 class attributes, `class A: pass`, a
methods-only class, a `@property`-only class, a `@staticmethod`-only namespace
class, and a PEP 695 `class Box[T]:` are all instantiable — matching CPython,
where every one of them inherits `object.__init__`.

The semantics call (instantiable, versus resolvable-as-a-namespace-but-not-
callable) and the mechanism (reuse the `@dataclass` path's
`synthesize_dataclass_init` with an empty field list) are recorded as **D-225**,
with both rejected alternatives written out. Per D-127 the fork was resolved
against this session's advisor rather than by asking the repository owner.

## The invariant this establishes, and its one hole

Every non-enum class lowered through `lower_class` now has a resolvable
`__init__`, by declaration, inheritance, or synthesis. Three sites previously
justified their `panic!`/`#[should_panic]` by "`lower_class` rejects this" — a
claim that is now false — and were reworded to assert the new invariant
instead: `crates/pycc_types/src/class/binding.rs` (the panic and its
`#[should_panic]` test comment) and `crates/pycc_mir/src/expr.rs`. No logic
changed at any of the three.

The hole is named in all three: an **enum class early-returns** through
`lower_enum_class` before `ensure_init` runs and still reaches `pycc_mir` with
no constructor, which panics. That is
[#921](https://github.com/rotnov/pycc/issues/921), confirmed reproducing at this
baseline and deliberately **out of scope here**.

## Behavior that deliberately did *not* change

Verified empirically, each pinned by a test in `tests/issue_912_no_init_class.rs`:

- An **abstract** class with no `__init__` still cannot be instantiated — the
  #380 abstract guard runs ahead of constructor resolution.
- **Inheritance still beats synthesis**: `class A: pass` / `class B(A): pass`
  gives `B` no `__init__` of its own; instantiating `B` resolves `A.__init__`
  through the MRO exactly as #432 already did (confirmed against the emitted
  binary's symbol table, then pinned as a `class::init` unit test).
- **#541 Part 2's exception rule is unchanged.** "Non-synthetic ancestor" is
  D-188 *provenance*, not a statement about who wrote the constructor body, so a
  user-declared ancestor carrying a synthesized `__init__` is still
  non-synthetic: `class Base: pass` / `class MyError(Base, Exception): pass` /
  `raise MyError("boom")` stays `C0001`, reported from the raise operand. Both
  `docs/TYPE_SYSTEM.md` and `docs/RUNTIME.md` were qualified to say so
  explicitly, since the shape was previously unreachable.
- `mro_attr_count` and the D-154 slot layout: the synthesized constructor
  establishes no attribute slots, so neither needed a change.
- The **#585/D-224 scalar-only invariant** at `crates/pycc_hir/src/class/body.rs`
  is untouched. This change does not relax it.
