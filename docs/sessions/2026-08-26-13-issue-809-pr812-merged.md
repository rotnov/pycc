## What happened after the 07 snapshot

1. **A Windows `LLVMString` crash (D-029)** was found and fixed in two

2. **A P1 automated-review finding** from the `chatgpt-codex-connector` bot
   on PR #812: `coerce_scalar_to_type`'s `(Ty::Optional(inner),
   Scalar::Optional(v))` arm's mismatched-struct branch unconditionally
   built the absent-value placeholder's field 0 with
   `tag_smallint_const(context, 0)` -- an `i64`-typed constant -- regardless
   of the target inner type. Correct only for `Ty::Int`. For `Ty::Float`
   (target struct `{f64, i8}`) this produced a `ConstantStruct` whose
   declared type disagreed with its own field-0 operand's actual type: a
   real, silent miscompile, confirmed by dumping IR (`store { double, i8 }
   { i64 1, i8 0 }, ptr @pyglobal_x`). Neither `module.verify()` nor LLVM's
   textual IR printer catch this, because the verifier only checks a
   `GlobalVariable` initializer's outer `Constant::getType()` without
   recursively re-validating each field's actual type, and the
   type-matching assert `build_insert_value`'s constant-folder would
   otherwise perform is compiled out of this project's release (NDEBUG)
   LLVM build.

   Fixed in commit `cc699c56` ("Fix bare-None coercion for
   Optional[float]/Optional[bool] payloads"): the placeholder's field 0 is
   now built from the actual declared inner type (`tag_smallint_const` for
   `Ty::Int`, a plain `f64` zero for `Ty::Float`, a plain `i8` zero for
   `Ty::Bool`, with a `panic!` catch-all for any other inner type, which
   `pycc_types::check` (T0049) should already have rejected before
   codegen).

   Added regression coverage for the two paths the finding named
   specifically and that no existing test exercised -- a bare `None`
   function argument and a bare `return None`, neither of which goes
   through `MirExpr::OptionalWrap` the way `HirStmt::Assign`/`AnnAssign`
   do -- plus a direct unit test pinning the new match's defensive
   catch-all arm, and a direct unit test (hand-built mismatched
   `Scalar::Optional`) for the new match's `Ty::Bool` case, which is
   unreachable through any real MIR program: `Ty::Bool`'s real
   `Optional[bool]` struct shape (`{i8, i8}`) is the literal same LLVM
   `StructType` value as the placeholder's own fixed shape (anonymous LLVM
   struct types are uniqued per-`Context` by field-type list), so the `if
   v.get_type() == struct_ty` branch always wins for that inner type
   instead of reaching the new match. Confirmed via `cargo llvm-cov
   --workspace --fail-under-lines 100 --fail-under-regions 100`: TOTAL
   100.00% across regions/functions/lines/branches, 0 missed, after adding
   that unit test (the first coverage run, before it existed, was short:
   99.99% regions / 99.98% lines in `pycc_codegen/src/lib.rs`, pinpointed
   via `--show-missing-lines` to the new `Ty::Bool` match arm).

   Replied into the bot's GitHub review thread
   (`PRRT_kwDOTiOo7s6cmZ_4`) explaining the fix and referencing `cc699c56`,
