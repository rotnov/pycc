# v0.2 PR-11a: dict[str, int] + set[int] thin slice Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship a working, type-checked, codegen'd `dict[str, int]` and `set[int]` — literal construction, `len()`, iteration, plus `dict`'s own `d[k]` read and `d[k] = v` insert-or-update — through the real `pycc build`/`run` CLI, exactly mirroring the "thin slice" pattern PR-10 already established for `list[int]`.

**Architecture:** Both containers are a dense, insertion-ordered array with **linear-scan** lookup/dedup — no hash function, no probing, no resizing logic. This is deliberately simpler than `docs/RUNTIME.md`'s aspirational "swiss table" wording; see Task 1's ADR for why that's the correct v0.2 choice, not a shortcut taken under time pressure. Both containers ship exactly one concrete type instantiation (`dict[str, int]`, `set[int]`); every other combination is rejected with a clean pre-codegen diagnostic, mirroring `list[int]`'s own `T0034` gate. `tuple[...]` is **out of scope for this plan** — it needs a fundamentally different (non-hashed, non-heap, LLVM-struct-based) representation and has its own follow-up plan; do not attempt it here.

**Tech Stack:** Rust workspace (`pycc_hir`, `pycc_types`, `pycc_mir`, `pycc_codegen`, `pycc_rt`), LLVM via `inkwell` (already a dependency), existing `tests/conformance.rs` dual-profile harness against pinned CPython 3.14.6.

- [ ] **Step 4: Record D-111 — dict/set representation is a dense insertion-ordered array with linear-scan lookup, not a hash table**

Append to `docs/DECISIONS.md` (use the real next-free D-number from Step 1):

```markdown
## D-111: dict[K, V]/set[T] v0.2 representation is a dense insertion-ordered array with linear-scan lookup, not a hash table

**Context:** `docs/RUNTIME.md` (line 11) and `docs/TYPE_SYSTEM.md` (line 56) both
already say "swiss table" for `dict`, and the v0.2 design doc's own PR
breakdown (item 4, `docs/superpowers/specs/2026-07-28-v0-2-collections-generics-design.md`
§3) explicitly names `set[T]`'s representation as PR-11's own ADR to record.
Neither doc ever elaborates what "swiss table" means beyond the name --
no open-addressing scheme, probe sequence, or group-metadata layout is
specified anywhere in this repository.

**Decision:** v0.2 ships `dict[str, int]`/`set[int]` as a dense,
insertion-ordered array (`Vec`-backed) with **linear-scan** lookup, using
the equality-comparison primitives `pycc_codegen` already has for each
scalar type (`pycc_rt_str_cmp` for `dict`'s `str` keys, raw `i64` equality
for `set`'s `int` elements). No hash function, no probe sequence, no load
factor, no resize/rehash logic exists in this PR's own runtime objects.
`dict`'s insertion-order guarantee (`docs/PYTHON_STANDARDS.md`'s
dict-insertion-order row) is trivially true of a dense array by
construction. `set`'s CPython-matching non-guaranteed iteration order is
likewise trivially satisfied -- our own array happens to iterate in
insertion order, which is *a* legal order Python permits, not necessarily
*the* order CPython's own hash table would produce for the same literal
(see D-113 below for why no fixture may assert on this).

**Alternatives considered:**
- A real open-addressed hash table (the literal "swiss table" the docs
  name) -- rejected for v0.2: this PR's own scope is small, fixed-arity
  literal construction plus at most one post-construction mutation
  operation (`dict`'s `d[k] = v`); a full hash table's probing/resize
  machinery is pure implementation risk for a data-structure property (O(1)
  amortized lookup) that no v0.2 fixture or benchmark actually measures.
  Per D-057's "simplest correct thing" precedent (already cited by D-089),
  the dense-array-plus-linear-scan design is strictly simpler, is
  trivially correct, and defers zero user-visible guarantee -- `dict`'s
  insertion order and `set`'s membership behavior are identical either way
  at the scale this PR's own fixtures exercise.
- Reusing `pycc_rt`'s existing per-scalar comparison functions generically
  via some kind of type-erased "compare any two `Scalar`s" runtime
  function -- rejected: pycc is statically typed end-to-end, and codegen
  already knows a given `dict`/`set`'s key/element type at every call
  site, so a type-erased runtime dispatch would add an indirection this
  static information makes unnecessary.

**Consequences:** `docs/RUNTIME.md`'s "swiss table" wording gets a
"Current state (through PR-11, D-111)" caveat (Task 10 of this plan),
mirroring `list[T]`'s own "Current state (through PR-10, D-105)" pattern
at line 10 -- the real hash-table design remains the v1.0 target, not
silently abandoned. A future PR that needs true amortized-O(1) lookup (a
`dict`/`set` used at a scale where linear scan is a real cost) replaces
`PyDictObj`/`PyIntSetObj`'s internals without changing either type's own
public FFI surface (`pycc_rt_dict_get`/`_set`/`_len`, `pycc_rt_int_set_add`/
`_len`), so callers in `pycc_codegen` do not need to change.
```

- [ ] **Step 5: Record D-112 — key/element type scope: only types with existing equality-comparison codegen, exactly one shipped combination**

```markdown
## D-112: dict[K, V]/set[T] key/element types are scoped to existing equality-comparable scalars; exactly one combination gets real codegen

**Context:** D-111's linear-scan lookup needs an equality comparison
between two keys (or two set elements) at every scan step. `pycc_codegen`
already implements `CmpOpKind::Eq` for all four scalar types (`Int`,
`Float`, `Bool`, `Str`) but has no equality comparison for any container
type (`List`/`Dict`/`Set`/`Tuple`) -- comparing two lists/dicts/sets/tuples
for equality is not implemented anywhere in this compiler. Mirroring
`list[int]`'s own D-105 scope cut 5 ("ship exactly one concrete element
type, gate everything else with a clean pre-codegen diagnostic"), this PR
ships exactly one key/value combination per container.

**Decision:** `dict`'s shipped combination is `dict[str, int]`; `set`'s is
`set[int]`. Any other combination (`dict[int, str]`, `set[str]`,
`dict[list[int], int]`, etc.) type-checks structurally (`Ty::Dict`/
`Ty::Set` are already fully general per D-089) but is rejected before
codegen by a new diagnostic (`T0036` for dict, `T0038` for set -- see Task
3/Task 7 of `docs/superpowers/plans/2026-08-01-v0-2-pr11-dict-set.md`),
exactly mirroring `list[int]`'s own `T0034`. This also transitively rejects
every non-scalar key/element type (no combination containing `List`/
`Dict`/`Set`/`Tuple` is the one shipped combination), which is the correct
behavior anyway since no equality codegen exists for those types.

**Alternatives considered:**
- Shipping `dict[int, int]`/`set[int]` for symmetry with `list[int]` --
  rejected: `dict[str, int]` is a more representative real-world dict
  shape (string keys are the overwhelmingly common case) and exercises
  `pycc_rt_str_cmp`'s existing comparison path, giving the
  dict-insertion-order fixture (D-113) a realistic, readable shape (e.g.
  `{"a": 1, "b": 2}`) rather than an arbitrary int-keyed one.
- General hashability inference (accept any type with a derivable
  equality, à la Rust's `#[derive(PartialEq)]`) -- rejected as far beyond
  this PR's "thin slice" scope; no user-defined types with
  `__eq__`/`__hash__` overloading exist in this compiler at all yet.

**Consequences:** widening either container's type coverage later needs
exactly the same two changes D-105's own Consequences section already
named for `list[int]`: (a) relax/remove the `T0036`/`T0038` gate (small,
isolated), and (b) add a new `pycc_rt` runtime object plus `pycc_codegen`
dispatch arms for that specific combination (the surrounding
`pycc_types`/`pycc_mir` inference logic is already fully generic over
`Ty::Dict`/`Ty::Set`'s structure and needs no changes either way).
```

- [ ] **Step 6: Record D-113 — dict gets `d[k] = v`; set gets construction/len/iterate only, no membership test, no fixture ordering claims**

```markdown
## D-113: dict[str, int] ships a `d[k] = v` insert-or-update operation; set[int] ships no membership test and no CPython iteration-order claim

**Context:** `list[int]`'s own v0.2 thin slice stayed read-only on
indexing (D-105 cut 2) but did ship one growable operation, `.append()`,
without which an empty list literal would be permanently empty. `dict`
has the same problem in reverse: a `dict[str, int]` literal is
constructible without any growable op, but `docs/PYTHON_STANDARDS.md`'s
own dict-insertion-order row and `docs/DELIVERY_PLAN.md` row 11's
"insertion-order fixture" deliverable are only genuinely demonstrated if
insertion order survives a *mutation*, not merely literal-construction
order (which is trivially insertion-ordered by definition of D-111's own
representation and would prove nothing). Separately, `set[T]` has no
analog of `.append()` in Python at all -- `set.add()` exists, but nothing
in this PR's own scope requires it, and the `in` operator this compiler
has no support for yet is the operation that would make a bare `set`
actually useful beyond `len()`.

**Decision:** `dict[str, int]` ships `d[k] = v` as an insert-or-update
operation (new key: appended in place, preserving insertion order;
existing key: value updated in place, key position unchanged) alongside
read (`d[k]`, panics if the key is absent -- no `KeyError` handling exists
in this compiler), `len(d)`, and `for k in d:` (iterates keys in insertion
order). `set[int]` ships only literal construction (with dedup at
construction time -- a repeated literal element is inserted once, matching
CPython's own set-literal semantics), `len(s)`, and `for x in s:`; it gets
no `.add()`, no indexing (real Python sets are not subscriptable --
`s[0]` is a `TypeError` in CPython too, so rejecting it with the existing
`T0033` "does not support indexing" diagnostic is not a v0.2 scope cut,
it is the semantically correct behavior), and no membership test (blocked
on the `in` operator not existing anywhere in this compiler yet -- tracked
as a `docs/ROADMAP.md` follow-up by Task 10 of this plan, not silently
assumed solved).

Because `set[int]`'s own iteration order in this implementation is
insertion order (D-111), but CPython's own set iteration order is
hash-dependent and unspecified, **no conformance fixture may assert
byte-for-byte equality between pycc's and CPython's printed set-iteration
output.** A `set` fixture may assert `len()` (order-independent) and may
print elements only after an order-independent transformation (e.g.
`sorted(...)`, if in scope) or not at all -- see Task 9 of this plan for
the exact fixture design this constrains.

**Alternatives considered:**
- No `d[k] = v` at all, matching list's own read-only-index precedent
  exactly -- rejected: unlike `list`, dict without any post-construction
  mutation makes the insertion-order fixture prove nothing beyond "a
  literal's pairs print in the order they were written", which is true of
  the source text alone and demonstrates nothing about the actual runtime
  representation.
- Implement `set`'s `.add()`/`in` in this same PR to make `set` genuinely
  useful -- rejected: `in` is a real, separate parser/HIR/type-checker/
  codegen feature (a new comparison-expression form) with its own scope
  large enough to warrant its own PR; bundling it here would make `set`'s
  own slice no longer "thin".

**Consequences:** a future PR adding `in` support project-wide should
revisit `set[int]`'s own scope to add membership testing as a natural,
small follow-up once the underlying language feature exists --
tracked as a `docs/ROADMAP.md` follow-up by Task 10 of this plan.
```

- [ ] **Step 7: Record D-114 — dict/set refcounting stays leak-only, extending D-107's exact reasoning**

```markdown
## D-114: dict[str, int]/set[int] refcounting stays leak-only, extending D-107's exact reasoning to two new heap object types

**Context:** D-107 chose leak-only refcounting for `list[int]`'s own
`PyIntListObj` in v0.2, citing pycc's actual target use (a short-lived,
single-shot compiled batch program) as justification for treating an
unbounded per-list leak as a bounded-by-process-lifetime resource cost
rather than a defect. `PyDictObj`/`PyIntSetObj` (this plan's own two new
heap object types) are structurally identical in this respect: nothing
about being a dict or a set changes the argument.

**Decision:** `PyDictObj`/`PyIntSetObj` get `pycc_rt_dict_incref`/`_decref`
and `pycc_rt_int_set_incref`/`_decref` FFI functions (implemented and
tested, exactly mirroring `pycc_rt_int_list_incref`/`_decref`'s own
unconditional-refcounting-with-free-at-zero shape), but **`pycc_codegen`
never calls either pair** in this PR's own scope -- every dict/set
allocation lives for the process's lifetime, identically to `list[int]`.
`PyDictObj`'s own keys (`*mut PyStrObj` pointers) are stored without
incref on insert and without decref ever, for the same leak-only reason --
this additionally sidesteps a subtle double-free risk `d[k] = v`'s
update-in-place case would otherwise raise (re-storing a key that
compares equal to an already-stored one) without a real design needed to
resolve it, since no decref ever happens on the old or new key either way.

**Alternatives considered:**
- Wire full refcounting now for the two new containers even though
  `list[int]` itself stays leak-only -- rejected: this would make
  `dict`/`set`'s own memory-lifetime behavior inconsistent with `list`'s,
  for no user-visible benefit in a batch-compiled-binary target, and
  duplicates the exact tradeoff D-107 already made once.

**Consequences:** identical to D-107's own: a future PR that needs real
refcounting for any of `list`/`dict`/`set` should very likely do all three
in one pass (the incref/decref call-site wiring at duplicate-reference
reads, reassignment cleanup, and scope-exit cleanup is the same shape for
all three container types), tracked as a single `docs/ROADMAP.md`
follow-up by Task 10 of this plan.
```

- [ ] **Step 3: Implement `PyDictObj` and its FFI functions**

Add near `PyIntListObj`'s own block, using the real D-number from Task 1 in place of `D-1xx`:

```rust
/// `dict[str, int]`'s runtime representation (D-1xx): a dense,
/// insertion-ordered array of `(key, value)` pairs. `Cell<Vec<...>>`
/// mirrors `PyIntListObj`'s own choice over `RefCell` -- `Cell::take`/
/// `_::set` never holds a borrow across a mutation, so there is no new
/// runtime-panic mode from overlapping borrows. Not `#[repr(C)]` -- never
/// crosses the LLVM/Rust boundary by value, only as an opaque pointer
/// (mirrors `PyStrObj`/`PyIntListObj`). Lookup is linear-scan comparison
/// via `pycc_rt_str_cmp` (D-1xx), not a hash table.
pub struct PyDictObj {
    rc: Cell<u32>,
    entries: Cell<Vec<(*mut PyStrObj, i64)>>,
}

/// Allocates a fresh, empty `PyDictObj` with refcount `1`. Never panics.
#[unsafe(no_mangle)]
pub extern "C" fn pycc_rt_dict_new() -> *mut PyDictObj {
    Box::into_raw(Box::new(PyDictObj {
        rc: Cell::new(1),
        entries: Cell::new(Vec::new()),
    }))
}

/// Insert-or-update (D-1xx): if `key` compares equal (`pycc_rt_str_cmp`)
/// to an already-stored key, that entry's value is overwritten in place,
/// preserving insertion order; otherwise `(key, value)` is appended.
/// Leak-only (D-1xx): the stored key pointer is neither increfed on
/// insert nor decrefed on update-in-place or ever.
///
/// # Safety
/// `dict` and `key` must be live pointers from `pycc_rt_dict_new`/
/// `pycc_rt_str_new`-family functions respectively.
#[unsafe(no_mangle)]
pub unsafe extern "C" fn pycc_rt_dict_set(dict: *mut PyDictObj, key: *mut PyStrObj, value: i64) {
    let mut entries = unsafe { &*dict }.entries.take();
    match entries
        .iter()
        .position(|(k, _)| unsafe { pycc_rt_str_cmp(*k, key) } == 0)
    {
        Some(i) => entries[i].1 = value,
        None => entries.push((key, value)),
    }
    unsafe { &*dict }.entries.set(entries);
}

/// Linear-scan lookup (D-1xx). Panics if no stored key compares equal to
/// `key` -- this compiler has no `KeyError` handling, so a missing key is
/// an honest panic rather than a silently wrong value.
///
/// # Safety
/// Same as `pycc_rt_dict_set`.
#[unsafe(no_mangle)]
pub unsafe extern "C" fn pycc_rt_dict_get(dict: *mut PyDictObj, key: *mut PyStrObj) -> i64 {
    let entries = unsafe { &*dict }.entries.take();
    let found = entries
        .iter()
        .find(|(k, _)| unsafe { pycc_rt_str_cmp(*k, key) } == 0)
        .map(|(_, v)| *v);
    unsafe { &*dict }.entries.set(entries);
    found.unwrap_or_else(|| panic!("pycc_rt: dict key not found"))
}

/// Number of entries. `Cell::take` followed by re-`set`ting it, mirroring
/// `pycc_rt_int_list_len`'s own exact pattern (never leave the `Cell`
/// empty on return).
///
/// # Safety
/// `dict` must be a live `PyDictObj` pointer.
#[unsafe(no_mangle)]
pub unsafe extern "C" fn pycc_rt_dict_len(dict: *mut PyDictObj) -> i64 {
    let entries = unsafe { &*dict }.entries.take();
    let len = entries.len() as i64;
    unsafe { &*dict }.entries.set(entries);
    len
}

/// Key at a given insertion-order position, used only by `ForDict`'s own
/// iteration codegen (Task 5) -- never a user-facing indexing operation
/// (dict has no positional index in Python).
///
/// # Safety
/// `dict` must be a live `PyDictObj` pointer; `index` must satisfy
/// `0 <= index < pycc_rt_dict_len(dict)` (an internal codegen invariant,
/// not user input -- `ForDict`'s own loop bound is `pycc_rt_dict_len`,
/// so an out-of-range call here would be a codegen bug, not a possible
/// user program).
#[unsafe(no_mangle)]
pub unsafe extern "C" fn pycc_rt_dict_key_at(dict: *mut PyDictObj, index: i64) -> *mut PyStrObj {
    let entries = unsafe { &*dict }.entries.take();
    let key = entries[index as usize].0;
    unsafe { &*dict }.entries.set(entries);
    key
}

/// Unconditional refcounting (D-1xx), mirroring `pycc_rt_int_list_incref`
/// exactly. No-op on null.
///
/// # Safety
/// `dict` must be null or a live `PyDictObj` pointer.
#[unsafe(no_mangle)]
pub unsafe extern "C" fn pycc_rt_dict_incref(dict: *mut PyDictObj) {
    if dict.is_null() {
        return;
    }
    let obj = unsafe { &*dict };
    obj.rc.set(obj.rc.get() + 1);
}

/// Mirrors `pycc_rt_int_list_decref` exactly: frees via `Box::from_raw`
/// once `rc` hits 0. Not called from any `pycc_codegen` site in this PR
/// (D-1xx, leak-only).
///
/// # Safety
/// `dict` must be null or a live `PyDictObj` pointer not used again after
/// its refcount reaches 0.
#[unsafe(no_mangle)]
pub unsafe extern "C" fn pycc_rt_dict_decref(dict: *mut PyDictObj) {
    if dict.is_null() {
        return;
    }
    let obj = unsafe { &*dict };
    let rc = obj.rc.get() - 1;
    obj.rc.set(rc);
    if rc == 0 {
        drop(unsafe { Box::from_raw(dict) });
    }
}
```

```rust
/// `set[int]`'s runtime representation (D-1xx): structurally identical to
/// `PyIntListObj` (a dense array of raw untagged `i64`), but insertion goes
/// through `pycc_rt_int_set_add`'s own dedup check (linear scan, D-1xx)
/// instead of `PyIntListObj`'s unconditional append -- this is the one
/// behavioral difference and the reason this is its own distinct type
/// rather than a reuse of `PyIntListObj` (mirrors the same reasoning
/// D-107 gave for `Scalar::List` needing its own variant instead of
/// reusing `Scalar::Str`: distinct semantics deserve a distinct type so
/// the compiler enforces every call site acknowledges the difference).
pub struct PyIntSetObj {
    rc: Cell<u32>,
    items: Cell<Vec<i64>>,
}

/// Allocates a fresh, empty `PyIntSetObj` with refcount `1`. Never panics.
#[unsafe(no_mangle)]
pub extern "C" fn pycc_rt_int_set_new() -> *mut PyIntSetObj {
    Box::into_raw(Box::new(PyIntSetObj {
        rc: Cell::new(1),
        items: Cell::new(Vec::new()),
    }))
}

/// Dedup-checked insert (D-1xx): linear-scan for an already-present equal
/// value; appends only if absent, preserving first-insertion order.
///
/// # Safety
/// `set` must be a live `PyIntSetObj` pointer.
#[unsafe(no_mangle)]
pub unsafe extern "C" fn pycc_rt_int_set_add(set: *mut PyIntSetObj, value: i64) {
    let mut items = unsafe { &*set }.items.take();
    if !items.contains(&value) {
        items.push(value);
    }
    unsafe { &*set }.items.set(items);
}

/// # Safety
/// `set` must be a live `PyIntSetObj` pointer.
#[unsafe(no_mangle)]
pub unsafe extern "C" fn pycc_rt_int_set_len(set: *mut PyIntSetObj) -> i64 {
    let items = unsafe { &*set }.items.take();
    let len = items.len() as i64;
    unsafe { &*set }.items.set(items);
    len
}

/// Element at a given insertion-order position, used only by `ForSet`'s
/// own iteration codegen (Task 9) -- `set` has no user-facing indexing in
/// Python (real CPython also rejects `s[0]`), so this is an internal
/// codegen helper only.
///
/// # Safety
/// `set` must be a live `PyIntSetObj` pointer; `index` must satisfy
/// `0 <= index < pycc_rt_int_set_len(set)` (an internal codegen
/// invariant, mirroring `pycc_rt_dict_key_at`'s own contract).
#[unsafe(no_mangle)]
pub unsafe extern "C" fn pycc_rt_int_set_get(set: *mut PyIntSetObj, index: i64) -> i64 {
    let items = unsafe { &*set }.items.take();
    let value = items[index as usize];
    unsafe { &*set }.items.set(items);
    value
}

/// Mirrors `pycc_rt_int_list_incref` exactly.
///
/// # Safety
/// `set` must be null or a live `PyIntSetObj` pointer.
#[unsafe(no_mangle)]
pub unsafe extern "C" fn pycc_rt_int_set_incref(set: *mut PyIntSetObj) {
    if set.is_null() {
        return;
    }
    let obj = unsafe { &*set };
    obj.rc.set(obj.rc.get() + 1);
}

/// Mirrors `pycc_rt_int_list_decref` exactly. Not called from any
/// `pycc_codegen` site in this PR (D-1xx, leak-only).
///
/// # Safety
/// `set` must be null or a live `PyIntSetObj` pointer not used again after
/// its refcount reaches 0.
#[unsafe(no_mangle)]
pub unsafe extern "C" fn pycc_rt_int_set_decref(set: *mut PyIntSetObj) {
    if set.is_null() {
        return;
    }
    let obj = unsafe { &*set };
    let rc = obj.rc.get() - 1;
    obj.rc.set(rc);
    if rc == 0 {
        drop(unsafe { Box::from_raw(set) });
    }
}
```
