# PR-11b: `tuple[int|bool|float, ...]` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make a fixed-arity, heterogeneous `tuple[...]` literal of `int`/`bool`/`float` elements constructible, storable, and readable (via a literal, in-range index) end-to-end — parse → HIR → type-check → MIR → LLVM codegen — closing PR-11's own combined `dict[K,V]`/`set[T]`/`tuple[...]` scope from `docs/DELIVERY_PLAN.md` row 11.

**Architecture:** Unlike `dict`/`set` (PR-11a), a tuple value needs no heap object and no refcounting: every v0.2-accepted element type (`int`/`bool`/`float`) is a fixed-width LLVM scalar known entirely at compile time, so `ty_to_basic_type` maps `Ty::Tuple(elems)` to an LLVM `struct` type and `pycc_codegen::Scalar` gets a `Tuple(StructValue)` variant holding the whole aggregate **by value** (an SSA register), not a pointer. Construction uses `get_undef()` + repeated `build_insert_value`; reading `t[k]` for a literal `k` uses `build_extract_value` directly on the loaded struct value — no `build_struct_gep`, no alloca-level field access, needed for this slice. Unlike dict/set, tuple also needs brand-new HIR-level literal support first: `Expr::Tuple` currently lowers to nothing (it is this codebase's own designated "genuinely unhandled at every level" fixture), so this plan's early tasks add that capability before any type-checking/codegen work is possible.

**Tech Stack:** Same workspace as PR-11a — `pycc_ast`/`pycc_hir`/`pycc_types`/`pycc_mir`/`pycc_codegen`/`pycc_rt`, `inkwell = "0.9.0"` (LLVM 22.1, opaque pointers, `default-features = false`), `ruff_python_ast = "0.0.6"`/`ruff_python_parser = "0.0.6"`.

## D-115: tuple[...] v0.2 representation is a fixed-arity LLVM struct-of-scalar-fields, held as an SSA aggregate value — no heap object, no refcounting question

- Status: accepted
- Context: `docs/TYPE_SYSTEM.md` (line 55) already says tuple's representation is "fixed heterogeneous ... inline struct (stack when non-escaping)". `Ty::Tuple(Box<Vec<Ty>>)` already exists as a stub (`crates/pycc_hir/src/lib.rs:54`); `pycc_codegen::ty_to_basic_type` currently panics for it (`crates/pycc_codegen/src/lib.rs`, locked in by `ty_to_basic_type_panics_clearly_for_tuple`). Unlike `list[int]`/`dict[str,int]`/`set[int]` (all heap-allocated, pointer-referenced `pycc_rt` objects), every v0.2-accepted tuple element type (`int`/`bool`/`float`, per D-116) is a fixed-width scalar with a compile-time-known count — LLVM's own aggregate (`struct`) value type models this directly, with no allocation needed at all.
- Decision: `ty_to_basic_type` maps `Ty::Tuple(elems)` to `context.struct_type(&field_types, false)` (not packed — ordinary field alignment). `pycc_codegen::Scalar` gets a new `Tuple(StructValue<'ctx>)` variant holding the whole aggregate **by value** — an SSA register, not a `PointerValue` to a heap or stack allocation, unlike every existing container variant. Construction uses `struct_type.get_undef()` followed by one `Builder::build_insert_value` per element (LLVM's `insertvalue`); reading `t[k]` for a literal, in-range `k` uses `Builder::build_extract_value` directly on the already-loaded `StructValue` (LLVM's `extractvalue`) — neither operation needs a pointer, so `Builder::build_struct_gep` (the facility this PR's original research assumed would be needed) turns out to be unnecessary for this slice: nothing here ever addresses a struct field through a pointer, only whole-value insert/extract on an SSA aggregate. Storage for a tuple-typed local needs no special-casing: `declare_module_globals`/`storage_slot_at_entry`/`emit_assign` already generalize over any `BasicTypeEnum`/`BasicValueEnum` via `Builder::build_store`/`build_load`, and `inkwell`'s `BasicValueEnum`/`BasicMetadataValueEnum` both already include a `StructValue` variant (verified against the installed `inkwell = "0.9.0"` source, `src/values/enums.rs:70-73`), so an alloca's store/load, an argument-marshalling site, and a function's return value all accept a `Scalar::Tuple`'s payload with a plain `.into()`, identically to `Scalar::Str`/`List`/`Dict`/`Set`'s own pointer payloads.

  Refcounting has no question to answer here (unlike D-114's extension of D-107 for dict/set): D-116 excludes `Ty::Str` from tuple's v0.2 element types specifically so that no tuple ever contains a refcounted field, so `compile_to_object`'s exit-time `slot.ty == Ty::Str` decref loop (`crates/pycc_codegen/src/lib.rs:2876`) is correctly untouched by this PR — a plain enum equality check that structurally can never match a `Ty::Tuple(_)`-typed slot regardless of that tuple's own element types. A tuple containing a `str` field would need real per-field teardown logic this project has never had to write for any type (a struct's fields need individual inspection, unlike every existing container, which is a single opaque pointer) — deferred to whichever future PR widens the element-type gate to include `str`.
- Alternatives considered:
  - A heap-allocated `pycc_rt` runtime object (`PyTupleObj`), pointer-referenced like `PyIntListObj`/`PyDictObj`/`PyIntSetObj` — rejected: a heap allocation buys nothing for a fixed-arity, fixed-layout aggregate of scalar fields known entirely at compile time, and would reopen D-114's leak-only-refcounting question for a fourth heap type where D-116's own element-type gate makes the question moot for an SSA-value representation.
  - `Builder::build_struct_gep` plus a stack alloca, mirroring the original research's assumption — rejected once `build_insert_value`/`build_extract_value` (operating directly on an SSA `StructValue`, no pointer or alloca required) were confirmed present and sufficient for this slice's read-only, whole-tuple-construction scope; kept as the natural upgrade path if a future PR needs field mutation (which Python's own tuples do not support anyway) or a tuple large enough that by-value passing becomes a real cost.
- Consequences: `ty_to_basic_type`'s `Ty::Tuple` arm and its own dedicated test (`ty_to_basic_type_panics_clearly_for_tuple`) both change in Task 5 of `docs/superpowers/plans/2026-08-01-v0-2-pr11-tuple.md` — the test's very name asserts a panic that Task 5 replaces with real struct-type construction. A future PR widening tuple's element types to include `str`/any container needs to revisit this ADR's "no heap object" premise for whichever field types are refcounted or themselves pointer-sized-and-owning.
```

## D-116: tuple[...] v0.2 scope — int/bool/float elements only, literal-index-only reads; pass-through operations extend uniformly, interpretive operations panic honestly

- Status: accepted
- Context: dict/set's own D-112 scoped to exactly one key/value combination each because their v0.2 slice needed a working equality comparison for hash-table-style lookup; tuple has no such constraint (D-115's struct representation needs no element equality for construction or literal-index reads), so tuple's scope question is different in kind: which element *types* are safe to put in a struct field with this PR's own codegen support, and what indexing form is type-checkable at all for a heterogeneous aggregate.
- Decision:
  1. Element types: exactly `Ty::Int`, `Ty::Bool`, `Ty::Float` (any mix, any arity ≥ 1) are accepted; any other element type (`Ty::Str`, `Ty::List`, `Ty::Dict`, `Ty::Set`, `Ty::Tuple`) is rejected pre-codegen by a new diagnostic, `T0039` ("tuple[...] is not compiled yet -- only int/bool/float elements are"), mirroring `T0034`/`T0036`/`T0038`'s "one shipped shape, everything else gets a clean diagnostic" pattern — except this gate is a type-*membership* test per element, not a single frozen shape, since D-115's per-field codegen already generalizes for free across any mix of these three scalar types. An empty tuple literal is rejected with the existing `T0021` pattern, mirroring `ListLiteral`/`DictLiteral`/`SetLiteral`'s own identical empty-literal gate.
  2. Indexing: `t[k]` requires `k` to be a literal (`HirExpr::IntLiteral`), non-negative, in-bounds integer — not merely `int`-typed, unlike `list[int]`'s own runtime-checked index (D-105/D-108). A heterogeneous tuple's element type at position `k` is only knowable when `k` is known at compile time, so a non-literal or out-of-range `t[k]` is rejected by a new diagnostic, `T0040` ("tuple index must be a non-negative literal integer within range"), covering all three failure shapes (non-literal, negative, out-of-range) under one code since they are the same underlying "not a valid compile-time position for this tuple" failure — a stricter, statically-checked version of D-108's own "no negative indexing" rule, caught at compile time here instead of `list[int]`'s runtime panic, because the literal is already in hand at type-check time.
  3. Deferred, tracked as `docs/ROADMAP.md` follow-ups (Task 7 of `docs/superpowers/plans/2026-08-01-v0-2-pr11-tuple.md`), not silently assumed solved: `for x in t:` iteration (needs per-position codegen for a heterogeneous tuple, a materially different problem than `ForList`/`ForDict`/`ForSet`'s homogeneous-element loops); tuple-unpacking assignment (`a, b = t`, a new multi-target assignment form nothing in `HirStmt::Assign`'s shape supports today); a `tuple[...]` annotation syntax (mirrors D-105 cut 1's identical deferral for `list[T]`); nested containers-of-tuples or tuples-of-containers (already rejected structurally by (1) above).
  4. NOT deferred, because D-115's representation makes it free: a tuple value may be a function's inferred return value or an unannotated/generic function's argument, exactly like `list[int]`/`dict[str,int]`/`set[int]` already can be (there is no annotation syntax for any of the four container types, so this was already call-site-structural-inference-only for all of them) — `build_call_to`'s argument-marshalling match and `MirStmt::Return`'s codegen both get a real `Scalar::Tuple(v) => v.into()` pass-through arm, not a panic, mirroring `List`/`Dict`/`Set`'s own existing arms there exactly.
- Alternatives considered:
  - Requiring homogeneous elements, mirroring `list`/`dict`/`set`'s own homogeneity gates — rejected: heterogeneity is tuple's entire distinguishing feature in real Python (`(1, "a", True)`); restricting to homogeneous tuples would ship a strictly worse-than-`list[int]` feature for no implementation-cost savings, since D-115's per-field codegen already handles any mix of the three accepted scalar types with zero extra work.
  - Accepting a non-literal integer index and picking, say, the first element's type as the whole subscript's result (unsound but simple) — rejected outright: silently-wrong types reaching codegen is exactly the defect class this project's testing/diagnostics discipline exists to prevent. CPython itself allows `t[i]` for a variable `i` only because its tuples are dynamically typed at every position; this compiler's static type system has no single `Ty` to give that expression when the tuple is heterogeneous, so rejecting it is the only sound option, not a scope cut.
  - Scoping function-parameter/return/argument-marshalling support out of v0.2 defensively, on an initial (later revised) assumption that struct-by-value crossed some unaddressed ABI complexity boundary — rejected after confirming `inkwell`'s `BasicValueEnum`/`BasicMetadataValueEnum` already include `StructValue` and every relevant call site (`build_call_to`, `MirStmt::Return`, `emit_assign`) is already generic over `BasicValueEnum`/`BasicTypeEnum`: excluding this would be an artificial restriction with no corresponding implementation risk.
- Consequences: a future PR widening `T0039`'s element-type gate to include `Ty::Str` must revisit D-115's "no refcounting question" premise before shipping. A future PR adding `for x in t:` or tuple-unpacking assignment is unblocked by anything in this ADR — both are additive, not corrections to this scope. `docs/ROADMAP.md`'s existing dict/set follow-ups (D-113's `in`-based set membership; D-114's future combined-refcounting pass) are joined by tuple's own three deferred items above.
```
