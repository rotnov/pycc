# nbody CI-Noise Evidence-Gathering Design (`ubuntu-latest` x86_64 leg)

**Status:** Approved by repository owner in brainstorming dialogue (2026-08-08). Spec self-review complete (adversarial three-lens review: fact-check, brainstorming self-review checklist, engineering-soundness). §3.5/§4.5 (pre-merge validation, added per repository-owner request during spec review) went through a second adversarial fact-check/self-review round; all findings from that round are fixed inline. Written spec reviewed and approved by the repository owner (2026-08-08, "правки не нужны" — "no corrections needed"). Proceeding to `writing-plans`.

**Origin:** [issue #414](https://github.com/rotnov/pycc/issues/414) ("Two independent performance gates ... failed repeatedly on `main`"), narrowed through brainstorming dialogue to exactly one CI step and one leg.

## 1. Problem

`tests/nbody_bench.rs:441`'s `nbody_release_binary_meets_required_speedup_over_cpython` test gates on a wall-clock speedup ratio (pycc `--release` vs CPython 3.14.6 on the same nbody fixture) of at least 20.0x on most CI legs. On `native-build-test (ubuntu-latest, x86_64-unknown-linux-gnu)`, run [31199041279](https://github.com/rotnov/pycc/actions/runs/31199041279) (`headSha e18dc632a87a58b83e08e0b9205daceed0da7eba`, 2026-08-07T16:44Z) missed the floor by 4% (19.22x). D-126/D-129 already investigated switching this gate to OS-level CPU-time accounting and found it did not reduce variance on this leg (19.7282x wall vs 19.7377x CPU-time on the same tree) and made things worse on Windows, so D-129 kept the gate on wall-clock. D-140 raised `RUNS` from 5 to 7 samples per side as the next mitigation and explicitly named the next step for a leg that keeps missing: *"this leg may need its own D-095/D-096/D-101-style floor investigation — escalate with real measurement data at that point."*

Three of the four Tier-1 legs already went through exactly that kind of leg-specific investigation and now run on a relaxed floor: macOS aarch64 → 12.0x (D-095), Windows → 15.0x (D-096), Linux aarch64 → 18.0x (D-101). `ubuntu-latest` x86_64 is the only Tier-1 leg still pinned to the unrelaxed 20.0x default, and its single documented failure to date missed by only 4%.

A prior direction considered in this same brainstorm — standing up a persistent self-hosted DigitalOcean runner so this one leg runs on dedicated, non-shared-tenant hardware — was found disproportionate to the evidence: it is a multi-component infrastructure project (droplet, Docker-ephemeral runner lifecycle, PAT/token handling, CI job restructuring, its own decision-log entry) built to address a single documented occurrence on the only leg it could reach. This design instead pursues the two approaches the repository's own precedent and this session's research point to as cheaper first steps, per the repository owner's explicit direction: *"Сначала A+B (дёшево), дроплет только если не поможет."* (Start with A+B, cheap; the droplet only if that doesn't help.)

## 2. Scope

In scope: `nbody_release_binary_meets_required_speedup_over_cpython` as it runs inside `native-build-test (ubuntu-latest, x86_64-unknown-linux-gnu)` only.

Out of scope (unchanged, deferred to future work): every other `native-build-test` leg (macos-15-intel, ubuntu-24.04-arm, windows-latest), `build-test-coverage`'s own `macos-14` instance of the same nbody test, and the entire Gate 2 (`frontend-throughput`, `scripts/check_frontend_throughput.rb`) investigation — including the three consecutive `main`-push failures on `macos-14` recorded in issue #414, which this design does not address because DigitalOcean has no Mac hardware and macOS was explicitly descoped from any self-hosted-runner discussion in this brainstorm.

## 3. Approach A — leg-specific floor investigation (D-095/D-096/D-101 precedent)

### 3.1 Data source: no new instrumentation needed

`tests/nbody_bench.rs:536-570` already writes `wall_ratio`, `cpu_ratio`, and both medians to `$GITHUB_STEP_SUMMARY` **unconditionally** — on every run, not only on failures. The code comment at that location states this was added specifically so a future floor revisit (naming D-101 by example) would have pass-side data to work from, not just the censored left tail of failures. This means Approach A needs no code change to start collecting; the data is already being produced by every `native-build-test (ubuntu-latest, x86_64-unknown-linux-gnu)` run today.

### 3.2 Collection mechanism

Add `scripts/mine_nbody_step_summaries.rb`, a research tool (not a CI gate) that:
1. Takes a GitHub run count or date range as an argument.
2. Uses `gh run list --workflow ci.yml --json databaseId,headSha,createdAt,conclusion` filtered to runs that include a `native-build-test (ubuntu-latest, x86_64-unknown-linux-gnu)` job, then `gh api` to fetch that job's step summary content for each run. **The exact `gh api` call or endpoint that exposes a job's rendered `$GITHUB_STEP_SUMMARY` content after the fact is an empirical-verification item for the implementation plan** — this repository has no existing precedent for it (a search of `scripts/*.rb` and `scripts/*.py` found no prior `gh api ... summary` usage), unlike GitHub's well-documented job-log endpoints.
3. Parses `wall_ratio=<float>x` out of the `nbody speedup: wall_ratio=...` summary line (the exact format `nbody_summary()` produces, per `tests/nbody_bench.rs:559-568` and its test fixtures at lines 241 and 248, e.g. `"nbody speedup: wall_ratio=21.2500x cpu_ratio=18.5000x ..."`), **and, when present, also parses `ir_ratio=<float>x` out of Approach B's own summary line (§4.2.5)** — both fields feed the §5 decision checkpoint, which needs a distributional view of each.
4. Emits a CSV or plain list of `(run_id, head_sha, timestamp, wall_ratio, ir_ratio_or_absent, conclusion)` tuples to stdout or a file for analysis.

This script is a research/analysis tool, run manually or from an autonomous session during the observation window below — it is not wired into CI and does not gate anything.

### 3.3 Observation window

Collect at least 30 real-traffic observations (mixing PR and `main` runs — no synthetic "hammering" of the CI to inflate the sample). The binding minimum is the sample count, not elapsed calendar time: at this repository's observed CI cadence (~48+ runs/day across all workflows as of 2026-08-08, per a live `gh run list` sample), 30 qualifying runs on this one leg will likely accumulate in a matter of days, far under a "2 weeks" figure that would otherwise read as a second, conflicting floor. The actual reason to avoid closing the window on the first burst of 30 is load-pattern diversity, not raw duration — so the window stays open until the collected set spans both weekday and weekend traffic, even if 30 samples arrive sooner. Re-run the mining script periodically during this window.

### 3.4 Decision rule

Once the observation window closes, apply the same method D-095/D-096/D-101 actually used (verified against their text, not assumed): choose a floor with real margin below the worst observed failure in the collected distribution — not merely below it, which would leave no room for ordinary noise — cross-checked against how much margin the other three relaxed legs each carry above their own worst failures (D-095: 12.0x vs. 14.95x observed; D-101: 18.0x vs. 19.86x observed worst failure). This is a qualitative judgment call in this repository's own established precedent, not a fixed statistical formula — but this effort's ≥30-sample regime is large enough to also compute a concrete candidate (e.g., a low percentile, such as the 5th or 10th, of the pass-side `wall_ratio` distribution) as a cross-check against the margin-based figure, with the final choice and its justification recorded in the decision entry itself rather than deferred further. Whichever reasoning actually sets the number, the decision entry also records the adopted floor's own empirical percentile rank within the mined pass-side distribution — §3.5's pre-merge validation bar depends on that recorded rank, not on an assumed one.

**Pass-side distribution eligibility:** a run's `wall_ratio` enters the "stable, non-regressed" pool used for this calculation only when nothing in that run's diff plausibly affects nbody's measured path (codegen, the runtime library, process spawn/exec) — mirroring how issue #414's own evidence excluded PR #412's diff (a compile-time-only redefinition check) as a candidate cause. A run whose diff does plausibly touch that path is excluded from the floor calculation regardless of its `conclusion`, since a genuine regression's data would corrupt the floor if folded into the "noise" pool.

Three outcomes are possible, evaluated in this order:
1. **Status quo confirmed.** The mined distribution shows the existing 20.0x floor already has an acceptably low false-positive rate and the original miss (§1) was ordinary noise within that rate — no floor change. This is the outcome §5 treats as fully resolving Approach A without any further action.
2. **Floor relaxation warranted.** The data supports a floor below 20.0x specifically for this leg → write a new decision under `docs/decisions/` (next available number, resolved at PR-open time per this repository's own numbering convention) narrowing `required_nbody_ratio()` (`tests/nbody_bench.rs`) to add a fourth relaxed case for `linux` + `x86_64`, mirroring the existing `macos`+`aarch64`, `windows`, and `linux`+`aarch64` cases already in that function. Update `required_nbody_ratio_is_relaxed_only_on_macos_aarch64_windows_and_linux_aarch64`'s own test (name and assertions) to reflect the new relaxed case.
3. **Inconclusive.** The distribution is too noisy, or too small a "clean" pool remains after excluding plausibly-affected runs, to support either of the above with confidence → extend the observation window rather than forcing a decision on weak data.

This process is not a way around D-114/D-112's rule that CI noise alone does not justify relaxing a performance gate — it **is** the evidence-gathering process D-114/D-112 requires before any threshold change, applied to the one leg that has never been through it.

### 3.5 Pre-merge validation (before merging the floor-change PR)

Requested by the repository owner during spec review, applying only when §3.4 reaches outcome 2 (floor relaxation warranted) and a PR touching `required_nbody_ratio()` exists. It does not apply to outcome 1 (status quo confirmed) or outcome 3 (inconclusive), since neither produces a PR to validate.

**Mechanism:** before merging that PR, collect 10 additional, independent, genuinely fresh measurements of `native-build-test (ubuntu-latest, x86_64-unknown-linux-gnu)` on the PR's own head commit, without merging. Use `gh run rerun <run-id> --job <job-id>` to rerun only that one job (the job ID comes from `gh run view <run-id> --json jobs --jq '.jobs[] | {name, databaseId}'`, per `gh run rerun --help`'s own documented caveat that the job number shown in the browser URL is not the right ID) rather than the whole matrix or the separate `build-test-coverage` job — this keeps the cost of the 10 reruns bounded to the one leg actually being validated.

**Guard against a real, already-observed failure mode of this exact mechanism:** D-109 directly documents that a `gh run rerun` attempt on this repository's CI can reuse a prior attempt's cached artifacts instead of producing a genuinely fresh measurement (byte-identical replicate medians and an identical result across two attempts of the same run) — D-109 itself names this check "verify the rerun actually remeasured" and attributes it to D-095/D-096/D-101's methodology, though that specific remeasurement-verification language is D-109's own retrospective framing: it does not appear in the text of D-095, D-096, or D-101 themselves, which establish a related but distinct principle (rejecting "rerun until favorable" as selection bias, addressed separately below). Before counting any of the 10 reruns, confirm its `$GITHUB_STEP_SUMMARY` output (or the job's own timestamps) differs from the prior attempt's — a rerun whose values are byte-identical to a previous attempt does not count as one of the 10 and must be re-triggered.

**Guard against selection bias:** this is explicitly *not* "keep rerunning until one attempt passes, then merge" — this repository's own precedent rejects exactly that pattern as selection bias, independently, four separate times (D-051, D-054, D-056, D-062, all in their own "Alternatives" sections). All 10 genuinely-fresh attempts are collected and every one of their outcomes counted, regardless of individual pass/fail, before any merge decision is made.

**Pass bar:** tied to the adopted floor's own empirical percentile rank within the mined pass-side distribution, as recorded in §3.4's decision entry (§3.4 records that rank regardless of whether the margin-based reasoning or the percentile cross-check actually set the number) — not a hard-coded range, since §3.4's primary rule is margin-below-worst-failure and nothing guarantees the adopted floor lands near any particular percentile. Model each of the 10 fresh draws as an independent trial with per-draw failure probability equal to that recorded rank: e.g. a recorded rank of 10% implies roughly 1 expected failure in 10 draws, and — because 10 draws is a small sample — a binomial calculation at that rate already gives roughly a 26% chance of seeing 2 or more failures purely by chance, even when the floor is functioning exactly as designed. 0-1 failures is consistent with the recorded rank and does not block merge. 2 or more failures is treated as inconsistent and is itself new evidence the floor needs revisiting — accepted here as an explicit, non-negligible false-recall tradeoff of validating with only 10 draws, not a defect to silently ignore. In that case, do not merge. Treat it the same as §3.4's own outcome 3 (inconclusive) rather than folding these deliberately-triggered reruns into the mined distribution: they are targeted reruns of a single commit, not the organic, diverse traffic §3.3 requires, and mixing intentionally-included failures into §3.4's pass-side-only pool is undefined by that pool's own eligibility rule. Extend the observation window with further organic traffic and re-apply §3.4's decision rule once it closes, rather than picking a different number ad hoc.

The exact per-job wall-clock/compute cost of 10 targeted reruns is an empirical-verification item for the implementation plan, consistent with how this spec already treats other operational unknowns (§3.2, §4.2, §4.4) — qualitatively, it is far cheaper than 10 full-matrix runs since only the one already-identified job reruns.

## 4. Approach B — Cachegrind non-gating spike (`ubuntu-latest` x86_64 only)

### 4.1 Rationale

Instruction-counting via Valgrind/Cachegrind counts discrete retired instructions rather than accounted time, so it is not exposed to the hypervisor-level steal-cycle and frequency-scaling noise that made D-126/D-129's CPU-time experiment fail to reduce variance. This is genuinely unexplored territory in this repository (zero references to valgrind, cachegrind, callgrind, or iai anywhere under `docs/decisions/`, confirmed by two independent searches this session). It only covers 2 of the repository's 5 Tier-1 legs (Linux x86_64 and Linux ARM64 are Valgrind's well-supported platforms; macOS aarch64 has no official support at all, macOS Intel's support is stale, Windows is out of scope upstream entirely) — which happens to include the one leg left in scope after this brainstorm's own descoping.

### 4.2 Mechanism

Add a new `#[ignore]` test in `tests/nbody_bench.rs`, alongside (not replacing) `nbody_release_binary_meets_required_speedup_over_cpython`: `nbody_cachegrind_instruction_ratio_is_recorded_non_gating`. Per §6's testing commitment, the platform-guard, failure-classification, and output-parsing logic below must be factored into small, parameterized pure functions unit-testable independently of the `#[ignore]`d test body — mirroring this file's existing pattern for exactly this problem (`oracle_binary_name(is_windows: bool)` at line 143, `required_nbody_ratio(is_macos_aarch64, is_windows, is_linux_aarch64)` at line 671, `parse_three_floats` at line 188): a helper for step 1's platform guard, a helper for step 4's `Ir`-count parsing, and a helper for step 6's Valgrind-failure classification. The `#[ignore]`d test body itself calls these helpers but stays a thin integration wrapper, the same relationship `nbody_release_binary_meets_required_speedup_over_cpython` already has with `required_nbody_ratio`. The test:
1. Guards on `cfg!(target_os = "linux") && cfg!(target_arch = "x86_64")`; on any other target it records a skip note (not a failure) and returns immediately, since Cachegrind is only meaningfully supported on this one platform combination.
2. Builds its **own** `--release` pycc binary at a path distinct from `nbody_release_binary_meets_required_speedup_over_cpython`'s. Copying that test's `std::env::temp_dir().join(format!("pycc_nbody_{}", std::process::id()))` expression verbatim would collide: `std::process::id()` is identical across threads in the same OS process, and `cargo test -- --include-ignored` gives no ordering guarantee between two `#[ignore]`d tests in one binary — on `ubuntu-latest` specifically, `--test-threads=1` is only set on Windows (D-029), so both tests can run concurrently and race to build/execute the same file. The new test's path must include a distinguishing literal (e.g. `pycc_nbody_cachegrind_{}`) so the two tests can never target the same file even if scheduled concurrently. Locate the same CPython 3.14.6 interpreter the existing test already uses.
3. Runs Cachegrind with determinism controls as the primary noise-reduction mechanism, not run count: disable ASLR for both measured processes (`setarch -R`, or the `personality(ADDR_NO_RANDOMIZE)` syscall — availability on the hosted `ubuntu-latest` image is an empirical-verification item) and pin `PYTHONHASHSEED` to a fixed value for the CPython-side run, since both ASLR-driven shared-library placement and per-process hash randomization are documented sources of run-to-run `Ir`-count perturbation independent of the measured algorithm itself. **Run count is itself an empirical-verification item**, not fixed at 1 here: with determinism controls in place, measure residual run-to-run `Ir` spread locally; if it is ~0, one run per side is sufficient (the cost-control case this spec assumes — at CPython's own recorded ~2.6s native wall median (issue #414's telemetry) and Cachegrind's documented ~20-50x overhead, one CPython-side run costs roughly 50-130 seconds, vs. 6-15 minutes for seven); if measurable spread remains even with determinism controls, move to a median-of-3 and record that cost tradeoff (roughly 2.75-6.8 minutes) explicitly in the implementation plan rather than silently absorbing it.
4. Extracts the total instruction count (`Ir`) from Cachegrind's own summary output (`cg_annotate <cachegrind-out-file>` or the `I   refs:` line Cachegrind itself prints) for both binaries, and computes `ir_ratio = cpython_ir / pycc_ir`. The exact parsing target (raw Cachegrind stderr summary vs. `cg_annotate` output) is an empirical-verification item for the implementation plan — both are viable and the plan should pick the one it can actually observe locally.
5. Writes `ir_ratio` (plus the two raw `Ir` counts) to `$GITHUB_STEP_SUMMARY` using the same non-gating, best-effort-write guard already used at `tests/nbody_bench.rs:552-570` (`if let Ok(summary_path) = std::env::var("GITHUB_STEP_SUMMARY")`, write failures silently ignored) — but format the full summary line first and issue exactly one `write_all` call per write, rather than `writeln!`'s multiple separate `write_all` calls (content, then a separate `"\n"` write). This applies to **both** this new write site and the pre-existing `wall_ratio`/`cpu_ratio` write site at lines 552-570: introducing a second `#[ignore]`d test that can run concurrently in the same process is what turns the existing site's `writeln!`-based append (previously single-writer, so the non-atomicity was latent) into a real risk of two runs interleaving a line in `$GITHUB_STEP_SUMMARY`. D-129's own decision text commits to continuing to record this data through "D-126's frozen summary schema" — this atomicity fix changes only the write mechanism (one `write_all` instead of `writeln!`'s two), not the byte content or format of the line itself, so it preserves that frozen schema rather than amending it.
6. **Never asserts on `ir_ratio`.** The test's only failure mode is a hard prerequisite failure (binary fails to build, CPython fails to spawn) — it does not fail merely because Valgrind is unavailable, exits non-zero, or reports an unsupported instruction. Any Valgrind-side failure (including the known AVX-512 "unhandled instruction bytes" decode risk on modern `ubuntu-latest` CPUs) is caught and the test still passes — this is diagnostic instrumentation, not a gate. Unlike a plain silent pass, this path still writes a distinguishable marker line to `$GITHUB_STEP_SUMMARY` (e.g. `nbody cachegrind: skipped reason=<...>`, never an `ir_ratio=` value) so the mining script (§3.2) and a human scanning summaries during the observation window can tell "collection ran but found nothing to report" apart from "the step never executed" — without this, Approach B could silently collect zero samples for the entire observation window while CI stays green throughout, with nothing surfacing why.

### 4.3 Why the ratio cannot inherit the 20x threshold, ever, without its own evidence round

CPython's bytecode-dispatch loop is low-IPC (branch-heavy, pointer-chasing, poor cache locality); pycc's AOT-compiled arithmetic is high-IPC. Cachegrind's default `Ir`-only mode prices every retired instruction identically regardless of its real cycle cost, which systematically understates CPython's wall-clock badness relative to pycc in the common case (`ir_ratio` reading below `wall_ratio` holds whenever `cpython_CPI > pycc_CPI`, the expected direction for an interpreter vs. AOT-compiled code — but not a certainty). This spec states that expectation with appropriate hedging rather than confidence: `tests/nbody_bench.rs`'s own doc comments already document `pycc_rt_float_pow` as an opaque, un-inlineable `extern "C"` cross-module call invoked millions of times over the benchmark (cited, D-093, as a real source of call/ABI overhead narrowing the gap between measured and theoretical-ceiling wall-clock ratios). That overhead raises pycc's own CPI relative to a fully-inlined ideal, narrowing the CPI gap this section's reasoning depends on. `ir_ratio` landing close to (rather than clearly below) `wall_ratio` should therefore be read as informative about this known overhead, not as evidence the measurement is broken.

A future decision to gate on `ir_ratio` — should the accumulated evidence support it — needs its own fresh evidence-based threshold-setting process, following this repository's actual established precedent for that (D-095/D-096/D-101's qualitative margin-below-worst-observed-failure method, §3.4) — not D-103, which governs an unrelated CI-file trust/propose-activate choreography and contains no statistical methodology. It can never simply inherit 20.0x (or whatever Approach A settles on for `wall_ratio`).

### 4.4 CI wiring

Runs as part of the same `--include-ignored` step that already runs `nbody_release_binary_meets_required_speedup_over_cpython` on the `ubuntu-latest` leg of `native-build-test`, so it collects data from the same organic PR/main traffic Approach A observes. It does not need a separate scheduled workflow. Whether the CI job needs a new `apt-get install valgrind` step (i.e., whether Valgrind ships preinstalled on the GitHub-hosted `ubuntu-latest` runner image) is an empirical-verification item for the implementation plan, not assumed here — **and this is not a cost-neutral unknown**: `scripts/check_roadmap_evidence.rb`'s `validate_evidence` hashes the entirety of `.github/workflows/ci.yml` and requires membership in the small, hand-reviewed `REVIEWED_PERF_CI_WORKFLOW_SHA256S` allowlist, so any byte change to that file — including adding one `apt-get install` line — fails CI outside this repository's own D-103 propose/activate sequence (`docs/decisions/D-103-keep-search-policy-successors-base-owned-through.md`), the same multi-round governance process D-114/D-112 each needed six rounds for. If the implementation plan's empirical check finds Valgrind is not preinstalled, budget for that sequence rather than treating the install step as a routine one-line addition.

### 4.5 Pre-merge validation (before merging the Cachegrind-test PR)

Applies to the PR that adds the new `#[ignore]` test itself (this PR typically merges before the observation window closes, since §3.2's mining needs `ir_ratio` data flowing during that window, not after). This validation targets a different risk than §3.5's: this PR does not touch `required_nbody_ratio()` or the 20.0x floor, so an ordinary `wall_ratio` miss on any of the 10 reruns is not evidence of a defect in this PR — it is exactly the pre-existing leg flakiness this whole design exists to investigate, and must not be treated as a merge blocker here.

What this validation does check: whether adding a second `#[ignore]`d test to the same binary destabilizes the *existing* gating test through the concurrency risk §4.2 step 2 already identifies and mitigates (a build-artifact path collision between two `#[ignore]`d tests that `--test-threads=1` does not serialize on `ubuntu-latest`, per D-029). Using the same mechanism as §3.5 (`gh run rerun <run-id> --job <job-id>`, targeting only `native-build-test (ubuntu-latest, x86_64-unknown-linux-gnu)`, with the same remeasurement-verification and selection-bias guards), collect 10 fresh reruns of this PR's head commit and inspect each for a failure mode attributable to the second test's presence specifically — a build/binary corruption, the wrong binary executed, or a crash unrelated to a plain ratio comparison — as distinct from an ordinary `wall_ratio`-below-floor failure, which passes this check regardless of how many of the 10 runs show it. Any run showing the former blocks merge until the path-collision fix (§4.2 step 2) is corrected; any number of the latter does not.

Per-run pass/fail alone cannot see one specific risk this PR introduces: the two `#[ignore]`d tests run concurrently on this leg (§4.2 step 2), and the Cachegrind test pins substantial CPU for tens to over a hundred seconds per side (§4.2 step 3) inside the same `--include-ignored` step that measures `wall_ratio` (§4.4). If that contention depresses `wall_ratio` without producing an outright crash or corruption, its symptom is indistinguishable, run by run, from the pre-existing flakiness this section otherwise explicitly does not block on — so a per-run check alone would let this PR's own contention hide inside the exemption it grants. Guard against this with a distributional check in addition to the per-run one: compare the median of the 10 fresh `wall_ratio` observations against the leg's own recent pre-PR CI history (the most recent available `native-build-test (ubuntu-latest, x86_64-unknown-linux-gnu)` runs before this PR's base commit — independent of whether §3.2's full mining has completed, since this PR typically merges before that window closes). A systematic downward shift in the median blocks merge as new evidence of this PR's own contention, even with zero individual floor misses among the 10 — most directly resolved by serializing the two `#[ignore]`d tests so their measurement windows never overlap, rather than merely giving them non-colliding build paths as §4.2 step 2 already does. This same distributional check doubles as the detector for a swapped or corrupted binary: either would distort `wall_ratio` sharply enough to show up as a shift, not just an occasional miss.

## 5. Decision checkpoint — when Approach C (self-hosted droplet) is reconsidered

After the observation window (§3.3) closes, evaluate the following in order — this mirrors §3.4's own outcome ordering for Approach A specifically, extended here to cover Approach B and the droplet fallback:

1. **A alone succeeds:** §3.4's outcome 1 or 2 obtains — the mined `wall_ratio` distribution supports either keeping the existing 20.0x floor (status quo confirmed) or adopting a stable, lower floor with an acceptably low false-positive rate for this leg (as it did for the three other relaxed legs) → adopt whichever via §3.4's process; outcome 2's floor-change PR additionally clears §3.5's pre-merge validation before merge. A §3.5 result of 2-or-more failures does not settle this outcome — it reopens the decision via §3.4 (treated as that section's own outcome 3) and this evaluation resumes once a fresh floor-change PR clears validation. No droplet, and Approach B's `ir_ratio` data is retained as informational but not required to reach this outcome.
2. **B informs a future gate change:** outcome 1 does not fully resolve it (§3.4's outcome 2 lands on a floor that still carries a false-positive rate the maintainer judges too high, or outcome 3/inconclusive persists after a reasonable extension of the window), **and** the mined `ir_ratio` distribution is meaningfully quieter by the same test §3.4 already applies to `wall_ratio` — a materially smaller spread between its worst observed "clean" value and its typical value, using the identical margin-below-worst-failure-with-percentile-cross-check method, not a separate ad hoc bar — then a later, separately evidenced decision may choose to gate on `ir_ratio` instead (§4.3), removing the wall-clock noise problem structurally, without infrastructure. No droplet, though this remains an explicitly *future*, separately evidenced decision, not an automatic consequence of this design.
3. **Neither resolves it:** outcome 1 fails to land on an acceptable floor **and** outcome 2's `ir_ratio` data does not clear that same quieter-by-the-same-method bar → Approach C (the self-hosted DigitalOcean droplet, structurally decoupled `native-build-test` job, `myoung34/docker-github-actions-runner`-based ephemeral lifecycle) becomes the fallback, revisited with this observation window's real data as its evidentiary basis rather than the single-occurrence arithmetic that made it disproportionate today.

## 6. Testing and error handling

- `scripts/mine_nbody_step_summaries.rb` (Approach A) gets unit tests for its step-summary parsing, mirroring this repository's existing `scripts/test_*.rb` convention (e.g. `scripts/test_check_frontend_throughput.rb`): a well-formed summary line, a missing/absent summary (run predates this instrumentation or the step never reached that point), and a malformed line. As a Ruby script, it is outside D-014's 100%-line/region-coverage gate by construction — that gate is `llvm-cov` measuring the Rust workspace, and a `.rb` file can never appear in a Rust `--ignore-filename-regex` entry. It needs no `docs/TESTING.md` exemption-table entry: that table exists to document deliberate carve-outs *from* a measurement that would otherwise apply, and this script was never inside that measurement's scope to begin with.
- The new Cachegrind test (Approach B) is Rust code, but it lives in `tests/nbody_bench.rs`.
