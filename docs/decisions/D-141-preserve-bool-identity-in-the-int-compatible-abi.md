## D-141: Preserve `bool` identity in the int-compatible ABI

- Status: accepted (closes issue [#240](https://github.com/rotnov/pycc/issues/240));
  superseded in part by
  [D-179](./D-179-range-loops-drive-bigint-bounds-steps-and.md), which replaces
  the decode-and-re-tag mechanism this decision specified for `range` operands
  with an encoded-word normalizer, so a bigint operand survives it. The
  bool-identity *contract* -- a range produces ordinary integer objects rather
  than forwarding its argument object -- is unchanged, as is every other part
  of this decision.
- Context: Python's `bool` is an `int` subtype, so the type checker accepts `bool` values at `int` assignments, parameters, returns, container values, and `range` operands. D-074 previously converted every such value into the ordinary smallint `0` or `1`. That preserved numeric behavior but silently lost object identity: `x: int = True; print(x)`, an `int`-declared function returning `True`, and a `True` round-trip through `list[int]` or `dict[str, int]` printed `1` instead of CPython's `True`. Manufacturing `value + 0` in MIR for an annotated initializer compounded the problem by making a non-arithmetic boundary indistinguishable from real arithmetic. D-106's raw container payload then made identity impossible to retain after storage even if the scalar ABI changed.
- Decision: retain the one-word `i64` ABI and odd smallint encoding, but reserve exact word `2` for a `False` object in an int-compatible slot and exact word `6` for `True`. A non-zero word whose two low bits are `00` remains an aligned `BigIntObj` pointer. A centralized runtime classifier accepts only odd smallints, those two exact markers, and non-zero aligned pointer words; zero and every other low-bits-`10` word panic deterministically before any pointer cast. Compile-time assertions require `BigIntObj` alignment of at least four bytes and a pointer width no larger than `i64`. Standalone `Ty::Bool` remains unboxed `i8`; codegen creates markers only when a bool crosses a statically-`int` boundary. MIR represents an annotated initializer boundary with `MirExpr::IntBoundary`, not synthetic arithmetic.
- Decision: runtime numeric consumers decode the markers as `0`/`1`, while arithmetic results use ordinary odd smallints (or bigint promotion) so `True + 0` remains the integer `1`. Formatting and printing recognize the markers as `False`/`True`. `range` operands are decoded and re-tagged as ordinary smallints before entering an induction phi, including all three comprehension emitters, because a range produces integer objects rather than forwarding its argument object. (Mechanism superseded by [D-179](./D-179-range-loops-drive-bigint-bounds-steps-and.md): the operand is now *normalized* in place by `pycc_rt_range_normalize_operand` -- markers become smallint `0`/`1`, smallints and heap bigints pass through -- which keeps this contract while letting a bigint operand drive the loop.) `list[int]`, `dict[str, int]`, and `set[int]` payloads now store the same encoded words unchanged, superseding D-106's raw-element contract; ingress still calls the checked decoder once to reject bigint values before storage, reads preserve the encoded word, and lengths/indices/slice bounds remain raw implementation counters. Set equality compares decoded numeric values (`True == 1`, `False == 0`) while preserving the first inserted encoding, matching Python's set behavior.
- Alternatives: add a second runtime type word or heap-box every widened bool (rejected because the two aligned-pointer tag bits already provide a safe one-word distinction); preserve only formatting metadata outside the value (rejected because identity must survive calls, returns, reassignment, and containers); keep raw container payloads and reconstruct bool from numeric value on read (rejected because ordinary `0`/`1` and `False`/`True` are semantically distinguishable for printing and first-object preservation); let every even word remain a pointer as D-061 originally stated (rejected because the marker design requires an explicit disjoint class and because treating zero or unknown `..10` words as pointers is unsafe).
- Consequences: assignment, parameter, return, nested forwarding, f-string/print formatting, list/dict round-trips, and set numeric dedup preserve CPython-visible bool identity without changing any public runtime function signature. Numeric comparison/conversion and arithmetic continue to consume bool as `0`/`1`; arithmetic outputs and range targets are ordinary ints (a bigint range target is one since D-179). Bigint-valued container elements remain an explicit unsupported boundary. D-061's statement that every even word is a bigint pointer is narrowed to non-zero aligned `..00` words, D-074's `bool`→`int` materialization gains identity preservation, and D-106 is superseded for container element/value payloads.
