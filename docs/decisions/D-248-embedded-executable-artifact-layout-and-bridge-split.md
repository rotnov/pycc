## D-248: Embed CPython for standard-library imports as an executable plus an OUT.pycc sidecar, sharing the ext C shim

- Status: accepted (Part 1 of #1028, [#1223](https://github.com/rotnov/pycc/issues/1223); macOS and Linux hosts, standard-library roots only)
- Context: [D-128](./D-128-preserve-ordinary-imports-while-making-cpython.md) makes `auto` the default interop policy: a plain `pycc build` of a program with a permitted CPython-backed import must produce an artifact that bundles the interpreter. Until #1223 every such program was refused with `I0403`, and `docs/CLI_SPEC.md` deferred the bundle's layout to "the v0.7 resolver and packaging plan". [D-244](./D-244-add-a-hosted-cpython-extension-module-artifact-mode.md) rule 2 requires one C-API bridge shared by the `ext` mode and the embedded mode, and #1045 asked for that split to be re-derived when the embedded mode became its second consumer. #1028 spans five independent seams, so it is delivered as five parts (#1223-#1227); this entry fixes what Part 1 makes irreversible: the artifact layout, the interpreter source, the relocatability rule and the bridge split.
- Decision:
  1. **The `auto` default, for standard-library roots.** A plain `pycc build` (and `pycc run`) whose program has at least one foreign import builds an embedded executable when every foreign import's root is in `src/embed/stdlib_roots.rs`'s `EMBEDDABLE_STDLIB_ROOTS` -- CPython 3.14.7's `sys.stdlib_module_names` minus the Tcl/Tk-backed `EXCLUDED_STDLIB_ROOTS` (`_tkinter`, `idlelib`, `tkinter`, `turtle`, `turtledemo`) -- the host is macOS or Linux, and no `--target` is given. Any other foreign import stays `I0403` with one reason, in this precedence: `--target`, a Windows host (#1226), an excluded standard-library root, a non-standard-library root (#1225). No new flag and no new diagnostic code: `--interop-policy`, `--pure` and `I0402` are Part 2 (#1224), because `--pure`/`deny` must govern `check`, `build`, `run` and `test` alike. The list is static so the frontend gate stays pure; an `#[ignore]`d test compares it with the pinned interpreter. A program with no foreign import stays native and links no libpython.
  2. **Layout.** `OUT` is the executable (the launcher, the unchanged `ext` shim, the compiled module and `libpycc_rt.a`). Beside it, `OUT.pycc/` holds `PYCC-BUNDLE` (a marker: `pycc-bundle 1`, the interpreter version, the probe's resolved `sys.executable`, and the sha256 of the source libpython's bytes as copied, before any rewrite), `lib/<libpython>` (macOS: `libpython3.14.dylib` with its id rewritten to `@rpath/libpython3.14.dylib` and ad-hoc re-signed; Linux: the `INSTSONAME` file, unchanged), `lib/python3.14/` (the standard library minus `site-packages`, `__pycache__`, `test` and each excluded root as a package, a module and `lib-dynload/<root>.*`), and, on macOS, vendored prefix-internal native libraries under `lib/`. `OUT.pycc/closure/` is reserved for Part 3's locked closure and is not created. The sidecar name is fixed at build time from `OUT`'s file name and used twice: the rpath (`@executable_path/<name>.pycc/lib` or `$ORIGIN/<name>.pycc/lib`, passed with `-Xlinker`) and the launcher's `home` (a generated C string literal). Renaming the executable keeps working; renaming the sidecar does not. An `OUT` whose file name contains `$` or `:`, or is not UTF-8, is refused for an embedded build with exit 2, because `ld.so` expands `$` tokens in and splits `DT_RUNPATH` on `:`, and no escaping fixes that.
  3. **Order and overwrite safety.** An existing `OUT.pycc` is checked first, before the interpreter is probed: without a current marker (or as a symlink or plain file) the build fails with exit 2 and leaves it untouched; with one it is replaced. The bundle is assembled as `OUT.pycc.tmp-<pid>` in `OUT`'s parent, swapped in (an old marked sidecar is renamed aside, restored if the final rename fails, and otherwise removed best-effort) and only then linked against, so the executable records `@rpath`/the SONAME, never the build host's path; a failed assembly, including a failed swap, removes its staging directory. A failed link can leave a fresh sidecar beside a stale `OUT`, which is harmless. A native rebuild of the same `OUT` leaves a stale `OUT.pycc/` alone.
  4. **Interpreter source.** `PYCC_PYTHON` names the interpreter to embed (default `python3.14`, not the `--ext` default `python3`, because D-128 pins 3.14). A separate probe reports its version, include and stdlib directories, `sys.base_prefix` and the `Py_ENABLE_SHARED`, `PYTHONFRAMEWORK`, `LDLIBRARY`, `LIBDIR`, `INSTSONAME` and `Py_GIL_DISABLED` config variables. Each refusal is an environment failure (exit 2, a plain `error:` line, no diagnostic code): the interpreter cannot be spawned or its output parsed; it is not 3.14.x; it is not shared (shared means `Py_ENABLE_SHARED == 1` or a non-empty `PYTHONFRAMEWORK`); it is free-threaded; `Python.h`, the shared library or the stdlib directory is missing.
  5. **Relocatability, fail-closed on macOS.** After copying, an `otool -L` worklist over libpython, every copied `lib-dynload` file and every vendored image classifies each dependency: `/usr/lib` and `/System/Library` are kept; the image's own id and `@rpath/<bundled libpython>` are kept; the source libpython's original id or realpath is rewritten to `@rpath/<bundled libpython>` and never vendored; a path under the interpreter's canonical `sys.base_prefix` is vendored into `lib/` with an `@rpath` id and an `@loader_path`-relative reference; anything else refuses the build with exit 2, naming the image and the dependency. Every image with an id or a rewrite is ad-hoc re-signed. Homebrew's interpreter is refused (its `lib-dynload` links `/opt/homebrew/opt/...`); python-build-standalone's is accepted. **Linux performs no ELF scan in Part 1**: libpython's SONAME is used unchanged and a `lib-dynload` dependency is resolved by the system loader. That is a stated gap, and native-library identity belongs to #1225's lock.
  6. **Bridge split (the #1045 answer, D-244 rule 2).** `src/ext/pycc_ext_module.c` stays the single `PyObject*`-moving layer and both modes compile it byte-for-byte; `pycc_rt::ext_bridge` keeps the decisions. The embedded mode's only new C is `src/embed/pycc_embed_launcher.c`, which holds interpreter lifecycle code and no boundary conversion. The module is compiled under `CompileOptions { ext: true, suppress_export_thunks: true }` as `__main__`, with an exports include that exports nothing but keeps the user exception classes the shim's pending-exception translation needs. A separate `pycc_rt_cpython` staticlib and a `#[cfg]`-gated Rust module are both rejected: no consumer needs a Rust-side mover, and a gated module carries no coverage record. `libpycc_rt.a` stays free of CPython symbols; a test asserts `nm -u` on a native executable lists no `Py*` symbol.
  7. **Launcher and its deviations.** The launcher uses `PyConfig_InitIsolatedConfig` with `site_import = 0`, `write_bytecode = 0`, `buffered_stdio = 0`, `platlibdir = "lib"` (the sidecar's fixed layout, not the build host's value, which a distribution build may set to `lib64`) and `home = <dir of realpath(exe)>/<sidecar name>`, then creates `__main__` with `PyModule_FromDefAndSpec`, registers it in `sys.modules` and runs `PyModule_ExecDef`. A failure prints with `PyErr_Print` and exits 1; a failing `Py_FinalizeEx` exits 120; `sys.exit(n)` exits `n`. `PYTHONPATH` and ambient site-packages are ignored. Deviations from CPython, all Python-side reads only: `sys.flags.isolated == 1`, `sys.flags.no_site == 1`, `sys.platlibdir == "lib"`, `sys.executable == OUT`, `sys.argv[0]` is the executable path; and an uncaught pycc exception prints only its final `Type: message` line, where a native build prints the whole chain. `buffered_stdio = 0` plus `pycc_rt`'s flush-per-newline keeps the two writers' output ordered; the day `print(..., end=...)` lands, a Rust-side flush must precede each foreign call.
  8. **What this narrows in D-128.** Part 1 narrows D-128; it does not satisfy it. **Rule 3** makes the lock schema, resolver and update command mandatory before implementation; Part 1 embeds without them because a standard-library-only program's only closure is the interpreter. The rejected alternative "the developer's system Python" and **NEG-002** ("absence of a compatible locked artifact is a build failure, not a host-environment fallback") are narrowed the same way: the embed source is the build host's `PYCC_PYTHON` interpreter, validated and identity-recorded in the marker, until #1225's lock pins it. **Rule 5** ("Native pycc execution remains GIL-free") is narrowed because the launcher runs the whole compiled module body inside `PyModule_ExecDef` with the GIL held; nothing is observable until threads (v0.6), which lift it. #1225 lifts the rule 3 and NEG-002 narrowings.
- Alternatives: an explicit `--embed` opt-in (rejected: a CLI surface D-128 does not have, which #1224 would have to retire); probing `sys.stdlib_module_names` at gate time (rejected: it would make `pycc check`'s diagnostics depend on the environment); a new code for a non-standard-library root (rejected: `I0403` keeps its meaning and only narrows, as `I0405` already carries several reasons); `OUT` as a directory (rejected: breaks `-o app && ./app`); a single-file self-extracting executable (a later optimization, needing extraction and cleanup); deriving `home` from the running executable's name (rejected: renaming `OUT` would desynchronize it from the baked-in rpath); a static libpython (Part 5, #1227; it does not remove the standard-library tree).
- Consequences:
  - **POS-001:** a standard-library-only CPython-compatible program builds and runs with `pycc build` and no flag, relocatably, on macOS and Linux hosts, and its output matches CPython 3.14.7 byte-for-byte on the oracle program.
  - **POS-002:** the layout reserves room for #1225's closure and the marker carries a format version, so a later format is detected as unmarked rather than silently overwritten.
  - **NEG-001:** an embedded artifact is roughly 26-32 MB and `pycc run` copies the standard library on every run; pruning or zipping is a later optimization.
  - **NEG-002:** Linux relocatability is not checked; an interpreter whose `lib-dynload` links a non-system library builds a Linux artifact that works only where that library exists, until #1225.
  - **NEG-003:** the embedded mode inherits exactly #1026's foreign-object surface (module-body only, scalar arguments, `print(str(o))` but not `print(o)`); Part 1 widens none of it.
