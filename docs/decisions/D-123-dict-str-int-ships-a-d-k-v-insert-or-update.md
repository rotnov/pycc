## D-123: dict[str, int] ships a `d[k] = v` insert-or-update operation; set[int] ships no membership test and no CPython iteration-order claim

- Status: accepted
- Context: `list[int]`'s own v0.2 thin slice stayed read-only on indexing (D-105 cut 2) but did ship one growable operation, `.append()`, without which an empty list literal would be permanently empty. `dict` has the same problem in reverse: a `dict[str, int]` literal is constructible without any growable op, but `docs/PYTHON_STANDARDS.md`'s own dict-insertion-order row and `docs/DELIVERY_PLAN.md` row 11's "insertion-order fixture" deliverable are only genuinely demonstrated if insertion order survives a *mutation*, not merely literal-construction order (which is trivially insertion-ordered by definition of D-121's own representation and would prove nothing). Separately, `set[T]` has no analog of `.append()` in Python at all -- `set.add()` exists, but nothing in this PR's own scope requires it, and the `in` operator this compiler has no support for yet is the operation that would make a bare `set` actually useful beyond `len()`.
- Decision: `dict[str, int]` ships `d[k] = v` as an insert-or-update operation (new key: appended in place, preserving insertion order; existing key: value updated in place, key position unchanged) alongside read (`d[k]`, panics if the key is absent -- no `KeyError` handling exists in this compiler), `len(d)`, and `for k in d:` (iterates keys in insertion order). `set[int]` ships only literal construction (with dedup at construction time -- a repeated literal element is inserted once, matching CPython's own set-literal semantics), `len(s)`, and `for x in s:`; it gets no `.add()`, no indexing (real Python sets are not subscriptable -- `s[0]` is a `TypeError` in CPython too, so rejecting it with the existing `T0033` "does not support indexing" diagnostic is not a v0.2 scope cut, it is the semantically correct behavior), and no membership test (blocked on the `in` operator not existing anywhere in this compiler yet -- tracked as a `docs/ROADMAP.md` follow-up by Task 10 of this plan, not silently assumed solved).

  Because `set[int]`'s own iteration order in this implementation is insertion order (D-121), but CPython's own set iteration order is hash-dependent and unspecified, **no conformance fixture may assert byte-for-byte equality between pycc's and CPython's printed set-iteration output.** A `set` fixture may assert `len()` (order-independent) and may print elements only after an order-independent transformation (e.g. `sorted(...)`, if in scope) or not at all -- see Task 9 of this plan for the exact fixture design this constrains.
- Alternatives considered:
  - No `d[k] = v` at all, matching list's own read-only-index precedent exactly -- rejected: unlike `list`, dict without any post-construction mutation makes the insertion-order fixture prove nothing beyond "a literal's pairs print in the order they were written", which is true of the source text alone and demonstrates nothing about the actual runtime representation.
  - Implement `set`'s `.add()`/`in` in this same PR to make `set` genuinely useful -- rejected: `in` is a real, separate parser/HIR/type-checker/codegen feature (a new comparison-expression form) with its own scope large enough to warrant its own PR; bundling it here would make `set`'s own slice no longer "thin".
- Consequences: a future PR adding `in` support project-wide should revisit `set[int]`'s own scope to add membership testing as a natural, small follow-up once the underlying language feature exists -- tracked as a `docs/ROADMAP.md` follow-up by Task 10 of this plan. `d[k] = v`'s own insert-or-update op, combined with `for k in d:` re-reading `pycc_rt_dict_len` on every iteration rather than hoisting it (see `MirStmt::ForDict`'s own codegen comment), is a deliberate, accepted v0.2 divergence from CPython: mutating a dict inside `for k in d:` to grow it (e.g. `d[new_key] = v`) silently iterates the newly-added key(s) too, where real CPython raises `RuntimeError: dictionary changed size during iteration` for that same program.
