## D-148: Reuse `L0001` for context-invalid `break`/`continue`/`async for`, not a new code (#141)

- Status: accepted
- Context: `pycc check` misclassified `break`/`continue` with no enclosing loop and `async for` with no enclosing async function as `C0001` ("valid Python, just not implemented yet"). CPython 3.14 (verified directly against the pinned `python3.14` oracle, 3.14.6, already used by `tests/conformance.rs`) rejects all three as `SyntaxError`: `'break' outside loop`, `'continue' not properly in loop`, `'async for' outside async function` — a different failure class (context-invalid, not merely unimplemented) that this compiler had no diagnostic for. Two corrections to the issue's own premise, confirmed empirically before implementing: (1) `break`/`continue` were `C0001` in *every* context, not only when context-invalid — HIR had no `HirStmt::Break`/`Continue` variant at all, so a real `for i in range(3): break` also produced `C0001` today; the fix therefore had to distinguish the context-invalid subset from the still-genuinely-unimplemented in-loop subset, not simply reclassify every occurrence. (2) The `for_stmt.is_async` check cannot be reached from inside a real `async def` today — `lower_function` unconditionally rejects any `async def` (`C0001` "async functions are not supported yet") before its body is ever lowered — so no `in_async_fn` context field is needed or addable without introducing untestable dead code under this repository's 100%-coverage gate; the async-for arm is unconditionally context-invalid.
- Decision: Reuse the existing `L0001` code (`docs/DIAGNOSTICS.md`: "syntax error (span + expected set)") for this new context-invalidity class rather than minting a new diagnostic code or domain prefix. `L0001`'s registered domain (`L0xxx`, "lexing / parsing / grammar") is a direct semantic fit for "CPython classifies this as a `SyntaxError`" — the issue's own suggestion. This repository has direct precedent for reusing an existing code family purely by matching *meaning* rather than emitting crate or mechanism (D-137's `C0001`→`C0002` reasoning; `C0001` itself is already emitted from both `pycc_hir` and `pycc_types`). Implementation: `crates/pycc_hir/src/stmt.rs` (new module, see below) threads a plain `in_loop: bool` parameter through `lower_stmt`/`lower_body`/`lower_elif_else_clauses` — `lower_checked`'s top-level call and `lower_function`'s body-lowering call pass `false`; `While`/`For`/`ForRange` bodies pass `true`; the `If` arm and `lower_elif_else_clauses` pass the caller's value through unchanged. `Stmt::Break`/`Stmt::Continue` branch on `in_loop`: `false` emits a new `context_invalid()` helper (sibling to the existing `unsupported()`/`unresolved_symbol()`, emitting `Diagnostic::error("L0001", ...)`); `true` keeps the existing `unsupported()` `C0001` path unchanged (loop control-flow codegen is still out of scope). The `for_stmt.is_async` arm unconditionally emits `context_invalid("'async for' outside async function", ...)`.
- The one internal inconsistency accepted, not fixed: `T0024` ("`return` outside a function") is the closest existing precedent for "keyword valid only in a specific enclosing context, CPython also raises `SyntaxError`" — and it lives under `T0xxx`, not `L0xxx`. No rationale for that prefix choice is recorded anywhere (`docs/DECISIONS.md`, `docs/DIAGNOSTICS.md`, and `T0024`'s own git history were all searched; it predates any recorded ADR). Minting a third prefix for this issue's three constructs would spread the same "keyword outside its valid context" family across three prefixes instead of two; reusing `L0001` keeps it at two and matches the issue's own suggestion. `docs/DIAGNOSTICS.md`'s "codes: stable forever" rule forbids renumbering `T0024` to fix this retroactively — the inconsistency is documented here instead.
- Alternatives: mint a new diagnostic code/domain (rejected — no prefix is a better semantic fit than `L0001`, and a third prefix for the same error family is strictly worse than two); catch this in `pycc_types` instead of `pycc_hir`, mirroring `T0024`'s own scope-aware dispatch mechanism (rejected — `T0024` works because `HirStmt::Return` is already representable everywhere and `pycc_types` already has module-vs-function-scope dispatch built for other reasons; `break`/`continue` have no `HirStmt` representation at all, so moving this to `pycc_types` would require inventing new HIR variants and match arms across `pycc_types` and eventually `pycc_codegen` — a much larger, riskier change than this issue's actual scope); add an `in_async_fn` context field for symmetry with `in_loop` (rejected — Correction 2 above: no reachable valid-but-unimplemented case exists for it today, so it would be dead, untestable code under the 100%-region coverage gate); bundle `yield`-outside-function into this same change (rejected — `yield` is an expression, not a statement, reached through the separate `lower_expr` seam this change does not touch; scoped out to a follow-up issue, same milestone).
- Module decomposition: per AGENTS.md's file-decomposition rule, `crates/pycc_hir/src/lib.rs` (already ~4,950 lines) had `lower_stmt`/`lower_body`/`lower_elif_else_clauses` extracted into a new `crates/pycc_hir/src/stmt.rs`, `pub(crate)`, in the same commit as the `in_loop` threading and the new diagnostic arms (an intermediate "moved but `in_loop` unused" state does not compile cleanly under this workspace's warnings-as-errors lint gate). `unsupported()`/`unresolved_symbol()`/`context_invalid()` stay in `lib.rs` (shared across statement lowering, expression lowering, and import/type-alias lowering) — `stmt.rs` calls them as private items of an ancestor module, which Rust's visibility rules already permit without any `pub(crate)` marking on them.
- Consequences: `pycc check` now reports `L0001` for `break`/`continue` with no enclosing loop and for any `async for` (module scope or inside a synchronous `def`), while the same constructs inside a real loop/async context keep their prior classification (`C0001` for break/continue in a loop; async-for's own arm has no reachable valid-but-unimplemented case left to preserve). New unit tests in `crates/pycc_hir/src/lib.rs`'s existing `mod tests` cover both directions for break/continue and both async-for positions; new CLI fixtures (`tests/diagnostics/l0001_break_outside_loop`, `l0001_continue_outside_loop`, `l0001_async_for_outside_async_function`, paired with `c0001_break_inside_loop`/`c0001_continue_inside_loop`) are not byte-for-byte CPython-oracle-diffed (per D-138's own precedent — different failure kinds) and assert pycc's own diagnostic output only. `docs/DIAGNOSTICS.md`'s `L0001` row is annotated to note the reused-without-an-expected-set case and cross-reference this ADR. `docs/ROADMAP.md`'s v0.3 triage paragraph marks #141 resolved. `yield`/other invalid-expression-context misclassification (the issue's own broader "invalid async/yield context" completion criterion) remains out of scope — tracked by [#361](https://github.com/rotnov/pycc/issues/361), same milestone, referencing #141 — since it is a separate `lower_expr` code seam with its own call graph, not `lower_stmt`'s. Issue #141 itself stays open until #361 merges, per this repository's autonomous-operation workflow.
