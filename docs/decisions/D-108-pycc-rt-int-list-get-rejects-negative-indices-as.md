## D-108: `pycc_rt_int_list_get` rejects negative indices as out-of-range; correcting Task 10's "D-105" mis-citation

- Status: accepted
- Context: Task 10 (D-105's `PyIntListObj` runtime object) implemented `pycc_rt_int_list_get`'s bounds check as `if index < 0 || index as usize >= len { panic!("pycc_rt: list index out of range") }`, and both its own doc comment and a dedicated `#[should_panic]` regression test (`int_list_get_rejects_negative_indices`, `crates/pycc_rt/src/lib.rs`) cited this scope cut as "(D-105)." D-105's own five scope cuts (this file, above) cover annotation syntax, read-only indexing, `.append()`/`len()` as hand-recognized special forms, `ForList`'s `ForRange`-reuse desugaring, and `list[int]`-only codegen — none of them mention index sign or bounds at all. Task 10's own independent task-review (recorded in this plan's `progress.md`) confirmed the *behavior* is correct and deliberate — `pycc_types` has no way to reject `lst[-1]` at compile time, since the index value is only known at runtime — but flagged the citation as pointing at a decision that never actually discusses it, and asked for "a real, discoverable home" for the scope cut rather than an inaccurate pointer, since `lst[-1]` is ordinary, type-checked Python source a user can actually write, not a hypothetical.
- Decision: record the negative-index rejection as its own decision, per this file's own append-only convention (an accepted decision is never edited in place; D-105's text is unchanged). `pycc_rt_int_list_get` panics on any negative index with the same message as an out-of-range positive one (`"pycc_rt: list index out of range"`) — real Python's `lst[-1]`-addresses-the-last-element semantics is out of scope for v0.2's thin slice. `crates/pycc_rt/src/lib.rs`'s doc comment on `pycc_rt_int_list_get` and `int_list_get_rejects_negative_indices`'s own test comment (Task 12) are corrected to cite D-108 instead of D-105.
- Alternatives: support negative indexing in v0.2 (rejected — a runtime-computed index can't be resolved to "count from the end" by a static rewrite the way a literal `-1` could, so this needs a real length-relative adjustment inside `pycc_rt_int_list_get` itself; strictly larger than this thin slice's own scope and not requested by any PR-10 task). Edit D-105's own text to add this scope cut retroactively (rejected — D-105 is already accepted, and this project's own convention is to supersede via a new decision, never silently rewrite an accepted one, exactly the same reasoning D-090→D-091 and D-091(+D-099)→D-100 already established). Leave the mis-citation as-is since the underlying behavior is correct (rejected — Task 10's own review explicitly asked for a durable, correctly-attributed record; a wrong citation next to a real, reachable panic is exactly the kind of doc-vs-reality drift this project's AGENTS.md "keep documentation honest" rule exists to catch).
- Consequences: `pycc_rt_int_list_get`'s doc comment and its regression test's comment both cite D-108, not D-105. `tests/fixtures/pep_0585_builtin_generics.py` (Task 12) must not exercise negative indexing, since it would panic here rather than matching CPython's last-element behavior. A future PR adding real negative-index support supersedes this decision, not D-105, and must update that fixture's own documented restriction at the same time. **Cross-reference note:** D-106's own Consequences section (above) still says this scope cut is recorded in "D-105's own text, Task 10's report" — that parenthetical predates this decision and is superseded by it: the scope cut's actual, discoverable home is this entry, D-108, not D-105. D-106 itself is left unedited, per this file's own append-only convention (the same convention this decision's own Alternatives section already applies to D-105); a reader following D-106's citation should resolve it here instead.
