## D-191: Milestone membership ranks first in issue-select's step 5 ordering

- Status: accepted
- Context: Issue #727 recorded an observed starvation run. Under a v0.3 milestone scope, seven consecutive autopilot merges (#674, #679, #681, #684, #688, #721, #726) were all D-185 oversized-file decomposition work outside the active milestone, while `scripts/check_conformance_breadth.py` reported the same 32-of-37 conformance rows at the start and at the end of the run — the milestone's own critical path (#541, #703, #542, #543, #719) was never reached. D-144 decision (a) placed active-milestone membership *below* the priority marker, as a same-priority tie-break only. That ordering is sound when the in-scope and out-of-scope pools carry comparable markers, but the tracker does not look like that: a steady supply of well-marked, small, cleanly-scoped out-of-scope issues outranks the milestone's own work on the marker alone, iteration after iteration, and each individual selection is locally defensible. The defect is in the ordering, not in any one pick.
- Decision: Supersede D-144 decision (a) only. When a milestone scope is in effect, membership in that scope ranks *first* in `issue-select`'s step 5 — ahead of the priority marker and ahead of size. Inside each group (in-scope, and out-of-scope among themselves) the order remains marker-then-size. Out-of-scope issues therefore sort below every in-scope survivor, so the scope is exhausted before any of them is reached; reaching outside the scope is permitted only when the scope contributes no survivor at all. Leaving the scope is a reportable event: step 5 requires the justification to state that the scope contributed no survivor and to name what disqualified each of its members (closed, excluded by the step 4 blocker screen, denylisted this run, premise unreproducible at step 6), and step 8's hand-off report carries that record. With no milestone scope in effect the ordering is unchanged — the repository's own priority markers rank first, then size. D-144's remaining decisions, including (b)'s unconditional post-cycle evidence check, stay in force untouched.
- Alternatives: Leave D-144 (a) as-is and rely on judgment at step 4's blocker screen (rejected — the observed run shows every individual pick was defensible under the existing rule; a defect that only appears across seven iterations cannot be caught by per-pick judgment). Restrict the candidate pool to milestone-tagged issues (rejected again, for D-144's own stated reason — a hard pool restriction removes reachability entirely and would strand the large unassigned backlog; ordering achieves the same starvation fix while every issue stays selectable). Cap the number of consecutive out-of-scope selections (rejected — an arbitrary threshold with no principled value, and it still admits starvation below the cap while blocking legitimately in-scope-empty runs above it). Weight membership as a numeric score alongside marker and size (rejected — a weighted sum has no honest calibration here and makes "why was this reached before that" unexplainable in a report, where a lexicographic order is auditable).
- Consequences: One sharp edge is deliberate and is stated in the skill text itself: under a scope, an *unmarked* in-scope issue outranks an out-of-scope P1. That is what membership-ranks-first means, and it is the property that stops the observed starvation. The escape hatch needs no separate mechanism — non-members sort last in a total order, and issues already excluded by steps 3 and 4 never reach step 5, so "the scope contributes no survivor" is exactly "no in-scope issue reached step 5"; only the reporting duty needs prose. `run_alpha_skill_evals.py`'s `issue_select_higher_ranked` gains a third defaulted parameter, `milestone_scope_in_effect`, which is inert when `False`, so the no-scope ordering is byte-identical to today's and every existing no-scope call site keeps working unchanged. `ISSUE_SELECT_CONTRACT` keeps the literal "the repository's own priority markers rank first" rather than moving it: the phrase remains literally true in the no-scope branch where it now sits, so keeping it is honest rather than a compatibility shim. Two further literals — "membership in that scope ranks first" and "only when the scope contributes no survivor at all" — are pinned alongside it so a future vague reword of the new rule fails the eval, matching D-111's precedent. A fifth `issue-select` eval case covers the starvation scenario (an in-scope P2 reached ahead of a smaller out-of-scope P1) and is registered in both `EXPECTED_RUNNERS` and `validate_agent_assets.py`'s mirror registry. `.agents/skills/issue-select/SKILL.md` is an eleven-line pointer to the canonical Claude-side file and needs no mirror edit. A run that legitimately has no in-scope survivor now costs one extra paragraph of justification; that is the intended price of making a starved milestone visible.
