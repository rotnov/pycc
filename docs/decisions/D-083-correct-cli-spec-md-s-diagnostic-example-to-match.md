## D-083: Correct CLI_SPEC.md's diagnostic example to match reality instead of building new rendering features

- Status: accepted
- Context: `docs/DELIVERY_PLAN.md` row 6's third acceptance bullet is "diagnostic output matches CLI_SPEC.md's example byte-for-byte." `docs/CLI_SPEC.md`'s example before this decision showed a short, message-independent caret label (`expected \`int\``), a populated `= help: did you mean \`int("35")\`?` line, and a precise span (`src/main.py:5:15`, a 4-column caret under `"35"`) -- none of which the compiler produces today. The implementation plan that authorized this decision assumed `crates/pycc_diag/src/lib.rs`'s existing `render_human_matches_cli_spec_format` unit test proved the real end-to-end shape; it does not -- that test hand-constructs a `Diagnostic` with a genuine `Span::new(26, 30)` and feeds it straight to `render_human`, exercising the *renderer's* capability to place a caret under an arbitrary span, never the type checker that actually produces `T0021` diagnostics. Running `pycc check` against a fully annotated fib-style fixture (`def fib(n: int) -> int: ...` called with a `str` argument) shows the real output is `error[T0021]: argument 1 of \`fib\` expects \`int\`, got \`str\`` at ` --> <path>:1:1` with a single-character caret on line 1 -- because every `T0021` (and every other `T0xxx`) diagnostic in `pycc_types` still constructs its `Span` as the `Span::new(0, 0)` placeholder (confirmed: all 19 `Span::new` call sites in `crates/pycc_types/src/lib.rs` use the placeholder; every existing `tests/diagnostics/*.expected.txt` fixture for a `T0xxx` code already bakes in `:1:1` with a one-character caret, e.g. `d0021_range_argument_type.expected.txt`). This is D-043's own third named gap ("every diagnostic's `Span` is still the `Span::new(0, 0)` placeholder"), not a new discovery -- D-043 already directs that `tests/diagnostics/` fixtures bake in the placeholder location "for exactly this reason." The caret label repeating the full diagnostic message (rather than an independent short label like `expected \`int\``) is also current, unavoidable behavior: `Diagnostic::error` always sets `label: Some(message.clone())`, and no call site anywhere in the workspace ever supplies an independent label.
- Decision: rewrite `docs/CLI_SPEC.md`'s example to the real, current end-to-end `pycc check` output for a `T0021` argument-type mismatch: full-message caret label, the `Span::new(0, 0)` placeholder location (`line 1, column 1`, one-character caret), and no help line. Add a checked-in `tests/diagnostics/cli_spec_example.py` (a fully annotated `fib`-style function called with a mismatched-type argument) + `.expected.txt` pair that runs the real compiler through this project's existing `tests/diagnostics/*.py`+`*.expected.txt` fixture convention (`tests/diagnostics_test.rs`'s explicit per-fixture `#[test]` registration) and proves the corrected example matches byte-for-byte -- except the displayed file path, which the test harness's own established convention (`assert_diagnostic_matches_fixture`, confirmed against every existing sibling fixture) always renders as the fixture's real repo-relative path (`tests/diagnostics/cli_spec_example.py`), not CLI_SPEC.md's illustrative `src/main.py` stand-in filename. `crates/pycc_diag/src/lib.rs`'s `render_human_matches_cli_spec_format` unit test is left unchanged: it is a renderer-capability regression test (and, per its own doc comment inside `render_human`, the only test exercising the multi-character-caret branch), not a claim about the checker's current behavior, and changing it risks the D-014 100% coverage gate for no benefit to this decision.
- Alternatives: implement real per-node span threading through HIR, independent short caret labels, and populated `help:` suggestions now, so the *original* aspirational example becomes true (rejected -- real spans are D-043's own explicitly deferred, PR-sized follow-up ("a future PR ... should thread real spans through HIR"), and short labels plus help population are separate, undersized-for-this-PR feature work; none of it belongs in a PR titled "Conformance + benchmark gate"). Codify `render_human_matches_cli_spec_format`'s hand-fed-span rendering as the documented "reality" and add a fixture that exercises `render_human` directly with a synthetic `Diagnostic` instead of the real CLI (rejected -- every existing `tests/diagnostics/` fixture drives the real `pycc check` binary end-to-end; a fixture that instead hand-constructs a `Diagnostic` bypassing the type checker would prove only the renderer's capability, which the existing unit test already covers, not that the CLI's actual, user-visible output matches CLI_SPEC.md, which is DELIVERY_PLAN.md row 6's actual acceptance bullet). Leave CLI_SPEC.md's example as aspirational prose with no enforcing fixture (rejected -- this project's own standing convention is that every normative documentation claim should be enforceable by a test where practical, and an unenforced, currently-false "byte-for-byte" claim in a public spec file is exactly the kind of stale-docs risk AGENTS.md warns against).
- Consequences: `docs/CLI_SPEC.md`'s example is now truthful and permanently checked against the real compiler, including its currently-imprecise placeholder span -- readers see, in the spec itself, that today's caret points at a fixed placeholder location rather than the real argument, matching D-043's already-documented gap rather than contradicting it. D-043 remains the tracked, correct place for the real-span, short-label, and help-population feature work, whenever it happens; once real spans land, this fixture must be regenerated by re-running `pycc check` and re-copying its stdout (per D-043's own consequence), not hand-edited to guess the new span.
