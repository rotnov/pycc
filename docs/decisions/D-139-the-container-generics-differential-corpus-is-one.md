## D-139: the container/generics differential corpus is one hand-authored, multi-feature fixture file, oracle-diffed like every other conformance fixture

- Status: accepted
- Context: D-088 point 1 replaces the unreachable "Tier-1 OSS corpus compiles" acceptance bullet with "a hand-authored container/generics differential corpus (list/dict/set/tuple literals, comprehensions, slicing, methods, generic functions), diffed against pinned CPython 3.14.6 on all 5 Tier-1 targets — the same fib/mandelbrot-ascii pattern D-085 already established for v0.1." D-085's pattern (confirmed by inspecting `tests/fixtures/` and `tests/conformance.rs`) is: a single, deliberately small, hand-written `.py` fixture per feature area, each with its own `*_matches_cpython_3_14_6_byte_for_byte` test entry, run in both `--debug`/`--release` across the 5 Tier-1 CI targets — not one giant fixture covering everything, and not a vendored/generated corpus.
- Decision: `tests/fixtures/v0_2_container_generics_corpus.py` is one new fixture (not several) that exercises, in a single straight-line script with deterministic printed output: a `list[int]` literal and a `dict[str, int]` literal and a `set[int]` literal and a `tuple[int, str]` literal; a list comprehension and a dict comprehension over those literals (PEP 709 scoping); slicing (`lst[1:3]`) on the list; the three PR-11/PR-12-added container methods (`.pop()`, `.get()`, `.add()`) each used once on their respective container; and a call to a one-type-parameter generic function (`def f[T](x: T) -> T`) applied to both an `int` and a `str` value, printing both results — deliberately reusing every already-shipped v0.2 feature in one composed program rather than testing any single feature in isolation (each feature already has its own dedicated fixture from PR-9 through PR-13; this corpus's job is proving they compose correctly together, which is what "corpus" means here, not redundant single-feature coverage). It is registered as exactly one new test, `v0_2_container_generics_corpus_matches_cpython_3_14_6_byte_for_byte`, in `tests/conformance.rs`, run dual-profile on all 5 Tier-1 targets like every other fixture in that file — no new test-harness machinery.
- Alternatives: multiple smaller "corpus" fixtures, one per container type (rejected — that's just re-testing single features in isolation again, which PR-9 through PR-13 already did; the acceptance bullet specifically asks for a corpus proving composition, and splitting it back into single-feature files would silently drop that goal). Attempt a literal reduced excerpt of `tomli`/`packaging`/`more-itertools` source (rejected — D-088 point 1 explicitly ruled this out: even a hand-trimmed excerpt would need stdlib modules (`re`, `typing`, `dataclasses`, ...) v0.2 does not ship, so it would not actually compile and would not be a real excerpt of the named packages either, just cosmetically resembling one for no honest benefit). Add the corpus as a standalone example under `examples/` instead of `tests/fixtures/` with a `tests/conformance.rs` entry (rejected — every existing D-085-pattern fixture lives under `tests/fixtures/` with an oracle-diff test; a standalone example would not be a binary, CI-enforced acceptance check the way ROADMAP.md's bullet requires).
- Consequences: one new fixture file and one new dual-profile conformance test, following the existing pattern exactly. `docs/ROADMAP.md`'s v0.2 acceptance line cites this corpus (via D-088's already-rewritten bullet) as satisfied once this test is observed green in CI on all 5 Tier-1 targets, per D-102's "never speculatively flip" policy — the docs sweep flips the corresponding status marker only after real CI evidence, not preemptively in the same commit that adds the fixture.
- Addendum (2026-08-04, Task 5 implementation): the shipped fixture uses a `tuple[int, int]` literal (`(7, 8)`), not this decision's own illustrative `tuple[int, str]` text above — verified directly against the compiler that a `str`-typed tuple element is still rejected with `T0039` ("tuple element type `str` is not compiled yet (D-116) -- only int/bool/float elements are"), a pre-existing v0.2 scope limit this ADR's drafting session did not check empirically. Also verified that printing a container value directly (`print(xs)` for any of `list`/`dict`/`set`/`tuple`) still panics in codegen today (D-107/D-124/D-116's existing, unrelated-to-this-PR limit) — every value in the shipped fixture is printed element-wise, via indexing, or via `len()`, matching `container_methods_slicing.py`'s own already-established pattern, not printed as a bare container. Neither narrowing changes what the fixture proves (that these already-shipped v0.2 features compose in one program); both are pre-existing compiler limits discovered while writing the fixture, not new ones introduced by it.
