## D-098: Replace D-097's byte-exact comparison with a relative-tolerance one

- Status: accepted
- Context: D-097's exact-byte comparison shipped at commit `fe24ac7` on the strength of a manual check performed only on macOS aarch64 (D-093's own re-verification). The very next CI run on `windows-latest` refuted it: the correctness check failed with pycc and CPython disagreeing on `tests/fixtures/nbody.py`'s output. Decoded, the three values were pycc (Windows): `0.008420846407363925 0.00387155830433383 -0.0003266188019087493`; CPython (Windows): `0.00842084640915777 0.0038715583072033615 -0.0003266188019391568`; and D-093's own macOS-recorded value (both pycc and CPython, byte-identical there): `0.008420846407813569 0.003871558303952385 -0.00032661880191911866`. All three values agree to roughly 10 significant digits before diverging -- ruling out a wrong formula, wrong iteration count, or wrong update order (any of those would diverge far earlier), and consistent instead with `pow`/libm rounding differences across platforms, amplified by this fixture's own chaotic 5-body dynamics over 525,000 iterations. Notably, pycc-on-Windows and CPython-on-Windows do not agree with *each other* any more closely than either agrees with the macOS value -- if both were simply calling the same platform libm `pow`, they would be expected to cluster together against macOS, and they don't -- so the divergence is not solely one shared-library identity issue; `pycc_rt_float_pow` and CPython's own float `**` evidently take at least partially different paths even on the same host. This is the first time any test in this repo has attempted byte-exact float-output comparison across platforms (`tests/conformance.rs`'s two fixtures print only integers and ASCII characters, never a non-integral float, confirmed by reading both fixture files directly) -- so this is new information about pycc/CPython cross-platform float fidelity, not a previously-known-and-ignored risk.
- Decision: parse each side's stdout into three `f64`s (`parse_three_floats`, asserting exactly 3 whitespace-separated tokens first so a truncated or malformed output fails loudly rather than comparing a degenerate subset -- the fixture's final `print(sun_x, sun_y, sun_z)` is the Sun's final position after the simulation, not a computed energy value), and compare with a **relative** tolerance of `1e-6` (`assert_relative_eq`) instead of exact bytes. Computing the actual relative difference for all three decoded values above: value 1 ≈ 2.13e-10, value 2 ≈ 7.41e-10, value 3 ≈ 9.31e-11 -- the worst is ~7.41e-10, not the ~2e-10 an earlier draft of this decision cited from only the first value. `1e-6` leaves roughly three orders of margin above that actual worst observed gap, while staying far below what a real miscompile would produce (those diverge in early digits, not trailing ones). A relative tolerance, not absolute, because the three reported values span multiple orders of magnitude (~8e-3, ~4e-3, ~3e-4) -- one absolute epsilon would be either too loose for the largest value or too strict for the smallest. `strip_windows_newline_translation` (D-097's own duplicate of `tests/conformance.rs`'s helper) is still applied to the oracle's side first, since CRLF bytes would otherwise corrupt tokenizing. D-097's untimed-check placement (immediately after the `--release` build, before the `RUNS = 5` timed loops) is unchanged by this decision.
- Alternatives: an absolute tolerance instead of relative (rejected -- see Decision above: the three values' differing magnitudes make one absolute epsilon either too loose or too strict). Keep exact-byte comparison but skip or relax it specifically on `windows-latest` (rejected -- arbitrary and unprincipled: nothing establishes that macOS x86_64, Linux aarch64/x86_64 would stay byte-exact either under a similarly precise cross-platform check, since none of them had ever been tested this way before D-097; singling out the one leg that happened to fail first, rather than fixing the comparison method for all five, would just move the untested-assumption problem instead of removing it). Reduce the fixture's iteration count to shrink the chaotic amplification instead of tolerating it (rejected -- out of scope: this would reopen D-093's own carefully-tuned amortization of fixed per-process overhead, which was fixed by *raising* the count, and would not eliminate cross-platform libm differences, only shrink how visible they are, at the cost of reintroducing D-093's original overhead problem).
- Consequences: a future miscompile that regresses nbody's actual computed output (not just its timing) still fails this test, now with a value-indexed relative-difference message, rather than silently passing on speed alone -- but a future divergence within `1e-6` relative on any single value will *not* be caught by this check; that is the accepted cost of tolerating real cross-platform float-formatting variance rather than gating on D-097's own since-refuted exact-byte assumption. Verified locally on real Apple Silicon hardware: `cargo test --test nbody_bench -- --ignored` passes end-to-end, reproducing D-093's own recorded output exactly (well within tolerance, trivially, since it is byte-identical there); this proves the tolerance does not introduce a false failure where the exact-byte version already passed, but `windows-latest` -- the leg that actually falsified D-097 -- is the real test of this fix, to be confirmed via the next CI run on this same pull request rather than assumed from local evidence alone. The ~10 digits of agreement observed across three independent platform/interpreter combinations (pycc-Windows, CPython-Windows, pycc/CPython-macOS) before divergence is itself new evidence of pycc's general cross-platform float fidelity for this workload, not previously demonstrated anywhere in this repo -- worth keeping in mind distinct from the ~7.41e-10 worst relative gap the tolerance now accepts. D-096's own Windows-Defender-hypothesis procedural-confound risk (D-097's untimed pycc launch potentially absorbing a first-launch-only AV-scan cost outside the timed measurement) is unaffected by this decision and remains recorded under D-097.
