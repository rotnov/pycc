## D-242: Product mode: the delivery process informs rather than blocks

- Status: accepted (Stage 1/2 for #1010 is the pull request that depends on it: policy, checker, and the diff-coverage script land there; the activation pull request swaps the live `ci.yml` step and is recorded as an inserted amendment line below when it merges)
- Context: The delivery apparatus accumulated by D-014 (100% line and region coverage of the whole workspace as a merge invariant), the D-080 stage-then-activate pattern for the byte-exact coverage-step prefix that `scripts/check_roadmap_evidence.rb` pins (`REVIEWED_TRUSTED_COVERAGE_STEPS`/`REVIEWED_COVERAGE_SCRIPTS`), the "record every irreversible or project-wide choice as an ADR" rule as practiced (ADRs for stdlib symbol registrations and scratch-directory names), the D-066/D-130/D-192 session snapshot per merged pull request, the per-task `.harden/findings/` pile plus `harden batch` pass that `issue-implement` mandates, and the full `issue-to-plan` adversarial loop for every multi-step task were each justified when the project's purpose was to prove that autonomous agents can build a compiler to a correctness bar. Together they now consume most of a run's wall-clock and tokens: reaching 100% region coverage on runtime error paths, staging a CI change across two pull requests, and writing three journals per merge cost more than the product change they accompany. The repository owner directed the project toward product delivery — real programs compiled unchanged, stdlib breadth, distribution (issue #1010). A process that blocks on every property cannot move at product pace; a process that reports the same properties still makes regressions visible.
- Decision: The merge gate is narrowed to the properties that protect correctness and repository integrity; every other property is measured and reported. One definition is shared by every rule below: an **incident** is a wrong merge decision, a defect that reached `main`, a gate that lied, or a run that lost meaningful time to a process mistake. Concretely:
  1. **Coverage.** The merge invariant is 100% line coverage of the Rust lines a compiler-relevant pull request adds or modifies, measured by `scripts/check_diff_coverage.py` from a `cargo llvm-cov --workspace --lcov` export joined against a zero-context `git diff` of the pull request's own changes (its base commit to `HEAD` in CI, the merge base with `origin/main` locally). A changed instrumentable file with no coverage record fails the gate closed. Total workspace line coverage (from the LCOV `LF`/`LH` totals) and the per-crate region table (`cargo llvm-cov report`) are printed in the same job as a report, never as a threshold. D-014's whole-file exemption mechanism and its `docs/TESTING.md` table stay; lowering the `--require-changed-lines` threshold, dropping `--workspace` from the LCOV run, disabling the job, or excluding code merely to pass stays forbidden. D-014 is narrowed accordingly (its Status line records this).
  2. **CI changes.** The base-owned `audit` validates the coverage job by named properties instead of a byte-exact match of its step sequence: the job-level shape (unconditional, dependency-free, failure-propagating, trusted runner, exact trusted workflow environment, no inherited defaults), an order-free set of pre-gate steps drawn only from the pinned checkout with `persist-credentials: false` and the enumerated trusted setup commands, and a gate step with the exact step name, exact two-key `env`, default shell, no condition, whose script contains each required line exactly once and in order (trusted `cargo-llvm-cov` path and pinned install, `nobody` ownership of the isolated root, the `run_isolated` sandbox definition, the sanitized `PATH`, the `--workspace --lcov` export, the `report` table, and the `check_diff_coverage.py --require-changed-lines 100` gate) and none of the forbidden fragments (`exit 0`, `|| true`, `|| :`, `set +e`, `trap `). D-172 already retired whole-file `ci.yml` digests for D-171-routed workflows; this decision retires the last byte-exact prefix, so a preparatory-build or gate-command change ships in one pull request. The second pull request is still required, and only then, when the base-owned `audit` must learn something first — a new roadmap-evidence identifier, a new trusted setup command, or a new required gate line — because `audit` runs the base revision of the checker against the head revision of the workflow. Privileged jobs keep every `scripts/check_ci_permissions.rb` check unchanged. D-080's byte-for-byte alignment clause is narrowed accordingly; its ordering rule (the conformance oracle's setup runs after the coverage gate, never inside its boundary) stays in force. **Threat model:** the audit now proves *shape* — unprivileged sandbox, trusted binary, workspace denominator, gate command line, threshold — not byte identity; a hostile edit placed between the required lines is caught by the D-068 full-diff review that precedes every merge, which is the compensating control.
  3. **ADR bar.** A new file under `docs/decisions/` is written only for a choice that is irreversible or project-wide: ABI and artifact formats, semantics that deliberately deviate from CPython, security and trust boundaries, and the operating model itself. Registering a stdlib symbol, adding a builtin method, naming a scratch directory, choosing a test layout, or fixing a gate is a pull request with tests and, where a rule changes, an `AGENTS.md` or owning-specification edit.
  4. **CPython oracle.** Byte-for-byte conformance against the pinned CPython oracle (the `docs/TESTING.md` "Conformance harness" contract behind the `*_matches_cpython_*_byte_for_byte` tests; D-080 governs only the oracle's CI placement and D-082 only Windows newline stripping) stays the rule for semantics: values, output order, exit codes, exception types. `docs/TESTING.md` gains an explicit "CPython oracle exception list"; an entry names the inessential text it exempts (traceback formatting, warning wording) and why. Anything not listed stays byte-exact; the list starts empty.
  5. **Journals.** `docs/sessions/` snapshots, `.harden/findings/` piles, `harden batch` passes, and `.harden/incidents/` entries are written only for an incident as defined above. An ordinary pull request writes none of them. `docs/AGENT_RETROSPECTIVE.md` keeps D-066's existing bar unchanged. D-066, D-130, and D-192's rule 5 are narrowed accordingly (their Status lines record this).
  6. **Planning.** `issue-to-plan` with its adversarial loop stays for architecturally consequential work: a new subsystem, a cross-crate seam, a CI trust boundary. A series of homogeneous items (several `str` methods, several stdlib registrations) gets one `issue-to-plan` plan for the series, published on the parent issue; each item is then a plain pull request that cites that plan and needs no plan of its own.
  Unchanged: protected `main` through pull requests (D-024); CPython as the oracle with fail-closed `C0001` on unsupported surface; full-diff review before merge (D-068); CI privilege boundaries; accepted-decision immutability (D-240); the D-021 preflight; the D-127 operating model.
- Alternatives: keep everything and accept the cost (rejected: the owner's direction is product delivery, and the measured cost is the majority of each run); drop the coverage gate entirely and rely on review (rejected: an unexecuted new line in a compiler is exactly the defect review misses, and diff coverage keeps that check at a fraction of the cost); keep 100% total coverage but relax regions only (rejected: total line coverage still forces every pre-existing path to stay reachable through any refactor, which is the cost being removed); keep the byte-exact coverage prefix and pre-register the new bytes as one more fixture (rejected: it reproduces the very stage/activate cost this decision removes and leaves every future preparatory-build change two pull requests); compute diff coverage in Ruby inside the checker (rejected: the checker is a workflow *auditor* run by `audit` without builds, and coverage data exists only inside the coverage job); `cargo llvm-cov --json` plus a JSON parser (rejected: LCOV is the smaller, line-oriented format and the only one `git diff` line ranges join against trivially; regions are reported by `report`); fail open when a changed file is absent from the LCOV (rejected as contradicting D-014's fail-closed exemption policy — a changed instrumentable file with no coverage record fails the gate); open two sub-issues for the two pull requests (rejected: the two-PR shape for one issue is an already-authorized pattern, and D-192 discourages tracker churn for a sequence that cannot merge out of order); drop the README coverage badge (rejected: `readme-coverage-badge-bound` and `scripts/check_readme_coverage_badge.rb` exist to stop a false public claim, and a "diff coverage: 100%" badge bound to `--require-changed-lines 100` keeps that contract); write journals but shorten them (rejected: the cost is the write-read cycle and the mandated read-back gates, not the length).
- Consequences: **What becomes one pull request:** any `ci.yml` change to the coverage job's preparatory builds, gate wording, or setup-step order that keeps the named properties. **What stays two:** a change that registers a new roadmap-evidence identifier, a new trusted setup command, or a new required gate line, because the base-owned `audit` must know it before the head can use it. **What stays byte-exact:** every privileged-job check in `scripts/check_ci_permissions.rb`, the trusted workflow environment (`TRUSTED_COVERAGE_ENV`), the pinned checkout action, and each required gate line itself. **The compensating control** for the shape-not-bytes audit is the D-068 full-diff review before every merge, which reads the coverage job's script as part of the diff. **The badge's new meaning:** `README.md`'s coverage badge states diff coverage bound to `--require-changed-lines`, and `scripts/check_readme_coverage_badge.rb` binds it there once the activation pull request lands. **Transitional state:** until the activation pull request merges, `ci.yml` still runs the whole-workspace `--fail-under-lines 100 --fail-under-regions 100` gate, `AGENTS.md` and `docs/TESTING.md` say so explicitly, and `scripts/check_roadmap_evidence.rb` accepts either shape; the activation pull request deletes those transitional sentences. **The legacy shape stays audit-recognized permanently** as a strictly stricter historical form (the D51/D56/D62/D80 "recognized but historical" precedent that `scripts/test_check_roadmap_evidence.rb`'s fixture tests assert), so a future `ci.yml` that reverted to the whole-workspace threshold would still pass `audit` — harmless, and `scripts/check_readme_coverage_badge.rb` would flag the badge mismatch. **What the diff gate cannot see:** coverage lost on *unchanged* lines — a deleted test that orphans an old path — never fails the gate; the `report` TOTAL row and the LCOV totals line are the only signal for that drift, and the D-068 review reads them; total coverage may therefore drift below 100% through refactors, visibly, and a later task may raise it, but nothing blocks on it. `AGENTS.md`'s "Testing and the coverage gate", "Keep documentation current", preflight step 10, and "Keep a retrospective log and a session handoff log" sections, the `issue-implement`, `sessions`, `review-findings`, `ultra-review`, `issue-select`, and `issue-to-plan` skills, `docs/sessions/README.md`, `docs/AGENT_TOOLING.md`, and `docs/TESTING.md` are rewritten in the same change; the two new evidence identifiers `ci-diff-coverage-100` and `readme-diff-coverage-badge-bound` are registered unchecked and cited by `docs/ROADMAP.md` only in the activation pull request. Existing `docs/sessions/` entries and `.harden/findings/` piles stay as history. The rule applies to the pull request that introduces it: neither pull request for #1010 writes a session file, a findings pile, or a harden batch unless an incident occurs.
