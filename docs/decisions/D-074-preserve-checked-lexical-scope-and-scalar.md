## D-074: Preserve checked lexical scope and scalar representations through MIR and LLVM

- Status: accepted (PR #132 Codex review found that backend lowering did not yet preserve several already-accepted type-system and control-flow contracts)
- Context: D-041/D-055 make module bindings available to function bodies regardless of declaration order while classifying every nested function assignment and `for` target as local from entry. The type checker also accepts `bool` wherever an `int` is required and fixes an inferred binding's representation at its first assignment. The original MIR/codegen walk was source-order and allocation-on-first-emission: functions could miss later globals, branch-local allocas did not dominate post-branch uses, and accepted `bool` values could reach an `i64` parameter, return, range, or existing binding as `i8`. A two-return `if` also left a synthetic merge block unterminated, and `None`-returning calls interpolated in f-strings reused an internal false placeholder instead of Python's text `None`.
- Decision: MIR registers functions, lowers top-level statements sequentially to preserve top-level forward-read errors, and lowers function bodies only after the module binding environment is complete. Codegen declares every supported module binding as an LLVM global before emitting bodies and seeds function name resolution from those globals. Every global and non-parameter local slot has an initialization flag: assignment sets the flag only after evaluating and storing its right-hand side, while an earlier read traps before an LLVM initializer, `undef`, or null can become a fabricated Python value. Parameters are initialized at entry and need no flag; #118 still owns earlier static rejection and structured definite-assignment diagnostics. Codegen recursively classifies each function's assignment and `for` targets and allocates all function-local slots in the entry block; parameters and local targets override same-named globals. A `for` uses hidden SSA induction state and writes the Python-visible target only on entry to a real iteration, so an empty range leaves a new target unbound, the post-loop target remains the last element, and body reassignment cannot alter iteration. The first binding type remains stable in MIR. At assignment, call-argument, return, and `range` boundaries, an accepted `bool` flowing to `int` is widened into the tagged D-061 representation. A synthetic `if` merge with no predecessor is terminated by `unreachable`, and a `None`-returning call in an f-string preserves the call side effect then materializes `None` text. General nested `None` values remain outside D-072.
- Alternatives: reject later module globals or accepted `bool`→`int` programs in the backend (rejected because `check` already promises they are valid); allocate on the first dynamically emitted assignment (rejected because an allocation inside one control-flow predecessor cannot safely serve other predecessors or a post-join read); add SSA and definite-assignment analysis now (rejected because D-057 deliberately keeps PR-5 MIR structural and #118 owns the later join analysis); store every scalar in one oversized tagged union (rejected because it discards the fixed representations that type checking exists to establish).
- Consequences: backend name resolution now matches D-041/D-055 without exposing a binding before execution initializes it, all local allocas dominate their uses, `for` target lifetime matches Python for empty, positive, negative, and body-reassignment paths, and `bool`→`int` compatibility has one representation-preserving realization across storage and ABI boundaries. Until Python exception objects land, an early global or local read is a deterministic process trap rather than a formatted `NameError`/`UnboundLocalError`; it cannot silently return a fabricated scalar or dereference a null string. Preallocating string slots also closes D-061/D-070's loop-body-first reassignment leak because every iteration can decref the slot's previous value. D-061/D-070 remain historical descriptions of the accepted PR-5 scope; D-074 supersedes only that loop-body-first leak. Unbound string temporaries and function-scoped string parameters/locals at return remain documented memory-safe leaks until `pycc_own`.
