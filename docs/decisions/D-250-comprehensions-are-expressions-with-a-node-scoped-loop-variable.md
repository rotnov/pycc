## D-250: Comprehensions are expressions with a node-scoped loop variable

- Status: accepted (implemented by [#1254](https://github.com/rotnov/pycc/issues/1254), Part 1 of [#1214](https://github.com/rotnov/pycc/issues/1214))
- Context: [D-117](./D-117-list-dict-set-comprehensions-are-statement-level.md) rule 1 limited a comprehension to the direct right-hand side of a bare-name assignment. Its one justification was that `pycc_codegen`'s expression emitter had no control flow. [#1211](https://github.com/rotnov/pycc/issues/1211) removed that premise: `crates/pycc_codegen/src/boolop.rs` and `compare_chain.rs` build basic blocks and a phi in expression position, and they re-read the phi predecessor after each operand, so an operand that creates blocks of its own is safe. Real programs pass comprehensions to calls and return them ([#1214](https://github.com/rotnov/pycc/issues/1214)). D-117 rule 2, the synthesized `0comp_<offset>_<name>` loop variable, is still correct.
- Decision:
  1. **One expression node.** A list, set or dict comprehension lowers to one `HirExpr::Comprehension` (and one `MirExpr::Comprehension`) in any expression position: a call argument, a `return` value, an annotated assignment, an f-string, a `while` or `if` test, a short-circuit operand, another comprehension. `name = <comp>` keeps D-117's statement form (`HirStmt::ListCompAssign`/`SetCompAssign`/`DictCompAssign`), built from the same node by `comp_assign_stmt`, and both forms share one codegen emitter.
  2. **The loop variable is scoped to the node.** D-117 rule 2's synthesized name is kept. In the expression form it is bound only in a scoped copy at every layer: a cloned `Environment` in the checker, a cloned `ConstraintEnvironment` in the solver, a cloned environment in the protocol monomorphizer, a pushed MIR scope frame, and in codegen a cloned `locals` map holding a new entry-block slot. The slot is zeroed in the entry block, so it is never a module global. The generic monomorphizer binds the name directly, which is harmless because no source can name it. After the loop, an `int` variable's last value is released and its slot re-zeroed; a `str` dict-key variable stays leak-only, like `ForDict` and the statement form.
  3. **A walrus inside any comprehension is refused.** `:=` anywhere in a comprehension, in either form, is `C0001` "a walrus assignment (`:=`) inside a comprehension is not supported yet", spanning the comprehension. CPython binds such a target in the enclosing scope, which the node-scoped model does not express.
  4. **The generator limits are unchanged.** Exactly one `for`, at most one `if`, a bare-name target, no `async`, and a `range(...)` or bare-name iterable; the produced container is `list[int]`, `set[int]` or `dict[str, int]` (D-119). Part 2 of #1214 (#1255) owns the iterable limit, Part 3 (#1256) the one-`if` limit, and #1257 the one-`for` limit; a non-bare-name target and `async` are not tracked yet.
  5. **Synthesized names are not definitions.** A name with a leading ASCII digit is one lowering synthesized, so it never enters the cross-module collision check in `program::link` ([#1237](https://github.com/rotnov/pycc/issues/1237)). The private-helper solver binds a comprehension statement's target to its container type, as it binds any other assignment's target.
- Alternatives: hoisting a comprehension into a temporary statement before the one that holds it (rejected: it runs a comprehension in an untaken short-circuit operand and reorders it against its sibling arguments, both of which the byte-exact oracle observes); three expression variants, one per kind (rejected: one boxed node with an element enum keeps every walker to one arm); lowering module-scope `name = <comp>` through the expression form, or qualifying the synthesized name per module, so that two modules never share a `0comp_` slot (rejected for now: the first changes D-117's statement form at module scope for every existing program, and statement lowering does not know the module's identity).
- Consequences: every expression walker gains a comprehension arm, and a wildcard walker must be checked by hand (`mark_truth_context` deliberately has none). A comprehension that raises part-way leaks its partial container and, for an `int` variable, the last value, as D-124's leak-only model already allows. The linked program is still one flat namespace, so two modules whose statement-form comprehensions have the same target name at the same byte offset share one module-global `0comp_` slot: the program runs when the loop variables have the same type, and is refused with `T0023` naming the synthesized variable when they differ (for example a `range` `int` and a `dict` `str` key). That residual stays tracked on #1237.
