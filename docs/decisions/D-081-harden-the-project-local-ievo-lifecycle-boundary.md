## D-081: Harden the project-local iEvo lifecycle boundary

- Status: accepted (strengthens D-077 after adversarial review)
- Context: implementing D-077 exposed additional ways that local shell syntax, conflicting intent fields, filesystem indirection, process interruption, or concurrent lifecycle invocations could make a destructive disable ambiguous. The original symmetric ownership decision remains valid, but its first implementation needs a stricter operational boundary. Arbitrary editors and upstream iEvo processes do not participate in a repository helper's advisory lock, and portable filesystems do not provide an atomic compare-and-swap replacement for a JSON path, so the helper must not claim that it can prevent every uncooperative external-write race.
- Decision: retain D-077's ownership and symmetry, while making `scripts/manage_ievo_hooks.py` fail closed on any supported shell/command form that can lexically reconstruct the managed subtree (including POSIX within-component escapes, unmodeled PowerShell call/control/method expressions, and ambiguous Windows DOS 8.3 components), incomplete or conflicting corrections-only intent before every lifecycle mutation, symlink/reparse/mount/device redirection, non-regular removal targets, traversal errors, or effective-ignore exceptions. Serialize cooperating helper invocations with one crash-released per-worktree OS advisory lock whose unresolved directory components, path entry, and opened descriptor are checked against link/reparse/type redirection; a non-git invocation keeps its fallback inside the validated root rather than shared temporary storage. During disable, snapshot configuration bytes and generated/vendor identities, reject external configuration changes observed immediately before each replacement, reparse written configuration, repeat ignore, identity, and complete ancestry validation before deletion, revalidate ancestry again before every individual unlink/rmdir, unlink only the validated regular files, and remove validated vendor directories deepest-first without `rmtree`. The byte comparison is a best-effort external-change detector, not an atomic CAS against an editor or upstream process that writes after the comparison; callers must not edit, regenerate configuration, or relocate managed filesystem ancestors concurrently with the lifecycle command. A Windows-only Rust integration harness runs the helper and policy-parser regressions inside the required native Windows matrix so reparse, advisory-lock, and DOS-short-name branches are not silently skipped by the macOS discovery run without changing D-062's byte-pinned workflow.
- Alternatives: treat every unknown reference as unrelated (rejected because a false negative can leave a dangling hook); recursively delete the known directory after a shallow check (rejected because late entries and redirected descendants enlarge the destructive scope); persist a PID lock file (rejected because crashes strand stale ownership); claim the advisory lock protects arbitrary tools (rejected because they do not acquire it); add platform-specific filesystem transactions (rejected because they are not portable across the Tier-1 lifecycle clients and still cannot coordinate unmodified external writers).
- Consequences: helper-to-helper operations are serialized and crash recovery needs no stale-lock override. External changes visible at the pre-replacement check abort safely, but an uncooperative writer in the remaining check-to-replace window can still be overwritten; likewise, portable path-based deletion narrows but cannot atomically eliminate a malicious check-to-operation ancestor race. These limitations are explicit and tested behavior must not be described as atomic concurrency protection. Focused tests cover matching/conflicting intent duplicates, shell/path/PowerShell-expression and DOS short-name aliases, ordinary/linked-worktree/root-local fallback lock paths plus redirected gitdir/lock entries, reparse and mount rejection, observed configuration edits, generated-file/vendor/ancestor snapshot drift, nested deepest-first vendor removal, and repeat-safe cleanup.
