## D-249: Lock the CPython dependency closure from the PYCC_PYTHON environment into a per-entry, per-triple pycc.lock

- Status: accepted (rules 1-6 implemented by Part 1 of #1225, [#1241](https://github.com/rotnov/pycc/issues/1241); rule 7 implemented by [#1242](https://github.com/rotnov/pycc/issues/1242); rule 8 implemented by [#1243](https://github.com/rotnov/pycc/issues/1243) for absolute macOS references and Linux, and by [#1259](https://github.com/rotnov/pycc/issues/1259) for macOS relative references)
- Context: [D-128](./D-128-preserve-ordinary-imports-while-making-cpython.md) rule 3 makes the lock schema, the resolver source, the artifact layout and the update command mandatory planning work before an embedded build may bundle a CPython package closure, and names the identities the lock records ("interpreter, package, wheel/native-library, target, version, and integrity"). [D-248](./D-248-embedded-executable-artifact-layout-and-bridge-split.md) rule 8 embeds the standard library without a lock and says #1225 lifts that narrowing. #1225 spans three seams and is delivered as three parts: the lock and its update command (#1241), the build consuming the lock (#1242) and native-library vendoring outside the interpreter prefix (#1243). An accepted decision is insert-only (D-240), so this entry fixes the whole contract in the first part that depends on it. Facts measured on the build host that shaped it: an installed `*.dist-info` does not record the wheel's hash; `pip` lists the installer-written `INSTALLER`, `REQUESTED` and `direct_url.json` in RECORD with hashes, and `direct_url.json` embeds an absolute `file://` URL; an untouched `pip` install has six RECORD mismatches (`pip/_vendor/distlib/*.exe`); Homebrew's `python3.14` has fifteen `*.dist-info` directories and none has a RECORD; `_PYTHON_HOST_PLATFORM` changes `sysconfig.get_platform()` even under `-I`; and a top-level `R.pyc` wins the import over a namespace package `R/`.
- Decision:
  1. **Resolver source.** The resolver reads the installed `*.dist-info` distributions in the `PYCC_PYTHON` interpreter's own `sysconfig` `purelib` and `platlib` directories: the same interpreter an embedded build bundles (default `python3.14`), typically a project venv. pycc parses METADATA and RECORD itself. It never reads user site-packages, a venv's base site-packages (including under `include-system-site-packages = true`), `PYTHONPATH`, or `.pth`-added directories. A site directory that is missing or unreadable when a scan runs is an exit-2 failure naming it. It never uses the network and does no version solving: the installer that populated the environment already did. The environment is read only by `pycc lock`; a build (rule 7) reads only the files the lock names, and re-hashes them.
  2. **Direct roots and closure.**
     - **Direct roots** are the program's CPython-backed import roots that the effective interop policy (D-128 rule 2) admits, minus every standard-library root (`EMBEDDABLE_STDLIB_ROOTS` and `EXCLUDED_STDLIB_ROOTS` in `src/embed/stdlib_roots.rs`).
     - **Distribution index.** A scanned distribution is indexed by the PEP 503-normalized `{name}` part of its `{name}-{version}.dist-info` directory name (the text before the last `-`); a directory name without `-` is not indexed. For a closure member, METADATA `Name` must normalize to the same value, or the lock is refused naming both. A malformed METADATA outside the closure is never read.
     - **Root ownership.** One predicate, `names_root(path, R)`, decides both ownership and coverage: a `/`-separated path whose first component is `R` followed by `/`, or which is exactly `R.py`, `R.pyc`, `R.so` or `R.<anything>.so`. A root `R` is owned by every indexed distribution whose RECORD parses and lists a `names_root` path; entries under the distribution's own `.dist-info` or `.data`, and entries with a `__pycache__` or `..` component, do not count. A RECORD-less or unparsable dist-info owns nothing.
     - **On-disk coverage.** For each direct root `R`, every scanned site directory is walked without following symlinks. Every file whose site-relative path satisfies `names_root` and has no `__pycache__` component must equal a *location* recorded by one of `R`'s owners (the owner's site directory joined with the RECORD path, lexically normalized); otherwise the lock is refused, naming the first unrecorded location in sorted order. A symlink met under a direct root is refused. This is what makes skipping unreadable RECORDs safe: a co-owner with no RECORD, or a file dropped in by hand, is caught here.
     - **Transitive closure.** The closure follows `Requires-Dist` from the direct roots' owners, which are entered with no extras. Each environment marker is evaluated against the lock interpreter's PEP 508 marker environment; a requirement is included when its marker holds with `extra = ""` or with `extra` equal to any extra requested of the distribution. Distribution names compare after PEP 503 normalization, extra names after PEP 685 normalization. A distribution outside the closure is never parsed beyond its RECORD's top-level names, so its metadata cannot refuse the lock. Version specifiers are not re-checked: the lock pins the exact installed version, and specifier consistency is the installer's contract.
     - **Fail closed.** Anything the resolver cannot evaluate on a closure edge refuses the lock: marker syntax outside the supported grammar, an unknown marker variable, `===`, an ordering comparison or a version-variable equality whose operand is not a plain release version (a pre-, post-, dev or local version such as `3.8.0rc1`, or a `.*` suffix).
     - **No direct roots.** When the program has no direct root, the site directories are not scanned.
  3. **Refusals.** Each is an exit-2 environment failure whose message names the distribution, the file or the requirement: a direct root no distribution owns; a direct root whose on-disk files its owners' RECORDs do not cover; a closure requirement whose marker holds but whose distribution is not installed as a `*.dist-info` (an `.egg-info` install counts as not installed); a closure member with a missing or unparsable METADATA or RECORD (the message suggests building from a venv, since distribution- and Homebrew-managed site-packages often have no RECORD); a closure member that is an editable install (`direct_url.json` has `dir_info.editable == true`; `serde_json` becomes a normal dependency of the `pycc` package to read it, the way D-094 recorded `toml`, and it was already in `Cargo.lock`); a closure member whose RECORD installs a top-level `*.pth` file, because the launcher never processes `.pth` files (this also catches setuptools- and hatch-style editable installs); a payload violation under rule 4; and two scanned dist-infos with the same normalized name when that name is reached by the closure or owns a direct root.
  4. **Integrity identity.** The scanned site directories are `purelib` and `platlib` after canonicalization and deduplication (a `lib64 -> lib` venv makes them one directory under two spellings). RECORD paths are `/`-separated and relative to the dist-info's parent, the *site directory*. Each RECORD entry of a locked distribution is classified in this order.
     - **Excluded, not an error:** RECORD itself, `RECORD.jws` and `RECORD.p7s`; the installer-written `<name>.dist-info/{INSTALLER,REQUESTED,direct_url.json}`; any entry with a `__pycache__` component; an entry whose path, resolved lexically against its site directory, lies outside every scanned site directory (such as `../../../bin/pip`, which is not importable).
     - **Refused (fail closed):** an absolute path; a path that resolves into the *other* scanned site directory (a distribution split across purelib and platlib); a path that contains `..` yet resolves back inside its own site directory; a remaining entry with no hash or a non-`sha256` hash; two entries with the same path; a payload file that is a symlink or has a symlinked directory between it and the site directory; a missing file; a digest mismatch (the message names the file and suggests reinstalling); and a payload path claimed by two locked packages, unless both are the same file with the same digest (a pkg_resources-style shared `R/__init__.py`), because the build copies every package into one `closure/`.
     - **Payload:** everything else. Each payload path is a plain relative path with no `..`, safe to join under `closure/`.
     RECORD hashes are `sha256=<urlsafe base64, no padding>`. A package's `tree-sha256` is the sha256 of the concatenation, in byte order of the path, of `"<path>\0<sha256-hex>\n"` for each payload file, where `<path>` is the RECORD path with `/` separators relative to the site directory and `<sha256-hex>` is pycc's own digest of the file's bytes, which must also match RECORD. The payload is exactly the set of files the build copies, so the digest names the bundled bytes and nothing else. An installed distribution carries no wheel hash, so this digest over the installed payload is the lock's package integrity identity in place of D-128 rule 3's "wheel" identity.
  5. **Schema.** `pycc.lock` is TOML, generated and never hand-edited, with a leading comment saying so. A section is keyed by **(entry, triple)**, so one lock serves several entry scripts in one project and several Tier-1 hosts:
     ```toml
     # Generated by `pycc lock`. Do not edit.
     version = 1

     [[target]]
     entry = "app/main.py"
     triple = "aarch64-apple-darwin"
     python = "3.14.7"
     cache-tag = "cpython-314"
     platform = "macosx-11.0-arm64"
     libpython-sha256 = "<hex of the source libpython bytes, as D-248's marker>"
     roots = ["tinypkg"]

     [[target.package]]
     name = "tinypkg"
     version = "1.0"
     site = "purelib"
     files = 3
     tree-sha256 = "<hex>"
     requires = ["tinydep"]
     ```
     - `version = 1`; every reader refuses any other value, naming it.
     - `entry` is the canonical entry path (`std::fs::canonicalize`, as `modules::load` uses) relative to the canonical lock directory, its components joined by `/`; a non-UTF-8 component is an exit-2 refusal. The lock directory is the entry's canonical parent or an ancestor of it, so `entry` never contains `..`, and every spelling of one entry (`./`, `..`, a symlinked directory, APFS letter case) is one key.
     - Sections are sorted by (`entry`, `triple`), packages by `name`, `roots` and `requires` lexically. Duplicate (`entry`, `triple`) pairs, non-Tier-1 triples, unknown fields and an `entry` with an empty, `.` or `..` component (so an absolute one too) are refused on parse.
     - `name` is the PEP 503-normalized distribution name; `version` is METADATA's `Version` verbatim; `files` is the payload file count after rule 4's exclusions; `requires` lists the normalized names of the closure members this package's evaluated `Requires-Dist` edges reach over the union of the extras requested of it, deduplicated, without self-edges and without extras; `site` is `purelib` or `platlib`, the scanned directory holding the `.dist-info` (`purelib` when the two are one directory).
     - The file holds no absolute path and no timestamp; the interpreter's path stays in the bundle marker.
     - `triple` is the host's Tier-1 triple, derived from the host architecture and OS and checked against the Tier-1 table; a non-Tier-1 host is an exit-2 refusal. `pycc lock` on a Windows host is an exit-2 refusal naming #1226, as an embedded build is; `x86_64-pc-windows-msvc` stays a valid key, reserved for #1226.
     - `[[target.native]]` (`name`, `sha256`, `required-by`) is defined and reserved: Part 1 always writes it empty, and rule 8 fills it.
  6. **Update command.** `pycc lock E` derives the (E, host-triple) section, or derives that there is none, and writes it; `--interop-policy`/`--pure` apply as in `check`, and a policy-rejected root is `I0402`, exit 1.
     - **Location.** The lock is `pycc.lock` beside the nearest `pycc.toml` found walking up from E's canonical parent (the walk source-root discovery does), or in E's canonical directory when there is none. The build finds it through the same walk.
     - **Derivation.** A program with no CPython-backed import has no section: `pycc lock E` removes any existing (E, host) section, writes no file if none existed, and never starts the interpreter. A standard-library-only program gets a section with the interpreter fields and `roots = []`, without a site scan; locking one is an explicit opt-in to interpreter pinning. Every other program gets the full section.
     - **Merging.** The new file is `render(replace_target(prune(parse(existing)), E, host, derived))`, where `prune` drops every section whose `entry` no longer names a file under the lock directory. A lock left with no sections is deleted.
     - **Writing.** The file is written to `pycc.lock.tmp-<pid>` in the lock's directory and renamed into place (D-248 rule 3's staging precedent); the temporary file is removed on any failure.
     - **Checking.** `pycc lock --check E` exits 0 if and only if the file's bytes equal what `pycc lock E` would write, where a standard-library-only program with no (E, host) section, or no lock at all, counts as current because the lock is optional there (rule 7). Otherwise it exits 1 with an `error:` line and writes nothing; a section `prune` would drop makes it fail.
     - **A bad existing lock** (unparsable, or `version` other than 1) is exit 2 for both forms, and `lock` never overwrites it.
     - **Upgrades** are an environment change followed by `pycc lock`; there is no separate verb.
     - **Probe environment.** The lock probe removes `_PYTHON_HOST_PLATFORM` and `_PYTHON_SYSCONFIGDATA_NAME` from the interpreter's environment. The build's interpreter comparison (rule 7) uses the same sanitized probe.
  7. **Build contract (implemented by #1242).** A program with no CPython-backed import never reads the lock. A program with at least one direct root needs the (entry, host-triple) section: its `python`, `cache-tag`, `platform` and `libpython-sha256` must equal the embed interpreter's and its `roots` the program's direct roots, or the build fails with exit 2 naming the mismatch and `pycc lock`; there is no fallback to the environment. The build copies each package's payload into `OUT.pycc/closure/<path>` from the lock interpreter's site directory, re-hashing every file; any difference in the file set or a digest is exit 2. The launcher appends `<sidecar>/closure` to `sys.path` after `Py_InitializeFromConfig` (prototyped on CPython 3.14.7: `PyConfig.pythonpath_env` is ignored under the isolated config, and setting `module_search_paths` replaces the standard-library entries). A standard-library-only program needs no lock; when its (entry, host-triple) section exists, the interpreter fields are verified the same way and a non-empty `roots` is stale (exit 2). The `I0403` non-standard-library reason is lifted for a macOS or Linux host with no `--target`.
  8. **Native libraries (implemented by #1243).** Closure Mach-O images go through D-248 rule 5's fail-closed classification, extended so an `@loader_path`/`@rpath` reference resolving inside the same distribution's payload is kept; a dependency outside the prefix, the system directories and the payload is refused (by #1242), naming #1243. #1243 vendors such libraries into `OUT.pycc/lib/`, records each in `[[target.native]]` with its sha256, and adds the Linux ELF scan D-248 NEG-002 lacks.
- Alternatives: a wheelhouse directory of `.whl` files (rejected: it needs a wheel installer and a version solver, and no offline wheel source is guaranteed); delegating to `uv` or `pip` (rejected: a network and tool dependency, nondeterministic across tool versions); per-file entries in the lock (rejected: numpy-sized distributions carry thousands of files, and the tree digest carries the same integrity); trusting RECORD hashes without re-hashing (rejected: they do not detect post-install edits); `importlib.metadata.packages_distributions()` in a probe (rejected: it walks `sys.path` rather than the chosen site directories, and its egg-info handling depends on private attributes); a mandatory lock for standard-library-only programs (rejected: it breaks #1223's zero-configuration build); a per-machine lock without a triple (rejected: a committed lock must serve every Tier-1 host a team builds on); sections keyed by triple alone with `roots` equal to the program's (rejected: two entry scripts under one `pycc.toml` would overwrite each other's section); triple-only sections holding the union of roots (rejected: a section would depend on which `pycc lock` runs came first, locks would only grow, and `--check` could not detect a removed import); locking only the manifest's `project.entry` (rejected: no other script in the project could build with a third-party root, and a program with no manifest would stay unsolved).
- Consequences:
  - **POS-001:** the closure an embedded build will carry is reviewable, committed, byte-stable across hosts and verifiable offline with `pycc lock --check`.
  - **POS-002:** one lock file serves several entry scripts and every Tier-1 host a team builds on, and a section is a pure function of (entry, environment, triple).
  - **NEG-001:** the lock is only as reproducible as its environment: two machines agree when they install the same distributions into the same interpreter build, and `libpython-sha256` makes a python-build-standalone interpreter and a python.org one different lock targets (D-128 NEG-002 intends this; the error names the differing field).
  - **NEG-002:** a RECORD-mismatched closure member (measured: pip's `distlib/*.exe`) cannot be locked until it is reinstalled.
  - **NEG-003:** files a wheel installs outside the site directory (`.data/scripts`, `.data/data`, `.data/headers`) are excluded, so a package that reads them at run time will not find them in the bundle.
  - **NEG-004:** the closure follows `Requires-Dist` exactly; a distribution that imports something it does not declare locks cleanly and fails at run time with `ModuleNotFoundError`, a defect in its metadata rather than in pycc.
  - **NEG-005:** the installer-file exclusions were measured with `pip` only; an installer that lists other generated files in RECORD makes the tree digest installer-dependent until a dated amendment extends the list.
- Amendment (2026-09-23, [#1242](https://github.com/rotnov/pycc/issues/1242)): rule 7 is implemented, and this decision gains the following statements about it. (a) *Order*: an embedded build runs the lock checks that need no interpreter first (lock present, parseable, a section for (entry, triple), no `[[target.native]]`, roots equal to the program's direct non-stdlib roots), then probes the interpreter, then compares `python`, `cache-tag` and `platform`, then plans and copies the payload; a missing lock is therefore reported before any interpreter is spawned. A malformed lock is exit 2, like every other lock refusal. The host triple is computed only when a lock is needed (the program has a non-stdlib root) or present; a standard-library-only program with no `pycc.lock` does no lock work. (b) *Payload source*: each locked distribution's payload is read from the RECORD in the recorded `site`, classified by the same shared classifier `pycc lock` uses (without re-hashing at plan time), after METADATA's `Version` is checked against the lock. Rule 1 is clarified accordingly: the build reads the recorded site's listing, the locked distributions' METADATA and RECORD, and the payload files, and nothing else. (c) *Digests*: every payload file is hashed on the bytes actually copied, before any Mach-O relocation, and checked against its RECORD digest and, per distribution, against the locked `files` and `tree-sha256`; a path two distributions share counts for every claimant, as in the lock, and two distributions that install one path with different contents are refused. The bundled libpython's bytes are checked against `libpython-sha256`, for a standard-library-only program with a matching section too. (d) *Copy*: a destination is created with create-new semantics, so two payload paths that differ only in case are refused (exit 2) on a case-insensitive file system rather than overwriting each other; payload permission bits are kept, with owner-write added for relocation. (e) *Layout*: `closure/` and the launcher's `sys.path` append exist only when the section lists at least one package. (f) *macOS closure images*: each copied Mach-O image's install name and dependencies are classified -- a system library, the bundled libpython, an `@loader_path`/`@rpath` reference that resolves inside the image's own payload, or anything else -- and `@rpath` is resolved in dyld order over the image's `LC_RPATH` entries, where a non-`@loader_path` candidate that precedes the payload match is refused rather than skipped, because dyld would load it first. An absolute dependency inside the interpreter prefix is vendored into `lib/`, as D-248 rule 5 vendors a standard-library image's; any other dependency outside the payload (an absolute path outside the prefix and the system directories, or an `@rpath`/`@loader_path` reference that does not resolve inside the image's own payload) is refused with a message naming #1243, and a non-empty `[[target.native]]` section is exit 2 until #1243 delivers rule 8.
- Amendment (2026-09-24, [#1243](https://github.com/rotnov/pycc/issues/1243)): rule 8 is implemented, and this decision gains the following statements about it. (a) *What a native is*: a library a closure image depends on, directly or through another native, that resolves outside the system library directories and the interpreter's canonical `sys.base_prefix` and is not the source libpython. Its entry records the name it takes in `OUT.pycc/lib/` (the file name on macOS; the `DT_NEEDED` name on Linux), the sha256 of the source bytes, and the sorted distributions that reach it. (b) *One derivation*: `pycc lock` and the embedded build run the same derivation over the same payload files (after rule 7's checks). The build compares its result with the section by name and refuses any difference as a stale lock naming `pycc lock`, before it writes anything. It then refuses a native whose bytes changed between that derivation and the copy. This replaces amendment (f)'s refusal of a non-empty `[[target.native]]`. (c) *macOS*: the derivation follows absolute install names only. The relocation classifies an absolute dependency outside the prefix and the system directories as a native, copies it into `lib/` with an `@rpath` id, rewrites every reference to it, and walks its own dependencies. A native the relocation reaches that the section does not list is refused as stale. Relative references outside an image's own payload stay refused, now naming [#1259](https://github.com/rotnov/pycc/issues/1259) (Part 4 of #1225). (d) *Linux*: each `DT_NEEDED` resolves as `ld.so` would on the build host: `DT_RPATH` only without `DT_RUNPATH`, then `DT_RUNPATH` with `$ORIGIN` expanded from the image's source directory, then the `ldconfig -p` cache, then the default directories, accepting only an ELF64 little-endian image of the requester's machine. A dependency that resolves nowhere is left to the target's loader when the image that needs it is loaded on import (a closure image or a `lib-dynload` extension), and refused when that image is one the build copies into `lib/`, because the executable loads those at start-up. A closure image's dependency that resolves through `$ORIGIN` to another image of the closure's payload (any distribution's) is kept, since the payload is copied with its layout intact. The build copies every prefix library and every native into `lib/` and links each into the executable by name (`--no-as-needed -l:<name>`), so the loader finds it already loaded by its `DT_SONAME`. Therefore a copied library's `DT_SONAME` must equal the name it is needed by. Refused, with exit 2: a `DT_NEEDED` given as a path that would need copying; a closure program image that needs a copied library; a copied library whose name is also the `DT_NEEDED` of a dependency kept on the system (it would answer that one too); and a dependency on the source libpython under a name other than the bundled one. On both platforms two libraries that need one `lib/` name, compared case-folded, or a native named like the bundled libpython, are refused. (e) *Deviation from the plan*: on Linux, `pycc lock` walks the closure's images only, as macOS does. The build additionally walks libpython and the copied `lib-dynload` extensions, which contribute prefix libraries and refusals (D-248 rule 5 now applies on Linux too) but never natives. So a lock never depends on the interpreter's own images. A consequence on macOS: the derivation claims `lib/` names for natives only, not for libraries vendored from the prefix, so a native whose name collides with a prefix library the build vendors is refused by the build (exit 2, naming both), not by `pycc lock`; the Linux walk claims both kinds for closure images at lock time. Rule 1 and amendment (b) of 2026-09-23 are widened accordingly: a section with `[[target.native]]` entries also makes the build read what the derivation resolves natives through (the images' search paths, the `ldconfig -p` cache, the system directories, and each native at the path it resolves to), since an entry records a native's name and digest but not its path. Because the executable links every copied library at start-up, their symbols join the process's global scope before any extension is imported; that is broader than CPython, which loads an extension's libraries only on import with local scope, and a symbol clash between two copied libraries surfaces at start-up rather than at import.
- Amendment (2026-09-24, [#1286](https://github.com/rotnov/pycc/issues/1286)): #1226 is delivered in two parts. Part 1 (#1286, [D-253](./D-253-windows-embedded-executable-a-stub-out-loading-a.md)) embeds standard-library roots on a Windows host with no lock; `pycc lock` there stays an exit-2 refusal, now naming [#1287](https://github.com/rotnov/pycc/issues/1287), and an embedded Windows build refuses a `pycc.lock` section at exit 2. The `x86_64-pc-windows-msvc` key rule 5 reserves for #1226 is delivered by Part 2, #1287.
- Amendment (2026-09-24, [#1259](https://github.com/rotnov/pycc/issues/1259)): rule 8 on macOS now covers relative references, and this decision gains the following statements about it; amendment (c) of 2026-09-24's "Relative references outside an image's own payload stay refused, now naming #1259" is superseded. (a) *Resolution scope*: every dependency of a closure image or a native, absolute or relative, is resolved on the build host from the image's canonical source directory (for `@loader_path`) and the image's own `LC_RPATH` entries only (for `@rpath`, in order); the rpath stack of whatever loads the image is not consulted. A system-directory candidate that is not on disk counts as found when the dyld shared cache contains it. (b) *Classification*, first match wins: the image's own id or an absolute system library is kept; the interpreter's libpython, by spelling and then by resolved path, is rewritten to the bundled one; a file of any locked distribution's payload is kept or rebound (the per-distribution keep of 2026-09-23 amendment (f) becomes per-closure, since `closure/` keeps every payload file's site-relative layout); a relatively named system library is rebound to its absolute path; a file under a scanned site directory or `<stdlib>/site-packages` is a native; a file under the canonical prefix is vendored as D-248 rule 5 vendors it; anything else is a native. The derivation and the relocation share this classification, and it now applies to absolute references too: an absolute install name that points at a locked payload file is rebound to its closure copy rather than recorded as a native, and a site-directory file inside the prefix (a non-venv interpreter's site-packages) is a native rather than an unrecorded prefix library. On Linux the site-directory arm, for closure images and natives, precedes both the system-directory arm and the prefix arm, so a distribution Python's site directory under `/usr/lib` still yields natives; only a closure image's `$ORIGIN` payload match is kept ahead of it. A payload file reached other than through `$ORIGIN` is a native copy there, since Linux has no rebind: as before when its site directory lies outside the prefix and the system directories, and now also when it lies under the prefix (formerly an unrecorded prefix copy) or under a system directory (formerly kept). (c) *Rule K (keep as spelled)*: a closure image's relative reference is left unchanged only when it resolves to a locked payload file, every candidate up to and including the match is `@loader_path`-relative without climbing above the site directory at any step of its spelling (one that leaves the site directory and comes back in is rebound, since `closure/` replaces that directory's name), and no earlier candidate's site-relative path is a locked payload path (with split purelib/platlib, `closure/` would hold that earlier file and dyld would load it first). A native's relative reference is never kept as spelled. (d) *Rebind*: every other payload match is rewritten with `install_name_tool -change` to an explicit `@loader_path/...` path from the image's sidecar location to the target's, so the shipped image no longer depends on `LC_RPATH` for it. The one #1242 keep-case that changes: an earlier `@loader_path` candidate that hits an unlocked file on the host is now what the image depends on (it is what the host loads), so that file is a native. (e) *Refusals*, exit 2, naming the image, the distributions that reach it, the reference and the reason; these are normative, not deferred work: R1 an `@executable_path` reference, or an `@executable_path` `LC_RPATH` entry the search reaches before a match (an entry after the match is never evaluated), because it resolves against the program that loads the image, which in the bundle is the pycc executable; R2 a reference that resolves nowhere from the image's own directory and `LC_RPATH` entries, because it could then only resolve through a loader's rpath stack, which differs between the host and the bundle; R3 any other form, neither absolute nor `@rpath`/`@loader_path`/`@executable_path` (a bare relative name included), as a reference or as an `LC_RPATH` entry the search reaches. The derivation never refuses, so `pycc lock` succeeds for a closure the build refuses, as before.
