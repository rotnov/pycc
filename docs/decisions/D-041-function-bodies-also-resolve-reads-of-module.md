## D-041: Function bodies also resolve reads of module-level global variables

- Status: accepted (PR-4 Task 9 follow-up, `pycc_types`; D-055 supersedes the `UnboundLocalError` deferral recorded below) -- corrects a factually wrong claim in D-040's own "Alternatives" section, does not merely extend it
- Context: D-040's "Alternatives" paragraph rejected threading module-level bindings into function bodies, reasoning "Python functions don't see their caller's or the module's locals without `global`/`nonlocal`." That statement conflates two different things: a *caller's* locals (correctly never visible to a callee -- Python has no dynamic scoping) and the *module's* globals (visible for *reading* in any function with no declaration needed at all; `global`/`nonlocal` is only required to *rebind* a name from inside a nested scope, not to read one). Verified directly against the built `pycc` binary: `x = 5` at module level followed by `def f() -> int:\n    return x` -- ordinary, extremely common Python (any module-level constant used inside any function has this exact shape) -- was rejected with `T0021: name \`x\` is not defined`, the same class of defect D-040 itself had just fixed for sibling function calls. The root cause was identical in kind: `check_function_in`'s scope (then called `child_for_function`) reset `bindings` to an empty map, discarding every top-level assignment the module-level `env` had already accumulated.
- Decision: `Environment` gains `#[derive(Clone)]` and the dedicated `child_for_function` helper is removed in favor of a plain `module_env.clone()` -- there is no longer any field that should be reset when entering a function body, since both the function registry (D-040) and the global-variable bindings (this decision) are meant to carry over in full; only the function's own subsequent `bind` calls (its parameters, then any local assignments in its body) mutate the *clone*, never the original module `env`, so nothing leaks back out or across sibling function checks. `check()` is restructured from one interleaved pass into three: (1) register every function signature (D-039, unchanged), (2) check every `HirItem::TopLevelStmt` in source order, growing `env`'s bindings as module-level assignments are encountered -- preserving real top-to-bottom evaluation order for top-level code, so a genuine top-level forward reference to a not-yet-assigned name is still an error -- then (3) check every `HirItem::Function`'s body against a clone of `env` as it stands once *all* top-level statements have been processed, regardless of whether that function's own `def` appears before or after the global it reads. Pass 3's "regardless of position" rule mirrors D-039's own justification for function signatures: real Python only evaluates a function body when the function is *called*, and by the time any call machinery could plausibly run, the module has typically already finished executing top to bottom.
- Alternatives: interleave global-registration with function-body-checking in a single pass, exposing only globals whose `Assign` textually precedes the function's `def` (rejected -- weaker than real Python, which has no such positional restriction for a *called* function, and it would still incorrectly reject the "def appears before the global" direction, i.e. exactly `a_function_can_read_a_module_level_global_defined_after_it`); model Python's actual `UnboundLocalError` rule (a name assigned anywhere in a function body, without `global`, is local for the *entire* function scope, even before the assignment) precisely (rejected as speculative scope for this fix -- no fixture or planned v0.1 acceptance criterion needs it, and function-local `Assign` already correctly shadows a same-named global via ordinary last-write-wins `HashMap` semantics on the cloned, independent copy, which is all current tests require).
- Consequences: a function body can read any module-level global regardless of source-code order, matching real Python semantics for the common "module-level constant used inside a function" pattern. A function parameter (or a function-local `Assign`) of the same name still correctly shadows a same-named global, verified by `a_function_parameter_shadows_a_module_level_global_of_the_same_name`. New regression tests `a_function_can_read_a_module_level_global_defined_before_it` and `a_function_can_read_a_module_level_global_defined_after_it` cover both directions. Real Python's `UnboundLocalError` nuance (assigning to a name anywhere in a function body makes it local for the whole function, retroactively) is *not* modeled -- pycc is currently more permissive than CPython here; revisit if a fixture ever needs that exact error.
