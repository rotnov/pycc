## D-134: PR-13 thin slice — one type parameter, one concrete scalar per call site, every other generic shape gets a clean diagnostic

- Status: accepted
- Context: matching PR-10/PR-11/PR-12's own established pattern (D-105 `list[int]` only, D-122 `dict[str,int]`/`set[int]` only, D-116 `tuple[int|bool|float, ...]` only), PR-13 needs its own scope cut for which generic-function shapes reach real codegen versus which get a diagnostic. `pycc_types`' signature-inference solver is scalar-only by construction (D-116 point 4's correction note, reconfirmed unchanged as of this ADR — no PR between PR-11b and PR-13 touched it), which bounds what a type parameter can be substituted with from real, unannotated call sites regardless of `Ty::Param`'s own generality (D-133).
- Decision: v0.2 ships real codegen for a generic function with **exactly one type parameter** (`def f[T](...) -> ...`, any number of parameters/return positions referencing that same single `T`), called from **any number of call sites**, where **each call site's argument used to resolve `T` is one of `Ty::Int`/`Ty::Float`/`Ty::Bool`/`Ty::Str`** (matching the solver's existing scalar-only reach) — each call site is monomorphized independently by substituting `Ty::Param("T") -> <that call site's concrete Ty>` (D-133) and lowering a specialized copy of the function body through the existing `pycc_mir`/`pycc_codegen` pipeline exactly as a non-generic function would, reusing D-105's monomorphization machinery (specialized-copy-per-instantiation, not a single polymorphic codegen path — matching this compiler's existing container monomorphization model, not a vtable). Two or more distinct concrete types instantiated at different call sites for the same generic function are both allowed and both reach codegen (this is what "monomorphization" means — `f(1)` and `f("x")` compile to two independent specialized function bodies, mirroring how `list[int]` and a hypothetical `list[str]` would be two independent instantiations if the latter reached codegen). Rejected before codegen with new diagnostic `T0042`: two or more type parameters (`def f[T, U](...)`); a type parameter used inside a container position (`def f[T](x: list[T])`, since D-105 already restricted container element types independently of genericity and stacking both gaps is out of scope); a call site whose argument type used to resolve `T` is not one of the four scalars above (e.g. passing a `list[int]` value where `T` is inferred); a call site where `T`'s occurrences in the signature are inconsistent (e.g. `def f[T](x: T, y: T) -> T` called as `f(1, "a")`, resolved via the same "every occurrence of `T` must substitute to the same concrete `Ty`" check the symbolic pass in D-133 already performs). Each rejection case gets its own snapshot test under `T0042`, matching `docs/DIAGNOSTICS.md`'s existing per-code quality bar (mirroring `T0034`'s own multi-case snapshot coverage, not a single combined test).
- Alternatives: ship zero call-site restriction and let the solver's own existing scalar-only limitation silently produce whatever diagnostic already exists for "type of this expression could not be determined" (rejected — that path was designed for ordinary type-inference failures, not deliberately-scoped generic instantiation limits, and would produce a confusing, non-actionable message for a case this PR can name precisely, breaking the project's established "clean diagnostic, not a leaked internal panic" convention from D-105 onward); support multiple type parameters from the start since `Ty::Param(Box<String>)` already generalizes to any number of distinct names (rejected — nothing in the design doc or delivery plan requires it for v0.2's conformance target, and D-105's own "exactly one concrete instantiation" precedent is the established v0.2-wide pattern this ADR is following, not inventing); restrict to exactly one call site per generic function (rejected — monomorphization's entire value is compiling the same generic body at multiple call sites with different concrete types, and the constraint solver's scalar-only limitation already bounds the real risk surface without needing this additional, artificial restriction).
- Consequences: `pycc_types` gains a symbolic type-checking pass for a generic function body (a shape gate rejecting more than one type parameter or a container-position occurrence, followed by ordinary body type-checking with `Ty::Param` participating as an opaque, self-consistent `Ty`, D-133) plus a per-call-site substitution step (`Ty::Param("T") -> <concrete Ty>` applied to the signature and body, producing the mangled specialization). There is deliberately **no** re-run of ordinary type-checking over the substituted body, and none is needed: a generic function's body is checked once symbolically, and because the shape gate admits only a single type parameter in bare, non-container positions, substituting one concrete scalar for every occurrence preserves well-typedness by construction. The one case that assumption cannot cover is a generic body calling a generic function — itself (direct recursion) or another generic function (possible indirect/mutual recursion) — since the callee's own specialization is not determined by the enclosing body's symbolic check; that shape is therefore rejected outright with `T0042` in `check_generic_function`, before any specialization is emitted, rather than being accepted by `pycc check` and crashing `pycc build` (PR-13 final review). A generic function's body is checked against the module's ordinary function-signature environment, so calling a *non-generic* sibling function from a generic body is fully supported. `pycc_mir`/`pycc_codegen` require no new generics-aware logic beyond what D-133 already establishes, since every call site's specialized body is an ordinary concrete-`Ty` function by the time it reaches them. `docs/DIAGNOSTICS.md` gains `T0042` with its four named rejection cases. `docs/ROADMAP.md` records multiple type parameters, container-position type parameters, and richer bound/constraint syntax (PEP 696 defaults, `TypeVar` bounds) as explicit v0.2 follow-ups, not silently dropped scope.
