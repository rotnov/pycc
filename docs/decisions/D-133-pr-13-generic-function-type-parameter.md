## D-133: PR-13 generic-function type-parameter representation is a new `Ty::Param(String)` variant, substituted before MIR lowering

- Status: accepted
- Context: D-089 defined `Ty`'s full recursive shape (`crates/pycc_hir/src/lib.rs`, `pub enum Ty { Int, Float, Bool, Str, None, Infer, List(Box<Ty>), Dict(Box<(Ty, Ty)>), Set(Box<Ty>), Tuple(Box<Vec<Ty>>) }`) but explicitly deferred the generic-function type-parameter case (`def f[T](x: T) -> T`) to whichever of PR-10/PR-13 implemented it first (design doc §4). Verified at PR-13 task-start (2026-08-03, commit `a2527a6`): PR-10 did not add it — `crates/pycc_hir/src/lib.rs`'s `lower_function` still contains an explicit `if def.type_params.is_some() { return Err(unsupported("generic function type parameters are not supported yet", def.range)); }` (the same shape as every other deliberately-unimplemented-syntax rejection in this compiler, e.g. `is_async`/`decorator_list`). No `Ty::Var`/`Ty::Param`/`TypeVar` construct exists anywhere in `pycc_hir`, `pycc_types`, or `pycc_mir` today. A representation is needed before `pycc_types`' `collect_expr_constraints`/`infer_expr_in` (`crates/pycc_types/src/lib.rs`) can type-check a generic function's body at all, since every expression there is checked against a concrete `Ty`.
- Decision: add `Ty::Param(String)` (the type parameter's source name, e.g. `"T"`) as a new leaf variant alongside `Ty::Infer`, distinct from it: `Ty::Infer` means "not yet resolved, must become concrete before codegen, resolution is compiler-driven unification," while `Ty::Param` means "resolved to whatever concrete `Ty` this specific call site substitutes for it, resolution is call-site-driven substitution, and the *same* function body type-checks once per instantiation." A generic function's parameter/return/body `Ty`s are checked once, symbolically, against `Ty::Param` positions (proving internal consistency: every use of `T` in the signature must agree), and then, per D-134, exactly one concrete instantiation per call site is substituted (`Ty::Param(name) -> concrete_ty`, a plain recursive tree rewrite, no unification) before that call site's specialized copy of the function reaches `pycc_mir`. `pycc_mir` and `pycc_codegen` never see `Ty::Param` — by the time MIR lowering runs, substitution has already produced an ordinary concrete `Ty` tree, so no new `MirExpr`/codegen case is needed for genericity itself (only for whatever concrete `Ty` the substitution produced, which is already handled).
- Alternatives: reuse `Ty::Infer` for type parameters too (rejected — conflates "the checker hasn't finished unifying this yet" with "this is deliberately symbolic and only becomes concrete at a call site"; the existing invariant that `Ty::Infer` must never leak into MIR, guarded by dedicated pre-MIR assertions per `crates/pycc_types/src/lib.rs`'s own comments near line 2787, would then also have to hold for every generic-function body pre-instantiation, doubling what that invariant means without a comment or type-level distinction saying so); a full unification-variable/substitution-map (`HashMap<TypeVarId, Ty>`) infrastructure, matching Rust's or a general Hindley-Milner solver's own generics model (rejected as disproportionate to PR-13's own scope — D-134 restricts this PR to a single type parameter per function with a call-site-known concrete argument, so full multi-variable unification buys nothing not already available from a name-keyed substitution and would be net-new machinery unlikely to be exercised end-to-end before v0.3's class-generics work, if ever, revisits this); representing a generic function as a distinct `HirItem` variant carrying an uninterpreted body (rejected — every other `Ty`-shaped consumer downstream, diagnostics, `to_str`-style debug rendering, existing `Ty` equality/hash derives, would need a second parallel code path instead of participating in `Ty`'s existing recursive matching for free).
- Consequences: `Ty`'s `derive(Debug, Clone, PartialEq, Eq)` set already covers a new unit-like `String`-carrying variant with no additional derive work. Every existing exhaustive `match ty { ... }` over `Ty` across `pycc_types`/`pycc_mir`/`pycc_codegen` gains one new arm requiring an explicit decision (typically: type-checking accepts it symbolically inside a generic function body, but `pycc_mir` lowering and `pycc_codegen` treat an unsubstituted `Ty::Param` reaching them as an internal-invariant panic, mirroring how `Ty::Infer` reaching MIR is already treated as an invariant violation, not a diagnosable user error). `size_of::<Ty>()` must be re-measured after adding this variant against D-109's 16-byte ceiling and the `frontend-perf-gate`'s 7% (D-114) threshold; a boxed variant is no larger than `Tuple`'s existing `Box<Vec<Ty>>` pointer shape, so the required concrete shape is `Ty::Param(Box<String>)`, not `Ty::Param(String)`'s naive two-word form. Verified empirically at PR-13 Task 1 (2026-08-04): `Box<str>` was tried first and measured `size_of::<Ty>() == 24`, breaking the D-109 ceiling, because `str` is unsized -- `Box<str>` is itself a fat (16-byte, data-pointer-plus-length) pointer, which broke the niche-filling layout uniformity the other thin-pointer variants rely on (the same phenomenon this ADR's sibling `Tuple`/`Box<[Ty]>` history in D-089/D-109 already documents). `Box<String>` is a single thin (8-byte) pointer to a further heap-indirected `String` and measured `size_of::<Ty>() == 16`, matching `Tuple`'s shape -- this is the shape actually shipped.
