## D-047: The frontend performance gate's early-start timeline is overridden; it moves to PR-6

- Status: accepted (timing supersession of D-042/D-044's deliberate "starting immediately, not deferred to a single check in PR-6" schedule from `docs/DELIVERY_PLAN.md`'s Performance gate section, resolving tracked audit issue #12; D-042/D-044/D-046's design and rationale are left intact and unedited)
- Context: `docs/DELIVERY_PLAN.md` explicitly chose to start the frontend performance gate in PR-4 rather than wait for PR-6, specifically to close audit issue #12 ("missing early performance gate"). PR-4's branch accordingly built its own `frontend-perf-measure`/`frontend-perf-gate` CI jobs (D-042, D-044, D-046) to honor that schedule. Merging `origin/main` into this branch surfaced a structural trust-anchor validator (`TRUSTED_PERF_LIFECYCLE_STEPS`/`validate_perf_gate_baseline_lifecycle` in `scripts/check_roadmap_evidence.rb`) that a concurrent, independent automated contributor added for a `frontend-perf-gate` job shape incompatible with this branch's own D-046 design, and whose whole-file SHA-256 allowlist (`TIER1_CI_WORKFLOW_SHA256S`, audited from the base ref under `pull_request_target`, immune to in-branch edits) had already moved on from this branch's earlier staged digest. Reconciling the two designs would have required a third staged-digest round trip against a validator a second actor keeps evolving independently -- two prior reconciliation attempts this same merge already failed to converge. Diff-checking confirmed the *entire* delta between this branch's `.github/workflows/ci.yml` and `origin/main`'s own copy was exactly the frontend-perf-gate job and its two `ci-gate` fan-in lines; nothing else in PR-4's actual deliverable (frontend HIR/types/diagnostics work) touches CI.
- Decision: this is a genuine override of the DELIVERY_PLAN's explicit early-start choice, not a relocation of misplaced work -- accepted anyway because continuing to chase a validator owned and evolving under a different, unpredictable automated actor was actively blocking PR-4's real deliverable with no guarantee of convergence. Revert `.github/workflows/ci.yml` to be byte-identical to `origin/main`'s copy (dropping the `frontend-perf-measure`/`frontend-perf-gate` jobs and their `ci-gate` fan-in entries entirely from this PR), and take `origin/main`'s own `scripts/check_roadmap_evidence.rb`/`scripts/test_check_roadmap_evidence.rb` wholesale rather than reconciling this branch's parallel edits into them. PR-4 merges with zero CI-trust-anchor delta -- its digest is already the currently-allowlisted `b77ab0c1c3bcc69e69d3cb8f08e081f6eae246e7d5d19c9356455db1ff4291d2`, so no staging PR is needed. The performance-gate feature (measurement job, hash-verified gate job, structural lifecycle validator, D-046's cache-scoping fix) is deferred whole to PR-6, re-designed and re-reviewed there against whatever `scripts/check_roadmap_evidence.rb` shape exists on `main` at that time; D-044's "required in `ci-gate`" requirement activates only once it actually lands there.
- Alternatives: do a third staged two-PR digest update to reconcile this branch's D-046 shape with the newer structural validator (rejected -- the validator is owned and evolving under a concurrent, independent contributor per the user's "an automated process, continue synchronizing" instruction, and forcing it to match this branch's preferred shape mid-merge is an unsynchronized fight, not synchronization; a third round with no guarantee the target stays stable is the thrashing this entry exists to stop); unilaterally rewrite the validator in this branch to accept D-046's guard (rejected -- `audit` checks the validator out from the base ref, so an in-branch rewrite has zero effect on this PR's own gate and only creates a second, conflicting definition of the same trust anchor); keep chasing convergence with further staged-digest rounds (rejected -- two rounds already failed to converge against a moving target, with no evidence a third would).
- Consequences: PR-5 loses the early, continuous per-PR frontend-regression detection that DELIVERY_PLAN.md's Performance gate section deliberately required starting at PR-4 -- a real, accepted regression-detection gap during PR-5, not merely a documentation update. `docs/DELIVERY_PLAN.md`'s Performance gate section, and `docs/ROADMAP.md`'s "Quality gates" and "Repository governance" rows, are corrected in this same change to stop claiming the frontend-perf-gate is enforced in `ci-gate` today. No v0.1 acceptance-checklist item cites frontend-perf-gate evidence, so nothing in the checked acceptance criteria becomes false. D-042/D-044/D-046 remain accepted as written; only *when* D-044's requirement takes effect changes.
