## D-168: Pages visit measurement capability contract: no analytics today, schema and privacy boundary for future activation
- Status: accepted
- Context: pycc has three non-overlapping discovery signals — Google Search Console (Google Search clicks/impressions), GitHub repository traffic (repository views/clones), and direct-provider engine-qualified visibility (SERP/answer citations). None of them measures visits to the GitHub Pages site from Yandex, DuckDuckGo, Perplexity, ChatGPT, other answer engines, ordinary referrals, or direct navigation. Issue #208 documented this gap: the five-page production artifact has no pageview/visit analytics integration, and the project has no owner-facing Pages request log. This leaves a material measurement gap — the project cannot tell whether a Yandex rank or an answer-engine citation produced a visit, which page became the entry page, or whether a visitor continued to GitHub. The gap also creates a reporting risk: a future monitor can incorrectly call GitHub repository views "website visits" or Search Console clicks "all organic traffic."
- Decision: Establish a measurement capability contract now, without adding any analytics script to the site. The contract defines the minimum fields, source-class vocabulary, collection-status vocabulary, data-minimization boundary, separation rules, and primary conversion (a click from a canonical Pages page to `https://github.com/rotnov/pycc`). The structured artifact `docs/PAGES_VISIT_OBSERVATIONS.json` is a template with no observations — it preserves the envelope format (`artifact_version`, `provenance`, `observations`, `latest_projection`) compatible with #163/#194/#198 and adds a `measurement_contract` block. The current explicit analytics decision is "keep no site analytics": the site has no project-selected analytics script, cookie, or external beacon, and the roadmap and SEO reports state that non-Google landing visits remain unobservable. A future PR that activates analytics must (a) record a superseding decision that justifies the visitor-data, retention, and external-service policy, (b) add an accurate public privacy/analytics disclosure before or with collection, (c) load the provider script non-blockingly on every canonical HTML page exactly once, (d) keep content and navigation functional when the provider is unavailable or blocked, and (e) establish the activation baseline at deployment time without synthesizing pre-installation history. The validator (`scripts/check_pages_visit_observations.py`) enforces the schema, rejects a non-zeroable collection status (`blocked`, `delayed`, `unauthorized`, `provider_error`, `unknown`) being converted to zero, and rejects prose that conflates repository views with Pages visits, Search Console clicks with all-provider visits, or analytics with a ranking factor.
- Alternatives: (1) Add a privacy-first analytics script (e.g. Cloudflare Web Analytics or Plausible) in this same PR. Rejected because the issue explicitly does not request adding analytics scripts, and a provider/data decision requires owner review of cost, retention, data location, account ownership, API access, script supply chain, and privacy obligations before selection. (2) Leave the gap undocumented. Rejected because a future monitor can silently mislabel repository views as website visits or Search Console clicks as all-provider visits, and the project would have no contract to reject that conflation. (3) Use GitHub's host-level security logging as a visit analytics surface. Rejected because GitHub documents Pages as static hosting and its security logging is not owner-facing visit/referrer analytics.
- Consequences: The measurement gap is now explicit and contract-bound. The template artifact and validator are ready for future activation without a schema redesign. The "keep no site analytics" decision means non-Google landing visits remain unobservable, and the roadmap and SEO reports must state this. Adding analytics later requires a superseding ADR, a public privacy disclosure, and a non-blocking integration that preserves content and navigation when the provider is unavailable. The data-minimization boundary forbids names, email/account identifiers, form contents, full IP addresses, full user agents, cookies, fingerprints, persistent cross-site IDs, session replay, arbitrary query strings/fragments, and raw search queries unless a separately accepted decision justifies them.
