## D-097: Verify pycc/CPython output equality before accepting the nbody speedup ratio

- Status: superseded by D-098
- Context: PR #188's own automated review (`chatgpt-codex-connector`) flagged that `nbody_release_binary_meets_required_speedup_over_cpython` (D-094's harness) only ever checked `time_command`'s `Command::status().success()` for both sides -- never that pycc's compiled binary and the CPython oracle actually computed the same values. A miscompile that runs successfully but produces wrong output (skips work, computes garbage, or silently truncates) could therefore still pass this gate purely by being fast, which is exactly the "measurement with near-zero signal for what it's meant to measure" failure mode D-093 already logged once for *performance* signal -- here the same shape of gap exists for *correctness* signal. `tests/conformance.rs` (D-078/D-085) already solves this exact problem for its own two fixtures (byte-for-byte `pycc` vs. CPython 3.14.6 comparison, with `strip_windows_newline_translation` normalizing CPython's Windows-only `\r\n` stdio translation, D-082), but nbody was never one of its fixtures, so nothing in the repo enforced output equality for it -- D-093's own "Re-verified byte-for-byte identical output... at the new count" claim was a one-off manual check during that investigation, not a standing, test-enforced guarantee.
- Decision: add one untimed correctness check to the existing test, immediately after the `--release` build and before the `RUNS = 5` timed loops: run the compiled pycc binary once via `Command::output()`, run the CPython oracle once via `Command::output()`, and `assert_eq!` pycc's stdout against the oracle's stdout after applying `strip_windows_newline_translation` (duplicated from `tests/conformance.rs`, matching this file's own established no-shared-module convention, see `oracle_python_bin`'s doc comment) to the oracle's side. Deliberately does *not* touch `time_command` or either `(0..RUNS)` timed loop -- those must stay exactly the shape they already are, since D-095's 12x and D-096's 15x floors were both measured against that exact timed-loop shape (`Command::status()`, no output capture); adding output capture to every timed launch would change what is actually being measured and would retroactively put those two gate floors on an unverified basis. Exact byte comparison, not a numeric tolerance: D-093's own manual check already established byte-for-byte equality at 525000 iterations for both debug and `--release` builds, so a tolerance would weaken the check with no evidence it is needed.
- Alternatives: capture output as part of the existing timed runs, reusing one of the five timed launches per side instead of adding a sixth untimed one (rejected -- would need `time_command` itself to grow an output-capturing variant or a parallel code path, adding branching to the one piece of this test whose current exact shape underwrites two already-committed gate floors, for a check that is naturally a one-time property of the build, not a per-run one). Assert on parsed/rounded numeric equality within a small epsilon instead of exact bytes (rejected -- no evidence this fixture's floating-point output is unstable across runs or builds; D-093's own repeated measurements were exact, and a tolerance here would be inventing slack this benchmark has never demonstrated needing). Reuse `tests/conformance.rs`'s `run_conformance_fixture` directly instead of duplicating its comparison logic (rejected -- that helper builds via a fixed `-o` path scheme and always runs `pycc build` without `--release`, neither of which fits this test's existing `--release`, fixed-temp-path build already in place; duplicating the ~10-line comparison function is smaller and more direct than reshaping that helper to take a release flag and a caller-supplied path).
- Consequences: a future miscompile that regresses nbody's actual computed output (not just its timing) now fails this test immediately, with a clear "disagree on tests/fixtures/nbody.py's output" message, rather than silently passing on speed alone. Verified locally: `cargo test --test nbody_bench -- --ignored` passes end-to-end on real Apple Silicon hardware with the new check active, reproducing D-093's own recorded byte-for-byte output (`0.008420846407813569 0.003871558303952385 -0.00032661880191911866`) exactly. Adds one build's worth of two extra untimed process launches (~1 second total) to this already-slow `#[ignore]`d test; negligible next to the existing ten timed launches plus the `--release` LLVM build itself.

  Two risks this decision accepts rather than resolves, caught by the pinned reviewer: (1) byte-exact equality between pycc's and CPython's long-precision float output has, per the record, only ever been verified on macOS aarch64 (this task's own local run plus D-093's manual check) -- neither of `tests/conformance.rs`'s two fixtures prints a non-integral float, so nothing before this decision has proven byte-exact float formatting holds across `pycc_rt_float_to_str`/CPython `repr` on the other four Tier-1 targets. This assertion is a new, previously-untested hard gate on all five. If it fails on a leg other than macOS aarch64, that should be investigated first as a possible float-formatting or libm `pow` divergence between targets, not assumed to be a miscompile -- the assertion message's own "a fast but wrong binary must not pass this speedup gate" wording does not distinguish the two causes. (2) The new untimed pycc launch runs the same freshly built binary D-096's own Windows-Defender hypothesis concerns, immediately before the timed loop. If that hypothesis's "scanned once, then cached" branch is the correct one (itself unconfirmed, see `required_nbody_ratio`'s own D-096 doc comment), this pre-launch would now absorb that one-time cost outside the timed measurement -- meaning any future `windows-latest` ratio could shift, favorably, relative to the 17.95x/17.78x/17.61x record D-096 reasoned from, with no corresponding code change to explain it. This does not threaten D-096's 15x floor (a favorable shift only makes passing easier), but a future investigator comparing new `windows-latest` measurements against D-096's own recorded numbers should know this procedural change exists.

  **Update:** D-098 later found this decision's own risk (1) above was real, not merely theoretical -- CI on `windows-latest` refuted the byte-exact comparison at commit `fe24ac7` on the very next run. This does not change this decision's own history (the untimed-check placement, CRLF-stripping approach, and macOS-only verification really were what shipped and passed locally at the time); it replaces only the exact-byte comparison method with a relative-tolerance one, recorded as its own new decision per this file's own edit policy rather than by rewriting this entry.
