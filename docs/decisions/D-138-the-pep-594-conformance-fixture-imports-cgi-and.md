## D-138: the PEP-594 conformance fixture imports `cgi` and asserts its unchanged `C0001` rejection, contrasted with a passing `math`/`sys` fixture

- Status: accepted
- Context: D-088 point 3 reassigned PEP 594 (dead-battery stdlib removals) to PR-14, reasoning that "there is no way to distinguish 'this module was removed' from 'imports aren't supported yet' until real stdlib-module resolution exists" — and D-137 deliberately does not build a dead-battery-specific diagnostic (that distinction stays folded into the ordinary `C0001` "not supported yet" rejection). PEP 594's own text (removed in CPython 3.13: `aifc`, `audioop`, `cgi`, `cgitb`, `chunk`, `crypt`, `imghdr`, `mailcap`, `msilib`, `nis`, `nntplib`, `ossaudiodev`, `pipes`, `sndhdr`, `spwd`, `sunau`, `telnetlib`, `uu`, `xdrlib`) needs a conformance fixture that is meaningfully about import resolution now that resolution is real for at least some modules, per D-088's own reasoning for why this row was blocked until PR-14.
- Decision: the fixture is `tests/fixtures/pep_0594_dead_battery.py`, a two-part file: (1) a top-level `import math` and a call using `math.sqrt`, asserting normal successful compilation and matching CPython's own runtime output byte-for-byte (proving import resolution genuinely works, not merely that rejection is unchanged); (2) a *second*, separately-compiled fixture, `tests/fixtures/pep_0594_dead_battery_rejected.py`, containing only `import cgi` at module level, asserting `pycc check` exits non-zero with diagnostic code `C0001` and a message mentioning `cgi` (proving the removed module is cleanly rejected, not silently accepted or a panic). The conformance test pairs both: `pep_0594_dead_battery_matches_cpython_3_14_6_byte_for_byte` runs fixture (1) through the existing dual-profile (`--debug`/`--release`) byte-for-byte harness exactly like every other `*_matches_cpython_3_14_6_byte_for_byte` test in `tests/conformance.rs`; a second, non-oracle test (`pep_0594_dead_battery_rejected_produces_c0001`, following the existing rejection-test pattern other diagnostics already use, e.g. `T0042`'s per-case snapshot tests) asserts fixture (2)'s diagnostic directly, with no CPython oracle involved (CPython 3.14 itself raises `ModuleNotFoundError` for `import cgi`, a fundamentally different failure shape than pycc's static `C0001`, so no byte-for-byte comparison is meaningful here — the two compilers are asserting different things about the same removed module for different reasons, and conflating them into one oracle-diffed fixture would be misleading).
- Alternatives: a single fixture that both imports `math` and `cgi` in one file (rejected — a single `check` invocation stops at the first unresolvable statement, so this compiles down to "does `cgi` get rejected," the `math` half never actually gets exercised end-to-end in the same run, making the "import resolution genuinely works" half of the claim untested by that file). Oracle-diff `cgi`'s rejection against CPython's own `ModuleNotFoundError` text (rejected, per Context above — different failure kinds, not a meaningful byte-for-byte comparison). Pick a different removed module than `cgi` (rejected as a non-decision — `cgi` is arbitrary among the 19 PEP-594 names; any one works equally well as a "real, once-existed, definitely-not-in-the-two-entry-allowlist" probe, and `cgi` is chosen only because it's PEP 594's own most-cited example).
- Consequences: `docs/PYTHON_STANDARDS.md`'s PEP 594 row flips from unreachable/blocked to a real, dual-fixture-backed pass, contributing to D-088 point 4's revised ≥15-row conformance target. Two new fixture files and two new `tests/conformance.rs` tests are added, one oracle-diffed and one diagnostic-asserting, matching this project's existing split between byte-for-byte conformance tests and dedicated diagnostic-snapshot tests elsewhere in the suite.

- Amendment (2026-09-14, Part 1 of #1026): fixture (2), `tests/fixtures/pep_0594_dead_battery_rejected.py`, is now `import cgi as c` rather than the plain `import cgi` the Decision above specifies, and `pep_0594_dead_battery_rejected_produces_c0001` is otherwise unchanged. The reason is the D-137 amendment of the same date: the plain form now binds an opaque CPython module object, so it no longer reaches `C0001`. The aliased form does (D-137 point 2 leaves aliasing unsupported), so it still asserts this decision's actual property -- a removed stdlib module is cleanly rejected rather than silently treated as a `pycc_std` module. Note that the Context's own observation that "CPython 3.14 itself raises `ModuleNotFoundError` for `import cgi`" has become pycc's behavior for the plain form as well; `tests/issue_1080_foreign_object.rs` asserts that failure shape directly in a hosted `--ext` run. Fixture (1) and the oracle-diffed test are untouched.
- Amendment (2026-09-24, [#1291](https://github.com/rotnov/pycc/issues/1291), Part 1 of #1282): fixture (2) is now `from cgi import escape` rather than `import cgi as c`, because [#1291](https://github.com/rotnov/pycc/issues/1291) makes the aliased form a foreign import too (see the D-137 amendment of the same date), so it no longer reaches `C0001`. The `from` form still does (`from x import name` on a module that is neither a project module nor a `pycc_std` module), so the fixture now pins the `from`-import refusal for a removed stdlib module; it no longer pins a refusal of every spelling. For the spellings that are now foreign imports, the property this decision cares about -- a removed stdlib module is never silently treated as a `pycc_std` module -- is kept by CPython itself: the host raises `ModuleNotFoundError` at module-exec time, exactly as CPython 3.14 does for the same line, and `tests/issue_1291_block_import.rs` and `tests/issue_1080_foreign_object.rs` assert that failure shape in a hosted `--ext` run. Fixture (1) and the oracle-diffed test are untouched.
- Amendment (2026-09-24, [#1278](https://github.com/rotnov/pycc/issues/1278)): fixture (2) is now `from cgi import escape as esc` rather than `from cgi import escape`, because [#1278](https://github.com/rotnov/pycc/issues/1278) makes an unaliased, top-level `from X import a, b` of an undotted foreign module a foreign import too (see the D-137 amendment of the same date), so it no longer reaches `C0001`. The aliased `from` form still does, so the fixture now pins that refusal; the property this decision cares about is kept for the admitted spellings by CPython itself, which raises `ModuleNotFoundError` at module-exec time, and `tests/issue_1278_from_foreign_import.rs` asserts that failure shape for the from form in a hosted `--ext` run. Fixture (1) and the oracle-diffed test are untouched.
