## D-165: Preserve daily GitHub traffic evidence in an immutable artifact
- Status: accepted
- Context: GitHub's Traffic API returns both a rolling 14-day aggregate total and a per-day breakdown for views and clones, plus top-ten referrer and popular-path lists for the same rolling period. The repository's `docs/SEARCH_VISIBILITY.md` ledger preserved only aggregate totals, discarding the daily rows. Because every snapshot covers a moving, overlapping 14-day window, aggregate-only rows cannot answer which calendar day produced a change, whether a later response is new activity or window expiry, whether a large clone burst is automation rather than human discovery, or how to compare two observations without subtracting incompatible rolling totals. Issue #194 identified that the current clone series is automation-heavy and unattributed — the large clone-to-view ratio, hundreds of clone uniques, and PR-heavy popular paths are consistent with CI/agent/automation activity, but the Traffic API cannot identify each actor.
- Decision: Define one machine-readable, append-only GitHub traffic evidence format in `docs/GITHUB_TRAFFIC_OBSERVATIONS.json`, reusing the same sanitized immutable evidence envelope introduced for #163's Search Console artifact (`artifact_version`, `provenance`, `observations`, `latest_projection`). Each observation preserves `observed_at` in UTC, the requested GitHub API version, the data-through date, endpoint totals for views and clones with `count` and `uniques` separate, every returned daily views and clones row, returned popular referrers and popular paths, repository stars/forks/watchers as separate point-in-time counters, and an explicit `collection_status` per section so unavailable or unauthorized data is `unknown`, never zero. Observations are append-only: if GitHub later backfills a previously returned day, a new snapshot is stored and the older response is preserved. Comparisons are derived by matching identical UTC calendar dates across snapshots, never by adding or subtracting aggregate rolling totals. Daily `count` rows reconcile to the endpoint total; daily `uniques` are not additive and the endpoint's rolling `uniques` value remains authoritative. The current clone series is labeled `automation-heavy / unattributed` and is not claimed as SEO lift. `scripts/check_github_traffic_observations.py` (with mutation tests in `scripts/test_check_github_traffic_observations.py`) validates the artifact format, the history table binding, and the prose projection, and rejects forbidden wording that equates clones with humans, visits, clicks, or SEO acquisition. The validator does not require the sum of daily `uniques` to equal the endpoint `uniques`; that would encode the same attribution error into CI.
- Alternatives: Continuing with aggregate-only snapshots was rejected because overlapping 14-day windows cannot be reconciled and the daily evidence needed to interpret a clone burst is discarded. Creating a separate evidence envelope incompatible with the Search Console artifact was rejected because #194 explicitly requires reusing the #163 envelope. Requiring daily `uniques` to sum to the endpoint `uniques` was rejected because the same actor can appear on multiple days and the Traffic API cannot identify actors; summing would manufacture a false precision. Treating clones as human discovery or SEO evidence was rejected because the clone-to-view ratio, PR-heavy paths, and hundreds of clone uniques are consistent with automation, not organic search acquisition.
- Consequences: The artifact preserves daily rows going forward; historical aggregate-only observations are marked `aggregate_only` with empty `daily_rows` so the validator does not reject them for missing data that was never captured. New observations with `daily_and_aggregate` status must have daily `count` sums that equal the endpoint `count`. The validator adds a CI check in `pages.yml` that runs on every pull request touching the traffic artifact or related docs. The artifact does not deanonymize visitors or clone actors, does not treat GitHub Traffic as lifetime analytics, and does not replace Google Search Console query/click evidence.
