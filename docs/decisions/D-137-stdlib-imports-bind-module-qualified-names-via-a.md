## D-137: stdlib imports bind module-qualified names via a per-module HIR import table; every other import form stays a clean `C0001`

- Status: accepted
- Context: `pycc_ast` already parses `Stmt::Import`/`Stmt::ImportFrom` (inherited from the vendored `ruff` parser; confirmed at `crates/pycc_ast/src/lib.rs` around the `stmt_range` match arms for `Stmt::Import`/`Stmt::ImportFrom`), but `pycc_hir::lower_stmt` (`crates/pycc_hir/src/lib.rs:541`) has no arm for either variant today, so `import math` currently falls through to the generic `C0001` "statement kind not supported yet" diagnostic (confirmed empirically, matching D-088 point 2's own finding). D-088 scopes v0.2's import support narrowly to `import math`/`import sys` and `from math import ...`/`from sys import ...` resolving against `pycc_std`'s registry (D-136); every other import shape (a third-party or unregistered stdlib module, a relative import, `import x as y` aliasing, a wildcard `from x import *`) must keep failing cleanly, not silently or by panic.
- Decision:
  1. `pycc_hir::lower_stmt` gains two new arms: `Stmt::Import` and `Stmt::ImportFrom`. Each is checked against a fixed allowlist of exactly two module names, `"math"` and `"sys"` (matching D-136's registry scope). A recognized `import math` binds the single module-level name `math` in the lowering environment as a "module namespace" marker (not a `Ty`-carrying value — `math` itself is never used as an expression on its own, only as the left operand of `math.<attr>` attribute access); a recognized `from math import sqrt, pi` binds each named symbol directly into the current scope as an alias for `math.sqrt`/`math.pi` respectively, validated against `pycc_std`'s registry at this point (an unregistered name, e.g. `from math import isnan`, is rejected immediately with a new diagnostic `C0002` — "stdlib symbol not supported yet" — distinguishing "we recognize this module but not this particular symbol" from the module-level rejection below). `Expr::Attribute` on a bound module-namespace name (`math.sqrt`) is resolved by `pycc_hir`/`pycc_types` to the same module-qualified registry key `from`-imports use, so both `import math; math.sqrt(x)` and `from math import sqrt; sqrt(x)` reach D-136's dispatch identically.
  2. Any `Stmt::Import`/`Stmt::ImportFrom` naming a module outside the two-entry allowlist (including every PEP-594 dead-battery module, every third-party package, and every other stdlib module not yet scheduled per `STDLIB_PLAN.md`) is rejected with the existing `C0001` "statement kind not supported yet" — deliberately the *same* code as today's blanket rejection, not a new one, because from this compiler's point of view general import resolution genuinely does not exist yet; only two specific, hand-recognized modules are special-cased. `import x as y` aliasing and `from x import *` are rejected with `C0001` unconditionally regardless of module name (neither is needed by `math`/`sys`'s D-136 scope, and D-088 does not ask for general aliasing/wildcard support). A relative import (`from . import x`) is likewise `C0001`, unchanged from today, matching D-088 point 2's explicit "relative imports ... remain v0.4 scope."
  3. This makes `C0001` vs. `C0002` the exact distinguishing signal PEP-594's fixture (D-138) needs: `import cgi` (a real, removed stdlib module, never in the two-entry allowlist) still produces `C0001`, identical to any other unrecognized module — this decision does not attempt to teach the compiler which stdlib module names are "real but removed" versus "just not implemented yet," since that distinction needs a much larger table (all ~200 stdlib module names) with no payoff beyond one conformance row. PEP 594 conformance is instead demonstrated by the *positive* side: `math`/`sys` importing and resolving correctly, contrasted with `cgi`'s clean, unchanged, pre-existing `C0001` rejection — proving import support exists and is real, not that dead-battery removal is specifically detected.
- Alternatives: give every unrecognized-but-real stdlib module name its own recognized-but-rejected diagnostic (e.g. a curated list of ~30 dead-battery module names each producing a dedicated "this module was removed in this CPython version" message) (rejected — this is exactly the "teach the compiler a large stdlib name table for one conformance row" cost D-088 point 3 already reasoned should not be paid; `C0001`'s existing generic message is honest and sufficient). Bind `math`/`sys` as ordinary `Ty`-carrying values (e.g. treat the module as an object with fields) (rejected — this compiler has no struct/record `Ty` shape yet; a namespace marker consumed only by attribute access on a known-static name is the minimal mechanism that unblocks D-136's dispatch without inventing a general value-of-module-type feature). Reuse `C0001` for the "recognized module, unregistered symbol" case instead of introducing `C0002` (rejected — collapsing both cases loses the diagnostic distinction between "not implemented at all" and "implemented, but you asked for a specific symbol we don't ship," which is worse debugging signal for the exact `from math import isnan`-style case v0.2 will realistically hit first).
- Consequences: `pycc_hir` gains a small, two-module-wide import-lowering pass and one new diagnostic code, `C0002` (next after `C0001`, both `C`-prefixed per this project's existing "C = control-flow/statement-coverage" diagnostic family in `docs/DIAGNOSTICS.md`). No general module-resolution, multi-file linking, or filesystem lookup is introduced. `docs/DIAGNOSTICS.md` documents `C0002` alongside `C0001`. Extending the allowlist later (e.g. adding a third stdlib module) is additive to this same two-arm pattern.
- Addendum (2026-08-04, Task 3 implementation, post-review): point 1's phrasing above ("`Expr::Attribute` on a bound module-namespace name ... is resolved by `pycc_hir`/`pycc_types` to the same module-qualified registry key") reads as though resolution consults whether `math` is actually a bound import — the shipped implementation does not (see D-136's own addendum): `pycc_hir::lower_expr` resolves `math.sqrt`/`math.pi` purely textually, against the receiver's bare source name, independent of the `HirModule.imports` side-table this decision's point 1 also describes (that table is still built and still gates the *import statement itself*, e.g. rejecting `import cgi`/`import math as m`/`from . import x`; it is simply not consulted again at each expression-level use site). A dedicated pre-review gap this trim reopened — a real local/parameter legally named `math` would otherwise silently shadow the stdlib module rather than producing a clean diagnostic — is closed in `pycc_types` (not `pycc_hir`, which has no binding-scope information): `collect_expr_constraints`/`infer_expr_in` check whether the qualified name's receiver (`"math"`) is itself a bound local/parameter *before* treating it as the stdlib module, emitting `C0001` ("`math` is a local name here, not the stdlib `math` module") if so, mirroring `float`'s own existing user-definition-takes-priority guard for a different hand-recognized name. Flow-sensitive "was `import math` textually present in this file" verification remains unattempted (that is a separate, narrower, and lower-severity trim than the shadowing gap this addendum closes).

- Amendment (2026-09-14, Part 1 of #1026): point 3's "`import cgi` ... still produces `C0001`, identical to any other unrecognized module" no longer holds for the *plain, unaliased, undotted* spelling. Part 1 of #1026 gives `import <name>` a meaning when `<name>` is neither a project module nor a `pycc_std` module: it binds an opaque CPython module object (`Ty::Object`), for use by `pycc build --ext`. `import cgi` therefore reaches `ModuleNotFoundError` in the host at module-exec time -- which is what CPython 3.14 does with the same line -- instead of a static `C0001`. Everything else this point says is unchanged: `import x as y`, `from x import *`, `from x import name`, a relative import, and a dotted `import a.b` are all still `C0001` unconditionally, so the aliased `import cgi as c` remains the spelling that exercises this rule. `docs/TYPE_SYSTEM.md` and `docs/RUNTIME.md` own the new binding; the refusals that keep it from being *used* are `I0403` (a native build) and `I0404` (any operation on the bound name).
- Amendment (2026-09-24, [#1291](https://github.com/rotnov/pycc/issues/1291), Part 1 of #1282): the 2026-09-14 amendment's "`import x as y` ... still `C0001` unconditionally" no longer holds for a foreign module. When the undotted `X` is neither a project module nor a `pycc_std` module, `import X as Y` now binds `Y` to the same opaque CPython module object the plain `import X` binds, and either form may also stand inside a module-level `if`/`try` block. It stays `C0001` for a dotted `X`, for a project module ([#964](https://github.com/rotnov/pycc/issues/964)), and for an alias pycc resolves by its spelling (any Python builtin such as `range`, a `pycc_std` module name, or a marker pycc recognises without an import such as `TYPE_CHECKING`, `Enum`, `dataclass` or `Final`), which is refused with a message of its own. So `import cgi as c` no longer exercises this rule; the D-138 amendment of the same date moves that fixture to `from cgi import escape`. `docs/DIAGNOSTICS.md`, `docs/TYPE_SYSTEM.md` and `docs/RUNTIME.md` own the new shapes.
- Amendment (2026-09-24, [#1278](https://github.com/rotnov/pycc/issues/1278)): point 2's rejection of a `from x import ...` naming a module outside the allowlist no longer holds for an unaliased, top-level `from X import a, b` of an undotted foreign module (neither a project module nor a `pycc_std` module). Each listed name now binds to the CPython object `X.<name>`, typed `object`, through the same foreign-import channel as `import X`. It stays `C0001` when a name is aliased (`from X import a as b`), for the wildcard, for a dotted `X`, inside a block body, and for a name pycc resolves by its spelling (which is refused with a message of its own). So `from cgi import escape` no longer exercises this rule; the D-138 amendment of the same date moves that fixture to `from cgi import escape as esc`. `docs/DIAGNOSTICS.md`, `docs/TYPE_SYSTEM.md` and `docs/RUNTIME.md` own the new shapes.
