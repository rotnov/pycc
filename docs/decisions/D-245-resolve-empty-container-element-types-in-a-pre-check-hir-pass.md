## D-245: Resolve empty-container element types in a pre-check HIR pass

- Status: accepted (issue #1021 is the work that depends on it)
- Context: An empty `[]` or `{}` carries no element type, and this compiler has no bidirectional or expected-type inference to hand one down from the surrounding context -- `infer_expr_in(env, local_names, expr)` is the only expression-inference signature and has no hint parameter. Every empty container literal was therefore a hard error (`T0021`, citing issue #927), *including* the annotated `xs: list[int] = []` form, because `AnnAssign` infers its value before it compares the annotation. That makes `xs = []; xs.append(1)` -- one of the most common shapes in real Python -- uncompilable, and it is the shape a 100%-annotated reference codebase actually hits. Two further facts force the shape of any fix. First, `pycc_mir` performs its **own**, independent type derivation from HIR: `MirExpr::ty()` derives a container's type from the literal's first element and *panics* on an empty literal. Resolving the element type inside `pycc_types` alone would make `xs = []; xs.append(1)` type-check and then abort the compiler in MIR, so the resolved type has to reach HIR itself. Second, `pycc check` and `pycc build` enter through two different functions (`check_all_keyed` and `check_and_resolve_all_keyed`), so any design that resolves in only one of them can let `pycc check` accept a program `pycc build` panics on.
- Decision: A new `pycc_hir::HirExpr::EmptyList(Ty)` / `HirExpr::EmptyDict(Box<(Ty, Ty)>)` pair carries a resolved empty container's element type on the node, with mirroring `pycc_mir::MirExpr` variants whose `ty()` returns the carried type directly. A single infallible HIR-to-HIR pass, `pycc_types::empty_container::resolve_empty_containers`, rewrites every resolvable empty literal into those variants, and it runs **once, at the top of both `check_all_keyed` and `check_and_resolve_all_keyed`, before any checking**. Concretely:
  1. **Construction invariant.** The two `HirExpr` variants are never built by `pycc_hir` lowering; `resolve_empty_containers` is their only construction site in the workspace. The invariant is documented on the variants themselves.
  2. **Where the type comes from**, in priority order: (a) the annotation on an `AnnAssign` target, which is purely syntactic and needs no environment at all; (b) the target's existing binding; (c) a forward scan of the enclosing function body for the first *producer* use. (b) and (c) are best-effort on an environment rebuilt the way the protocol-monomorphization pre-pass already rebuilds one (`concrete_function_environment`, then this function's own declared parameters, then `bind_local_types_in_body`), swallowing inference failures exactly as that function does. When `concrete_function_environment` returns `None` -- any module with a `Ty::Infer` private-helper signature -- (b) and (c) degrade rather than fail; (a) is unaffected, which is why the annotation path, the motivating case, never depends on the environment.
  3. **Producers, not consumers.** Only `HirExpr::ListAppend` and `HirStmt::DictSet` supply an element type. `for x in xs`, `xs[0]`, `len(xs)` and `xs.pop()` *read* a type that is already known; in a single forward synthesis pass with no backward unification they cannot produce one. `in` is not an operator this compiler has at all.
  4. **No set path.** `HirExpr::SetAdd` is a structurally dead producer: a set binding can only originate from an empty set literal, `{}` parses as a dict, and `set()` is rejected as `C0001` at `pycc_hir` lowering. Writing a set branch would add Rust lines no `.py` source can reach. `set[T]` stays issue #1017's and #927's.
  5. **Branch collision resolves first-wins within the scope.** `if c: xs = []; xs.append(1)` / `else: xs = []; xs.append("a")` resolves *both* nodes from the first producer, and the second branch's `append` then fails with the ordinary element-type mismatch. A name-keyed resolution cannot represent two types for one binding, and neither can the binding itself. This is a fixture, not a comment.
  6. **The resolved type still passes through `check_container_ty`.** An inferred `list[str]` produces `T0034` and an inferred `dict[int, int]` produces `T0036`, exactly as the written annotations do -- D-228's rule that a written annotation and an inferred literal share one gate. The pre-pass stores what it resolved without validating it; the check phase is the single gate. Only a fully concrete `Ty` is ever stored, never `Ty::Infer`.
  7. **`T0003` replaces `T0021` for an unresolved empty container**, and its registered prose is broadened from "assigned to a name with no surrounding annotation" to *any* position with no inferable element type. A position-specific `T0003` is not cheaply implementable: `infer_expr_in` has no position context at all, so the empty arm cannot know whether it sits in a binding position, a call argument (`f([])`), a return (`return []`), or a nested literal (`[[]]`). Where a binding name *is* available -- the function-scope `Assign` and `AnnAssign` seams -- it is substituted into the message, which is the only locator a `T0003` gets: `HirStmt::Assign` carries no span, and every container diagnostic in this crate renders at `1:1`. No new diagnostic code is minted: `T0003` was registered with exactly this meaning and never emitted.
  8. **Scope.** Function bodies, class methods included. Module-level statements, `self.x = []`, `L, R = [], []`, and nested `match`/`try` producer scans are out; each keeps failing. A module-level empty literal now fails with `T0003`; `self.x = []` and `L, R = [], []` never reach the element-type check at all and keep their pre-existing `C0001` (the D-154 scalar-slot rule and the bare-name assignment-target rule respectively). Empty tuples `()` and `set()` are out too and keep their existing `T0021`/`C0001` diagnostics unchanged.
- Alternatives: **Check records, resolve applies** -- extend `checked_function_signatures_all` to return an empty-container resolution side table keyed by function and expression position, and have a new post-check resolve phase in `check_and_resolve_all_keyed` apply it mechanically (rejected: it exists only because it assumes the rewrite runs *after* checking, and running the pass *before* both entry points dissolves the problem it solves. Pre-check placement makes the `pycc check`-accepts-what-`pycc build`-panics-on hazard structurally impossible rather than an asserted invariant, eliminates the positional-keying problem entirely, needs no signature change, and makes every `pycc_types` check-phase arm reachable from `.py` source instead of only from hand-built HIR). **A pending `BindingState`/`Ty` variant** (rejected: invasive to the core enum, and `Ty::Infer` already demonstrates the leak surface of an unresolved type variant -- it is constructed in four places across two crates, not the one its own docs imply). **Defaulting `[]` to `list[int]` and `{}` to `dict[str, int]`** (rejected, and explicitly *not* on cost grounds: because D-105/D-122 gate codegen to exactly those two, it is observationally equivalent for every program pycc accepts today, and it is tempting to call it a ten-line change -- but it is not ten lines. `MirExpr::ty()` panics on an empty literal no matter what type `pycc_types` assigned to the binding, so the default pays exactly the same four-crate HIR/MIR/codegen plumbing this decision does; it is that plumbing minus the resolution pass. The rejection rests on the diagnostics actively misleading -- appending a `str` would report a conflict with a declaration the user never wrote -- on `T0003` never being emitted even though the issue asks for it, and on the default becoming silently wrong the moment #1017 widens D-105/D-122). **Putting the typed variant only in `MirExpr`, constructed during MIR lowering** (rejected: superficially attractive because lowering runs after every other pass, so no `HirExpr` arm would be unreachable -- but HIR nodes carry no ids, so a side table would still need positional keys, and this shape would additionally have to thread that table through `lower_expr`'s whole call chain. Under pre-check placement the unreachability it was avoiding does not arise in the first place). **Bidirectional / expected-type inference as a general mechanism** (rejected: no expected-type plumbing exists anywhere, and it is far larger than this issue). **Minting a new diagnostic code instead of activating `T0003`** (rejected: `T0003` is registered with precisely this meaning and has never been emitted; a second code for the same failure would be a registry defect).
- Consequences: **What now compiles:** `xs: list[int] = []`, `d: dict[str, int] = {}`, `xs = []; xs.append(1)`, `d = {}; d["k"] = 1`, `xs = [1]; ...; xs = []`, and iteration over a resolved-empty list -- which invalidates the "unreachable, because `pycc_types` rejects an empty list literal" premise stated in `pycc_codegen`'s own `for`-over-empty-list comment; that comment is corrected and the path fixtured. **What does not:** anything beyond `list[int]` and `dict[str, int]` while D-105/D-122 stand -- an inferred `list[float]` needs #1017 as well, so this decision does not unblock it. `f([])`, `return []`, `[[]]`, `{"k": []}`, and module-level empties all report `T0003`; `self.x = []` and `L, R = [], []` still report `C0001` from earlier gates that this pass runs behind; `()` is untouched and still reports `T0021` citing #927. **Irreversible surface:** two new public `HirExpr` variants and two new public `MirExpr` variants; every exhaustive match over either enum in the workspace gains an arm. Where the new variant genuinely has no children, it joins an existing already-covered no-children arm rather than getting an `unreachable!()` -- an `unreachable!()` is itself a changed line that D-242 rule 1 would require be reached, so it buys nothing. **Type-parameter substitution is deliberately absent:** `monomorphize`'s `substitute_stmt` rewrites `Ty` only in an `AnnAssign` annotation and never walks expressions, and a `Ty::Param` can never survive into a live `EmptyList` anyway -- `check_container_ty` rejects `list[T]` as `T0034` in the check phase, which runs before `monomorphize`, exactly as `xs = [x]` in a generic function already does. **`T0021`'s remaining empty-container uses** are the set and tuple arms. The set arm is unreachable from `.py` source (`set()` is `C0001` at lowering); the tuple arm is reachable -- `t = ()` and `t: tuple[int] = ()` both hit it. Both messages still cite #927 because for those shapes #927 really is still the gap, and the tuple arm is deliberately left alone: an empty tuple is not a growable container, so none of this decision's three evidence sources applies to it. **#927 is not closed by this**: its body also covers `s: set[int] = set()`, and `set()` is still `C0001` at lowering.
