## D-245: Resolve empty-container element types in a pre-check HIR pass

- Status: accepted (issue #1021 is the work that depends on it)
- Context: An empty `[]` or `{}` carries no element type, and this compiler has no bidirectional or expected-type inference to hand one down from the surrounding context -- `infer_expr_in(env, local_names, expr)` is the only expression-inference signature and has no hint parameter. Every empty container literal was therefore a hard error (`T0021`, citing issue #927), *including* the annotated `xs: list[int] = []` form, because `AnnAssign` infers its value before it compares the annotation. That makes `xs = []; xs.append(1)` -- one of the most common shapes in real Python -- uncompilable, and it is the shape a 100%-annotated reference codebase actually hits. Two further facts force the shape of any fix. First, `pycc_mir` performs its **own**, independent type derivation from HIR: `MirExpr::ty()` derives a container's type from the literal's first element and *panics* on an empty literal. Resolving the element type inside `pycc_types` alone would make `xs = []; xs.append(1)` type-check and then abort the compiler in MIR, so the resolved type has to reach HIR itself. Second, `pycc check` and `pycc build` enter through two different functions (`check_all_keyed` and `check_and_resolve_all_keyed`), so any design that resolves in only one of them can let `pycc check` accept a program `pycc build` panics on.
- Decision: A new `pycc_hir::HirExpr::EmptyList(Ty)` / `HirExpr::EmptyDict(Box<(Ty, Ty)>)` pair carries a resolved empty container's element type on the node, with mirroring `pycc_mir::MirExpr` variants whose `ty()` returns the carried type directly. A single infallible HIR-to-HIR pass, `pycc_types::empty_container::resolve_empty_containers`, rewrites every resolvable empty literal into those variants, and it runs **once, at the top of both `check_all_keyed` and `check_and_resolve_all_keyed`, before any checking**. Concretely:
  1. **Construction invariant.** The two `HirExpr` variants are never built by `pycc_hir` lowering; `resolve_empty_containers` is their only construction site in the workspace. The invariant is documented on the variants themselves.
  2. **Where the type comes from**, in priority order: (a) the annotation on an `AnnAssign` target, which is purely syntactic and needs no environment at all; (b) *any* successfully-inferred binding for that name anywhere in the enclosing function; (c) a forward scan of the enclosing function body for the first *producer* use. (b) and (c) are best-effort on an environment rebuilt the way the protocol-monomorphization pre-pass already rebuilds one (`concrete_function_environment`, then this function's own declared parameters, then `bind_local_types_in_body`), swallowing inference failures exactly as that function does. **(b) is deliberately order-insensitive, not a backward scan.** That whole-function environment is completed *before* any rewriting begins and is then reused for every occurrence regardless of position, so `xs = [1]; ...; xs = []` and `xs = []; xs = [1]; ...` resolve identically. It is safe because the pass only resolves and never accepts: item 6's `check_container_ty` gate admits exactly `list[int]` and `dict[str, int]`, so any resolution is either the single element type the program could have compiled with or a `T0034`/`T0036`, and the check phase re-validates the whole function in true program order (D-040's sticky-representation rule included). Restricting (b) to strictly-prior bindings could only turn some compilable programs into `T0003`; it could not change which accepted program is produced. The same completed-before-rewriting property is why `bind_local_types_in_stmt`'s `AnnAssign` arm seeds the declared annotation when the value does not infer (`xs: list[int] = []`, whose raw literal is not yet rewritten): without it a resolution derived from `xs` -- `for x in xs: ys.append(x)` -- found `x` unbound and fell through to `T0003`. When `concrete_function_environment` returns `None` -- any module with a `Ty::Infer` private-helper signature -- (b) and (c) degrade rather than fail; (a) is unaffected, which is why the annotation path, the motivating case, never depends on the environment.
  3. **Producers, not consumers.** Only `HirExpr::ListAppend` and `HirStmt::DictSet` supply an element type. `for x in xs`, `xs[0]`, `len(xs)` and `xs.pop()` *read* a type that is already known; in a single forward synthesis pass with no backward unification they cannot produce one. `in` is not an operator this compiler has at all. A producer is recognized only in **statement position** -- a bare `xs.append(v)` or `d[k] = v`; `HirExpr::ListAppend` is also a valid value expression (`y = xs.append(v)` binds `None`) and such an occurrence does not resolve anything, per item 8. The scan visits a block statement's nested suites in source order -- for a `try`, the body, then each handler, then `else`, then `finally`, matching the rewrite walk's own traversal of the same node, and pinned by the `a_try_s_suites_are_scanned_for_producers_in_source_order` fixture. It returns the first *syntactic* producer for the name rather than the first shape-compatible one; item 6's gate makes a cross-shape hit cost a missed resolution (`T0003`), never a wrong element type.
  4. **No set path.** `HirExpr::SetAdd` is a structurally dead producer: a set binding can only originate from an empty set literal, `{}` parses as a dict, and `set()` is rejected as `C0001` at `pycc_hir` lowering. Writing a set branch would add Rust lines no `.py` source can reach. `set[T]` stays issue #1017's and #927's.
  5. **Branch collision resolves first-wins within the scope.** `if c: xs = []; xs.append(1)` / `else: xs = []; xs.append("a")` resolves *both* nodes from the first producer, and the second branch's `append` then fails with the ordinary element-type mismatch. A name-keyed resolution cannot represent two types for one binding, and neither can the binding itself. This is a fixture, not a comment.
  6. **The resolved type still passes through `check_container_ty`.** An inferred `list[str]` produces `T0034` and an inferred `dict[int, int]` produces `T0036`, exactly as the written annotations do -- D-228's rule that a written annotation and an inferred literal share one gate. The pre-pass stores what it resolved without validating it; the check phase is the single gate. Only a fully concrete `Ty` is ever stored, never `Ty::Infer` -- and that invariant is enforced *at this downstream gate rather than inside the pass*: the pass performs no `Ty::Infer` check of its own, but a resolved `Ty::Infer` cannot survive `check_container_ty` and so can never reach MIR.
  7. **`T0003` replaces `T0021` for an unresolved empty container**, and its registered prose is broadened from "assigned to a name with no surrounding annotation" to *any* position with no inferable element type. A position-specific `T0003` is not cheaply implementable: `infer_expr_in` has no position context at all, so the empty arm cannot know whether it sits in a binding position, a call argument (`f([])`), a return (`return []`), or a nested literal (`[[]]`). Where a binding name *is* available **and the failing empty literal is the directly-assigned value** -- the function-scope `Assign` and `AnnAssign` seams -- it is substituted into the message, which is the only locator a `T0003` gets: `HirStmt::Assign` carries no span, and every container diagnostic in this crate renders at `1:1`. The substitution is gated on the assigned value itself being the empty literal precisely because a `T0003` can also propagate out of a *nested* element position: `xs: list[int] = [[]]` fails on the inner `[]`, while `xs` is validly annotated, so naming `xs` there would point the user at the wrong node. Such a diagnostic keeps the generic wording. No new diagnostic code is minted: `T0003` was registered with exactly this meaning and never emitted.
  8. **Scope.** Function bodies, class methods included. Within a function body the pass walks every block statement the HIR has -- `if`/`else`, `while`, both `for` forms, every `match` case body, and every `try`/`except`/`except*`/`else`/`finally` suite. An earlier revision of this entry excluded nested `match`/`try` bodies from the *producer scan*; the bot review round on PR #1035 showed the omission was broader than that, because one shared inventory function feeds both the producer scan and the rewrite walk, so even the environment-free annotation source never ran inside those suites and a valid `xs: list[int] = []` there reported `T0003`. Traversing them removes that boundary outright rather than moving it, which is why it was fixed rather than documented, and the producer scan was widened along with the rewrite instead of being split off: a `match` case and an `except` suite are conditionally executed exactly as an `if` branch is, and item 5's first-wins rule already governs that. One gap remains and is stated rather than closed: source 2's environment comes from `bind_local_types_in_body`, a pre-existing pass shared with protocol monomorphization whose own statement walk has no `match`/`try` arm, so a binding *created inside* such a suite is not visible to it -- a missed resolution (`T0003`), never a wrong element type, and widening a shared pass belongs to its own change. Module-level statements, `self.x = []`, `L, R = [], []`, and producers in *value* position (`y = xs.append(1)`) are out; each keeps failing. The value-position exclusion was raised in review round 3 and kept deliberately: recognizing one more nesting form (an assignment whose value *is* a `ListAppend`) would move the boundary rather than remove it -- `print(xs.append(1))` and `[xs.append(1)]` would still be out -- and removing it entirely needs a generic `HirExpr` walker that does not exist in this workspace, whose every arm is a changed line D-242 rule 1 requires be covered. The restriction matches the rewrite side, which is likewise direct-assignment-value-only, and it is pinned by the `t0003_value_position_append_is_not_a_producer` fixture rather than left to prose. A module-level empty literal now fails with `T0003`; `self.x = []` and `L, R = [], []` never reach the element-type check at all and keep their pre-existing `C0001` (the D-154 scalar-slot rule and the bare-name assignment-target rule respectively). Empty tuples `()` and `set()` are out too and keep their existing `T0021`/`C0001` diagnostics unchanged.
- Alternatives: **Check records, resolve applies** -- extend `checked_function_signatures_all` to return an empty-container resolution side table keyed by function and expression position, and have a new post-check resolve phase in `check_and_resolve_all_keyed` apply it mechanically (rejected: it exists only because it assumes the rewrite runs *after* checking, and running the pass *before* both entry points dissolves the problem it solves. Pre-check placement makes the `pycc check`-accepts-what-`pycc build`-panics-on hazard structurally impossible rather than an asserted invariant, eliminates the positional-keying problem entirely, needs no signature change, and makes every `pycc_types` check-phase arm reachable from `.py` source instead of only from hand-built HIR). **A pending `BindingState`/`Ty` variant** (rejected: invasive to the core enum, and `Ty::Infer` already demonstrates the leak surface of an unresolved type variant -- it is constructed in four places across two crates, not the one its own docs imply). **Defaulting `[]` to `list[int]` and `{}` to `dict[str, int]`** (rejected, and explicitly *not* on cost grounds: because D-105/D-122 gate codegen to exactly those two, it is observationally equivalent for every program pycc accepts today, and it is tempting to call it a ten-line change -- but it is not ten lines. `MirExpr::ty()` panics on an empty literal no matter what type `pycc_types` assigned to the binding, so the default pays exactly the same four-crate HIR/MIR/codegen plumbing this decision does; it is that plumbing minus the resolution pass. The rejection rests on the diagnostics actively misleading -- appending a `str` would report a conflict with a declaration the user never wrote -- on `T0003` never being emitted even though the issue asks for it, and on the default becoming silently wrong the moment #1017 widens D-105/D-122). **Putting the typed variant only in `MirExpr`, constructed during MIR lowering** (rejected: superficially attractive because lowering runs after every other pass, so no `HirExpr` arm would be unreachable -- but HIR nodes carry no ids, so a side table would still need positional keys, and this shape would additionally have to thread that table through `lower_expr`'s whole call chain. Under pre-check placement the unreachability it was avoiding does not arise in the first place). **Bidirectional / expected-type inference as a general mechanism** (rejected: no expected-type plumbing exists anywhere, and it is far larger than this issue). **Minting a new diagnostic code instead of activating `T0003`** (rejected: `T0003` is registered with precisely this meaning and has never been emitted; a second code for the same failure would be a registry defect). **Narrowing `bind_local_types_in_stmt`'s `AnnAssign` fallback to the empty-literal shape** -- seed the declared annotation only when the value is an empty literal, rather than on *any* inference failure (raised in review round 2 as a possible source of spurious diagnostics, and rejected on evidence gathered by running the freshly built compiler. The finding's mechanism does not exist: `xs = []` followed by `xs: list[str] = undefined_name` reports `T0034` at the annotation's own span, and the *same* file with the preceding `xs = []` removed reports the identical `T0034` at the identical span -- so the diagnostic is about the D-105-incompatible annotation, not about the pre-pass having resolved `xs = []` into `EmptyList(Str)`. A container diagnostic carries no span and renders at `1:1`, so one rendering at the annotation's span cannot have originated in the pre-pass at all. The narrowing is also a net regression on the *compatible* case: with the broad fallback, `xs = []` followed by `xs: list[int] = undefined_name` reports the real `T0021` naming `undefined_name` as not defined; with the narrowing it reports a spurious `T0003` instead and hides the actual defect. That behaviour is now pinned by the `t0021_annotated_broken_value_still_reports_the_real_defect` diagnostics fixture rather than left incidental).
- Consequences: **What now compiles:** `xs: list[int] = []`, `d: dict[str, int] = {}`, `xs = []; xs.append(1)`, `d = {}; d["k"] = 1`, `xs = [1]; ...; xs = []`, and iteration over a resolved-empty list -- which invalidates the "unreachable, because `pycc_types` rejects an empty list literal" premise stated in `pycc_codegen`'s own `for`-over-empty-list comment; that comment is corrected and the path fixtured. **What does not:** anything beyond `list[int]` and `dict[str, int]` while D-105/D-122 stand -- an inferred `list[float]` needs #1017 as well, so this decision does not unblock it. `f([])`, `return []`, `[[]]`, `{"k": []}`, and module-level empties all report `T0003`; `self.x = []` and `L, R = [], []` still report `C0001` from earlier gates that this pass runs behind; `()` is untouched and still reports `T0021` citing #927. **Irreversible surface:** two new public `HirExpr` variants and two new public `MirExpr` variants; every exhaustive match over either enum in the workspace gains an arm. Where the new variant genuinely has no children, it joins an existing already-covered no-children arm rather than getting an `unreachable!()` -- an `unreachable!()` is itself a changed line that D-242 rule 1 would require be reached, so it buys nothing. **Type-parameter substitution is deliberately absent:** `monomorphize`'s `substitute_stmt` rewrites `Ty` only in an `AnnAssign` annotation and never walks expressions, and a `Ty::Param` can never survive into a live `EmptyList` anyway -- `check_container_ty` rejects `list[T]` as `T0034` in the check phase, which runs before `monomorphize`, exactly as `xs = [x]` in a generic function already does -- pinned by the `a_producer_derived_type_parameter_element_is_rejected_in_the_check_phase` fixture, added in review round 4, rather than left as an argument. **`T0021`'s remaining empty-container uses** are the set and tuple arms. The set arm is unreachable from `.py` source (`set()` is `C0001` at lowering); the tuple arm is reachable -- `t = ()` and `t: tuple[int] = ()` both hit it. Both messages still cite #927 because for those shapes #927 really is still the gap, and the tuple arm is deliberately left alone: an empty tuple is not a growable container, so none of this decision's three evidence sources applies to it. **#927 is not closed by this**: its body also covers `s: set[int] = set()`, and `set()` is still `C0001` at lowering.
- Amendment (2026-09-13): item 6's claim that the "only a fully concrete `Ty` is ever stored" invariant is enforced *at the downstream `check_container_ty` gate rather than inside the pass* was wrong about where the enforcement has to live, and review round 7 on PR #1035 demonstrated it. `Ty::Infer` is the private-helper constraint solver's placeholder; this pass runs *before* that solver, so a producer whose value is an unannotated private-helper parameter (`def _f(x): xs = []; xs.append(x)`) resolves to `Ty::Infer` here. Nothing downstream substitutes into a rewritten node, so `check_container_ty` does reject it -- but it rejects it by reporting `T0034: list[<inferred>]`, naming a type the source never mentions, for a program whose `xs = [x]` spelling the solver accepts. The gate therefore contains the resolution without preserving this decision's "never wrong, only missed" property. The pass now discards any resolution containing `Ty::Infer` anywhere inside it (`empty_container::concrete` / `contains_infer`), turning that case into the `T0003` a missed resolution is supposed to produce. The change is strictly `T0034` -> `T0003` over a bounded set -- `check_container_ty` admits only `list[int]` and `dict[str, int]`, so no program ever compiled through the frozen-placeholder path -- and it cannot regress a program that compiles. `Ty::Param` is deliberately *not* discarded: both spellings of a generic element already report the identical `T0034: list[T]`, as item 21's `a_producer_derived_type_parameter_element_is_rejected_in_the_check_phase` fixture records, so there is no asymmetry to repair and discarding it would introduce one.
- Amendment (2026-09-13): the same "never wrong, only missed" property fails a second way, shown by review round 8 on PR #1035, and for a reason the preceding amendment's concreteness filter does not cover. Both *inferred* sources -- source 2's whole-function binding and source 3's producer scan -- read the flat `Environment`, whose narrowing overlay is empty, while the check phase resolves the same name inside a narrowed branch. For `def f(x: int | None): if x is not None: xs = []; xs.append(x)` the pass resolves `Optional[int]` and `check_container_ty` reports `T0034: list[int | None]`, while the `xs = [x]` spelling of the same program compiles and runs; the dict path is symmetric, reporting `T0036: dict[str, int | None]` where `d = {"k": x}` compiles. Narrowing in this repository is exclusively `Optional` narrowing -- `narrow::narrowing_target` recognizes only a top-level `name is None` / `name is not None` test whose subject looks up as `Ty::Optional`, and returns `None` for every other shape -- so a resolution carrying `Ty::Optional` is exactly the set the flat environment can get wrong. The pass now discards such a resolution on the two inferred sources (`empty_container::inferred` / `contains_optional`), producing the `T0003` a miss is supposed to produce. As with the placeholder filter, the change is strictly `T0034`/`T0036` -> `T0003` over a bounded set and cannot regress a compiling program: `check_container_ty` compares for exact equality against `Ty::Int` and `(Ty::Str, Ty::Int)`, so any `Optional` anywhere in an element, key, or value position was already rejected. The **annotation** source is deliberately not filtered: `xs: list[int | None] = []` states the type in source, no narrowing is involved, and its `T0034` names the real D-105 gap where a `T0003` miss would be the worse diagnostic. The alternative the review suggested -- carrying the branch or continuation narrowing environment into producer inference -- was rejected: it would thread branch-local environments plus `apply_post_if_narrowing`'s continuation shape through this pass's recursion, reimplementing ahead of the checker the statement-walk ordering the checker already owns, in a pass whose design justification is that it is infallible and pure. That is a capability improvement (turning misses into successes), not a correctness repair, and this decision's invariant obliges only the latter.
- Amendment (2026-09-13): item 8 attributes the `match`/`try` environment gap to source 2 alone; review round 9 on PR #1035 showed it applies to source 3 identically, and for the same single cause. `find_producer` infers the producer's value with `infer_expr_in(env, local_names, value)` using the very same flat whole-function `Environment` that `bind_local_types_in_body` builds for source 2, so a name bound only inside a `match` case or a `try` suite is invisible to both sources, not just to source 2. Measured on the branch build: `case y: xs: list[int] = []; xs.append(y)` compiles (source 1 is purely syntactic and needs no environment), while `case y: xs = []; xs.append(y)` does not. The consequence class is unchanged -- a missed resolution, never a wrong element type -- so this amendment corrects the attribution, not the design, and the module documentation of `pycc_types::empty_container` is corrected in the same commit.
- Amendment (2026-09-13): what a miss of that kind *reports* is also not always `T0003`, and the difference is not attributable to this pass. A miss leaves the concrete path failing, which routes the module into the private-helper constraint solver; that solver's `HirStmt::Match` arm clones the case environment without ever binding the pattern's capture names, while `collect_local_names` does register them as locals, so reading a capture inside a case body yields `T0021` with the "local name is not bound before this use" message, and D-220's solver-first merge lets that false diagnostic win over the true `T0003`. Three facts establish that this is pre-existing rather than introduced here, all measured against a build of `origin/main` at this branch's merge base `1ede16ff72bfdc09dc0c469136ba72b5e6dce9cb`: `main` emits the byte-identical message for the same program; it emits it for a `match` program containing no empty container anywhere; and the solver arm is unchanged from the merge base in this pull request's diff. The direction of change is the opposite of a regression -- `case y: xs: list[int] = []; xs.append(y)` is rejected by `main` with that same false `T0021` and accepted by this branch, so on `match`-case programs the branch resolves strictly more than `main` and worsens none. The solver's match-capture blindness is therefore tracked as its own issue, #1046, rather than repaired inside #1021; the `try` half of the same gap keeps reporting the truthful `T0003`.
- Amendment (2026-09-13): the "never wrong, only missed" property fails a third way, shown by review round 14 on PR #1035, and through *boundness* rather than through the resolved type the two preceding amendments filter. `bind_local_types_in_body` is a flat forward binder: it records every target it walks as `BindingState::Definitely`, a name bound only inside an `if` branch or a loop body included. The checker does not -- such a name joins back as `BindingState::Maybe`, and reading it is `T0041`. So for `def go(flag: bool): if flag: v = "s"` / `xs = []` / `xs.append(v)` the producer source resolved `list[str]` from `v` and the check phase reported `T0034` against the resolved container, masking the `T0041` the `xs = [v]` spelling of the same program reports. That is a resolution manufactured from evidence the checker is not entitled to read, which is exactly what this decision's invariant forbids. The pass now demotes, after the binder runs, every binding not established at the function body's own top level (`empty_container::demote_conditional_bindings`), and the producer scan restores per nested body the names that body's construct binds -- its own top-level bindings plus a `for` target (`empty_container::scoped_for_body`) -- so a producer *inside* the branch that binds its value still resolves while one reading the name from outside is declined. The outcome for the masking program is `T0003`, not `T0041`: this pass can only decline to resolve, it cannot make the checker report a different code, and a miss is what the invariant asks for. The definite set is deliberately under-approximated -- an `if`/`else` binding the same name in both arms really does join to `Definitely` and is demoted anyway -- because computing the true join would mean reimplementing the checker's statement walk ahead of it, in a pass whose design justification is that it is infallible and pure; the cost is a missed resolution, never a wrong element type. Module-level statements are unchanged and stay out of scope per item 8; the same class of defect is not reachable there, because the pass resolves nothing at module level at all.
- Amendment (2026-09-13): `T0003`'s `help` text was position-blind and, at module level, named a remedy that does not work. It read "annotate the assignment target (`xs: list[int] = []`) or append a value to it" in every position, but item 8 puts module-level statements outside this pass's scope entirely, so `xs: list[int] = []` at module level reports the same `T0003` as the bare `xs = []` it was offered as the fix for -- a circle, shown by review round 14 on PR #1035. The wording is now chosen from `Environment::in_function_body` at the emit site: inside a function body it is unchanged, and at module level it names the one remedy that does work, moving the binding into a function body. `pycc explain T0003` carries the same distinction. Item 8's decision that module-level statements stay out of scope is not revisited here -- honouring an annotation there would extend the pass to a position it deliberately does not walk, and the review round showed a misleading `help`, not a missing capability.
- Amendment (2026-09-13): item 2's parenthetical names `concrete_function_environment` as the function the pre-pass rebuilds its environment from, and its closing sentence describes sources 2 and 3 degrading whenever that function "returns `None` -- any module with a `Ty::Infer` private-helper signature". Review round 13 on PR #1035 showed that contract loses both inferred sources for every module containing one unannotated private helper, which is most real modules, so it was not implemented that way and item 2 no longer describes the code or the fixtures that govern it. What the pass actually builds is `empty_container::annotated_function_environment`: it registers *every* function signature including `Ty::Infer` ones, seeds module-level bindings, adds this function's own declared parameters, and then runs `bind_local_types_in_body` -- and it is infallible, so there is no `None` case and no degradation branch at all. The substitution is safe in the direction this decision cares about: a `Ty::Infer` signature registered here can only produce a resolution containing `Ty::Infer`, which the first amendment above already discards outright, so the broader registry widens what source 2 and source 3 can *see* without widening what they may store. Item 2's ordering, its order-insensitivity argument for source (b), and its `AnnAssign`-seeding rationale are unchanged and still describe the implementation; only the environment-construction function and the degradation sentence are superseded here.
- Amendment (2026-09-13): the "never wrong, only missed" property fails a fourth way, shown by review round 15 on PR #1035, and this one is a divergence between item 3's stated contract and the code rather than a new design question. Item 3 says the scan "returns the first *syntactic* producer for the name"; `find_producer` returned the first *inferring* one, because a producer arm that matched the target but failed to infer its value yielded `None` and the loop simply continued. The two differ exactly where the flat whole-function environment cannot see a value name -- item 8 already records that `bind_local_types_in_body` has no `match`/`try` arm -- so for `try: v = 1; xs = []; xs.append(v); xs.append(True)` the first producer was skipped and the second resolved `list[bool]`, reported as `T0034`, while the `xs = [v]` spelling of the same program compiles and runs. That is a resolution the program's own first use contradicts, which is the wrong-not-missed outcome this decision forbids. The scan now distinguishes three outcomes (`empty_container::ProducerScan`: `NotFound` / `Matched` / `Resolved`) and ends at the first *match*, inferring or not, so the outcome is the `T0003` a miss is supposed to produce. Two properties of the fix are load-bearing and fixtured rather than left to prose: the stop propagates out of the recursion, so a matching-but-uninferable producer inside a nested body ends the enclosing scan too and a later producer sitting after the block cannot select a type either; and the `HirStmt::DictSet` arm counts as a match when *either* the key or the value fails to infer, so the two container shapes stay symmetric. The change is strictly `T0034`/`T0036` -> `T0003` over the set of programs where a producer's value did not infer, so it cannot regress a program that compiles, and the first-wins rule of item 5 is unaffected and separately pinned: a first producer that *does* infer still selects the element type and a later differing producer still reports the ordinary element-type mismatch. Teaching `bind_local_types_in_stmt` about `match`/`try` bodies -- which would turn these misses into successes -- remains out of scope here for the reason item 8 already gives: it is a shared pass with its own change, and this amendment repairs a correctness divergence, not a capability gap.
- Amendment (2026-09-13): the "never wrong, only missed" property fails a fifth way, shown by review round 16 on PR #1035, in the per-body promotion the third amendment introduced. `empty_container::scoped_for_body` re-promotes the names a nested body's own top-level statements bind, so a producer inside an `if` branch or a loop body may read a name that branch binds -- but the *type* it promoted was the flat whole-function binder's, which a **different, mutually exclusive** branch may have contributed. For `if flag: v = True` / `else: v = 1; xs = []; xs.append(v)` the flat pass retains `bool` from the `if` arm, the `else`'s producer was therefore resolved as `EmptyList(Bool)`, and the check phase reported `T0034` -- while the `xs = [v]` spelling of the same program sees the branch-local `int` and `pycc check` accepts it. Wrong, not missed. The repair is to **decline the evidence**: a name bound by more than one syntactic binding site anywhere in the function (`empty_container::collect_binding_sites`, counting `Assign`, valued `AnnAssign`, both `for` targets and walrus targets at every nesting depth) is no longer promoted, so `Environment::lookup` returns `None` for it, the producer's value fails to infer, and the round-15 scan ends with the `T0003` a miss is supposed to produce. Reconstructing the body's own environment instead was rejected for the reason the second amendment already gives for the same shape: threading a per-body binder ahead of the checker would reimplement the statement-walk ordering the checker already owns, inside a pass whose design justification is that it is infallible and pure -- a capability improvement, not a correctness repair. The site test is deliberately under-approximated in the safe direction: two sites assigning the *same* type are declined too, which costs a `T0003` and never a wrong element type. The round-14 property that motivated the promotion in the first place -- a producer reading a name its own branch binds, bound nowhere else, still resolves -- is unaffected and stays fixtured. The reference spelling of the program above is fixtured on `pycc check` alone, because building and running it aborts in the runtime's int decoding -- a D-040 sticky-representation defect in a branch-divergent `bool`/`int` binding that reproduces on `main` with no empty container anywhere in the program, filed as issue #1057 and untouched by this pass.
