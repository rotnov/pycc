## D-128: Preserve ordinary imports while making CPython interop policy-controlled

- Status: accepted (planned v0.7 contract; no current compiler behavior is claimed)
- Context: pycc's invariant is standard Python input, but the original v0.7 sketch in `docs/RUNTIME.md` required users to replace ordinary code such as `import numpy as np` with `from pycc.interop import cpython` plus `cpython.import_module("numpy")`. That source rewrite made otherwise-portable code pycc-specific. It also treated an empty `[interop].allow` list as pure mode, so every CPython-backed package needed a redundant permission even though its source `import` already expressed intent. Existing NumPy extension modules cannot load directly into `pycc_rt`: they export CPython extension entry points and depend on the CPython object model, C API, allocator, interpreter state, and GIL, whereas pycc uses its own unboxed/native representations and no libpython. Source compatibility therefore requires pycc to generate and package a real CPython boundary, not pretend those ABIs are interchangeable. The current v0.1 compiler still rejects every `import` with `C0001`; this decision changes only the future v0.7 contract.
- Decision:
  1. Ordinary standard-Python imports are the primary v0.7 interop surface. The resolver classifies each import as native pycc or CPython-backed. `import numpy as np` remains unchanged source; a CPython-backed classification makes pycc generate the bridge and bundle a pinned CPython 3.14 runtime plus the resolved package/native-library closure. The deployment artifact must not require a separately installed Python and must not search ambient `site-packages`. A low-level `pycc.interop.cpython` API may remain for advanced explicit handles, but normal package use cannot require it.
  2. The interop policy is a closed three-value enum shared by `pycc.toml` and the CLI: `auto` (default) permits every direct CPython-backed import root present in the source; `allowlist` permits only roots named by `[interop].allow`; and `deny` rejects every CPython-backed import while leaving native pycc imports available. `--interop-policy auto|allowlist|deny` overrides project configuration. `--pure` is shorthand for `deny` and conflicts with an explicit `--interop-policy` instead of depending on argument order.
  3. An allowlisted root covers its submodules and the exact transitive dependency closure selected for that root. Another direct source import root needs its own entry. The resolver records the complete interpreter, package, wheel/native-library, target, version, and integrity identity in a reproducible `pycc.lock`; the embedded environment exposes only that locked closure. Exact lock schema, resolver source, artifact layout, and update command are mandatory v0.7 planning work before implementation, not silently chosen by the first code change.
  4. CPython-owned values remain behind the compiler's typed interop representation. Package stubs supply the public type surface; a genuinely untyped value leaking into pure pycc code remains `I0401`, and a policy-rejected import is `I0402`. Standard-Python scalar/container conversions and supported buffer protocols provide source-compatible marshalling. The boundary benchmark must report copied and zero-copy transfers separately; automatic compatibility is not a claim that the bridge is free.
  5. The embedded interpreter owns its GIL only while executing CPython-backed operations. Native pycc execution remains GIL-free, and packages may release the embedded GIL internally according to their own contracts.
- Alternatives: keep `pycc.interop.cpython.import_module()` as the only supported spelling (rejected because it violates the standard-source invariant and forces code forks); make `allowlist` the default (rejected because the source import already expresses intent and ordinary compatibility should not require duplicate configuration); load the developer's or target machine's system Python and `site-packages` automatically (rejected because it makes builds and deployments environment-dependent rather than autonomous and reproducible); implement enough of the CPython C API inside `pycc_rt` to load existing extension modules without CPython (rejected because faithfully reproducing the CPython object/interpreter ABI is effectively another interpreter and would undermine pycc's own runtime model).
- Consequences:
  - **POS-001:** CPython-compatible source, including aliases and `from ... import ...`, can remain unchanged when compiled with pycc.
  - **POS-002:** `auto` provides zero-configuration compatibility, while opt-in `allowlist` and `deny`/`--pure` builds give deployment and supply-chain policy a fail-closed mode.
  - **POS-003:** Interop artifacts are autonomous at runtime because the interpreter and locked dependency closure travel with the application; pure artifacts retain the no-libpython guarantee.
  - **NEG-001:** Interop artifacts are materially larger and retain CPython's GIL and object-model costs inside the boundary.
  - **NEG-002:** Cross-compilation now includes target-specific interpreter, wheel, native-library, loader-path, signing, and license work; absence of a compatible locked artifact is a build failure, not a host-environment fallback.
  - **NEG-003:** The v0.7 implementation must build import classification, stub-aware typing, deterministic resolution/locking, bundling, diagnostics, and a measured marshalling layer before the feature can be called complete on any target.
