## D-072: `print()`'s `None` result cannot be used as a nested expression in v0.1

- Status: accepted (surfaced by `build-test-coverage` failing on this branch's own merge with `main`: PR-5's real MIR/codegen lowering makes D-035's tracked panic unreachable, breaking `scripts/run_alpha_skill_evals.py`'s `classify-planned-backend-boundary-without-write`/`refuse-accepted-pr5-boundary-publication` fixtures, which hard-code that exact now-closed panic as their reproducer)
- Context: D-035 defined `pycc_mir`'s "codegen lands in PR-5" panic as PR-4's frontend/backend gap, and the `pycc`/`pycc-feedback` alpha skills (and their offline eval harness) cited it as the canonical example of an "intentional temporary alpha boundary, not a reportable defect." PR-5 closes that exact gap for real -- `pycc_mir` has no such panic left (`grep -n "panic!" crates/pycc_mir/src/lib.rs` shows only one internal-invariant panic, unrelated). Verified directly: `def main() -> None:\n    value = 1\n    print(42)\n\nmain()\n` (D-035's own fixture) now builds and runs cleanly. But not every construct a valid, type-checked v0.1 program can express is lowered: `pycc_types` types `print(...)` as `Ty::None` (matching CPython), and assigning that result to a name (`value = print(42)`) type-checks fine, yet `pycc_codegen::emit_expr`'s `MirExpr::Call` arm has no general representation for a `None` value flowing through an `alloca`/parameter/return -- no PR-5 task needed one, since RUNTIME.md's `None` mention is about the scalar's eventual representation, not a promise that every expression position accepts it in v0.1.
- Decision: keep this a named, explicit panic (`"pycc_codegen: using print()'s result as a nested expression is not supported yet"`, `crates/pycc_codegen/src/lib.rs`'s `Call` arm) rather than inventing a placeholder `None` value -- consistent with this project's standing convention that unsupported-but-out-of-scope constructs panic loudly instead of silently miscompiling. Point the `pycc` and `pycc-feedback` alpha skills, and their eval fixtures, at this exact message and this decision instead of D-035's now-unreachable one. D-035's own text is left unedited (it accurately described PR-4's state); this is a new decision, not a rewrite.
- Alternatives: implement full `None`-as-a-general-expression-value support now (a real singleton/sentinel that can be stored, compared, and passed) -- rejected as scope creep beyond PR-5's stated v0.1 feature set (int/float/str/bool arithmetic, control flow, recursion, f-strings), with no `docs/ROADMAP.md` acceptance criterion depending on it. Silently returning a garbage/zero value for `print()`'s result -- rejected, violates the no-silent-wrong-result convention this same file already applies elsewhere (D-026, D-061's own accepted-leak notes).
- Consequences: `value = print(x)` (or any other nested use of `print(...)`'s return value) is a documented, intentional exit-101 alpha boundary, not a defect -- agents using the `pycc` skill must recognize this exact message and not route it to `pycc-feedback`. Closing this gap for real is a documented future item, not a v0.1 requirement. `scripts/run_alpha_skill_evals.py`'s `classify-planned-backend-boundary-without-write` and `refuse-accepted-pr5-boundary-publication` cases are updated in this same change to reproduce this message instead of D-035's.
