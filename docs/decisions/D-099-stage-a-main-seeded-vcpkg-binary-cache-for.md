## D-099: Stage a main-seeded vcpkg binary cache for Windows libxml2

- Status: accepted (active until D-100 composed it with D-091)
- Context: issue [#225](https://github.com/rotnov/pycc/issues/225) measured `native-build-test (windows-latest)` at roughly 10m17s, with D-027's `Install libxml2 (Windows, via vcpkg, for llvm-sys's system-libs)` step alone taking 7m31s. vcpkg builds that port from source on each fresh hosted runner, even though its default files-provider binary cache can restore an ABI-matching compressed archive in seconds. This is a CI setup bottleneck, not a compiler or PR-8 behavior change. The workflow remains protected by D-080's base-owned `pull_request_target` audit, so the target `ci.yml` bytes and their digest cannot safely activate in the same pull request that first authorizes them.
- Decision: stage [`tests/fixtures/d99-vcpkg-libxml2-cache-ci.yml`](../tests/fixtures/d99-vcpkg-libxml2-cache-ci.yml), defined as the live D-084 workflow plus exactly three Windows-only cache steps, and authorize its digest alongside live D-084 and independently staged D-091. The identity step fails closed unless `git -C $VCPKG_INSTALLATION_ROOT rev-parse HEAD` yields an exact 40-digit commit and the hosted runner's system `ImageVersion` is present with a cache-key-safe value; it creates a dedicated directory under `RUNNER_TEMP` and exports it as `VCPKG_DEFAULT_BINARY_CACHE`. `actions/cache/restore` and `actions/cache/save` are pinned to the immutable v6.1.0 commit `55cc8345863c7cc4c66a329aec7e433d2d1c52a9`. The exact restore key contains runner OS and architecture, hosted image version, D-015's `LLVM_VERSION`, D-027's `x64-windows-static-md` triplet, and the hosted image's vcpkg commit; no prefix `restore-keys` are permitted. The image component makes an MSVC or other runner-toolchain refresh publishable under a fresh immutable outer key even if the runner ships the same vcpkg commit. The normal `vcpkg install` command always runs, so vcpkg still checks its own package ABI hash and materializes the installed tree before the existing `xml2s.lib` validation/aliasing. Pull requests restore only. The separate save action runs only on an exact-key miss under `github.event_name == 'push' && github.ref == 'refs/heads/main'`, reuses the restore action's primary key and path, and therefore cannot publish pull-request-built archives.
- Alternatives: use the combined `actions/cache` entrypoint and let every successful branch job attempt a branch-scoped save (rejected because the main-seeded read-only pull-request boundary is simpler to audit and grants less mutation capability); adopt `lukka/run-vcpkg` plus a repository manifest (rejected because the existing one-port classic-mode install already works and does not justify another action/configuration surface); cache `%LOCALAPPDATA%\vcpkg\archives` under only the LLVM version, triplet, and vcpkg commit (rejected because GitHub caches are immutable per key, so an image/MSVC change could leave every future run rebuilding an ABI-mismatched package without any way to publish the replacement); cache the mutable `installed/` tree itself (rejected because vcpkg's binary archive is the supported reusable unit and retains its own ABI validation).
- Consequences: staging merged separately in [PR #227](https://github.com/rotnov/pycc/pull/227); activation (PR #228) copied the reviewed fixture byte-for-byte into `.github/workflows/ci.yml` and retired D-084's digest to historical-only. D-091's fixture and decision remain byte-for-byte untouched, but that activation retired its pre-D-099 digest from the public allowlist so it could not replace the live cache workflow on its own. **Update:** D-100 composes D-091's changes with this decision's cache boundary into the digest that actually activates in v0.2 PR-8, exactly as this decision's own Context anticipated ("If PR-8 lands after D-099 activates, its workflow changes need a newly staged composed digest"). The roadmap milestone and delivery decomposition do not change: this reduces Tier-1 CI setup time without changing compiler behavior, supported platforms, acceptance evidence, or PR-8's language/runtime scope.

  **Second update:** D-100's own digest also needed its own separate stage PR ([#231](https://github.com/rotnov/pycc/pull/231)) before it could activate, for the identical reason this note already describes -- see D-100's own Update note below for the full account. That stage PR registered `D100_COMPOSE_D91_D99_CI_WORKFLOW_SHA256` on `main` alongside this decision's own active digest before retiring it.
