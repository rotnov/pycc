## D-146: Preserve list bindings during private-helper constraint collection (#239)

- Status: accepted
- Context: The private-helper signature-inference solver (`infer_function_signatures_with_solver`) runs `collect_expr_constraints` over every expression in a module whenever any function has a `Ty::Infer` parameter or return. That collector's `ListLiteral`, `Subscript`, and `ListPop` arms all returned `Ok(None)` — no unification term — mirroring every other container arm under D-116's stated reasoning that this solver only infers scalar `Ty::Infer` parameters/returns and a container-producing expression has no unification-friendly term to give. The practical consequence was an actively misleading diagnostic: `def _first(): xs = [1]; return xs[0]` reported "local name `xs` is not bound before this use" (T0021) even though `xs` is assigned on the preceding line, because `collect_block_constraints`'s `Assign` arm only registers a binding when `collect_expr_constraints` produces `Some(term)` — an `Ok(None)`-producing assignment target never receives a solver binding at all, so a later read of that target inside the same solver-path function fails. This was the pre-existing D-116 solver binding gap, tracked as issue #239 and flagged in `docs/ROADMAP.md`'s v0.3 triage as directly relevant to the same binding-collection machinery `case` pattern capture bindings will need.
- Decision: Give `collect_expr_constraints` narrow capabilities to represent `Ty::List` as a destructured element-type carrier — never unified, only destructured. (1) The `ListLiteral` arm captures each element's term; when all elements produce `Some(Ok(ty))`, all element types are exactly equal (exact `Ty` equality, matching `infer_expr_in`'s own homogeneity rule — NOT `merge_inferred_types`, which would silently widen `bool` to `int`), and the shared element type is a private-solver scalar (`is_private_solver_scalar` — `Ty::Int`/`Ty::Float`/`Ty::Bool`/`Ty::Str`/`Ty::None`), it returns `Some(Ok(Ty::List(Box::new(element_ty))))`. Heterogeneous lists, empty lists, non-scalar element lists, or any element producing `None`/`Err` keep the historical `Ok(None)` behavior. (2) The `Subscript` arm captures the base's term; when the base resolves to `Some(Ok(Ty::List(Box::new(element_ty))))`, it returns `Some(Ok(*element_ty))`; otherwise it keeps the historical `Ok(None)` behavior (base/index recursion already propagated genuine errors). (3) The `ListPop` arm looks up `list` in `env.bindings`; when bound to `Some(Ok(Ty::List(Box::new(element_ty))))`, it returns `Some(Ok(*element_ty))`; otherwise `Ok(None)`. The `is_private_solver_scalar` gate prevents nested-container carriers (`list[list[int]]`) and non-scalar element types this solver has no representation for. `unify_terms` and `merge_inferred_types` are unchanged — the carrier is destructured, never unified. No codegen changes — the inferred return type is always a scalar (`Ty::Int` etc.), so the existing scalar codegen path handles it. No new diagnostic codes.
- Alternatives: give container-typed terms a real unification representation (rejected — D-116's own correction note identified this as needing two independent fixes, (a) a unification representation and (b) codegen's `emit_expr` container-result dispatch arm; this decision delivers only the narrower, lower-risk element-type carrier that fixes the scalar-return reproduction without touching unification or codegen); register a fresh-variable binding for every `Ok(None)`-producing assignment target (rejected — the plan's work item 4 flagged this as higher-risk since it changes behavior for all `Ok(None)`-producing assignments, not just list-element cases; work items 1+3 alone fix the reproduction, so the broader change is dropped to keep this minimal); use `merge_inferred_types` for list homogeneity (rejected — it would silently widen `bool` to `int`, diverging from `infer_expr_in`'s own exact-equality homogeneity rule and producing a different inferred element type than the real check pass would validate).
- Consequences: `collect_expr_constraints`'s `ListLiteral`/`Subscript`/`ListPop` arms now produce element-type terms for homogeneous scalar-element lists, enabling scalar return-type inference for `def _first(): xs = [1]; return xs[0]` and `def _pop(): xs = [1, 2]; y = xs.pop(); return y`. The carrier is destructured, never unified — `unify_terms` and `merge_inferred_types` are unchanged. `dict`/`set`/`tuple` remain in the scalar-only gap (their own `DictLiteral`/`SetLiteral`/`TupleLiteral`/`DictGetOrDefault` arms still return `Ok(None)`); closing those is a separate follow-up. `docs/TYPE_SYSTEM.md` notes the solver now carries `Ty::List` element-type info. `docs/ROADMAP.md`'s D-116 follow-up at the PR-11b paragraph is updated and #239 is marked resolved in the v0.3 triage. `docs/SPEC.md`'s DECISIONS.md range extends to D-146. The existing `list_pop_assigned_inside_an_unannotated_private_helper_hits_the_pre_existing_solver_binding_gap_today` test is updated from asserting T0021 to asserting successful compilation with return type `Ty::Int`. New unit tests cover all new behaviors and edge cases (heterogeneous, empty, non-scalar element, error propagation, `Subscript` on `Ty::List`-bound name, `ListPop` on bound list, `ListAppend` after binding, inline `return [1][0]`); new integration tests cover the end-to-end reproduction and an annotated companion.
