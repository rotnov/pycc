## D-149: Reuse `L0001` for context-invalid `yield`/`yield from`, not a new code (#361)

- Status: accepted
- Context: `pycc check` misclassified `yield`/`yield from` used outside any function body as `C0001` ("valid Python, just not implemented yet"). CPython 3.14 (verified directly against the pinned `python3.14` oracle, 3.14.6) rejects both as `SyntaxError` — `'yield' outside function` / `'yield from' outside function`, two distinct messages, not one — a context-invalidity failure, exactly the class D-148 established `L0001` for on the statement side (`break`/`continue`/`async for`). This is that decision's direct sequel for the expression side: `yield`/`yield from` are expressions, reached through `lower_expr`, a seam D-148 explicitly declined to touch (its own "Alternatives" note: "bundle `yield`-outside-function into this same change" — rejected because `lower_expr` is a separate seam D-148 does not touch). `lower_expr` had **zero** context parameters before this change and no `HirExpr::Yield`/`YieldFrom` representation at all — both fail during lowering itself, in every context, including the genuinely valid one (inside a real function), confirmed empirically (`pycc check` on `def f() -> None: yield 1` produced the same `C0001` "expression kind not supported yet" as the module-scope case, with no way to distinguish them).
- Decision: Reuse `L0001` again (same domain fit as D-148: CPython classifies this as a `SyntaxError`), and stay entirely inside `pycc_hir` rather than moving the check to `pycc_types`. The `pycc_types` alternative was re-examined, not merely inherited from D-148's precedent, and rejected on stronger grounds than the `break`/`continue` case: `pycc_types::check_stmt`/`check_stmt_in_function` already has a module-vs-function dispatch mechanism (`T0024`, `return` outside a function) that works specifically because `HirStmt::Return` is representable in HIR unconditionally; `yield`/`yield from` have no HIR representation at all today, so moving the check to `pycc_types` would require inventing new `HirExpr` variants, making `lower_expr` succeed for the valid case (out of scope — generator codegen is not implemented), and building a scope-aware dispatch `pycc_types::infer_expr` has no existing split for (unlike `check_stmt`, `infer_expr`/`infer_expr_in` is a single scope-agnostic function). Implementation: thread a new `in_function: bool` parameter through `lower_expr` and every function that transitively calls it, mirroring `in_loop`'s existing shape (D-148) but for the expression side. `false` at `lower_checked`'s module-level dispatch; `true` at `lower_function`'s body dispatch; every recursive `lower_expr` call inside `lower_expr` itself, and every pass-through call inside `stmt.rs`'s three functions, forwards the caller's value unchanged. New match arms, guarded so the valid-context (`in_function == true`) case falls through unchanged to the existing generic `other =>` fallback:
  ```rust
  Expr::Yield(y) if !in_function => {
      return Err(context_invalid("'yield' outside function", y.range));
  }
  Expr::YieldFrom(yf) if !in_function => {
      return Err(context_invalid("'yield from' outside function", yf.range));
  }
  ```
  Every position lexically *inside a comprehension*'s own scope (`if`-filter `cond`, `elt`, `key`, `value`) hardcodes a literal `true` instead of forwarding the ambient `in_function` value — deliberately preserving today's exact `C0001`-in-both-scopes behavior there. This is not an oversight: CPython's real rule for a comprehension-internal `yield` is a third, scope-independent classification (`'yield' inside list comprehension`, confirmed against the oracle — unconditionally invalid regardless of what encloses the comprehension, since Python 3.8 makes a comprehension its own implicit function scope), which this issue does not implement. Applying the ordinary scope-dependent `in_function` rule there would emit the wrong CPython wording at module scope while leaving the function-scope case silently wrong in the other direction. `lower_comprehension_iter`'s one `lower_range_call` call (the comprehension iterable's `range(...)` bounds) is a documented exception to that framing, not an application of it: a comprehension's outermost iterable actually evaluates in the *enclosing* scope per real CPython grammar (confirmed by a further oracle probe: `[x for x in range((yield 3))]` is `'yield' outside function` at module scope and valid inside a `def` — the ordinary scope-dependent rule, not the comprehension-internal one), so "comprehension-internal" is not the theoretically correct justification for hardcoding `true` there — it is a deliberate, conservative choice that reproduces today's behavior with zero regression risk while the enclosing-scope split for that one narrow sub-position is deferred (see Consequences).
- This refines, not supersedes, D-148's own "the two lowering passes stay independently parameterized" framing. That framing is true in the sense the two flags matter: `in_loop` and `in_function` never share a variable or collapse into one enum. It is incomplete about `stmt.rs`: D-148's `in_loop` lived entirely inside `stmt.rs` and never needed to reach `lower_expr`, so `stmt.rs` was untouched by that change's own signatures. This change's `in_function` *does* need to reach `lower_expr`, and the only route from the two places that decide it to `lower_expr` is through `lower_stmt`/`lower_body`/`lower_elif_else_clauses` — every one of those three functions calls `lower_expr` directly and recurses into itself. So `stmt.rs` gains a second, purely pass-through parameter here; its own `in_loop`-driven `break`/`continue`/`async for` logic is unchanged line for line.
- Alternatives: move the check to `pycc_types` (rejected — see Decision above: `yield`/`yield from` have no HIR representation to reach `pycc_types` with, unlike `T0024`'s `HirStmt::Return` precedent); a single shared `LowerCtx { in_loop: bool, in_function: bool }` struct instead of two plain bools (rejected — would still touch the same ~40 call sites regardless of whether the new state is a bare bool or a struct field, diverges from this repository's only existing precedent of plain bool parameters, and blurs `stmt.rs`'s/`expr.rs`'s ownership of their own context dimension); thread-local/ambient context to avoid touching call sites (rejected — no precedent anywhere in this lowering pipeline for implicit state; every other piece of context, `aliases`/`in_loop`/the alias table, is explicit-parameter-threaded, and ambient state would complicate the 100%-region-coverage gate's reachability reasoning).
- Module decomposition: per AGENTS.md's file-decomposition rule, mirroring D-148's own `stmt.rs` extraction, `lower_expr` and its comprehension/range helper cluster (`lower_range_call`, `lower_comprehension_iter`, `lower_comprehension_header`, `lower_list_comp_assign`, `lower_set_comp_assign`, `lower_dict_comp_assign`, `rename_name_in_expr`, `synthesize_comp_var_name`) were extracted from `lib.rs` into a new `crates/pycc_hir/src/expr.rs`, `pub(crate) mod expr;`, in the same commit as the `in_function` threading. `unsupported()`/`context_invalid()` stay in `lib.rs`, visible to both sibling modules as private items of an ancestor module, the same D-148 precedent. Unlike `stmt.rs`'s own extraction, this one is not fully test-transparent: two existing unit tests (`lower_comprehension_header_rejects_an_empty_generators_slice`, `rename_name_in_expr_rewrites_every_hir_expr_variant`) call cluster functions directly, bypassing the public `lower_checked` entry point. Both stayed in `lib.rs`'s existing `mod tests`, with an explicit `use crate::expr::{lower_comprehension_header, rename_name_in_expr};` added to that module so the direct calls keep resolving (a `super::*` glob import only reaches items defined directly in `lib.rs`, not items re-exported from a sibling module).
- Consequences: `pycc check` now reports `L0001` for `yield`/`yield from` used at module scope or nested inside a module-scope `if`, while the same constructs inside a real function body keep their prior `C0001` classification (generator codegen remains out of scope), and every comprehension-internal position (`if`-filter, `elt`, `key`, `value`, and the outermost iterable) is unchanged, staying `C0001` in both scopes. New unit tests in `crates/pycc_hir/src/lib.rs`'s existing `mod tests` cover both directions, a module-scope-nested-in-`if` regression guard, and a comprehension-internal regression-pinning guard. New CLI fixtures (`tests/diagnostics/l0001_yield_outside_function`, `l0001_yield_from_outside_function`, paired with `c0001_yield_inside_function`/`c0001_yield_from_inside_function`) follow the same not-byte-for-byte-oracle-diffed convention D-148 established. `docs/DIAGNOSTICS.md`'s `L0001` row is extended to also cover this second post-parse HIR-lowering case, cross-referencing this ADR alongside D-148. `docs/ROADMAP.md`'s v0.3 triage paragraph marks #361 resolved. Getting the comprehension-internal classification (the third, scope-independent CPython rule) and the outermost-iterable enclosing-scope split fully correct remain explicitly out of scope, along with `await` — a real but separate candidate for the same `in_function` pattern, investigated during this issue's planning and found to interact with comprehension async-ness in a way that needs its own dedicated verification pass; not folded into this change.
