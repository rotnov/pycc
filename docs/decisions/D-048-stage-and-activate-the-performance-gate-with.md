## D-048: Stage and activate the performance gate with exact-predecessor artifacts

- Status: accepted (supersedes D-047's timing deferral and D-046's Actions-cache transport; preserves D-044's required-gate invariant and D-046's successful-main-only provenance)
- Context: PR-4 has merged, so its compiler delivery is no longer coupled to the competing trust-anchor branch that forced D-047's temporary deferral. Review of the deferred workflow also found that ref-scoped Actions-cache fallback could select PR-local or non-predecessor state, and that treating every cache miss as a bootstrap would silently disable the >2% merge block after eviction or a failed publication. GitHub run artifacts provide immutable run identity, an explicit source run, retention metadata, and an API surface that can be filtered and independently revalidated against the exact predecessor commit. The first split-workflow pull request and its first `main` push still cannot have such an artifact, so activation needs one narrowly bounded transition rather than a reusable missing-baseline rule.
- Decision: land the transition in three reviewed phases. First, while the pre-split workflow remains active, check in inert byte-exact fixtures for both the activation workflow and its bootstrap-free steady-state successor; the trusted base checker binds their whole-file digests and validates the complete `frontend-perf-measure`, `frontend-perf-gate`, and aggregate `ci-gate` shapes for each. Second, create the activation branch from the refreshed post-staging `main` and replace `ci.yml` byte-for-byte from the activation fixture; after tests and independent review, an administrator confirms `PERF_ACTIVATION_HEAD` is absent, sets that repository Actions variable to the one final head SHA, reads it back, and records the base SHA, head SHA, setter, timestamp, and verified value in the activation PR. No later commit is permitted on that attempt. If the base or head must change, delete and verify removal of the variable, close the attempt, refresh/re-review, and only then set a replacement value. Pull requests query successful `push` runs of `ci.yml` on `main` for the exact `pull_request.base.sha`; main pushes query the exact `push.before` SHA. The gate revalidates every returned `head_sha`, skips expired artifacts, and downloads `frontend-perf-current` by explicit repository and run ID. A missing exact-predecessor artifact fails closed except during activation: the pull-request half requires run attempt 1, the exact variable-bound head, target `main`, a base SHA equal to the live `main` head, and the pre-split predecessor digest. The activation push half requires `refs/heads/main`, matching event/checkout/live-main SHAs, and that same predecessor digest; retries of that exact push remain eligible so a flaky or cancelled first run cannot permanently prevent baseline publication, while any different or superseded main SHA fails closed. Third, after a successful activation push publishes the first 90-day artifact, immediately delete and verify removal of the variable, record that evidence, replace `ci.yml` byte-for-byte from the already-reviewed steady-state fixture, and remove both bootstrap branches plus the pre-split and activation digests while retaining only the steady-state digest.
- Alternatives: retain D-046's main-scoped cache (rejected because restore-key lookup is ref-sensitive and cannot prove an exact predecessor); compare with the newest successful main run (rejected because overlapping workflows can make that run older than the PR's actual base); check in generated timing data (rejected because noisy machine-dependent output would become source state); hardcode the activation commit in its own workflow (impossible because the commit SHA depends on the bytes that would contain it); keep a mutable bootstrap variable permanently (rejected because an administrative transition value must not become a feature flag).
- Consequences: D-047's PR-6 delay ends once the staged activation completes, but the staging commit itself must remain honest that the gate is not active yet. Performance measurements are untrusted data, while comparator code and baseline provenance remain main-owned and hash-verified. Strict up-to-date protection determines sequencing: the activation head is finalized only after the staging merge, then recorded and audited once; any later base or head change invalidates that attempt and requires the documented delete/refresh/re-review/set lifecycle. The transition is incomplete until the first main artifact exists and the cleanup removes all bootstrap state. After cleanup, a missing, expired, cancelled, or non-exact predecessor artifact is a merge-blocking failure, never a new bootstrap.
