## D-092: `--release` also links a release-built `pycc_rt`, not always the debug build

- Status: accepted
- Context: PR-8, Task 5's `tests/nbody_bench.rs` (D-094's harness) measured pycc `--release`'s nbody speedup far short of expectations. Root-cause investigation found `src/main.rs::find_pycc_rt_lib_dir`/`find_pycc_rt_lib_dir_in` unconditionally resolved `target/debug` (or `target/<triple>/debug`) regardless of the `--release` flag — `--release` only ran LLVM's O3 pipeline over the *compiled module's own IR*, never selecting an optimized `pycc_rt` static library to link against, so every runtime call (`pycc_rt_float_pow` included) ran through unoptimized debug code even under `--release`.
- Decision: `find_pycc_rt_lib_dir`/`find_pycc_rt_lib_dir_in` gain a `release: bool` parameter, resolving `target/release` (or `target/<triple>/release`) when true; `try_build`'s own already-resolved `release` bool threads through to this lookup. The "no build found" error message now suggests `cargo build --release [--target ...] -p pycc_rt`. CI gains a "build `pycc_rt`, release profile" step on `build-test-coverage` and every `native-build-test` leg (5 Tier-1 targets), alongside each leg's existing debug-profile step, since nothing built a release `pycc_rt` there before and `tests/nbody_bench.rs`'s `--release` benchmark needs one to actually exist.
- Alternatives: build `pycc_rt --release` lazily inside `tests/nbody_bench.rs`'s own Rust test code (e.g. shelling out to `cargo build --release -p pycc_rt` at test-run time) instead of a dedicated CI step — rejected: this would make the ignored benchmark test itself responsible for a build side effect unrelated to what it measures, paid on every invocation rather than once per job, and undiscoverable from the job log the way every other leg's existing debug-profile build step already is.
- Consequences: this decision's own release-profile `pycc_rt` CI step was staged as `D90_RELEASE_PYCC_RT_CI_WORKFLOW_SHA256` (PR #187), then found incomplete before it ever activated — `build-test-coverage`'s own isolated `nobody` sandbox built `pycc_rt` for its cross-compile target and in debug profile, but never in release profile, so `tests/pycc_toml_release_default.rs`'s non-ignored test would have failed the moment that digest went live. D-091 folded the missing coverage-sandbox build into its own composed digest (PR #189) alongside an unrelated, independently-discovered fix (relaxing `frontend-perf-measure`'s manifest contract) and superseded D-090's fixture entirely; this same v0.2 PR-8 merge activates D-091's composed digest, so this decision's release-profile build step is live in `ci.yml` today via that composed digest, not via a dedicated D-092 digest of its own. `ci.yml`'s own release-`pycc_rt` step comments still literally say "D-091" — that text names main's own D-091 CI-fix decision (a different, unrelated decision from this branch's own renumbered D-092/D-093/D-094), which is correct as written and needs no exemption or rename.
