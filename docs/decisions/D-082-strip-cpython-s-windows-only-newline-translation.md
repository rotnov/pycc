## D-082: Strip CPython's Windows-only newline translation before the conformance byte-for-byte comparison

- Status: accepted
- Context: an adversarial review of Task 6's CI-wiring fix (D-080) confirmed a real bug the review's own security lens didn't catch: once the fix makes `native-build-test`'s Windows leg actually resolve and run the CPython oracle (instead of panicking on a missing `python3.14`, D-080's own bug), `tests/conformance.rs`'s raw `assert_eq!(pycc_stdout, cpython_stdout)` would fail on essentially every line boundary. CPython's `sys.stdout` is a `TextIOWrapper` opened with `newline=None` on Windows, which translates every `\n` written by `print()` into `\r\n` at the io layer -- and this happens even when stdout is piped/redirected to a child-process capture (confirmed via CPython's own bug tracker: bpo-11990 "redirected output - stdout writes newline as \n in windows" and bpo-13119 "Newline for print() is \n on Windows, and not \r\n as expected," both resolved as intentional, stable since 3.2.4/3.3, and reproduced there with `subprocess.check_output`, the same capture shape `tests/conformance.rs` uses via `Command::output()`). `pycc_rt`'s `print()` is implemented with Rust's `println!`/`print!` macros, which never perform platform-specific newline translation on any target. This translation is a quirk of CPython's own C runtime's stdio layer, not part of the Python language's `print()` semantics -- nothing in the language specifies that `\n` becomes `\r\n` on any platform.
- Decision: add `tests/conformance.rs::strip_windows_newline_translation`, applied to the CPython oracle's captured stdout only (never to pycc's own output, which needs no correction) before the byte-for-byte comparison. It removes every `\r` immediately followed by `\n`, leaving any other byte -- including a lone `\r` not followed by `\n` -- untouched. This runs unconditionally on every platform (not gated behind `cfg!(windows)`), since it is a no-op on platforms where CPython never inserts the `\r` in the first place, keeping the function and its regression test (`strip_windows_newline_translation_removes_cr_before_lf_only`) simple and uniformly exercised everywhere rather than only under a Windows-only test path.
- Alternatives: reconfigure the fixture `.py` files themselves (e.g. `sys.stdout.reconfigure(newline='\n')`) to suppress CPython's translation at the source (rejected -- this adds Windows-specific plumbing into fixtures that are meant to be plain, portable Python programs, and D-085/Task 4/5 already fixed these fixtures' exact source; changing them again for an unrelated platform-io concern is out of scope and would need re-verifying their already-reviewed byte-exact provenance). Normalize both sides symmetrically, e.g. via a general `\r\n`/`\r`/`\n`-to-`\n` line-ending canonicalization (rejected as broader than necessary -- pycc_rt provably never emits `\r` on any target, so a one-directional, narrowly-targeted strip is simpler to reason about and cannot silently mask a genuine `\r` byte pycc itself produced). Skip or gate the conformance tests on Windows entirely (rejected -- defeats Task 6's own stated goal of running the real oracle diff on every Tier-1 target, and CPython's line-ending translation is well-understood, stable, decade-old behavior, not a source of genuine platform ambiguity).
- Consequences: the byte-for-byte comparison now checks program-output content across all 5 Tier-1 targets uniformly, independent of which OS's stdio layer produced the oracle's bytes. A future third conformance fixture needs no special Windows handling of its own -- `run_conformance_fixture` applies the strip for every caller. This PR's originally-planned D-080 slot for Task 8's CLI_SPEC.md fix, already renumbered once to D-081 and then to D-082 by two prior concurrent-ID collisions, is renumbered again to D-083, since this decision claimed D-082 first while closing out Task 6's review findings.
