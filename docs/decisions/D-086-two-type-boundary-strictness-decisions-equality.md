## D-086: Two type-boundary strictness decisions -- equality confirms, numeric widening exceeds, `mypy --strict`

- Status: accepted
- Context: two independent read-only frontend audits (#116, #122) each found a case where `pycc check` rejects standard, unambiguous Python that CPython accepts: `1 == "1"` (#116, `crates/pycc_types/src/lib.rs`'s `HirExpr::Compare` arm reuses `numeric_or_bool_compatible` for `Eq`/`NotEq` and ordering alike) and `identity(1)` for `def identity(value: float) -> float` (#122, `is_assignable` in the same file only permits exact-type equality plus `bool`→`int`). `docs/TYPE_SYSTEM.md`'s own contract states "checking is strict -- what mypy calls `--strict` is pycc's only mode." Empirically verifying both cases against `mypy` 2.3.0 settles which side of that contract each one falls on: `mypy --strict` (specifically its `--strict-equality`/`comparison-overlap` check) rejects `1 == "1"` exactly as pycc does today, but `mypy --strict` *accepts* `identity(1)` unconditionally -- the Python typing spec's numeric-tower special case ("an `int` is acceptable where `float` is annotated") is not gated behind any mypy strictness flag, because rejecting it would make a type checker non-conformant with the spec it implements, not merely stricter. Ordering operators (`<`/`>`/`<=`/`>=`) between incompatible types are untouched by this decision in either direction: CPython itself raises `TypeError` for these at runtime, so pycc rejecting them at compile time was never in question (both issues' own "control case" reproductions confirm this).
- Decision: keep both diagnostics as hard `T0021` compile errors, unchanged from current behavior, and record the rationale explicitly rather than leave it an undocumented accident of `numeric_or_bool_compatible`/`is_assignable`'s shared implementation:
  1. `==`/`!=` keep using `numeric_or_bool_compatible`'s existing rule: operands are comparable if both are in the numeric-like group (`int`/`float`/`bool`, interchangeably -- so `1 == 2.5` and `True == 1` both type-check as `bool`) or both `str`. This is *not* the same, stricter relation `is_assignable` enforces at parameter/return/assignment boundaries (exact type, plus `bool`→`int` only) -- it is the same relation ordering operators already use. Confirming this rejects genuinely incompatible pairs (`int`/`str`) is not a new deviation -- it is `docs/TYPE_SYSTEM.md`'s already-declared "mypy --strict is our only mode" contract, made explicit, since neither the spec nor the deviation ledger previously named this case (#116's own finding).
  2. Numeric widening (`int` accepted where `float` is annotated) at a parameter, return, or annotated-assignment boundary requires an explicit conversion rather than an implicit one. This *does* go beyond `mypy --strict`, deliberately: pycc's own runtime representation makes `int`→`float` a real, non-trivial bit-level conversion at every crossing (D-001/D-061's tagged 63-bit fixnum vs. a native, unboxed `f64`, per `docs/TYPE_SYSTEM.md`'s representation table), not a free reinterpretation the way CPython's uniform object model makes it look. Requiring the conversion to be visible in source, rather than silently inserted by the compiler at a boundary, matches this project's general preference for explicit over implicit (the same reasoning already applied to `Any`, rule 3, and implicit narrowing, rule 4). **This decision's remedy is not yet usable**: pycc has no callable `float(...)` (or any other numeric-conversion builtin) today -- `HirExpr::Call`'s type-checking (both `infer_expr_in` and the private-helper inference path `collect_expr_constraints` in `crates/pycc_types/src/lib.rs`) only special-cases `callee == "print"`, so `float(x)` itself produces `T0021: call to undefined function `float``. Implementing it is tracked as separate follow-up work in #181, reusing the existing `int_to_float`/`pycc_rt_int_to_float` runtime conversion (`crates/pycc_rt/src/lib.rs`) and the existing `to_float` codegen helper (`crates/pycc_codegen/src/lib.rs`) that already promotes `int`/`bool`/`float` scalars for arithmetic-operator promotion. Until #181 lands, an `int` value cannot actually be moved across a `float`-typed boundary in pycc at all; this decision fixes what the *rule* should be, not that a conversion path already exists. No `Severity::Warning` path exists anywhere in the compiler today (`pycc_diag`'s `Severity::Warning` variant is exercised only by that crate's own unit tests, under a placeholder `W1001` code; no production diagnostic uses it, and no exit-code logic in `src/main.rs` distinguishes severities) -- introducing one for this single case, where the only sensible non-blocking behavior would be to silently perform the conversion anyway, would both require new infrastructure and undermine the explicitness this decision exists to enforce.
  3. Arithmetic-operator promotion is explicitly out of scope and unaffected: `1 + 2.5` still computes a fresh `float` result via `numeric_result_type`'s existing operator-level rules -- that is a new value produced by an operation, not an existing value re-typed across a boundary, and no accepted decision (D-001/D-058/D-061) or `docs/ROADMAP.md` text governing it is touched here.
- Alternatives: accept both as CPython/typing-spec compatibility (the issues' own proposals) -- rejected for #122 specifically per this decision's rationale above; for #116, rejecting is actually the status quo consistent with the project's own stated contract, so "accepting" would have been the deviation, not the fix. Add a genuine warning severity and silently promote `int` to `float` at boundaries -- rejected: no warning infrastructure exists, building it for one case is disproportionate, and silent promotion defeats the purpose (a warning nobody reads while the compiler still does the implicit thing is not meaningfully different from no diagnostic at all). Split equality and ordering into fully separate compatibility functions even though they now enforce the same rule -- rejected as unnecessary: the current shared `numeric_or_bool_compatible` already produces the correct answer for both under this decision, so splitting it would add indirection with no behavioral benefit.
- Consequences: no production code changes -- `numeric_or_bool_compatible` and `is_assignable` are correct as they stand. `crates/pycc_types/src/lib.rs` gains one new regression test, `an_int_argument_for_a_float_parameter_is_a_clean_error`, alongside the pre-existing `comparing_a_string_and_an_int_is_a_clean_type_error`, so both halves of this decision have an explicit, named regression rather than resting on incidental coverage. `docs/TYPE_SYSTEM.md` gains an explicit strictness rule for equality-vs-ordering and rewrites rule 4 from "no implicit numeric narrowing" to "no implicit numeric narrowing or widening" without naming `float(...)` as a working remedy, closing the gap both issues' own audits found in the specification. Issues #116 and #122 are closed as decided-not-to-change (their as-filed requests to loosen pycc's behavior are declined), not as bugs fixed, since no code changed; #122's close comment notes that the conversion this decision requires does not exist yet in-language and is tracked separately as #181. **Correction (2026-08-03, #181):** point 2's own bolded sentence above ("**This decision's remedy is not yet usable**: pycc has no callable `float(...)` ... today ... Until #181 lands, an `int` value cannot actually be moved across a `float`-typed boundary in pycc at all") no longer holds. `#181` implemented `float(x)` for `x: int | float | bool` as a hand-recognized builtin, mirroring `len()`'s own three-crate dispatch shape (`crates/pycc_types/src/lib.rs`'s `infer_expr_in` and `collect_expr_constraints`, `crates/pycc_mir/src/lib.rs`'s `lower_expr`, `crates/pycc_codegen/src/lib.rs`'s `emit_expr`), reusing the existing `int_to_float`/`pycc_rt_int_to_float` runtime conversion and `to_float` codegen helper this decision already named as available. An `int` value can now be moved across a `float`-typed boundary in-language (`def f(x: int) -> float: return float(x)`), satisfying this decision's own point 2 for the first time -- for a smallint-range `int`; a bigint-valued `int` (produced by arithmetic overflow, e.g. `float(fib_iter(100))`) still aborts via `require_smallint`, the same pre-existing "no bigint-to-float" limitation every other numeric promotion through `to_float` already has (post-merge review finding: reproduced directly, e.g. `fib_iter(100) + 1.5` hits the identical abort on `main` before this PR), not a new gap `float()` introduces -- see `tests/slice1_codegen_depth.rs`'s `a_float_call_on_a_bigint_argument_aborts_honestly` test, mirroring the existing `list_append_bigint_aborts` precedent. `float("...")` (string parsing) remains unimplemented and out of scope (rejected with `T0021`, the same code every other ordinary call's argument-type mismatch already uses -- `len()` is the deliberate exception: its `T0033` reuse is domain-specific to container operations, per D-105 point 3 -- so no new diagnostic code was minted for `float`); `int(...)`/`bool(...)`/`str(...)` conversions remain entirely unimplemented and unaffected. **Further correction (2026-08-03, post-merge review):** the paragraph above, as originally written, also failed to guard the builtin against a user-defined `float`: `def float(x: int) -> int: return x + 1` was a valid, working program on `main` immediately before this PR (verified directly against a pristine checkout, printing `6`), and the initial hand-recognized dispatch would have silently reinterpreted it as this builtin instead, producing `5.0`. All four dispatch sites now check for a registered user function first, mirroring `len`/`print`'s own dispatch order except for this added guard (which `len`/`print` do not need, since no currently-valid program predates their own introduction as builtins) -- see `crates/pycc_types/src/lib.rs`'s `a_user_defined_float_function_takes_priority_over_the_builtin` and its sibling tests in `pycc_mir`/`pycc_codegen`/`tests/slice1_codegen_depth.rs`.
