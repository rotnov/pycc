## D-135: `type` statement and legacy `TypeAlias` are compile-time-only name substitution, no runtime or `Ty` representation

- Status: accepted
- Context: design doc §2 groups PEP 695's `type` statement and PEP 613's legacy `TypeAlias` syntax as "the same underlying alias mechanism." Verified at PR-13 task-start: `crates/pycc_ast/src/lib.rs`'s `stmt_range` already matches `Stmt::TypeAlias(ruff_python_ast::StmtTypeAlias { range, .. })` (the vendored parser already produces this node for `type X = ...`; a legacy `X: TypeAlias = ...` parses as an ordinary `Stmt::AnnAssign`/`Stmt::Assign` with `TypeAlias` as an ordinary annotation expression, not a distinct AST node), but `pycc_hir`'s `lower_stmt` has no dedicated arm for either shape today, so both currently fall through to the generic `C0001` "statement kind not supported yet" catch-all (the same fate PR-11 recorded for `CmpOp::In` and PR-12 for `Expr::UnaryOp`).
- Decision: both the `type X = <expr>` statement and a legacy `X: TypeAlias = <expr>` assignment are resolved entirely inside `pycc_types`/`pycc_hir` as a **compile-time name-to-`Ty` binding table**: lowering a `Stmt::TypeAlias` (or an `AnnAssign` whose annotation is exactly the name `TypeAlias`) evaluates its RHS expression as a type expression (reusing the existing annotation-to-`Ty` resolution path already used for parameter/return annotations) and records `alias_name -> Ty` in a module-scoped table consulted wherever an annotation expression is later resolved. No `HirItem`/`MirItem` is emitted for the alias itself — it produces zero HIR nodes, zero MIR nodes, and no runtime object; it is purely a preprocessing step that lets a later annotation spell a `Ty` two different ways. A generic alias (`type Alias[T] = list[T]`) is out of scope for v0.2 (no generic classes and no container-of-type-parameter per D-134): a `type` statement's own left-hand side is rejected pre-codegen with `T0042` if it declares type parameters, reusing the same diagnostic code as D-134's generic-function rejection cases since both are "generic shape beyond this PR's one-type-parameter, non-container thin slice."
- Alternatives: represent an alias as a real `Ty::Alias(String, Box<Ty>)` variant that downstream code has to unwrap (rejected — every other `Ty` consumer would need a new match arm purely to strip a wrapper that carries no information not already available by resolving the alias eagerly at the point of use, unlike `Ty::Param`, D-133, which genuinely carries information downstream code cannot discharge until a call site is known); defer resolution to `pycc_mir`/`pycc_codegen` (rejected — an alias is a pure naming convenience with no runtime existence in real Python either; resolving it any later than annotation-checking time would require every later pipeline stage to know about aliasing for no benefit).
- Consequences: `pycc_hir`/`pycc_types` gain a small new preprocessing pass (record each alias binding into a module-scoped table as lowering reaches it, strictly left-to-right in source order — an alias is visible to every later annotation but not to any earlier one, so a `type` alias used before its own statement is an ordinary unknown-annotation `C0001`; there is no hoisting pass) and one new diagnostic reuse (`T0042` shared with D-134's generic-shape rejections, not a fifth new code). `pycc_mir`/`pycc_codegen` require no changes at all for this feature. `docs/TYPE_SYSTEM.md`'s Generics section, which already asserts "PEP 695 syntax ... and legacy `TypeVar` both supported" as an aspirational v1.0 statement, is corrected to describe the v0.2 thin slice precisely (D-134/D-135's own scope, not the full PEP 696-defaults/variance-inference model that sentence currently implies is already true).
