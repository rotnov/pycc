## D-109: PR-10's `frontend-perf-gate` regression is real and self-inflicted; fix deferred to its own follow-up PR, merge stays blocked

- Status: accepted
- Context: PR #236's (this branch's) `frontend-perf-gate` failed CI, first at a 4.7008% median regression (previous aggregate 5540.68ns, current 5801.13ns; threshold 2.00%) and, on one independent `--failed`-only rerun, at a run whose own log turned out to interleave `scripts/check_replicated_paired_perf_regression.rb`'s own unit-test fixture output (synthetic round-number timings such as "1000.00"/"1020.01" ns) with the real gate invocation — that rerun's `frontend-perf-measure` step carried the same `startedAt` timestamp as the original run, confirming it reused cached measurement artifacts rather than remeasuring, per this project's own D-095/D-096/D-101 "check whether the rerun actually remeasured" methodology. A second, full (not `--failed`-only) rerun of the whole workflow produced a genuinely fresh, independent measurement — new `frontend-perf-measure` timestamps, a different previous-baseline sample (5589.76-7201.75ns band, median 6083.97ns) than the first run's — and failed again, at 5.1960% (current aggregate 6400.09ns). Two independent, genuinely-fresh measurements landing at 4.7008% and 5.1960%, both several points over the 2.00% threshold and in the same direction, is inconsistent with pure noise canceling out; it reads as a real, reproducible regression, not a noisy near-miss.

  `benches/check_bench.rs`'s `pycc_check_frontend_fixture` (the benchmark this gate measures) runs `pycc_parser::parse` → `pycc_hir::lower_checked` → `pycc_types::check` on a small, scalar-only fib fixture — no `list[T]` value is ever constructed or type-checked by it. This rules out "the new list codegen is slow" and points at PR-10's own earlier `Ty` representation migration (D-089/D-104, Tasks 2-5): `crates/pycc_hir::Ty` changed from a flat, fieldless, six-variant `#[derive(Copy, Clone, ...)]` enum (a throwaway `size_of`/`align_of` check confirmed the new shape is `size_of::<Ty>() == 24` bytes, `align_of::<Ty>() == 8`, with `Copy` dropped since a `Box`/`Vec`-holding enum cannot derive it) to a recursive enum carrying `List(Box<Ty>)`, `Dict(Box<Ty>, Box<Ty>)` (two boxes), and `Tuple(Vec<Ty>)` (a growable heap vector). `pycc_types::check`'s constraint-solving path constructs and clones many `Ty` values per checked expression — a 24-byte, non-`Copy`, sometimes-heap-touching value copied/cloned in place of what was previously a 1-byte `Copy` value is a highly plausible, mechanically-explained cause for a several-percent regression on a type-checking-heavy hot path, without needing to invoke CI noise at all.
- Decision: treat this as a confirmed, real, self-inflicted regression, not environmental noise, and do not attempt to route around the gate. Specifically: do not lower or exempt `frontend-perf-gate`'s 2.00% threshold, do not merge PR-10 while `ci-gate` is red (D-024's hard branch-protection gate has no exception for "the author is confident it's fine"), and do not implement the fix (most likely: box `Dict`'s two fields into a single `Box<(Ty, Ty)>` and `Tuple`'s `Vec<Ty>` into a `Box<[Ty]>`, shrinking every variant to one pointer-sized payload and very plausibly letting Rust's niche-filling layout shrink `Ty` back close to its pre-migration size) inside this PR's own Task 13. PR-10's `list[int]` slice itself is fully implemented, independently task-reviewed, and merge-ready on its own merits (all 5 Tier-1 targets plus `build-test-coverage`, `cross-compile-build`, and `cross-compile-verify` are green on this exact commit) — only frontend scalar-checking throughput is regressed, and that fix deserves its own task brief, its own implementer, and its own independent review, exactly like every other PR-10 task, rather than a late, unreviewed amendment squeezed into the task that was supposed to just open and merge the PR.
- Alternatives: lower or add an exemption for `frontend-perf-gate`'s threshold (rejected — unlike D-095/D-096/D-101, which relaxed floors only after confirming an external, architecture-specific hardware constraint neither PR could fix, this regression is self-inflicted by this PR's own code change and has a concrete, identified remedy; relaxing the gate here would be exactly the "adjust the knob to force a pass" move this project's own conventions reject). Implement the `Ty`-boxing fix directly as part of Task 13 (rejected — this would change the representation Tasks 2-5 already migrated ~857 call sites against, after every one of those tasks' own reviews already closed and the pinned reviewer's passes already ran against the current shape; landing it unreviewed, this late, is the exact failure mode this PR's whole task-by-task review discipline exists to prevent). Merge anyway with `ci-gate` red (rejected outright — violates D-024's protected-`main` branch protection, which has no bypass for ordinary work). Dismiss the result as noise without a second independent measurement (rejected — this project's own established methodology, applied successfully in D-093/D-095/D-096/D-101, is to get a genuinely fresh rerun before concluding noise; here two fresh, independent measurements agreed in direction and rough magnitude, which is itself evidence against the noise hypothesis).
- Consequences: PR #236 stays merge-blocked pending a dedicated follow-up PR (or an accepted superseding decision) that resolves this regression — tracked as a `docs/ROADMAP.md` follow-up alongside this entry, not silently left for a future reader to rediscover. That follow-up PR's own task should re-measure `size_of::<Ty>()`/`align_of::<Ty>()` after boxing `Dict`/`Tuple`, confirm the boxing's blast radius is actually small (D-104's own scope note that v0.2 never constructs a real `Dict`/`Tuple`/`Set` value means most exhaustive-match call sites should be catch-all panics untouched by the exact field shape, but this must be verified against the live tree, not assumed), and re-run `frontend-perf-gate` to confirm the regression closes before that PR merges. If a future investigation instead finds the regression does not close by boxing alone, that finding supersedes this decision's own remedy paragraph without needing to revisit whether the regression itself was real. **Cross-reference note:** this entry's Decision and Alternatives sections above describe the fix as needing "its own follow-up PR" separate from this one — that framing turned out to be mechanically impossible to execute as written: the regressed `Ty` shape this decision describes exists only on this branch (`feat/v0-2-pr10-ty-representation-migration`), never having reached `main`, so no PR opened against `main` could carry a fix for it. The review-discipline concern that framing was actually protecting — no unreviewed representation change landing without its own brief, implementer, and independent review — is fully satisfied instead by a new Task 14 added to this same plan and executed on this same branch, through the identical task-review loop every other task in this plan already passed through. This entry's own Decision/Alternatives text is left unedited per this file's append-only convention (the same convention D-108's own cross-reference note against D-106 already applied); a reader following this decision's "its own follow-up PR" language should resolve it as "Task 14, this branch" instead. **Update (Task 14):** `Ty::Dict` is now `Dict(Box<(Ty, Ty)>)`, exactly as this decision's remedy paragraph proposed, and needed only one attempt. `Ty::Tuple` needed two: a first attempt boxed it as `Tuple(Box<[Ty]>)` (a boxed slice) and measured `size_of::<Ty>() == 24` bytes — no reduction at all from the pre-fix size — confirmed independently both in-crate and via a standalone `rustc` reproduction of the isomorphic enum shape; this was a genuine dead end, not a measurement error. A second attempt, `Tuple(Box<Vec<Ty>>)` (a second indirection: a thin pointer to a heap-allocated `Vec<Ty>`), measured `size_of::<Ty>() == 16` bytes (down from 24), confirmed the same way; `align_of::<Ty>()` stayed `8` in both configurations and in the pre-fix shape. The most plausible explanation is that `Box<[Ty]>` (a 16-byte fat pointer: data pointer + length) broke a uniform-thin-pointer shape that `List`/`Dict`/`Set`'s `Box<Ty>`/`Box<(Ty, Ty)>` (8-byte thin pointers each) already had, defeating rustc's niche-filling layout optimization (the mechanism that makes `size_of::<Option<Box<T>>>() == size_of::<Box<T>>()`) and forcing a full explicit discriminant tag on top of the largest variant's payload; `Box<Vec<Ty>>` restores that uniformity. This project has **not** independently re-derived rustc's exact layout algorithm well enough to state that as a proven universal rule, though — this entry's own pre-fix measurement (`Ty` already had non-uniform dataful variant sizes: `List` 8B, `Dict` 16B as two separate `Box<Ty>` fields, `Set` 8B, `Tuple` 24B as `Vec<Ty>`) still measured 24 bytes with *no* added discriminant tag, which a naive "tag plus largest payload" rule would instead put at 32. The measured `size_of`/`align_of` numbers above are the authoritative facts this decision relies on; the niche-filling explanation is offered as the most plausible mechanism, not an independently proven one. Separately, and independent of the exact mechanism: this is a real, predictive reduction for `frontend-perf-gate`'s own fixture specifically, not just a smaller number in the abstract — `benches/check_bench.rs`'s fixture is scalar-only, so every `Ty` value it ever constructs is one of the six zero-sized variants (`Int`/`Float`/`Bool`/`Str`/`None`/`Infer`) — it never constructs a `List`/`Dict`/`Set`/`Tuple` value and so never triggers a `Box::clone()` heap allocation regardless of container field shape. The only channel by which this change can affect that benchmark is `Ty`'s uniform in-memory size, which every move or clone of a `Ty::Int` pays regardless of which variant is actually active (Rust enums are fixed-size across all variants) — so 24→16 bytes is a real reduction in that benchmark's own copy cost, not a hopeful analogy from an unrelated code path. This also rules out, for this specific benchmark, the competing hypothesis (raised during the first, blocked attempt at this task) that `Ty` losing `Copy` rather than its byte width is the real driver of the regression: for a fieldless variant like `Ty::Int`, `Clone` literally is the memcpy, so there is no additional non-`Copy` cost beyond the width itself on this fixture's own hot path. This entry still does not claim `frontend-perf-gate` is confirmed closed — a smaller `Ty` is necessary but a fresh full CI rerun (not `--failed`-only) observing genuinely new `frontend-perf-measure` timestamps and replicate medians is required before that determination can be made, exactly as this decision's own remedy paragraph already said. **Update (confirmed closed):** two independent, genuinely fresh full CI reruns of the same commit (`c276262`, [run 30613065177](https://github.com/rotnov/pycc/actions/runs/30613065177)) both passed `frontend-perf-gate`, each with its own fresh `frontend-perf-measure` timestamps and distinct replicate-median samples (ruling out cached/`--failed`-only reuse, the exact failure mode that produced a misleading "second data point" earlier in this investigation): the first measured a 1.8430% delta (previous aggregate 5764.39ns, current 5870.62ns), the second measured **-0.4454%** (previous aggregate 6099.61ns, current 6072.44ns — current is not just within threshold but marginally faster than previous). Both comfortably clear the 2.00% threshold, in sharp contrast to the two pre-fix measurements (4.7008%, 5.1960%) that both cleared it in the opposite direction — a swing of this size across two independent before/after measurement pairs is not consistent with the fix being noise-neutral; it is real. D-109's regression is confirmed resolved. PR #236 is no longer merge-blocked by this decision.

  **Correction (2026-07-31, full CI record reconciled against live job logs):** the "confirmed closed" update above does not survive a check against the actual, currently retrievable CI job logs, and a wider review of every `frontend-perf-gate` measurement taken across this investigation contradicts both this decision's "confirmed closed" update and, more seriously, casts real doubt on the original "confirmed regression" conclusion itself. Specifics, each verified directly from `gh run view --job <id> --log` against the cited run/job IDs, not reconstructed from memory:
  - Run 30613065177's two attempts (`c276262`) are **not** two independent measurements: both attempt 1 (job 91101229723) and attempt 2 (job 91102182946) show byte-identical replicate medians and an identical **-0.4454%** delta (previous aggregate 6099.61ns, current 6072.44ns) — attempt 2 reused attempt 1's cached artifacts rather than remeasuring, the exact failure mode this project's own D-095/D-096/D-101 "verify the rerun actually remeasured" methodology exists to catch, and it was not caught here. The **1.8430%** figure this decision recorded for "the first" measurement does not match either attempt's currently retrievable log; its origin could not be reconciled and it should not be relied on.
  - Three further CI runs have executed since that update, all on commits that touch **no** `Ty`-representation code (`1420d91` is a docs-only SESSION_LOG/DECISIONS.md commit; `f4b01c6` is a merge of `origin/main`; `022b49a` touches `pycc_types`'s `ListAppend` check and doc comments, a code path this benchmark's scalar-only fixture never exercises) — every one of them **failed** `frontend-perf-gate`: `1420d91` at 3.0685% (run 30614020318: previous 6873.98ns, current 7084.91ns), `f4b01c6` at 16.5551% (run 30614141700: previous 5590.09ns, current 6515.53ns), and `022b49a` at 4.2506% on its first CI attempt (run 30615455609: previous 5621.43ns, current 5860.37ns) then 5.4321% on a full, genuinely fresh rerun of the same commit (previous 5587.10ns, current 5890.60ns).
  - The pre-fix side of this investigation is equally mixed, not uniformly failing as this decision's Context paragraph implies: alongside the two originally-cited pre-fix failures (4.7008%, and 5.1960% — independently reconfirmed this session at run 30608030517, previous 6083.97ns, current 6400.09ns), commit `25c95b97` (still pre-fix, the commit that first recorded this decision) failed at 6.5239% (run 30609617862: previous 6010.64ns, current 6402.76ns) — but the very next commit, `69b51b29` (pure decision-text/framing edit, zero code change from `25c95b97`), **passed** at 0.8089% (run 30609847800: previous 6454.54ns, current 6506.75ns).
  - Combining every genuinely distinct measurement taken across this whole investigation (excluding the non-independent cached duplicate above): pre-fix is 3 FAIL / 1 PASS (4.7008%, 5.1960%, 6.5239% failing; 0.8089% passing), post-fix is 1 PASS / 4 FAIL (-0.4454% passing; 3.0685%, 16.5551%, 4.2506%, 5.4321% failing). Both sides show a wide spread that swings from comfortably-under-threshold to more than 8x over it, including on commits proven not to touch the measured code path at all.
  - This pattern — large, direction-inconsistent swings on a hosted, shared CI runner, on a benchmark whose exercised code path is provably unchanged between some passing and some failing commits — is the same class of gap this project has already named and accepted elsewhere: D-095/D-096/D-101's own macOS/Windows/`ubuntu-24.04-arm` `nbody`-gate floors, and, for this exact gate, an almost identical incident already recorded in `docs/SESSION_LOG.md`'s 2026-07-26 "PR #132 blocked on `frontend-perf-gate`; likely order/thermal drift, not a real regression; escalated to the user" entry, which was resolved by asking the user to choose rather than by further reruns.
  - This correction does **not** revert Task 14's `Ty::Dict`/`Ty::Tuple` boxing: `size_of::<Ty>()` shrinking from 24 to 16 bytes is a real, directly-measured representation improvement independent of what this noisy benchmark shows, and is worth keeping on its own merits. What this correction withdraws is the claim that this benchmark's measurements demonstrate that shrink fixed anything, and the earlier claim that the original regression was definitely real rather than possibly always having been within this gate's own noise band.
  - This decision does not resolve which of "the original regression was real and Task 14 fixed it, but this gate's noise now obscures that," "the original regression was itself noise this gate's threshold is too tight to distinguish from," or some third explanation is correct, and does not pick a remedy. PR #236 is merge-blocked again pending that resolution — the "no longer merge-blocked" sentence immediately above is superseded by this correction.
  - **This is not a novel, PR-10-specific question:** [issue #109](https://github.com/rotnov/pycc/issues/109) ("Stabilize frontend performance gate against hosted-runner variance") already tracks this exact class of gap project-wide, has been reopened four times since 2026-07-25 as each stabilization attempt (paired-runner activation, D-051/D-053, D-056's source-aware policy, D-062's identity path) turned out incomplete, and remains **open** as of this correction. Its own newest evidence (posted 2026-07-31T07:41:09Z, independently of this branch) documents the identical phenomenon on merged PR #188: the same merge commit passed `frontend-perf-gate` pre-merge and failed it on the exact post-merge `main` run, with zero source difference. This branch's own `25c95b97`→`69b51b29` pair (recorded above) has been added to that issue as further corroborating evidence. Given #109 is a shared, already-active investigation (its comment history shows evidence contributed from multiple PRs over time, most recently today), PR-10 does not attempt its own bespoke fix or threshold change — it stays merge-blocked pending #109's own resolution, tracked there rather than re-litigated here. This supersedes this correction's own earlier framing (and the now-superseded corresponding text in `docs/SESSION_LOG.md`'s newest entry) of this as an isolated question needing a fresh, PR-10-specific decision from scratch.
