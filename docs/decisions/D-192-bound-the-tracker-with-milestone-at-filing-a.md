## D-192: Bound the tracker: milestone at filing, a 4:1 merge quota, a ceiling on non-milestone issues, and one session file per merged pull request
- Status: accepted
- Context: this project's autonomous loop files issues far faster than it closes them, and the surplus is almost entirely work about the project's own apparatus rather than about the compiler. Measured on 2026-08-23 at `4df39320` (`gh issue list --repo rotnov/pycc --state open --limit 300 --json number,milestone`): 118 open issues, 70 of them with no milestone assigned — a majority of the open tracker is unscheduled by construction. Three existing mechanisms each contribute. [D-021](#d-021-agent-task-preflight-and-documentation-refresh) step 9 required a milestone at filing but carried an explicit escape hatch ("in the rare case it genuinely is not `vX.Y`-scoped work, explicitly record 'no milestone — cross-cutting' reasoning in the issue body"); the escape hatch became the common case rather than the rare one, and `.claude/skills/ultra-review/SKILL.md` wired it into the autonomous filing path as a first-class option. [D-066](#d-066-maintain-an-agent-retrospective-log-and-a-session-handoff-log) and [D-130](#d-130-decompose-the-session-handoff-log-into-per-checkpoint-files) put the session-file trigger at "a meaningful checkpoint", which an agent can create at will, so a single task can emit several handoff files and each one is a commit and a review surface. And nothing anywhere bounded the *rate* at which non-milestone work is allowed to consume merge capacity: `issue-select` scored candidates but never counted how much recent throughput had already gone to work outside a milestone. The result is an apparatus that measures, journals, and governs itself faster than it compiles Python, with the milestone's own critical path competing against an unbounded backlog of process observations for the same finite merge slots.
- Decision: bound the tracker with five rules, placed in the documents that already own each topic rather than in a new policy section.
  1. **A milestone is required at filing.** D-021 step 9's "no milestone — cross-cutting" escape hatch is removed. An observation that fits no milestone is not an issue at all: it becomes a line in `docs/AGENT_RETROSPECTIVE.md`. Genuinely cross-cutting work still exists and still needs a home, so each cross-cutting area (CI governance, website, agent tooling) gets exactly **one standing umbrella issue**, and further observations in that area become checklist items inside it rather than new issues. The tracker's issue count then tracks scheduled work, and the umbrella issues absorb the rest without growing the count. Exactly two categories of issue may therefore carry no milestone: those standing umbrella issues, and the enumerated [D-185](#d-185-permit-a-dedicated-tracking-issue-per-oversized-file) per-oversized-file tracking issues (#544-#552), which this decision keeps as-is; D-185's Status line records that narrowing, and its instruction to record a free-form "no milestone — cross-cutting" note is retired with the escape hatch itself. Each umbrella issue is titled `Umbrella: <area> — ...` and labeled `umbrella`, so `gh issue list --state open --label umbrella` is the one query that tells a filer whether an area's umbrella already exists; opening a second one for the same area is the same defect as filing the observation separately.
  2. **A 4:1 merge quota.** For every five *issue-closing* merges to the default branch, at most one may be non-milestone work. The denominator is deliberately issue-closing merges rather than all merges: a merge that closes no issue is not selection output, and this project routinely lands docs checkpoints, chores, and D-185 partial-decomposition pull requests that carry no `Fixes #N` at all. `issue-select` step 5 counts the last five such merges from `git log`/`gh` before proposing a candidate and declines a non-milestone candidate once that one slot is spent, falling through to the next-ranked survivor. The quota is a rate limit on apparatus work, not a prohibition: process work still merges, at one fifth of throughput.
  3. **A ceiling of 20 non-milestone issues.** While more than 20 non-milestone issues are open, a new one may be filed only in place of one that closes. `issue-select` step 2 already walks the complete open list on every iteration, so it enforces the ceiling arithmetically there, from the same read it uses for milestone triage. The count is gross: it includes the two permitted milestone-less categories above, which therefore consume the cap deliberately, since a single trivially-checkable number is worth more here than a count with exceptions an agent must reconstruct correctly. At the ceiling the backlog can only shrink or hold, never grow.
  4. **A filing bar for process observations.** An observation about the project's own apparatus — a gate, a skill, a checker, a policy document — becomes tracked work only if it can (a) cause an incorrect merge decision or (b) hide a compiler defect. "A gate does not detect X", where X has never actually occurred, fails the bar and is a retrospective line. This is the qualitative filter behind rules 1 and 3: it decides what is even eligible to be filed, before the ceiling decides whether there is room.
  5. **One session file per merged pull request.** D-066's "at meaningful checkpoints" trigger, and D-130's inheritance of it, are narrowed to at most one `docs/sessions/` file per merged pull request. Everything the old trigger would have captured mid-task — a fix round, an intermediate CI result, a lesson — goes to `docs/AGENT_RETROSPECTIVE.md`, whose whole purpose is that content. A task that merges nothing writes no session file. D-066 and D-130 are not rewritten: their Status lines gain a narrowing reference to this decision, mirroring the [D-024](#d-024-protected-main-and-audited-emergency-bypass)/[D-125](#d-125-session-driven-temporary-ci-check-relaxation-narrowly-superseding-d-024d-054) precedent, while their prose stands as the record of what was true when they were written.
- Alternatives:
  - **Do nothing.** Rejected on the measured trend: 70 of 118 open issues carry no milestone, and every one of them competes for the same merge slots as the active milestone. Left alone, the loop's own self-observation output grows without bound, because each apparatus gap an agent notices is cheap to file and expensive to close.
  - **A hard cap alone, without the quota.** A ceiling on open non-milestone issues bounds the backlog's *size* but not its *throughput share*: at the cap, an agent may still spend every merge slot closing process issues and refiling replacements, leaving the milestone untouched while the count looks healthy. The quota is what protects merge capacity; the ceiling is what protects the backlog. Neither substitutes for the other, so both are adopted.
  - **A time-based auto-close of stale process issues.** Rejected because staleness is not the defect. An issue that was worth filing does not stop being worth fixing after 30 days, and one that was not worth filing should never have been filed — auto-close would hide the filing-side problem behind a janitor, destroying real findings and the audit trail of what was dropped, while leaving the intake rate exactly where it was. `issue-select`'s existing staleness screen already closes issues whose *premise* is provably gone, which is the honest form of this idea and is retained unchanged.
  - **Revert [D-185](#d-185-permit-a-dedicated-tracking-issue-per-oversized-file) (the dedicated per-oversized-file tracking issues).** Rejected: those nine issues were filed on 2026-08-20 in direct response to a repository-owner request, and the decomposition work they track is measurably progressing (see the merged `refactor(mir)`/`refactor(codegen)` pull requests against them). They are not the source of the imbalance — they are scheduled, owner-requested, and closing. Retiring them would remove real work while leaving the actual intake path untouched.
- Consequences: the tracker's open-issue count becomes a measure of scheduled work rather than of accumulated observation. Process observations that fail the filing bar leave a durable trace in `docs/AGENT_RETROSPECTIVE.md`, so nothing is lost, but they stop consuming triage and merge capacity — the cost is that a future session must read the retrospective, not the tracker, to rediscover them, and the retrospective is explicitly informational (per `AGENTS.md`, a lesson there must be promoted into policy before it binds). `issue-select` gains two arithmetic gates it must evaluate before proposing, which makes a proposal slightly more expensive and makes a refusal reportable: a declined candidate must say which gate declined it. The quota can starve legitimate apparatus work when a real governance defect appears during a run of milestone merges; the escape is that a defect meeting the filing bar's clause (a) — it can cause an incorrect merge decision — is a governance incident handled through the existing D-024/D-125 paths, not through the ordinary selection queue. Session files become sparser and each one covers a merged unit of work, which makes `docs/sessions/` a per-delivery record rather than a per-moment one; a long session that merges nothing now hands off through the retrospective and the branch itself. Rules 1 and 3 are enforced by agent instruction, not by CI: no checker rejects a milestone-less issue at the GitHub API boundary, so they hold exactly as well as the skills that implement them, and `.claude/skills/ultra-review/SKILL.md`'s filing path had to be corrected in the same change to stop instructing the very omission rule 1 forbids.
