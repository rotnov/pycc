## D-140: Raise nbody's `RUNS` from 5 to 7 samples per side

- Status: accepted
- Context: on `chore/autopilot-async-monitoring-skill` (a docs/skill-only PR touching neither `pycc_rt` nor `pycc_codegen`), `native-build-test (ubuntu-latest, x86_64-unknown-linux-gnu)`'s `nbody_release_binary_meets_required_speedup_over_cpython` failed once with `19.69x` against the required `20x` floor (wall median 0.1343s pycc vs. 2.6432s CPython; CPU-time ratio `19.73x`, essentially identical). Because the failing PR's diff cannot possibly have changed nbody's runtime behavior, this is single-run measurement noise, not a regression — the same conclusion D-084/D-132 reached for the `pycc check` throughput floor. `ubuntu-latest` x86_64 is one of only two Tier-1 legs still held to the full `20x` floor (D-095/D-096/D-101 already carved out lower floors — 12x/15x/18x — for macOS aarch64, `windows-latest`, and `ubuntu-24.04-arm` specifically because those legs showed a genuine, reproducible lower compute ceiling, not noise); this leg has no such evidence and stays at 20x.
- Decision: raise `tests/nbody_bench.rs`'s `RUNS` constant from 5 to 7. Both pycc and CPython already run `RUNS` times each in back-to-back blocks and the gate compares the median of each side (design doc §1, D-093/D-098); this is the same median-of-more-samples mitigation D-132 applied to the D-084 throughput floor, adapted to a benchmark that already had a median-of-N harness rather than D-084's original single-sample one. Two explicit non-fixes for this specific leg, both already evidence-backed by prior work in this repo rather than re-derived here: (a) CPU-time does not substitute for wall-clock here — D-126/D-129 measured CPU-time variance as effectively unchanged from wall-clock on this exact leg (Ubuntu x86_64), because on a virtualized hosted runner "CPU time" per `getrusage`/`wait4` still counts throttled/steal cycles as full-rate CPU-seconds, so hypervisor-level noise (co-tenant CPU steal time, turbo/frequency scaling driven by neighboring load) leaks into CPU-time measurement almost as much as it leaks into wall-clock; CPU-time is immune only to pure OS-scheduler preemption, which is not what dominates here; (b) lowering the 20x floor for this leg would not fix noise, it would silently weaken the acceptance bar on one of only two legs still held to the design doc's original, non-relaxed target — the other three legs' floors were lowered only after real, reproducible sub-20x measurement evidence (D-095/D-096/D-101), which does not exist for this leg.
- Alternatives: switch to CPU-time gating (rejected, per D-126/D-129's own already-gathered evidence above — this repeats a question this project already answered rather than opening a new one); lower the `ubuntu-latest` floor below 20x (rejected — no measurement evidence supports a genuine sub-20x ceiling on this leg the way D-095/D-096/D-101's evidence supports the other three, and doing so without evidence would be exactly the "erode the gate to make CI quiet" anti-pattern this project's own D-014/D-084 discipline exists to avoid); interleave pycc/CPython runs instead of block-executing them (rejected — the existing block-execution rationale in `tests/nbody_bench.rs`'s own doc comment already reasons that a per-side median blunts most drift exposure, and interleaving would be a larger, riskier change to the harness's measurement methodology for an unproven benefit versus simply adding more samples to the median it already computes); do nothing and rely on `gh run rerun --failed` when this recurs (rejected — same reasoning as D-132: this is what already costs real session time when it happens, and a wider median is a genuine, low-risk mitigation available right now).
- Consequences: `tests/nbody_bench.rs`'s ignored `nbody_release_binary_meets_required_speedup_over_cpython` test now runs the pycc/CPython binaries 7 times each (14 timed launches plus 1 untimed correctness check per side, 16 total program executions, up from 12) — a small, bounded increase in this already-`#[ignore]`d test's own wall-clock cost (verified locally: ~14s total for both sides combined), not a new CI job or new required check. A future sustained regression must move the median of 7 runs, not just avoid one unlucky run among 5, which is a strictly stronger signal than before. If `ubuntu-latest` x86_64 continues to show boundary failures even at `RUNS = 7`, that would be new evidence this leg may need its own D-095/D-096/D-101-style floor investigation — escalate with real measurement data at that point rather than raising `RUNS` again preemptively.
