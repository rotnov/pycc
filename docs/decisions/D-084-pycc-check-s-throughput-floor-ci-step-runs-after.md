## D-084: `pycc check`'s throughput-floor CI step runs after `cargo test`, not right after `cargo build`

- Status: accepted
- Context: Task 7 wires `scripts/check_frontend_throughput.rb` (D-079) into `build-test-coverage`'s CI job, invoking the freshly built `target/debug/pycc` binary. A Task-7 implementer subagent's local testing found the exact measurement flaky on its dev host: 3 of 6 fresh-shell trials of `ruby scripts/check_frontend_throughput.rb target/debug/pycc tests/fixtures/pr6_1000_loc_bench.py 50` reported multi-second failures (2481ms/2853ms/2712ms) that `/usr/bin/time -p` proved were not `pycc`'s own compute -- one cold run split as `real 2.71s` vs `user 0.01s`/`sys 0.01s`, meaning over 99% of the wall time was spent in process-spawn/exec overhead (likely first-exec code-signature validation of the freshly-linked, ad-hoc-signed binary) before `pycc check` itself ran at all. Steady-state (warmed) runs were consistently ~15ms, comfortably under the 50ms floor -- the anomaly is a one-time cold-start cost, not a `pycc check` regression.
- Decision: place the new CI step immediately after the job's existing `cargo test --workspace (incl. ignored conformance tests, D-078)` step, not immediately after `cargo build --workspace`. `cargo test` already execs the same freshly-linked binary via existing integration tests, so any one-time first-exec cold-start cost lands there instead of inside the throughput measurement, keeping the measurement itself representative of `pycc check`'s own steady-state speed.
- Alternatives: place the step directly after `cargo build --workspace`, per the implementation plan's original Step 6 wording (rejected -- this would make the throughput check itself the first exec of the freshly-linked binary in the job, risking exactly the cold-start flakiness the implementer observed locally, on a check whose entire purpose is measuring `pycc check`'s own steady-state speed). Add a dedicated warm-up exec of the binary before measuring (rejected as unnecessary complexity -- the job already execs the binary via `cargo test`'s integration tests immediately before this step, so a separate warm-up step would be redundant).
- Consequences: `scripts/check_frontend_throughput.rb` and `tests/fixtures/pr6_1000_loc_bench.py` are unchanged from Task 7's implementer subagent's work; only the step's position in `ci.yml` differs from the plan's original Step 6 text. This changes `ci.yml`'s whole-file digest again, so `scripts/check_roadmap_evidence.rb`'s `REVIEWED_PERF_CI_WORKFLOW_SHA256S` gains `D84_THROUGHPUT_FLOOR_CI_WORKFLOW_SHA256` as its new sole active entry, retiring `D80_CONFORMANCE_ORACLE_CI_WORKFLOW_SHA256` the same way `D51`/`D56`/`D62` were retired before it -- staged onto `main` first via a separate stage PR (#173, mirroring D-080's own precedent), since a single PR cannot both change `ci.yml` and teach the base-branch-only `pull_request_target` audit checker its new digest (see D-080's "Staging note").
