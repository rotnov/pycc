## D-152: Populate `Diagnostic.help` for arity/type-mismatch and missing-annotation call sites (#367, Part 2 of #338)

- Status: accepted
- Context: `docs/CLI_SPEC.md` has documented a `help[]` array in the diagnostic-occurrence JSON schema since PR-4 (D-036/D-043), and `render_json` (`crates/pycc_diag/src/lib.rs`) has emitted `"help": []` unconditionally, for every diagnostic, ever since — D-043 named "`help:` suggestions are never populated" as one of three explicitly tracked, accepted, non-blocking follow-ups from that PR. `docs/DIAGNOSTICS.md`'s quality bar ("help with a suggestion when one is safe") has been normative text since PR-4 too, just unenforced for `help` until now. This issue is D-043's second gap, narrowed but not closed. It is not "add a new JSON field" — the field and its documentation already existed; the work is populating it conditionally, and only where a safe suggestion is textually determinate from the diagnostic's own message.
- Decision (field and builder shape): add `help: Option<String>` as a sixth `Diagnostic` field. Every production construction of `Diagnostic` goes through `Diagnostic::error`/`Diagnostic::warning` (94 real call sites across `crates/pycc_types/src/lib.rs`, `crates/pycc_hir/src/lib.rs`, and `crates/pycc_parser/src/lib.rs`; the sole bare `Diagnostic { .. }` struct literal anywhere is test-only), so both constructors keep their signatures byte-for-byte unchanged and simply set `help: None`. A new builder, `Diagnostic::with_help(self, impl Into<String>) -> Self`, is chained onto a call site that needs one: `Diagnostic::error(code, message, span).with_help(text)`. Rejected: a separate `Diagnostic::error_with_help(...)` overload (forces every future call site to pick between two similarly-named constructors, and reads worse at the ~46 sites building `help` text from the same interpolated variables already in the `format!` call one line above); `..Default::default()` struct-update syntax (`Diagnostic` has no sensible default for `code`/`message`/`span`, so deriving `Default` only to support this one field is a bigger, unrelated API change).
- Decision (selection rule, 46 of 94 sites): populate `help` exactly at a call site whose message text, as already written, states a determinate, safe replacement — an exact expected type, an exact expected count, an exact "add an annotation" instruction, or an already-embedded usage example — with nothing invented beyond what the message's own interpolated variables already carry. Leave `help: None` where the fix requires the compiler to guess design intent (an undefined/unbound name, which side of a redeclaration conflict is "correct", which operator the author meant) or where the message names a pycc-capability limitation with no in-code remedy ("not compiled/supported yet", "in v0.2"). Applying this rule to the current tree yields 46 sites with `help` (8 exact-arity-count sites, 11 exact-expected-type sites, 5 "expected X (from context), found Y" sites, 10 assign/append/add/use mismatch sites where the message's operand order is actual-type-first — the *reverse* of the other families, so their `help` text mirrors that reversed order rather than a mechanically copy-pasted template, 3 return-type sites, 3 self-contained tuple-index sites, 4 sites whose message already embeds the fix, and 2 missing-annotation `T0001` sites in `pycc_hir`) and leaves 48 at `help: None` (name resolution/binding, ambiguous multi-value conflicts with no canonical "correct" side, pycc capability/version limitations, container-capability "does not support X" messages with no single replacement, `'return' outside a function`, one internal-ordering guard not normally user-reachable, the generic `T0042` instantiation-rejection helper's several judgment-requiring shapes, and the parser's one generic `L0001` site). This is a broad but textually justified set, not an inflated one: "unambiguous" (the issue's own framing) is a property of the fix, not of how many call sites happen to share one, and roughly half of this compiler's diagnostic surface being arity/type-mismatch-shaped is a fact about the codebase.
- Decision (JSON rendering): `Diagnostic.help` stays `Option<String>` in Rust (matching the issue's own literal request and `DIAGNOSTICS.md`'s singular "help with a suggestion" wording), but `render_json` adapts it to the array-shaped wire format at the one point that needs to know about JSON at all — `"help": ["<text>"]` when `Some`, `"help": []` when `None` — preserving the existing array type every current and future consumer already expects, per `docs/CLI_SPEC.md`'s own "JSON structure must not change" rule.
- Consequences: `crates/pycc_diag/src/lib.rs` gains the `help` field, `with_help`, the updated `render_json`, and new unit tests for both; its one pre-existing test-only `Diagnostic { .. }` struct literal gains `help: None`. 44 call sites in `crates/pycc_types/src/lib.rs` and 2 in `crates/pycc_hir/src/lib.rs` gain a chained `.with_help(...)`. `tests/diagnostics/d0021_range_argument_type.expected.json` is a new fixture (paired with the pre-existing `.py`/`.expected.txt` fixture) showing a populated `"help":["pass an \`int\` value"]`; `tests/diagnostics_test.rs`'s existing `d0021_range_argument_type` test gains the matching `assert_json_diagnostic_matches_fixture` call. `docs/CLI_SPEC.md` gains one clarifying sentence on when `help[]` is populated. `docs/ROADMAP.md`'s Diagnostics row is updated to state which families now populate `help`. This entry is added under `docs/decisions/` per D-151's own per-file decomposition, and `docs/decisions/README.md`'s generated index is regenerated to include it. **This narrows, but does not close, D-043's second gap**: 46 of 94 call sites now populate `help`; the remaining 48 (name resolution, capability limitations, ambiguous conflicts) still leave `help: None` by design, not by omission. `render_human` gains no `help:` line codepath at all in this PR — D-083's pin ("no help: line" in the human-format example) stays correct and unchanged; only the JSON contract's `help[]` array actually starts varying. D-043 itself is not edited (existing decisions are never rewritten); D-152 supersedes only the "never populated" half of its second gap. A known, unaddressed gap this decision leaves: `help` text is free text derived from, but not mechanically tied to, the `message`/`format!` call beside it, so a later edit to one could leave the other stale with no automated check catching it — flagged here, not solved, matching how D-043 itself named gaps without solving them.
- Alternatives: retrofit `help` onto the remaining 48 call sites (rejected — explicit issue non-goal; every excluded site genuinely requires guessing intent or names a capability limitation with no in-code remedy); render `help` in `render_human` output in this same PR (rejected — a materially larger, independent seam requiring an audit and regeneration of the 59 `.expected.txt` fixtures, worth its own follow-up issue rather than bundling into a PR titled around the data model and JSON schema); a bare nullable string for the JSON `help` field instead of a populated/empty array (rejected — would break the array type every existing and future JSON consumer already expects, violating `docs/CLI_SPEC.md`'s own no-JSON-structure-change quality bar).
