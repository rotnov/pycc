## D-056: Identical executable inputs make paired timing non-blocking telemetry

- Status: accepted (active; supersedes D-051 only as the live workflow/comparator authorization while retaining its paired provenance controls)
- Context: D-051 removed cross-runner variance but did not remove order and thermal drift inside one hosted runner. Post-merge main run [30198852753](https://github.com/rotnov/pycc/actions/runs/30198852753) measured byte-identical compiler inputs at `7031.66 ns` then `7252.75 ns` and failed at `+3.14%`; the next unchanged-input main run [30199477003](https://github.com/rotnov/pycc/actions/runs/30199477003) measured `6573.61 ns` then `6630.12 ns` and passed at `+0.86%`. Both runs had valid exact revisions, sealed artifacts, and comparator execution, so retrying until favorable would select runner state rather than compiler evidence. [Criterion's own guidance](https://bheisler.github.io/criterion.rs/book/user_guide/command_line_output.html) says noisy environments may require longer warm-up and measurement, and its comparison logic uses uncertainty as well as a noise threshold; however, no statistical treatment can turn a timing difference between identical executable inputs into evidence that source code regressed. Google Benchmark's merged [random-interleaving change](https://github.com/google/benchmark/pull/1105) reduces order-dependent variance, while rustc-perf's [dedicated-machine experiment](https://github.com/rust-lang/rustc-perf/issues/1450) reduced wall-time variance by disabling turbo boost and simultaneous multithreading. Neither mechanism is directly available here: interleaving would execute candidate code before the trusted predecessor evidence is sealed, and the repository has no reviewed self-hosted runner.
- Decision: first stage `tests/fixtures/d56-source-aware-ci.yml` while leaving `.github/workflows/ci.yml` byte-identical to D-051, then activate the reviewed fixture byte-for-byte in a fresh-base pull request and retire D-051's active authorization. The active workflow retains exact predecessor/candidate revisions, the immutable predecessor upload, distinct exact artifact IDs, the isolated predecessor-owned comparator, and the greater-than-2% threshold. Before any candidate code executes, a fixed trusted step compares the complete `src/` and `crates/` trees and emits exactly `true` or `false`. The already-enforced benchmark contract separately requires `benches/`, root and workspace Cargo manifests, `Cargo.lock`, both root toolchain filenames, root `.cargo/`, and every tracked local `build.rs` to be identical. Together those checks cover every repository-owned executable input to this benchmark. Both benchmarks and artifacts are still produced. The hash-verified `check_source_aware_perf_regression.rb` records the observed delta but returns success for an exact `true`, because that delta is environment telemetry; for `false` it applies the unchanged `>2%` failure rule. Missing, malformed, late, incomplete, or unbound identity evidence fails closed.
- Alternatives: raise or average the 2% threshold (rejected because it weakens D-044 and can hide real regressions); use Criterion confidence intervals alone (rejected because systematic order drift can produce narrow non-overlapping intervals for identical code); lengthen sampling or rerun a failed job (rejected as insufficient evidence for the same executable and, when repeated until green, selection bias); randomize or interleave predecessor and candidate execution (rejected because candidate execution before the predecessor upload violates the reviewed trust boundary); require a self-hosted performance machine now (deferred because no such runner or operating procedure exists); skip performance jobs for documentation-only changes (rejected because retaining both measurements exposes runner drift and continuously exercises the artifact and comparator path).
- Consequences: the staging change did not alter the live gate; the byte-exact activation makes D-056 current. Non-code changes cannot be blocked by a timing delta that is logically incapable of proving a code regression, while every change under `src/` or `crates/` remains subject to the same hard median threshold. Any future repository-owned build input outside the bound sets requires a reviewed contract extension before it can affect the benchmark. The D-051 fixture and comparator remain historical audit evidence, but their digest is no longer accepted by the active policy.
