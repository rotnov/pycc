## D-111: Issue priority is the title's leading `P[1-3]:` prefix, not a GitHub label

- Status: accepted
- Context: `issue-select`'s scoring order names "the repository's own priority markers" as its primary sort key (rank first: P1 before P2 before P3 before unmarked), but this repository has never had GitHub priority labels — `gh label list -R rotnov/pycc` returns only `{bug, documentation, duplicate, enhancement, good first issue, help wanted, invalid, question, wontfix}`. The only live mechanism is an informal `P1:`/`P2:`/`P3:` issue-title prefix: as of 2026-08-01, `gh issue list -R rotnov/pycc --state open` showed 85 of 104 open issues carrying it (0 of 104 carrying any label at all). This convention was previously mentioned only in `docs/SESSION_LOG.md`, a D-066 informational journal that `AGENTS.md` itself says must not be relied on as policy until its lessons are promoted into `AGENTS.md`, `docs/DECISIONS.md`, or an owning specification. An agent reading `issue-select`'s own text literally — "priority **labels** or markers", GitHub-native term first — could reasonably check labels, find the confirmed-empty set, and silently flatten the ordering for the 82% of the open pool that carries the informal prefix but no label.
- Decision: the issue title's leading `P1:`, `P2:`, or `P3:` prefix (exact syntax, colon required, no other punctuation or spacing variant recognized) is this repository's accepted issue-priority mechanism. An issue without that exact prefix is unmarked, ranking after every `P3:`-prefixed issue in `issue-select`'s scoring order (P1 before P2 before P3 before unmarked, unchanged from the pre-existing rule — this decision only fixes where the marker itself is read from). No GitHub label carries priority meaning today; `issue-select`'s own text is updated to state the live mechanism directly rather than describing a label-based check that would find nothing.
- Alternatives: adopt real GitHub priority labels and bulk-relabel the open tracker to match the existing title-prefix convention (rejected for this decision — a separate, larger, riskier live-tracker mutation across 104 issues, deliberately not bundled into a skill-hardening pass; a future decision may adopt this instead, superseding this one); leave the mechanism undefined and rely on a capable agent inferring the convention from context (rejected — this is exactly the informal-journal reliance `AGENTS.md`'s own D-066 rule prohibits for a criterion the skill calls "fixed" and non-negotiable, and the audit that surfaced this gap showed it is not merely hypothetical: a literal reading of "labels or markers" naturally checks labels first).
- Consequences: `issue-select/SKILL.md` states the `P1:`/`P2:`/`P3:` prefix mechanism directly in step 2 instead of the prior generic "priority labels or markers" phrasing. `scripts/run_alpha_skill_evals.py`'s `ISSUE_SELECT_CONTRACT` pins a fragment of the concrete syntax, not just the "priority markers rank first" sentence surviving, so a future edit that silently drops the mechanism definition fails the offline eval suite. If this repository later adopts real GitHub priority labels, that is its own future decision superseding this one, not a silent edit here.
