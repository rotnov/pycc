## D-143: `issue-implement`'s delegated `issue-to-plan` invocation also runs inside a dispatched `Agent`

- Status: accepted
- Context: D-142 isolated `issue-implement`'s step 4 (implementation) into a dispatched agent, but step 3's delegated `issue-to-plan` invocation — establishing the baseline, refuting the issue's own claims against the current tree, establishing the repository's governing constraints, empirically verifying what can be verified (including real `cargo`/`pycc` builds and runs), drafting the plan, and running an adversarial review loop until a round changes nothing — was left running directly in the orchestrating session's own context. `issue-to-plan`'s own steps 1-5 and step 6 generate comparable file-reading and tool-call volume to step 4's implementation itself; one real planning session for issue #181 (`float(x)` as a builtin) involved reading and cross-referencing multiple large source files, reproducing the issue's exact repro against a built tree, and three rounds of adversarial review before the plan was judged clean, all in the orchestrating session's own context. `issue-to-plan`'s own step 6 already calls for "an independent reviewer... in a context that has seen the work," which already implies agent dispatch for the review rounds specifically — but the surrounding baseline/refute/verify/draft work, and the decision of whether to dispatch review at all, still executed directly. Whether a dispatched agent can itself dispatch a further, nested agent for that review loop was not assumed — it was tested directly in this same session (a trivial nested `general-purpose` dispatch from within a dispatched `general-purpose` agent, confirmed to return successfully) before this decision relied on it.
- Decision: `issue-implement`'s step 3, when no current plan exists or the existing one needs refreshing, dispatches the entire delegated `/issue-to-plan` invocation to a freshly-spawned `Agent`, instructed to invoke the `issue-to-plan` skill itself (via the `Skill` tool, passing the target issue number) and run it to completion — baseline through publish — inside the same task branch/worktree the orchestrating session already created in step 1's D-021 preflight. The dispatched agent has read/build access to that worktree for its own empirical verification (`issue-to-plan`'s own step 4) but makes no commits there, matching `issue-to-plan`'s existing Non-negotiable #4 (no repository mutation beyond the published comment) unchanged by running inside a dispatched agent rather than directly. `issue-implement`'s own declared write authorization substitutes for `issue-to-plan`'s per-payload publish approval exactly as it did before this decision — that substitution is unaffected by which context actually executes the publish. The dispatched agent runs `issue-to-plan`'s own step 6 adversarial review loop via its own further, nested `Agent` dispatch, confirmed directly (not assumed) to work in this environment. `issue-implement`'s own orchestrating session expects back exactly what `issue-to-plan`'s own Output section already specifies — the published comment URL and its short summary — nothing more.
- Alternatives: dispatch only `issue-to-plan`'s own step 6 review loop (already effectively true before this decision, since that step already calls for an independent reviewer) while leaving steps 1-5 in the orchestrating session's own context (rejected — steps 1-5's own baseline/refute/verify/draft work is the larger share of a planning session's context cost by the issue #181 evidence above, so isolating only the review loop leaves most of the problem D-142 already solved for implementation unsolved for planning); keep the standalone, user-facing `/issue-to-plan` invocation (a human directly asking to plan an issue, not a delegated one) running inside a dispatched agent too (rejected — that path's own per-payload publish approval requires the human to see and approve the exact comment body before it posts, which needs live interactive turn-taking with the actual session the human is talking to; a dispatched agent returns only a final report and cannot pause mid-task to solicit that approval, so this decision is scoped to the delegated-by-`issue-implement` path only, where the approval gate is already waived, exactly as D-142 scoped context isolation to implementation and not review-only work outside an autonomous run); build a bespoke, purpose-specific dispatch harness for planning rather than reusing the plain `Skill`-tool-invocation pattern (rejected as unnecessary — the dispatched agent has the exact same tool access, including `Skill` and nested `Agent`, that the orchestrating session itself has, so there is no missing capability a bespoke harness would need to supply).
- Consequences: `issue-implement`'s step 3 text describes this dispatch pattern explicitly, mirroring D-142's own step 4 pattern. No new authorized-write or eval oracle is introduced. Unlike D-142, this does add one new Stop-conditions bullet to `issue-implement`'s per-issue list — the step 3 dispatch-failure case (fails to start, hangs, or returns no usable report twice in a row): step 4's own dispatch-failure retry folds cleanly into the pre-existing "plan is refuted twice on the same point" bullet, but step 3 has no equivalent existing bucket to fold into — the adjacent "delegated `/issue-to-plan` call is stopped by its own stop condition" bullet covers a different failure, `issue-to-plan`'s own internal review-loop exhaustion, not a failure of the dispatch mechanism itself — so a dedicated bullet was needed instead. `issue-to-plan`'s own SKILL.md needs no *behavioral* change — it already runs identically whether invoked directly by a human-facing session or from inside a dispatched agent acting under `issue-implement`'s delegated authorization; only the caller's own dispatch decision changed, not the skill being dispatched. Its step 7 Publish paragraph does gain one clarifying sentence, added in this same change, naming this dispatched-agent case explicitly as covered by the existing delegated-invocation exception, so a future reader of that skill's own text does not have to infer it from this ADR alone. This is the first live exercise of two-levels-deep nested agent dispatch in this project's own autopilot (an `issue-implement`-dispatched agent itself dispatching review-round agents); a future session finding recursion depth, report-size, or nested-dispatch reliability an actual problem in practice should record that finding and its own resolution as a correction to this entry, not silently revert to direct in-session planning.
