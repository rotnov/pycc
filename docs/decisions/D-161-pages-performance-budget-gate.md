## D-161: Pages performance budget gate
- Status: accepted
- Context: The public website (`site/`) is published to GitHub Pages and serves as the project's evidence hub for search engines and prospective contributors. Prior to this decision, no CI gate protected the published pages against performance regressions in the source artifacts — a change that bloated HTML, CSS, JS, or image bytes could merge without any performance check. Issue #229 requested a hermetic, reproducible performance budget gate that runs in CI and prevents regressions without making unsupported claims about search ranking effects.
- Decision: Add a Pages performance budget gate (`scripts/check_pages_performance_budget.rb`) that runs in CI as the `pages-performance` job, bound to `ci-gate` so a pull request cannot merge unless the gate passes. The gate uses pinned Lighthouse 12.8.2 in mobile emulation mode against a hermetic local server (`scripts/serve_pages_fixture.py`) that serves the checked-out `site/` directory — no external network requests are made, making the gate fully reproducible. It checks the 5 canonical pages (landing, status, architecture, python-aot-compilers, AI-native experiment) plus the 404 error page. Each page is measured with 5 Lighthouse replicates, and the median of each metric across replicates is compared against budget thresholds for LCP, CLS, TBT, and Performance score. Resource byte-count budgets are enforced for HTML, CSS, JS, and image types per page, defined in `tests/fixtures/pages-performance-budget.json` with the page-to-URL mapping in `tests/fixtures/pages-performance-manifest.json`. The `pages-performance` job has `contents: read` permission only, no `continue-on-error`, is not push-only, and is wired into `ci-gate.needs`; `scripts/check_roadmap_evidence.rb`'s lifecycle validator enforces these structural invariants on every pull request. The gate is protected by the policy-successor manifest and the D-103 audit check, ensuring it cannot be silently removed or weakened.
- Alternatives: A field-data-based gate using CrUX or Search Console data was rejected because field data reflects real-user devices, networks, and usage patterns that are not reproducible in CI and cannot be attributed to a specific source-artifact change. An unpinned Lighthouse version was rejected because version drift would make the gate non-reproducible and could introduce pass/fail changes unrelated to the source artifacts. A single-replicate measurement was rejected because Lighthouse has inherent single-run variance; the 5-replicate median strategy dampens that variance. Relying on the existing `frontend-perf-gate` (which measures compiler performance, not website performance) was rejected because it covers a different surface entirely.
- Consequences: The gate is a **lab** measurement, not **field** data. Lighthouse scores can differ from Chrome User Experience Report (CrUX) field data for the same URL. TBT (Total Blocking Time) is a lab metric measuring main-thread blocking during page load; it is **not** INP (Interaction to Next Paint), the field-data Core Web Vital measuring real user interaction latency. The gate does not claim direct search ranking benefits — page experience is one of many signals search engines use, and this gate's purpose is to prevent source-artifact regressions. The gate adds CI runtime for the Lighthouse replicates, but the hermetic local server keeps it self-contained. The pinned Lighthouse version will need periodic updates, each requiring a new policy-successor activation round to update the accepted ci.yml digest. The resource budgets may need adjustment as the website grows, but any change must go through the same reviewed activation process.
