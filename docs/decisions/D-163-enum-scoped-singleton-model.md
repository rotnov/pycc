## D-163: Enum scoped singleton model — compile-time members, no enum.Enum module
- Status: accepted
- Context: PEP 435 enums (`class Color(Enum): RED = 1; GREEN = 2`) are part of v0.3's scope (#379, PR-19). pycc has no `enum` module in `pycc_std` and no import system yet (v0.4), so `enum.Enum` cannot be supported as a real base class. Enums must coexist with the existing class model (`HirClassDef`, `Ty::Instance`, runtime instance allocation) without introducing a new runtime type category or requiring import resolution. The design must be production-safe: no positional value inference, no uninitialized global reads, no codegen panics on valid type-checked programs, and no silent semantic deviations from CPython for the supported subset.
- Decision: `Enum` is recognized as a bare builtin marker name at HIR-lowering time. A class whose sole base is `Enum` is an enum class: `Enum` is consumed as a marker (not registered as a real base, not instantiated, not in the MRO), the class has no `__init__`, no methods, and no items, and its members are stored in `HirClassDef.enum_members: Vec<(String, i64)>` preserving the actual integer literal from the source (not a position-derived sequence). Member values must be integer literals; non-integer values, duplicate names, multiple bases, generic enums, and method definitions in enum bodies are all rejected with `C0001`. Members are compile-time singleton instances of `Ty::Instance(class_name)`. `C.MEMBER` resolves to a synthetic global `<Class>.<Member>.enum_member` at the MIR level (a `MirExpr::Name`), and codegen allocates a 2-slot runtime instance per member (slot 0 = the integer value via `tag_smallint_const`, slot 1 = the member name string via `emit_string_literal`) during module initialization, before any top-level code runs. `C.MEMBER.value` returns the `int` literal; `C.MEMBER.name` returns the member name as a `str`. `for c in C:` iterates members in declaration order — the loop is unrolled into sequential body copies by a HIR→HIR rewrite pass (`unroll_enum_loops`) before MIR lowering, so MIR never sees an enum iterable directly. The unrolling works in both module-scope (`check_stmt`) and function-scope (`check_stmt_in_function`) `for` loops.
- Alternatives: (1) Treat `Enum` as a real base class with an `enum` module — rejected because `pycc_std` has no `enum` module and v0.4's import system is not yet available. (2) Represent enum members as `Ty::Int` with a const table — rejected because it loses singleton identity (`Color.RED is Color.RED` semantics) and complicates `.name` attribute access. (3) Derive member values from source-order position (1, 2, 3, ...) — rejected as a hack that silently produces wrong values for non-sequential definitions (`RED = 10, GREEN = 20`). (4) Lower enum iteration at the MIR level — rejected because MIR has no concept of "iterate a class's members"; unrolling at the HIR level reuses the existing `ForList` body-cloning infrastructure.
- Consequences: What gets easier: enum member access is a simple global read (no runtime dispatch, no vtable); enum iteration is fully unrolled at compile time (no runtime loop overhead); the design extends the existing `Ty::Instance` and runtime instance infrastructure with no new runtime type category. What gets harder: `enum.Enum` module import is not supported (users must use bare `Enum`); non-integer member values (strings, floats, tuples) are not supported; `auto()` is not supported; `@enum.unique`, `@enum.verify`, `Flag`, `IntEnum`, and other enum subclasses are not supported. Irreversible: the synthetic global naming convention (`<Class>.<Member>.enum_member`) is part of the MIR/codegen contract and cannot change without a coordinated HIR+MIR+codegen update.
