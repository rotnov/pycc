## D-114: Raise `frontend-perf-gate`'s threshold to 7.0% for PR-10's `Ty`-migration cost, via a corrected per-target D-103 sequence

- Status: accepted (all six corrected rounds merged in sequence, propose then activate per target -- #298, #299, #300, #301, #302, and this round's own activation PR; `.github/workflows/ci.yml` and `scripts/test_check_roadmap_evidence.rb` now both live at the 7.0% threshold shape, verified with no emergency bypass at any of these six rounds -- the earlier, abandoned first attempt at this raise, #286, did require one to revert via #291, per this decision's own Context above and this project's SESSION_LOG)
- Context: PR-10 (#236, the `Ty` representation migration, D-104) changes `Ty` from a 1-byte `Copy` enum to a recursive, boxed enum needed for `list[int]`/container types. This is a real, already-accepted architectural cost (D-109), not hosted-runner noise: `frontend-perf-gate`'s `pycc_check_frontend_fixture` benchmark consistently regresses by roughly 4.2%-5.2% across independent measurements on PR-10's head, most recently `4.5340%` (previous replicate medians ~10119-10566ns, current ~10823-10955ns, CI run `30792499192`), well above the gate's `2.0%` threshold and confirmed non-noise since D-112 moved this gate to `ubuntu-latest`, whose own observed false-positive band tops out at `1.6%`. Two independent `Ty`-boxing attempts (D-104's own Task 14, shrinking `Ty` from 24 to 16 bytes) already closed part of the gap with no further single-cause reduction found; this decision does not reopen that exclusion process.
  `.github/workflows/ci.yml`'s `frontend-perf-measure` job resolves its comparison predecessor live, every run, from the pull request's own base SHA (`github.event.pull_request.base.sha`) or the push's `before` SHA — there is no separate, pinned historical baseline artifact to re-pin instead of the gate's threshold. This means the regression trips the gate for exactly the pull request that introduces it: once PR-10 merges, every later pull request's own predecessor already includes this cost, and the delta returns to ~0% relative to that new baseline. A permanent threshold raise is therefore broader than the triggering problem strictly requires, but the gate has no narrower "for this one merge" mechanism — see Alternatives.
  A first attempt at this exact raise (this decision's own PR #286, "round 1: propose raising frontend-perf-gate threshold to 7.0%") staged all three D-103-protected targets (`.github/workflows/ci.yml`, `scripts/check_roadmap_evidence.rb`, `scripts/test_check_roadmap_evidence.rb`) in one propose round, planning a single subsequent activation PR (#290) to flip all three at once. The repository owner's own diagnosis, closing #290, found this created an unconditional deadlock: `workflow-policy.yml`'s `audit` job runs two independent checks against the same file — `check_ci_permissions.rb`'s `validate_policy_successor_transition` (requires the candidate's live `ci.yml` to byte-match what `main`'s manifest already has staged) and `check_roadmap_evidence.rb`'s own base-executed `validate_evidence` (requires the candidate's `ci.yml` digest to already be present in `main`'s *currently live* `REVIEWED_PERF_CI_WORKFLOW_SHA256S` array, which cannot include a digest that the same candidate is trying to introduce). No candidate against that base state could satisfy both, in either direction (activating or reverting). PR #291 reverted #286 to restore steady state; this decision's own re-derivation of the correct sequence, cross-checked against D-112's own real six-plus-round history (PRs #269/#270 → #271/#273 → #277/#278 → #283) confirms the fix is per-target propose/activate ordering, not the threshold-raise idea itself.
  D-112's own Alternatives section rejected lowering `frontend-perf-gate`'s threshold to accommodate **runner noise** ("the gate is a spec requirement, not a knob to relax to force a pass"). This decision is different in kind: it accommodates a one-time, already-accepted, real architectural cost from an accepted decision (D-109), and it is scoped narrowly to what that cost actually needs, not stretched to swallow measurement noise on top of it.
- Decision: raise `frontend-perf-gate`'s comparison threshold from the implicit `2.0%` default to an explicit `7.0%` (measured regression `~4.5%` plus D-112's own observed maximum noise `1.6%` ≈ `6.1%`, rounded up for margin), via six D-103 rounds — one live target change per round, learning from both #290's and D-112's own round-7a gap:
  1. Propose a new `D114_RAISED_THRESHOLD_FRONTEND_PERF_GATE_JOB` constant in `scripts/check_roadmap_evidence.rb` (the existing `D112_UBUNTU_FRONTEND_PERF_GATE_JOB` with an explicit `"7.0"` threshold argument added to the "Compare exact predecessor and candidate" step) and widen `validate_source_aware_perf_gate_lifecycle`'s existing `D112_UBUNTU_FRONTEND_PERF_MEASURE_JOB` branch from an exact `==` match to membership in `[D112_UBUNTU_FRONTEND_PERF_GATE_JOB, D114_RAISED_THRESHOLD_FRONTEND_PERF_GATE_JOB]`. This round stages both `scripts/check_roadmap_evidence.rb` and its own `scripts/test_check_roadmap_evidence.rb` successors together (the new constant needs matching test coverage) — safe to co-stage, since #290's deadlock came from simultaneously *activating* three targets, not from proposing two together; nothing about a propose-only round makes any target self-authorizing. Inert: no digest added to `REVIEWED_PERF_CI_WORKFLOW_SHA256S`, `ci.yml` untouched.
  2. Activate round 1's successor.
  3. Propose a second checker successor: add `D114_FRONTEND_PERF_THRESHOLD_CI_WORKFLOW_SHA256` (the exact final new `ci.yml` bytes' digest) to `REVIEWED_PERF_CI_WORKFLOW_SHA256S`, coexisting with `[D100, D112]` (mirroring D-090/D-091/D-112's own coexist-then-later-retire precedent for this array — this decision does not retire D100 or D112, matching the "activate without retiring" recovery issue #275 independently confirmed for D-112's own analogous round). This digest and content turn out to be byte-identical to the already-registered, retained historical fixture `tests/fixtures/d114-frontend-perf-threshold-ci.yml` (PR #286's own now-reverted content, kept per this project's D-051/D-056/D-062 convention) — `main` has not touched this region of `ci.yml` since that fixture was first reviewed. Round 3 therefore reuses that exact fixture and its existing manifest entry as the reviewed activation target, rather than registering a second, distinct fixture: the retained file is no longer audit-evidence-only once this round lands, it is also the live successor `ci.yml`'s own eventual shape.
  4. Activate round 3's successor.
  5. Propose `ci.yml`'s own successor (the `"7.0"` threshold argument) **and** a third checker successor updating `test_check_roadmap_evidence.rb`'s digest-naming assertions together, in the same round — the exact co-staging D-112's own round 6 (PR #277) omitted, which is what forced round 7a (PR #278) into an emergency-bypass-gated `ci-gate` failure. Every assertion naming an "active" digest or gate-job shape (grepped, not assumed from #290's own narrower list) is enumerated and updated here.
  6. Activate both of round 5's successors together in one PR: each promotes a successor already staged in round 5, so no target is self-authorizing its own activation, and `ci-gate` stays green because the test assertions describing "the active digest" change in the same commit as the bytes they describe.
  No round in this sequence requires an emergency bypass; reaching for one at any point is a signal the round's own ordering is wrong, not that protection needs relaxing.
  Because the trigger is a one-time merge cost, not a standing measurement-noise problem, lowering the threshold back toward `2.0%` once PR-10's own cost is absorbed into every future baseline is a live, tracked follow-up obligation ([issue #296](https://github.com/rotnov/pycc/issues/296), no promised date or session) rather than an immediate same-day commitment this decision cannot actually guarantee it will execute.
- Alternatives: keep the threshold permanently at `7.0%` with no follow-up tracked (rejected — honest about being over-broad relative to the one-time trigger, but abandoning the follow-up silently understates the cost instead of tracking it); re-pin a separate, stored historical baseline artifact instead of raising the threshold (rejected — the gate's own design recomputes the predecessor live from the pull request's base SHA every run, by the source-aware/replicated design D-056/D-062 already established; there is no separate baseline artifact to re-pin); a third round of `Ty`-boxing to close the remaining ~4.5% gap without any gate change (rejected — D-104's own Task 14 exclusion process already found no further single-cause reduction; re-opening it here duplicates work already done and reported); repeat #286's single-round three-target staging (rejected — empirically deadlocks per #290's own diagnosis, this decision's whole reason for existing).
- Consequences: `REVIEWED_PERF_CI_WORKFLOW_SHA256S` grows to `[D100, D112, D114]`, none retired by this decision — issue #275's own tracked D100/D112 retirement work (independent of this decision) still applies separately once filed for D114 too, if ever pursued. PR-10 (#236) can rebase onto the resulting `main` and pass `frontend-perf-gate` at its measured `~4.5%` regression. A future architectural change that similarly regresses this benchmark by up to `7.0%` will not trip the gate on its own merge either — this is the deliberate, disclosed cost of the wider threshold, offset against the tracked follow-up to narrow it again once this repository has headroom to do the six-round sequence for the reverse direction.
