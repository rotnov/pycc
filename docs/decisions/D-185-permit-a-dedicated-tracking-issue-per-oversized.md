## D-185: Permit a dedicated tracking issue per oversized source file, without weakening the same-change decomposition rule

- Status: accepted (the "no milestone — cross-cutting" note this decision's Consequences prescribe for a future oversized-file tracking issue is narrowly superseded by [D-192](#d-192-bound-the-tracker-milestone-at-filing-a-41-merge-quota-a-ceiling-on-non-milestone-issues-and-one-session-file-per-merged-pull-request), which makes these trackers one of two enumerated categories permitted to carry no milestone and therefore needing no free-form note — see that decision for the current scope; every other clause here, including the carve-out itself and #544-#552's standalone selectability, remains in force unchanged)
- Context: `AGENTS.md`'s "Keep source files decomposable" section says that when a task's own work touches a Rust source file over the project's ~1,000-line threshold, decomposition happens "as part of that same change — not as a separate dedicated refactor task, and not by rewriting unrelated code." On 2026-08-20 the repository owner asked whether a tracking issue existed for decomposing `lib.rs` and the project's other oversized files; none did, and every non-test Rust source file over the threshold was still undecomposed, several by a wide margin (`crates/pycc_types/src/lib.rs` at 31,673 lines and `crates/pycc_codegen/src/lib.rs` at 17,665 lines among them). Nine issues (#544-#552) were filed in response, one per file, split `P1:` for the four files at 6,000+ lines and `P2:` for the remaining five at 1,000-5,300 lines. Each issue body had to argue around the section's literal wording to justify its own existence — that a tracking issue is legitimate as a prioritization target even though the section forbids treating decomposition as "a separate dedicated refactor task" — which produced nine copies of the same ad hoc reconciliation instead of one durable rule, and left `issue-select`/`issue-implement` with no policy basis for ever selecting one of the nine as a standalone unit of work: read literally, the section still requires some other, unrelated task to be the reason a session ever opens one of those files.
- Decision: Amend the "Keep source files decomposable" section to add an explicit carve-out: a dedicated GitHub issue tracking decomposition of one specific oversized file is a legitimate artifact in its own right, and working that issue is itself "a task whose own work touches" the file — the issue's scope supplies the justification the original rule requires, rather than needing an unrelated change to supply it. The behavioral constraint the original rule protects is kept intact and restated explicitly for this case: each pull request against such an issue still extracts one or more cohesion-driven submodules and does not rewrite unrelated logic or behavior, exactly as the "same change" the rule already describes would be scoped. Because a file measured in the tens of thousands of lines cannot be brought under the threshold in one pull request, the issue is not closed per pull request; each merge is followed by a comment narrowing the issue to what remains (files and line ranges still over threshold), and the issue closes only once the tracked file is under the ~1,000-line threshold or is removed/merged away entirely. Issues #544-#552 are the concrete instances this decision legitimizes as standalone, independently-selectable work items; no issue body needs editing as a result, since each already carries a "no milestone — cross-cutting" note and a description of the tension this decision now resolves at the policy level instead of per-issue.
- Alternatives: leave the wording unchanged and rely on each issue's own text to argue around it (rejected — already produced nine duplicate reconciliation notes instead of one rule, and leaves `issue-select`/`issue-implement` unable to ever pick one of these issues on its own, since both skills read `AGENTS.md`'s rule directly rather than trusting an issue's own framing to override it); drop the "not as a separate dedicated refactor task" clause entirely, so any standalone decomposition pull request is allowed regardless of whether a tracking issue exists (rejected — the original rule exists to prevent low-value, purely mechanical refactor pull requests with large diff and merge-conflict surface against whatever else is concurrently touching the same file; removing the clause entirely would reopen exactly that risk for the many files that are not on the priority list, not just narrow it for the nine that are); allow standalone execution only as one single big-bang pull request per file (rejected — infeasible for the largest files at this project's line counts, and contrary to the project's own decomposition guidance elsewhere, e.g. `AGENTS.md`'s D-021 step 10 rule that an issue spanning multiple independent seams is split into a dependency-ordered sequence of independently-mergeable issues, each closed by its own pull request, which this decision's incremental-narrowing shape mirrors).
- Consequences: `AGENTS.md`'s "Keep source files decomposable" section gains a second bullet stating this carve-out and citing this decision. `issue-select` may score #544-#552 (and any future issue filed the same way) as ordinary standalone candidates using its existing priority-marker and size-based ordering, without a special exception in that skill's own text — the unblocking happens at the `AGENTS.md` rule level both skills already read, not by editing either skill. A future oversized-file tracking issue filed under this decision inherits the same shape by construction: `P1:`/`P2:` priority marker, "no milestone — cross-cutting" reasoning (or an assigned milestone when the file's decomposition is itself milestone-scoped work), and narrowing comments rather than a single closing pull request. This decision does not relax the underlying rule for any file without such an issue — touching an oversized file for unrelated reasons still requires decomposing the touched part in the same change, exactly as before.
