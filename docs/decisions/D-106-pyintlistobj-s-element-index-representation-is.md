## D-106: `PyIntListObj`'s element/index representation is raw untagged `i64`, not D-061-tagged; the boundary conversion and its bigint exclusion are `pycc_codegen`'s job

- Status: accepted
- Context: D-104 (Task 10) specified `PyIntListObj`'s tests literally as `pycc_rt_int_list_append(list, 10)` then `pycc_rt_int_list_get(list, 0) == 10` — not `tag_smallint(10)`. Those tests are binding, and the implementer shipped `PyIntListObj` (`crates/pycc_rt/src/lib.rs`) storing exactly that: raw, untagged 64-bit slots, matching `docs/RUNTIME.md`'s existing "growable vec of unboxed `T`... SIMD-friendly" line. This is a real departure from D-061's own general rule ("every arithmetic/comparison/print operation on `int` is a call to a `pycc_rt` function taking/returning this exact tagged `i64`, never a raw untagged value") — a rule D-061's own consequences section already grants one prior exception to, for `bool`'s "own, simpler, untagged `i8` representation." Task 10's pinned local reviewer (D-068) confirmed this is a real, unresolved cross-task contract question and flagged it as the one open item for whoever picks up Task 11 (`pycc_codegen`). Separately: `pycc_rt_int_add`/`_sub`/`_mul`/`_floordiv` already promote a same-crate scalar `int` to a heap `BigInt` on arithmetic overflow (`tag_bigint(...)`, e.g. `crates/pycc_rt/src/lib.rs` lines ~277/312/337/380) — this is reachable today from ordinary, already-type-checked Python source (e.g. `y = 9223372036854775807 * 2`), not a hypothetical. `untag_smallint` cannot detect a bigint-tagged input; it silently reinterprets the bigint heap pointer's bits as a shifted integer if given one. A raw `i64` list slot has no room to represent a bigint at all.
- Decision: `PyIntListObj` keeps its shipped raw-untagged-`i64` representation — a second, deliberate, narrow exception to D-061's tagging rule, parallel to `bool`'s. `pycc_codegen` owns crossing this boundary in both directions, and the two directions are asymmetric:
  - **Input side (a tagged `Ty::Int` value about to cross into `PyIntListObj`: `.append()`'s value, `x[i]`'s index):** this direction requires discriminating smallint from bigint before dropping the tag bit — genuine tag-bit interpretation, which per this crate's own established principle ("only `pycc_rt` may interpret its bits" — see `to_float`'s doc comment on why `int`-to-`float` goes through `pycc_rt_int_to_float` rather than a raw LLVM cast) belongs inside `pycc_rt`, not inlined as LLVM IR in `pycc_codegen`. Task 11 adds exactly one new `pycc_rt` extern "C" function for this: check the tag bit (mirroring the existing private `is_smallint`/`require_smallint` helpers), panic with an honest `"pycc_rt: <description>"` message if the value is bigint-tagged, else `untag_smallint` and return the raw `i64`. One function, reused at all three input-side call sites (`ListLiteral`'s per-element value, `ListAppend`'s value, `Subscript`'s index).
  - **Output side (a raw `i64` read back out: `x[i]`'s result, `len(x)`'s result):** always safe to re-tag, by construction — the input-side guard above already proves every raw slot holds a value that fits `tag_smallint`'s 63-bit range (an `untag_smallint` of a valid smallint-tagged input can never itself exceed that range), and a list's element count is bounded far below it in any realistic run. No bigint case exists on this side, so no `pycc_rt` call is needed: `pycc_codegen` constructs the tagged value directly via the same inline LLVM IR shape `to_tagged_int`'s `Scalar::Bool` arm already uses (`build_left_shift` then `build_or` with the tag bit) — this is the precedent for the *construct a tagged value from a value already known to be in range* direction, as opposed to `to_float`'s precedent for the *interpret an existing tagged value's bits* direction.
  - **The bigint case is an honest runtime panic, not silent corruption**, exactly this project's existing "unrecoverable runtime conditions are `panic!(\"pycc_rt: <description>\")`" convention. It is explicitly a v0.2 scope cut (bigint list elements are unsupported), not a bug, and — since it is reachable from ordinary type-checked source per the Context above — Task 11 owes it a real, executing regression test for D-14's coverage gate, not just a documented gap.
- Alternatives: store `PyIntListObj` elements D-061-tagged instead (rejected — contradicts Task 10's own binding tests, already shipped and reviewed; would also defeat `docs/RUNTIME.md`'s stated unboxed/SIMD-friendly design goal for exactly the element type v0.2 ships). Silently truncate or reinterpret a bigint-tagged value on `.append()` instead of panicking (rejected — directly violates this project's "honest panic over silently wrong data" convention; a truncated bigint stored as a raw `i64` is exactly the kind of quiet correctness bug this project's conventions exist to prevent). Do the input-side tag-bit check inline in `pycc_codegen` via raw LLVM IR instead of a new `pycc_rt` function (rejected — this direction requires interpreting the tag bit's meaning, which this crate's own `to_float` precedent already reserves for `pycc_rt`, not codegen; keeping it in `pycc_rt` also means the bigint check's exact bit-level definition lives in exactly one place, next to `is_smallint`/`require_smallint`, rather than being duplicated as LLVM instructions).
- Consequences: Task 11's plan section is updated with the exact per-call-site conversions this decision specifies (one new `pycc_rt` extern function for input-side untagging-with-a-bigint-guard; inline LLVM IR mirroring `to_tagged_int`'s bool arm for output-side re-tagging), so its implementer does not need to rediscover this contract by reading Task 10's report. A future PR that lets `list[int]` elements actually be bigints (not just reject them) would need to either widen `PyIntListObj`'s raw `i64` slot to something bigint-capable, or move `list[int]`'s storage to D-061-tagged after all — a strictly bigger change than this decision's own scope, left to whichever later PR actually needs it. This decision does not touch the separate, already-recorded negative-index scope cut (D-105's own text, Task 10's report) — that stays where it is.
