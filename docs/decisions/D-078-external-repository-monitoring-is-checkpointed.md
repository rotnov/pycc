## D-078: External repository monitoring is checkpointed and event-driven

- Status: accepted
- Context: repository documents correctly retain historical evidence, including D-054's closed issue #125 and merged staging PR #119. Treating those citations as current work caused a monitor to poll completed objects that had not changed after the task began, creating status noise and obscuring the actually live repository state. Documentation relevance and post-checkpoint repository activity are different signals and need an explicit boundary.
- Decision: every monitoring cycle records the exact refreshed remote default-branch commit plus the number, state, draft status, and exact head of every open pull request; task-active pull requests additionally record mergeability, unresolved review threads, and required checks. After that checkpoint, only a newly observed default-branch commit; a newly opened or reopened pull request; a state, draft-status, or head change relative to an inventoried pull request's baseline; or a mergeability, review-thread, or required-check change on a task-active pull request enters the live set. An `updated_at` change caused only by comments, reactions, labels, or activity outside those fields does not qualify. A task-active close or merge is evaluated once and then removed. Documentation, ADR, retrospective, and session-log citations never add an item to the live set by themselves; closed issues are inspected only when the active task explicitly names one for a bounded audit. Before waiting for CI, the monitor rechecks PR state, draft status, mergeability, exact head, and unresolved threads. For each new default-branch merge it inspects the introduced commit range and the post-merge workflows for that exact commit before advancing the checkpoint.
- Alternatives: poll every PR or issue mentioned by project documentation (rejected because durable historical evidence then creates perpetual status work); use only an object's `updated_at` timestamp (rejected because bot reactions and unrelated comments can change a timestamp without making the object relevant to the active task); poll check runs without rechecking PR state and head (rejected because a merged, closed, conflicting, or superseded PR makes the old wait meaningless).
- Consequences: monitoring is bounded, repeatable, and focused on repository transitions observed after an explicit base. Historical incidents remain discoverable without re-entering the work queue, while explicitly requested issue audits and new PR activity remain possible. Canonical agent instructions carry the operational rule, repository governance specifies its scope, and agent-asset validation fails if its exact unindented list items disappear from the exact D-078-linked active monitoring section. Plain prose, fenced, raw-HTML, HTML-commented, indented-code, blockquoted, nested-container, duplicate, renamed, and out-of-section copies cannot satisfy that gate; CommonMark fence, container-boundary, comment-boundary, tab-stop, and invalid-info-string handling prevents hidden text from becoming policy or literal code from hiding it.
