## D-091: Relax `frontend-perf-measure`'s exact-manifest requirement, and complete D-090's coverage-sandbox build, in one composed digest

- Status: accepted; activated by this same v0.2 PR-8 (see D-092's own dependency choice, below, for the `toml`/`serde` addition this activation exists to unblock)
- Context: v0.2 PR-8 needs `toml`+`serde` as root-package dependencies for `pycc.toml` parsing (D-092's own choice, recorded below). Opening PR-8's actual pull request against `main` surfaced two independent, previously-undetected CI gaps at once:

  1. `frontend-perf-measure`'s "Verify exact benchmark revisions" step immediately failed: its `contract_paths` array (`benches`, `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `rust-toolchain`, `.cargo`) requires each path to be byte-identical between the predecessor and candidate checkouts, aborting the job on any diff — and adding a dependency necessarily changes root `Cargo.toml`/`Cargo.lock`. `ci-gate` requires `frontend-perf-measure` literally, with no escape hatch, so this blocks PR-8 entirely.

     Verified via `git log` that this is not a violated project convention: PR-4 (`c738f7f`, merged 2026-07-25 15:26) predates `frontend-perf-measure`'s own activation (`9bed860`, 18:58 the same day) by roughly 3.5 hours, so no historical merged pull request has ever changed root `Cargo.toml` against an *active* gate. The one apparent precedent, `cec43d9` ("Keep pre-commit checks within the performance contract"), dropped a `regex` root dependency in favor of a hand-rolled equivalent — but that was a same-day, trivially-avoidable case authored right after the gate went live, not an established rule binding every future dependency addition. `pycc.toml`'s TOML parsing is not comparably trivial to reimplement without a dependency (real nested-table schema, already specified in `CLI_SPEC.md`), and reimplementing it would additionally reverse PR-8's own planned dependency choice and add meaningful new code under the D-014 100%-coverage gate for a config file the compiler reads once at startup, not on `pycc check`'s own measured path.

     The existing check itself already treats a dependency-manifest change more strictly than an actual source-code change: `crates/**/Cargo.toml` and `**/build.rs` were hashed and hard-required identical via a separate `local_contract_digest` function inside the same "Verify exact benchmark revisions" step, while the surrounding `crates/` directory as a whole — real `.rs` source, the primary thing the benchmark exists to measure — was already permitted to differ, subject only to the softer `executable_inputs_equal` classification (which still applies the existing 2% regression threshold to any change, per the "Classify executable benchmark inputs" step and `scripts/check_replicated_paired_perf_regression.rb`). That is backwards from what the gate is actually trying to guarantee.

  2. `build-test-coverage` failed independently, for an unrelated reason: `tests/pycc_toml_release_default.rs`'s non-ignored test needs a release-built `pycc_rt` to exist, but D-090's own staged fixture never built one inside the coverage gate's isolated `nobody` sandbox (see D-090's "Correction before activation" note). Every affected Tier-1 CI leg was inspected before deciding this: `native-build-test`'s three passing legs (`ubuntu-24.04-arm`, `ubuntu-latest`, `macos-15-intel`) confirmed `nbody_release_binary_is_at_least_20x_faster_than_cpython` itself runs and passes there, and `windows-latest` failed that same assertion at a real 17.95x (not a crash or missing-binary error) — so this bug is scoped to `build-test-coverage`'s own isolated sandbox, not a symptom of the nbody gate value itself.
- Decision: one composed digest fixes all four, built on top of D-090's originally-intended release-profile `pycc_rt` step (still correct and needed) rather than replacing it:
  1. The dependency manifest (root `Cargo.toml`/`Cargo.lock`, replacing the separate nested-crate `Cargo.toml`/`build.rs` digest, which is already covered by the plain `crates/` directory diff) is reclassified rather than hard-required identical. `Cargo.toml`/`Cargo.lock` move into `executable_inputs_equal`'s existing `src`/`crates` loop in "Classify executable benchmark inputs"; `contract_paths` in "Verify exact benchmark revisions" shrinks to `benches`, `rust-toolchain.toml`, `rust-toolchain`, `.cargo`, and the `local_contract_digest` function is removed entirely (redundant once `crates/**/Cargo.toml` is already covered by the whole-directory `crates` diff). This is not a weakening of the gate's power to catch real regressions: a dependency `pycc check` never invokes at runtime (parsing `pycc.toml` is not on that path) cannot confound the timing comparison, and if a manifest change did somehow shift measured timing, the exact same strict 2% threshold already applied to any other executable-input change still catches it — folding the manifest into that classification does not skip the assertion, it only stops aborting the job before the comparison is even attempted. Only `benches` (the corpus itself) and the toolchain/`.cargo` genuinely measure incomparable work if they differ; no numeric threshold can fix that, which is why those stay a hard, unconditional abort.
  2. A separate, standalone check in the same "Verify exact benchmark revisions" step -- not an addition to `contract_paths`, since it diffs a sub-region of one file rather than requiring a whole path byte-identical -- keeps root Cargo.toml's bench-defining tail (`[dev-dependencies]` through end-of-file, which today is exactly `[dev-dependencies]` plus `[[bench]]`) a hard abort even though the rest of the manifest is reclassified by (1). Reclassifying the whole file would let a PR that only bumps `criterion`'s version or edits the `[[bench]] name = "check_bench"` target pass by making the *measurement itself* faster or different, rather than the compiler faster — indistinguishable from a real speedup under `executable_inputs_equal`'s softer path. The check extracts each checkout's `Cargo.toml` from its first `[dev-dependencies]` line to EOF (`awk '/^\[dev-dependencies\]$/,0'`) and diffs the two, guarded by two asserted invariants so a future manifest edit cannot silently widen or narrow the pinned region: (a) `[dev-dependencies]` exists and no section header other than `[[bench]]` follows it, so an unrelated section landing after `[dev-dependencies]` can never be swallowed into the softer classification; (b) every `[[bench]]` section in the file (`grep -c '^\[\[bench\]\]$'` on the whole file) is inside that extracted tail (the same count on the tail alone), so reordering `[[bench]]` to appear *above* `[dev-dependencies]` cannot silently move it out of the pinned region and into the reclassified path -- both directions abort loudly instead of mis-scoping. This check does not, and cannot without parsing TOML, isolate criterion's own transitive entries within `Cargo.lock`; `Cargo.lock` stays fully reclassified into `executable_inputs_equal`; a `criterion` version bump that changes `Cargo.lock` without touching root `Cargo.toml`'s `[dev-dependencies]`/`[[bench]]` region is an accepted, documented residual gap, not an oversight, since blocking every lockfile change unconditionally is the exact over-broad behavior this decision fixes. Two further residuals, both accepted for the same reason (closing them costs more than the exposure they remove): a `[[bench]]` stanza written with non-canonical inner whitespace (`[[ bench ]]`, which TOML permits but neither Cargo nor this manifest ever emits) would not match either invariant's exact-line regex and so would not be counted by invariant (b) at all -- not reachable without first already having tripped the tail `diff` in the asymmetric case, and requires both checkouts to independently carry the same non-canonical spelling above `[dev-dependencies]` to matter in the symmetric case; and invariant (b)'s `grep -c ... || true` idiom exists to tolerate the legitimate zero-count case (grep exits 1 on no matches) but would also swallow a genuine read failure on the same manifest already read successfully moments earlier by the `[dev-dependencies]`-existence check in the same loop iteration -- a narrower trigger window than the check's own precondition allows in practice.
  3. A root-level `build.rs` (not present today, but a plausible future addition — `local_contract_digest` used to hash `**/build.rs`, not just crate-nested ones) is added to the same "Classify executable benchmark inputs" loop alongside `src`/`crates`/`Cargo.toml`/`Cargo.lock`, guarded by the same exists-on-either-side check `contract_paths` already uses, so a future root `build.rs` cannot silently fall through unclassified the way a naive removal of `local_contract_digest` would have left it. Per-crate `build.rs` files stay covered by the existing whole-directory `crates` diff, as before.
  4. `build-test-coverage`'s "Hard coverage gate" step's isolated sandbox gains its own `run_isolated "$TRUSTED_CARGO" build --release -p pycc_rt` call, alongside the existing cross-compile-target and debug-profile calls, before `llvm-cov` runs. Verified (not assumed) that this lands the library where the test looks: the sandbox's `CARGO_TARGET_DIR=$ISOLATED_ROOT/target` combined with the job's own `ln -s "$ISOLATED_ROOT/target" "$GITHUB_WORKSPACE/target"` symlink means the release build appears at `$GITHUB_WORKSPACE/target/release`, exactly the `env!("CARGO_MANIFEST_DIR")`-relative path `find_pycc_rt_lib_dir_in` resolves to.

  Items 2 (bench-manifest tail) and 3 (build.rs) were both flagged by GitHub's automated review (`chatgpt-codex-connector`) on PR #189 before merge and folded into this same digest rather than filed as follow-ups, for the same reason D-090 was folded into this decision rather than left as a separate one: `ci.yml`'s two-phase trust boundary means every gap discovered before this digest activates is cheaper to fix now than after.

  Staged the same way as D-090: `tests/fixtures/d91-relax-frontend-perf-manifest-ci.yml` (built from PR-8 branch's own `ci.yml`, which already carries D-090's release-profile build steps, plus all fixes above) was added by a separate stage PR (#189) and its digest (`D91_RELAX_FRONTEND_PERF_MANIFEST_CI_WORKFLOW_SHA256`) authorized alongside active D84. D-090's own digest was removed from the allowlist entirely (see D-090's correction note) rather than kept alongside this one — the two are not independent alternatives, D-091 is the corrected, complete version of what D-090 started. This same v0.2 PR-8 merge is the byte-exact activation pull request the paragraph above anticipated: `.github/workflows/ci.yml` now matches this fixture exactly (verified via `shasum -a 256`), and D84 is retired from the allowlist below.
- Alternatives: hand-roll a minimal TOML parser to avoid the new dependency entirely, matching `cec43d9`'s `regex` precedent — rejected: that precedent was a same-day, trivially-avoidable substitution, not a binding rule, and `pycc.toml`'s real schema makes a hand-rolled parser substantially more code/coverage surface/review than a config file deserves, while also reversing PR-8's own planned dependency choice for no correctness benefit. Move `toml`/`serde` into a separate, non-root workspace crate instead of the root package — rejected: `local_contract_digest`'s existing nested-crate-manifest digest already hard-required every `crates/**/Cargo.toml` to be byte-identical too, so relocating the dependency would trip the exact same abort from a different path; the fix has to be the classification rule, not where the dependency lives. Leave the hard-fail contract as-is and grant PR-8 a one-off manual exception — rejected: an undocumented exception invites the next PR to read the gate as negotiable whenever inconvenient, whereas this decision states precisely why the contract was over-broad, generalizing to every future PR that adds a dependency, not just this one. Fix the coverage-sandbox gap as its own separate decision/digest — rejected: both fixes must land before PR-8's `ci.yml` can activate correctly regardless of order, and D-090's digest was never live, so there is no cost to composing them into the one digest that actually needs to go live.
- Consequences: PR #189's own staging commits did not change live CI behavior; this v0.2 PR-8 merge is the activation that does — `.github/workflows/ci.yml` is replaced with the reviewed `d91-relax-frontend-perf-manifest-ci.yml` fixture's exact bytes, verified via `shasum -a 256` rather than assumed. `scripts/check_roadmap_evidence.rb` gains `D91_VERIFY_REVISIONS_SCRIPT`/`D91_EXECUTABLE_INPUT_IDENTITY_SCRIPT` (the manifest-relaxation-plus-bench-tail-fingerprint step bodies) and `D91_RELAX_FRONTEND_PERF_MANIFEST_MEASURE_JOB` (derived from the existing `REPLICATED_PERF_MEASURE_JOB`, matching `D56`/`REPLICATED`'s own derivation pattern), and `validate_source_aware_perf_gate_lifecycle` accepts this job shape as a third valid `frontend-perf-measure` body alongside the two existing ones.

  `build-test-coverage`'s own coverage-sandbox fix is *not* unmodeled by this file, and needed the exact same coexist-then-retire treatment as the whole-file digest array — caught by the pinned reviewer before merge, then verified directly by reading `.github/workflows/workflow-policy.yml`: its `audit` job's "Audit head roadmap evidence" step runs the *full*, unconditional `scripts/check_roadmap_evidence.rb` (not a narrower entry point) against the PR head's `ci.yml` under `pull_request_target`, and `validate_evidence` calls `coverage_gate_present?` unconditionally alongside the digest and lifecycle checks. `coverage_gate_present?` previously matched the "Hard coverage gate" step's `run` body against a *single* `COVERAGE_SCRIPT` constant — mutating it in place (an earlier draft of this commit did exactly that) broke validation of the still-live D84-shaped `ci.yml` this stage commit does not touch. The fix mirrors `REVIEWED_PERF_CI_WORKFLOW_SHA256S`'s own array pattern instead: `D91_COVERAGE_SCRIPT` (the new shape, with the release-profile build line) is added alongside the original `COVERAGE_SCRIPT`, both collected in `REVIEWED_COVERAGE_SCRIPTS`; `D91_TRUSTED_COVERAGE_STEPS` mirrors `TRUSTED_COVERAGE_STEPS` with only its last step's body swapped, both collected in `REVIEWED_TRUSTED_COVERAGE_STEPS`; `coverage_gate_present?` accepts either. A later activation commit, once `ci.yml` itself matches only the D91 shape, can retire the old constants from these arrays the same way `REVIEWED_PERF_CI_WORKFLOW_SHA256S` retires a superseded digest.

  The reviewed-workflow allowlist held only D91 as of this decision's own drafting -- this v0.2 PR-8 merge was expected to retire D84 (kept as a historical audit-fixture digest, matching D51/D56/D62/D80's own retirement pattern) the same way D84's own activation retired D80. **Update:** D-099 (an independent, unrelated Windows vcpkg-caching change) activated first, retiring D-091's own digest to audit-only status before this PR-8 merge landed; D-100 composes D-091's changes with D-099's cache boundary into the new digest that actually activates. D-091's own substantive changes (release-mode `pycc_rt` step, relaxed manifest classification) are unaffected by this reordering and are exactly what D-100 carries forward -- only which digest constant is "the live one" changed, not the reviewed content itself. A future PR that adds a workspace dependency alongside a genuine `pycc check`-affecting source change now correctly has `executable_inputs_equal=false` and is held to the real regression threshold, rather than being unable to open a comparable pull request at all, and `build-test-coverage` correctly finds a release-built `pycc_rt` for any test that needs one.
