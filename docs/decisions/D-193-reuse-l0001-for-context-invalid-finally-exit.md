## D-193: Reuse `L0001` for `return`/`break`/`continue` that exit a `finally` block, gated on a valid escape target (PEP 765, #738)

- Status: accepted
- Context: PEP 765 (targeted at Python 3.14) disallows a `return`/`break`/`continue` that would exit a `finally` block. As of the pinned `python3.14` oracle (3.14.6), CPython does not yet make this a hard `SyntaxError` — it emits a `SyntaxWarning` and otherwise compiles the module normally, *provided a valid escape target for the statement already exists outside the `finally`* (an enclosing loop for `break`/`continue`, an enclosing function for `return`). pycc's stated policy is to reject the construct outright rather than accept CPython's still-permissive 3.14 behavior, following this repository's own precedent of getting ahead of upcoming hard-error PEPs. This is the direct sequel to D-148 (`break`/`continue` outside a loop) and D-149 (`yield`/`yield from` outside a function): the same "reuse `L0001` for a post-parse context-invalidity violation caught during HIR lowering" pattern, applied to a third context-invalidity family member.
- Decision: Thread a third piece of context, `in_finally: bool`, through `crates/pycc_hir/src/stmt.rs`'s `lower_stmt`/`lower_body`/`lower_elif_else_clauses`/`lower_match` and `crates/pycc_hir/src/stmt/exception.rs`'s `lower_except_handler`, mirroring `in_loop`'s (D-148) and `in_function`'s (D-149) existing shape as a fourth, independently-threaded plain `bool` parameter rather than folding all three into one context struct (same rationale D-149 already gave for that alternative: touching call sites is unavoidable either way, and a struct would blur `stmt.rs`'s ownership of one context dimension per file). It becomes `true` only while lowering the `finalbody` of a `Stmt::Try` (the `body`, `handlers`, and `orelse` of that same `Try` inherit whatever value was already in scope — entering a `finally` clause is the only thing that sets it), propagates unchanged through `if`/`elif`/`else`, a nested `try`'s non-`finally` parts, and `match`/`case`, and is reset to `false` when lowering the body of a `while`/`for` loop reached from inside that `finally` (mirroring `in_loop`'s own reset on loop entry) or when entering a function body via `lower_function`.

  `Stmt::Return`, `Stmt::Break`, and `Stmt::Continue` each check `in_finally` alongside a second condition before emitting the finally-specific diagnostic — `in_finally && in_function` for `Stmt::Return`, `in_finally && in_loop` for `Stmt::Break`/`Stmt::Continue` — rather than checking `in_finally` alone. This gating was added after an independent review round caught that the initial unconditional design mis-prioritized CPython's own diagnostic precedence: verified directly against `python3.14 -W all`, a `break`/`continue`/`return` directly in a `finally` with NO valid escape target anywhere (e.g. a bare `break` at module scope, no enclosing loop at all) makes CPython's *actual fatal error* the pre-existing `SyntaxError` for the missing target (`'break' outside loop`, `'continue' not properly in loop`, `'return' outside function`) — the finally-specific `SyntaxWarning` prints alongside it, but is not itself fatal and does not override the missing-target error (confirmed transcripts: `python3.14 -W all` on a bare `try: pass\nfinally: break` with no enclosing loop prints both the `SyntaxWarning: 'break' in a 'finally' block` line and then still raises `SyntaxError: 'break' outside loop`, exit code 1 either way; the same module wrapped in `while True: ... finally: break` prints only the `SyntaxWarning`, exits 0). Only once a real target exists outside the `finally` does CPython's fatal outcome become the finally-specific one. pycc mirrors that precedence: without a valid target, `stmt.rs` falls through to its own pre-existing `in_loop`-driven `L0001`/`C0001` split for `break`/`continue`, and lets `Stmt::Return` lower normally so the pre-existing `pycc_types` `T0024` ("`return` outside a function") path — the same deferred-to-type-check precedent D-149 already relies on for every other top-level `return` — reports the missing-function case instead.

  The loop-reset rule itself (an intervening loop shields all three statement kinds identically, including `return`) was separately verified against the same oracle: `def f() -> int:\n    try:\n        pass\n    finally:\n        for i in range(3):\n            return i\n` compiles cleanly (exit 0, no warning at all) under `python3.14 -W all`, confirming a loop defined *inside* the `finally` shields a `return` exactly as it shields `break`/`continue`, even though a naive reading of the PEP's text (a `return` always escapes the `finally` regardless of loop nesting) would predict otherwise. A two-flag design mirroring that naive reading (one flag for `return`, a separate one for `break`/`continue`) would silently diverge from upstream's own diagnostic surface, so both are governed by the single shared `in_finally` flag instead.

- Alternatives: check `in_finally` alone, unconditionally, for all three statement kinds (the initial implementation of this issue) — rejected after independent review surfaced the precedence bug above, confirmed against the oracle rather than assumed; two independent flags, one for `return` and one for `break`/`continue` (rejected — the loop-shielding oracle evidence shows both are governed by the identical rule, so one shared flag is both simpler and more faithful); moving the check to `pycc_types` (rejected for the same reason D-149 rejected it for `yield`: `Stmt::Try`'s three-part structure and the loop/function-reset rules are HIR-lowering-local state that `pycc_types` has no equivalent scope-tracking mechanism for today, unlike `T0024`'s existing module-vs-function dispatch which this decision still defers to for the no-valid-function-target case rather than reimplementing it).
- Module decomposition: no new file extraction was needed — `in_finally` reuses the same `crates/pycc_hir/src/stmt.rs`/`crates/pycc_hir/src/stmt/exception.rs` module pair D-148 already established, unlike D-149's `expr.rs` extraction (this issue never needed to reach `lower_expr`).
- Consequences: `pycc check` now reports `L0001` ("`'return'`/`'break'`/`'continue'` in a `'finally'` block") for the three statement kinds when a valid escape target exists outside the `finally`, and continues to defer to the pre-existing `L0001` "outside loop"/"not properly in loop" or `T0024` "outside function" diagnostics when no valid target exists anywhere — matching CPython 3.14's own fatal-error precedence rather than only its warning text. New unit tests in `crates/pycc_hir/src/tests.rs` cover both directions for all three statement kinds, including the `if`/nested-non-`finally`-`try`-part/`match` propagation cases, the `orelse` pass-through, the loop-shielding success path, and a nested-`finally`-forces-`true`-again regression guard. New CLI fixtures under `tests/diagnostics/` (`l0001_return_inside_finally`, `l0001_break_inside_finally`, `l0001_continue_inside_finally` for the valid-target case; `l0001_break_inside_finally_with_no_enclosing_loop`, `l0001_continue_inside_finally_with_no_enclosing_loop`, `d0024_return_inside_finally_with_no_enclosing_function` for the no-valid-target fallback) follow the same not-byte-for-byte-oracle-diffed convention D-148/D-149 established, wired into `tests/diagnostics_test.rs`. `docs/DIAGNOSTICS.md`'s `L0001` row and `crates/pycc_diag/src/explain.rs`'s `pycc explain L0001` text are both extended to mention this third context-invalidity family member. `docs/PYTHON_STANDARDS.md`'s PEP 765 conformance-matrix row is deliberately left at `☐` (not flipped to `◐`/`✅`): row promotion under `scripts/check_conformance_breadth.py` (D-177) requires citing an already-observed green Tier-1 CI run for a checked-in conformance fixture, which does not exist yet for this row and cannot be created in the same pull request that would produce that run: this PR only implements the syntax-rejection semantics, and CPython 3.14 itself still only warns rather than errors, so a run-and-compare fixture would encode a divergence from CPython's own current behavior rather than conformance with it. `docs/ROADMAP.md`'s v0.3 status paragraph is likewise left unchanged, since the matrix it describes is unchanged. Part 1 of #543; #543 stays open for the remaining PEP 3151 and PEP 758 rows.
