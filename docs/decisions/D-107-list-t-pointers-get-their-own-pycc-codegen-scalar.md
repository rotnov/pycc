## D-107: `list[T]` pointers get their own `pycc_codegen::Scalar::List` variant; refcounting stays leak-only in v0.2

- Status: accepted
- Context: Task 5 (D-089) made `emit_expr`'s `Name` arm read a `Ty::List(_)`-typed local by reusing `Scalar::Str` to carry the pointer (`crates/pycc_codegen/src/lib.rs`, the `Ty::List(_)` arm next to `Ty::Str`'s), explicitly documented as safe only because "no `MirExpr` can construct a `list[T]` value yet," and explicitly flagged as "a general Task-11 tripwire" for `truthy` and `to_str` specifically, both of which are **exhaustive** matches over `Scalar` with no catch-all. Before dispatching Task 11 (codegen), checked whether that tripwire is actually reachable rather than assuming either way: `pycc_types` accepts a `Ty::List`-typed operand in a boolean context (`crates/pycc_types/src/lib.rs:1214`, `infer_expr(env, test)` with the comment "any type is accepted as truthy for v0.1 -- Python's own truthiness has no static type restriction") and as `print`'s argument (`crates/pycc_types/src/lib.rs:310-312`, an unconditional `Ok(Ty::None)` for any argument type, no type check at all). So `if x:` and `print(x)` for `x: list[int]` both type-check successfully today and would reach `truthy(Scalar::Str(list_ptr))`/`to_str(Scalar::Str(list_ptr))` once Task 11 makes `list[int]` values actually constructible from real source — not a hypothetical, a live reachable path. `PyIntListObj`'s layout (`rc: Cell<u32>`, `items: Cell<Vec<i64>>`) is entirely different from `PyStrObj`'s (`rc: Cell<u32>`, `payload: PyStrPayload`), so `pycc_rt_str_truthy`/`pycc_rt_*_to_str` misreading a list pointer's bytes as string data is genuine undefined behavior, not a defensible interim gap. Separately, checked whether `list[T]` refcounting is wired anywhere in `pycc_codegen`: it is not. `decref_str_slot_before_store` (the existing reassignment-cleanup path `str` locals use) is gated on `slot.ty != Ty::Str` and panics if called on anything else, and is confirmed never reached for a `Ty::List` assignment target — so reassigning or aliasing (`y = x`) a list variable neither increfs nor decrefs anything today. This is leak-only, never a premature free or a double free, since nothing frees a list value early either.
- Decision: `Scalar` (`crates/pycc_codegen/src/lib.rs`) gains its own `List(PointerValue<'ctx>)` variant, replacing the `Scalar::Str` reuse. This turns every exhaustive `Scalar` match (`truthy`, `to_str`, and any other site the compiler flags) into a compile error until it adds a `List(_)` arm — the same "let the compiler enumerate every site" principle Task 5's own `Ty` catch-all audit already established, rather than manually hunting for every place a list pointer could reach an operation that assumes `str`. `truthy(list)`/`to_str(list)`/any arithmetic-on-list arm gets an honest `panic!("pycc_codegen: <description> on a list[T] value is not supported yet")`, matching this project's "honest panic over silently wrong data" convention — v0.2 genuinely has no `bool(list)`/`str(list)`/list-arithmetic semantics, so this is a true, currently-real feature gap, not a regression introduced by this decision. `list[T]` refcounting stays exactly as it is today: leak-only. `pycc_rt_int_list_incref`/`_decref` (already shipped by Task 10) are not called from anywhere in Task 11's own scope; a list's backing allocation is freed only if some future task wires that call. For pycc's actual target use (a short-lived, single-shot compiled batch program), an unbounded per-list leak is a bounded-by-process-lifetime resource cost, not a defect visible in any program's observable output.
- Alternatives: keep reusing `Scalar::Str` and add a manual `Ty`-gated check at every `truthy`/`to_str`-style call site instead (rejected — exactly the kind of easy-to-forget manual enumeration Task 5's own catch-all-audit precedent exists to avoid; a new call site added by a later task could silently omit the same check, whereas a missing `List(_)` arm on an exhaustive match is a compile error no task can miss). Wire full `list[T]` refcounting now (incref-on-duplicate-reference, decref-before-reassignment, decref-at-scope-exit, mirroring `str`'s own D-060 pattern exactly) (rejected for v0.2's own "thin slice" scope — this multiplies Task 11's diff for a memory-lifetime property that affects no program's observable output and is bounded by process lifetime for pycc's actual batch-compiled-binary use case; better sized as its own task once a real usage pattern — e.g. an unbounded loop appending large lists — actually motivates it).
- Consequences: Task 11 splits into 11a (this decision's own scope, plus D-106's `pycc_rt_int_untag_checked`/`raw_i64_to_tagged_int`) and 11b (wiring the four new MIR forms against the now-settled `Scalar::List` representation). A future PR that needs real `list[T]` refcounting must wire `pycc_rt_int_list_incref`/`_decref` at the same three sites `str`'s own D-060 refcounting already covers (duplicate-reference reads, reassignment cleanup, scope-exit cleanup) — tracked as a `docs/ROADMAP.md` follow-up by Task 12, not silently assumed solved by this PR.
