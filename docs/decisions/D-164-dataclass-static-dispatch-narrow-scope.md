## D-164: Dataclass static dispatch and narrow scope
- Status: accepted
- Context: PEP 557 dataclasses and PEP 681 `dataclass_transform` require auto-generated `__init__`, `__eq__`, and `__repr__` methods from class-level annotated fields. The full PEP 557 specification includes field defaults (`field(default=...)`, `field(default_factory=...)`), frozen dataclasses, ordering (`__lt__`/`__le__`/`__gt__`/`__ge__`), slots, and post-init processing. pycc's existing architecture uses static dispatch (D-006) with no vtables or runtime dynamic dispatch, and class instances are opaque heap objects accessed through FFI accessors (D-154). The dataclass implementation must integrate with the existing HIR → type checker → MIR → LLVM code-generation pipeline without introducing new runtime polymorphism. PEP 3129 class-decorator syntax is a prerequisite for `@dataclass` itself — pycc has no general decorator support (function decorators remain unsupported), so class-decorator parsing and lowering must be added as part of this work.
- Decision: Implement a narrow, statically dispatched dataclass feature. Accept bare `@dataclass` and bare `@dataclass_transform()` (keyword arguments accepted but ignored) as the only recognized class decorators; reject all other class decorators with `C0001`. Support required fields only — class-level annotated assignments (`x: int`) become dataclass fields; reject field defaults, `field()`, `field(default=...)`, and `field(default_factory=...)` with `C0001`. Reject `@dataclass(frozen=True)` and any other option-bearing form with `C0001`. Auto-generate `__init__` (one required parameter per field, in declaration order), `__eq__` (field-by-field equality returning `bool`), and `__repr__` (producing `ClassName(field=value, ...)`). Lower `__ne__` at the MIR level as the negation of the generated `__eq__` call — no separate `__ne__` method is synthesized. Rewrite `print()` and f-string interpolation of dataclass instances at the MIR level to call `__repr__`. Accept same-class `==`/`!=` comparisons when `__eq__` exists (resolved via the MRO); reject incompatible class comparisons with `T0021`. Support dataclass inheritance: merge parent fields (via MRO, parent-before-child order, deduplicating redeclared fields) with the child's own fields; reject dataclass inheritance from a non-dataclass base with `C0001`. Reject explicit `__init__`, `__eq__`, or `__repr__` definitions in a `@dataclass` body with `C0001`. Carry dataclass metadata (`is_dataclass: bool`, `dataclass_fields: Vec<(String, Ty)>`) on `HirClassDef` through the pipeline. Synthesize generated methods as ordinary `HirItem::Function`s with mangled names (`ClassName.__init__`, `ClassName.__eq__`, `ClassName.__repr__`), flowing through the existing method infrastructure with no new MIR or codegen variant.
- Alternatives: (1) Full PEP 557 implementation including defaults, frozen, ordering, slots, and post-init — rejected because defaults require optional constructor parameters (the existing instantiation model requires all arguments), frozen requires write-time checks (no existing infrastructure), and ordering requires four additional comparison methods. (2) Runtime introspection of `__annotations__` for field discovery — rejected because pycc evaluates annotations statically at compile time (TYPE_SYSTEM.md) and has no runtime annotation object. (3) Separate `__ne__` method synthesis — rejected as unnecessary since `__ne__` is always the logical negation of `__eq__` and can be lowered at the MIR level. (4) General decorator support (function + class) — rejected as out of scope; only class decorators are needed for `@dataclass`, and general function-decorator syntax stays unsupported until a PR actually needs it.
- Consequences: Dataclass classes work end-to-end with auto-generated constructors, equality, and repr. The narrow scope means common Python patterns like `field(default_factory=list)` or `@dataclass(frozen=True)` are rejected with `C0001` — users must write explicit `__init__` methods for those patterns. The static-dispatch model means no runtime polymorphism is introduced; generated methods are resolved at compile time through the existing method infrastructure. PEP 3129 class-decorator syntax is now supported for `@dataclass` and `@dataclass_transform()` only; other class decorators are rejected. The `HirClassDef` struct gains two fields (`is_dataclass`, `dataclass_fields`) that are carried through the pipeline but are unused for non-dataclass classes. Field defaults, frozen, ordering, slots, and post-init remain future work — a later PR can add them by extending the `classify_class_decorator` function and the field-lowering logic.
