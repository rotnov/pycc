## D-066: Maintain an agent retrospective log and a session handoff log

- Status: accepted (the "should update the session log at meaningful checkpoints" clause in "Decision" below is narrowly superseded by [D-192](#d-192-bound-the-tracker-milestone-at-filing-a-41-merge-quota-a-ceiling-on-non-milestone-issues-and-one-session-file-per-merged-pull-request), which narrows the trigger to at most one session file per merged pull request — see that decision for the current scope; every other clause here remains in force unchanged)
- Context: this project runs sustained autonomous agent work, sometimes with multiple independent agents active on the repository concurrently (see D-013). Two related but distinct kinds of context were being lost between sessions: process mistakes worth learning from (a session repeating the same failed dispatch pattern four times before adapting; three staged-digest reconciliation rounds against a moving CI target before deciding to decouple; an ADR-numbering collision from two independent actors reserving the same ID range days apart) had no durable home, and a long autonomous session's current state (what's done, what's in flight, what a fresh session needs to know to resume) existed only in conversation transcripts, which do not survive a handoff to a different session or a different agent platform.
- Decision: add `docs/AGENT_RETROSPECTIVE.md` (process-mistake journal, newest entry first, for retrospective learning — never a merge gate, never containing credentials or personal information) and `docs/SESSION_LOG.md` (running handoff snapshot: overall status, what's in flight, known follow-ups, where to look to resume — snapshots, not a full transcript). Both are ordinary tracked markdown documents, reviewed like any other documentation change; neither is machine-generated or CI-enforced. An agent should add a retrospective entry when a mistake cost meaningful time and the lesson is actionable by a future session, and should update the session log at meaningful checkpoints (a PR opened or merged, a milestone reached, before ending a long session) rather than after every action. Each session snapshot must identify the commit and repository state actually inspected and must distinguish uncommitted or unmerged work from delivered work.
- Alternatives: fold this into `docs/DECISIONS.md` itself (rejected — that log is for irreversible design choices with alternatives considered, not process narrative, and mixing the two would dilute both); keep it only in conversation memory or an external tool (rejected — does not survive a handoff to a different session, different agent, or different platform, which is exactly the failure mode this decision addresses); a single combined file (rejected — retrospective entries are timeless lessons revisited occasionally, while the session log is a fast-changing snapshot meant to be read once at resume time; combining them would make the useful lessons hard to find under fast-changing status noise).
- Consequences: future sessions gain a place to check for known process pitfalls before repeating them and a concrete resume point after a handoff, at the cost of two more documents to keep current — both are explicitly snapshots/journals rather than normative contracts, so they carry none of the enforcement machinery (CI checks, roadmap-evidence markers) that governs `docs/ROADMAP.md` or `docs/DECISIONS.md` itself.
