## D-116: tuple[...] v0.2 scope — int/bool/float elements only, literal-index-only reads; pass-through operations extend uniformly, interpretive operations panic honestly

- Status: accepted
- Context: dict/set's own D-122 scoped to exactly one key/value combination each because their v0.2 slice needed a working equality comparison for hash-table-style lookup; tuple has no such constraint (D-115's struct representation needs no element equality for construction or literal-index reads), so tuple's scope question is different in kind: which element *types* are safe to put in a struct field with this PR's own codegen support, and what indexing form is type-checkable at all for a heterogeneous aggregate.
- Decision:
  1. Element types: exactly `Ty::Int`, `Ty::Bool`, `Ty::Float` (any mix, any arity ≥ 1) are accepted; any other element type (`Ty::Str`, `Ty::List`, `Ty::Dict`, `Ty::Set`, `Ty::Tuple`) is rejected pre-codegen by a new diagnostic, `T0039` ("tuple[...] is not compiled yet -- only int/bool/float elements are"), mirroring `T0034`/`T0036`/`T0038`'s "one shipped shape, everything else gets a clean diagnostic" pattern — except this gate is a type-*membership* test per element, not a single frozen shape, since D-115's per-field codegen already generalizes for free across any mix of these three scalar types. An empty tuple literal is rejected with the existing `T0021` pattern, mirroring `ListLiteral`/`DictLiteral`/`SetLiteral`'s own identical empty-literal gate.
  2. Indexing: `t[k]` requires `k` to be a literal (`HirExpr::IntLiteral`), non-negative, in-bounds integer — not merely `int`-typed, unlike `list[int]`'s own runtime-checked index (D-105/D-108). A heterogeneous tuple's element type at position `k` is only knowable when `k` is known at compile time, so a non-literal or out-of-range `t[k]` is rejected by a new diagnostic, `T0040` ("tuple index must be a non-negative literal integer within range"), covering all three failure shapes (non-literal, negative, out-of-range) under one code since they are the same underlying "not a valid compile-time position for this tuple" failure — a stricter, statically-checked version of D-108's own "no negative indexing" rule, caught at compile time here instead of `list[int]`'s runtime panic, because the literal is already in hand at type-check time.
  3. Deferred, tracked as `docs/ROADMAP.md` follow-ups (Task 7 of `docs/superpowers/plans/2026-08-01-v0-2-pr11-tuple.md`), not silently assumed solved: `for x in t:` iteration (needs per-position codegen for a heterogeneous tuple, a materially different problem than `ForList`/`ForDict`/`ForSet`'s homogeneous-element loops); tuple-unpacking assignment (`a, b = t`, a new multi-target assignment form nothing in `HirStmt::Assign`'s shape supports today); a `tuple[...]` annotation syntax (mirrors D-105 cut 1's identical deferral for `list[T]`); nested containers-of-tuples or tuples-of-containers (already rejected structurally by (1) above). *(Added 2026-08-01, final-review fix wave, not Task 7):* string conversion of a tuple (reachable via `print(t)` and f-string interpolation) and truthiness of a tuple (`if t:`/`while t:`) both type-check today (`pycc_types` places no restriction on either context) but panic honestly in `pycc_codegen`'s `to_str`/`truthy` respectively (see those arms' own doc comments) — unlike `list`/`dict`/`set`'s identical-shaped panics, which predate this whole PR-11 effort or were already in place before PR-11b started, this reachability for `tuple[...]` is new as of this PR-11b's own Task 2 (`HirExpr::TupleLiteral` lowering): before that change, any program containing a tuple literal failed to lower at all and got a clean `C0001` diagnostic instead.
  4. NOT deferred, because D-115's representation makes it free: a tuple value may be a function's inferred return value or an unannotated/generic function's argument, exactly like `list[int]`/`dict[str,int]`/`set[int]` already can be (there is no annotation syntax for any of the four container types, so this was already call-site-structural-inference-only for all of them) — `build_call_to`'s argument-marshalling match and `MirStmt::Return`'s codegen both get a real `Scalar::Tuple(v) => v.into()` pass-through arm, not a panic, mirroring `List`/`Dict`/`Set`'s own existing arms there exactly.
- Alternatives considered:
  - Requiring homogeneous elements, mirroring `list`/`dict`/`set`'s own homogeneity gates — rejected: heterogeneity is tuple's entire distinguishing feature in real Python (`(1, "a", True)`); restricting to homogeneous tuples would ship a strictly worse-than-`list[int]` feature for no implementation-cost savings, since D-115's per-field codegen already handles any mix of the three accepted scalar types with zero extra work.
  - Accepting a non-literal integer index and picking, say, the first element's type as the whole subscript's result (unsound but simple) — rejected outright: silently-wrong types reaching codegen is exactly the defect class this project's testing/diagnostics discipline exists to prevent. CPython itself allows `t[i]` for a variable `i` only because its tuples are dynamically typed at every position; this compiler's static type system has no single `Ty` to give that expression when the tuple is heterogeneous, so rejecting it is the only sound option, not a scope cut.
  - Scoping function-parameter/return/argument-marshalling support out of v0.2 defensively, on an initial (later revised) assumption that struct-by-value crossed some unaddressed ABI complexity boundary — rejected after confirming `inkwell`'s `BasicValueEnum`/`BasicMetadataValueEnum` already include `StructValue` and every relevant call site (`build_call_to`, `MirStmt::Return`, `emit_assign`) is already generic over `BasicValueEnum`/`BasicTypeEnum`: excluding this would be an artificial restriction with no corresponding implementation risk.
- Consequences: a future PR widening `T0039`'s element-type gate to include `Ty::Str` must revisit D-115's "no refcounting question" premise before shipping. A future PR adding `for x in t:` or tuple-unpacking assignment is unblocked by anything in this ADR — both are additive, not corrections to this scope. `docs/ROADMAP.md`'s existing dict/set follow-ups (D-123's `in`-based set membership; D-124's future combined-refcounting pass) are joined by tuple's own three deferred items above. **Correction (2026-08-01, Task 7 of this same plan):** point 4's claim that "a tuple value may be a function's inferred return value or an unannotated/generic function's argument" describes only the codegen layer's readiness (Task 5's `compiles_a_function_with_a_tuple_parameter_and_tuple_return_value`/`passing_a_tuple_value_as_a_function_argument_marshals_it_by_value` unit tests, which construct MIR directly), not an end-to-end capability reachable from real Python source. Empirically, `pycc_types`' private-helper signature-inference solver (`infer_function_signatures_with_solver`) is scalar-only by construction: `collect_expr_constraints` returns no unification term for `TupleLiteral`/`ListLiteral`/`DictLiteral`/`SetLiteral` (its own doc comment says so directly — "this solver only exists to infer scalar `Ty::Infer` parameters/returns"), so an entirely unannotated (`_`-prefixed) private helper can never have a container-typed parameter or return type inferred from real source. Three concrete reproductions, all rejected today: `def _make_pair(): return (10, 20)` fails T0021 ("cannot infer return type"); `def _identity(t): return t` called as `_identity((1, 2))` fails T0021 ("cannot infer type of parameter `t`"); and, worse, `def _make_pair(): t = (10, 20); return t` fails with the actively misleading `T0021` "local name `t` is not bound before this use" even though `t` is assigned on the immediately preceding line — because a container-literal assignment's target never receives a solver binding at all, not because of any real use-before-definition. The same reproduction with a bare `[1, 2, 3]` list literal in place of the tuple fails identically, confirming this is a pre-existing gap shared by `list`/`dict`/`set`, not something this PR introduced or was expected to fix. `tests/fixtures/tuple_heterogeneous.py` (Task 7) was written around this constraint — it exercises literal construction, literal-index reads, and both module-global and function-local storage, but not a tuple value crossing a function boundary. See `docs/ROADMAP.md`'s matching follow-up for the fix this correction defers. **Further correction (2026-08-01, final-review fix wave):** the paragraph above names only one blocker (`pycc_types`' scalar-only signature-inference solver). There is a second, independent one: even a hypothetical future fix to that solver would not be sufficient by itself, because `pycc_codegen`'s own `emit_expr` function has no dedicated `MirExpr::Call` result-dispatch arm for `Ty::List`/`Ty::Dict`/`Ty::Set`/`Ty::Tuple` either — its catch-all `other` arm (see that match's own doc comment, `crates/pycc_codegen/src/lib.rs`) panics with a message naming the specific type ("a `{ty}`-typed call result is not supported yet") for all four container types today. So `p = make_pair()` for a hypothetically-now-inferrable unannotated function returning a `tuple[...]` (or any other container) would still panic — just in `pycc_codegen` instead of `pycc_types` — until that second, independent gap is also closed. Both blockers must be fixed, not just the solver, before any container value can genuinely cross a function boundary from real source.
