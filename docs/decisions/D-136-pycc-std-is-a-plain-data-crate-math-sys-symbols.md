## D-136: `pycc_std` is a plain data crate; `math`/`sys` symbols are hand-recognized inside `pycc_types::infer_expr_in`, reusing the `print`/`len` pattern

- Status: accepted
- Context: PR-14 (D-088 point 2) ships `import math`/`import sys` and `from math import ...`/`from sys import ...` as compile-time intrinsic bindings against a stdlib registry, explicitly "the same category of special-case `infer_expr_in` already uses for `print`" (D-088's own words), not a general FFI/native-call mechanism. `pycc_types::infer_expr_in` (`crates/pycc_types/src/lib.rs`) already hand-recognizes `print` (returns `Ty::None` unconditionally, line ~495) and `len` (returns `Ty::Int` after an argument-shape check, line ~499 on) as call-site intrinsics with no user-declarable signature and no general dispatch table. `pycc_codegen` likewise special-cases `print`/`len` by callee name at the MIR-lowering/codegen boundary rather than through a generic native-call ABI. There is currently no `pycc_std` crate and no runtime FFI surface for calling into libm or the C standard library from generated code.
- Decision:
  1. `pycc_std` is a new workspace crate containing only plain Rust data: a static registry (`&[StdSymbol]` or equivalent, no macros, no build-script codegen) enumerating every stdlib symbol v0.2 recognizes, each entry naming its module (`"math"` or `"sys"`), its bare name (`"sqrt"`, `"pi"`, `"sys.argv"` is out of scope — see below), its shape (function-with-signature vs. constant-with-`Ty`), and for functions its parameter `Ty`s and return `Ty`. `pycc_std` has zero dependency on `pycc_types`/`pycc_hir`/`pycc_codegen` (those crates depend on it, not the reverse), matching this workspace's existing layering (`pycc_ast` -> `pycc_hir` -> `pycc_types` -> `pycc_mir` -> `pycc_codegen`).
  2. The exact v0.2 symbol subset, chosen because it is the largest subset expressible with this compiler's existing scalar-only type system (no structs, no `Option`, no exceptions/errno modeling) without inventing a general native-call ABI: `math.sqrt(x: float) -> float`, `math.floor(x: float) -> float`, `math.pow(x: float, y: float) -> float`, `math.pi: float`, `math.e: float` (all five map to a single already-existing LLVM intrinsic or libm symbol each, taking/returning `Ty::Float` only — no integer overload, no `math.isnan`/`math.frexp`-style multi-value or out-parameter shapes, which don't fit this compiler's single-return-value scalar calling convention); `sys.exit(code: int) -> None` (maps to a process-exit runtime call, mirroring how `pycc_codegen` already lowers `raise SystemExit`-shaped control flow if present, else a direct trap-free process-exit call). `sys.argv`, `sys.stdin`/`stdout`/`stderr`, `sys.path`, and every other `sys` attribute are out of scope: they need `list[str]`/file-object representations this compiler either lacks entirely or has not yet wired to a process-level source of truth. `math.isnan`, `math.floor` returning `int`, `math.gcd`, and the rest of the `math` module are out of scope for the same "needs a shape this type system can't express yet, or wasn't needed to unblock the PEP-594 fixture / container corpus" reason. This list is deliberately small; growing it is ordinary follow-up work, not a new design decision, as long as a new entry stays within the existing scalar-in/scalar-out shape.
  3. Dispatch reuses the existing pattern exactly: `pycc_types::infer_expr_in`'s `Expr::Call` arm gains a lookup against `pycc_std`'s registry, keyed by the *resolved* module-qualified name (`math.sqrt`, established by D-137's import binding, not by the bare, potentially-shadowed callee string `print`/`len` use — module-qualified names can't collide with user locals the way `print` already can, per D-105's existing shadowing precedent, so no shadowing check is needed here). A registry hit returns the entry's declared `Ty` immediately, exactly like the `print`/`len` special cases, with no new signature-inference machinery, no new `Ty` variant, and no change to the constraint-collection pass's general shape. `pycc_codegen` gains one new match arm per registry entry (a fixed, enumerable set, not a loop over the registry at codegen time) that lowers the call to the corresponding libm/runtime symbol — the same one-arm-per-intrinsic style `print`/`len` already use in codegen, not a generic FFI trampoline.
- Alternatives: a general native-call/FFI mechanism (declare an external symbol's signature generically, call any of libm) that `math`/`sys` would be the first two consumers of (rejected — D-088 explicitly scopes this PR away from building general dispatch; a real FFI mechanism needs to solve ABI marshaling, error/errno propagation, and multi-value returns none of which this PR's two modules require, and building it now would be speculative generality the project's own D-057 precedent rejects). Making `pycc_std` a proc-macro or build-script-generated registry from a spec file (rejected — the registry is under a dozen entries; a codegen step adds a build dependency and an indirection layer for no benefit at this size, and plain static data is trivially reviewable and testable). Putting the registry directly inside `pycc_types` instead of a new crate (rejected — `pycc_codegen` also needs the same symbol list for its lowering arm, and duplicating the list in two crates risks drift; a shared, dependency-free data crate is the standard fix already used elsewhere in this workspace's layering).
- Consequences: one new crate (`pycc_std`) with no logic, only data and its accompanying tests (one test per registry entry asserting its declared shape, plus a completeness test asserting every entry's module/name pair is unique). `pycc_types` and `pycc_codegen` each gain a small, fixed number of new match arms, not a new general mechanism. Extending the registry later (e.g. adding `math.isnan` once boolean-returning intrinsics are wanted) is a small, additive change to this same pattern, not a redesign.
- Addendum (2026-08-04, Task 1/4 implementation): the registry actually shipped by this PR is narrower than point 2's symbol list above — `math.sqrt`, `math.pi` only. `math.floor`, `math.pow`, `math.e`, and the entire `sys` module (including `sys.exit`) are withheld from v0.2's registry, not merely deferred silently: (a) verified at implementation time that `pycc_codegen` already declares external symbols via `add_function`/`Linkage::External` and the linker driver already passes `-lm` (`crates/pycc_codegen/src/lib.rs`), so `math.sqrt`'s libm call needed no new mechanism, but `math.floor`/`math.pow`/`math.e` had no concrete Task 4 lowering slice actually written in this PR and this ADR's own point 2 forbids a registry entry that type-checks but is unlowerable; (b) `sys.exit` diverges (never returns), which has no existing `NoReturn`-shaped precedent in `pycc_types`/`pycc_mir` today and was judged out of this PR's thin-slice scope rather than rushed; `sys.argv` was already flagged above as needing a `list[str]`-from-process-args construction path this compiler doesn't have. Growing the registry to the rest of point 2's list remains ordinary, non-design-decision follow-up work exactly as the original Consequences note anticipated — this addendum records that v0.2 itself ships the smaller `math.sqrt`/`math.pi`-only slice, not the full point-2 list, and that `pycc_std::StdModule` has no `Sys` variant at all in this PR (adding an empty enum variant with no registry entries would leave a `pycc_std` unit test unable to exercise it, an avoidable D-014 coverage gap).
