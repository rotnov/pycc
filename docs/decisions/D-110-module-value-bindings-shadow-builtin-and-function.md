## D-110: Module value bindings shadow builtin and function call lookup, callee-first

- Status: accepted
- Context: issue #133 — `pycc check` accepted `helper = 1` followed by `helper()` (and `print = 1` followed by `print()`), resolving the call through the function/builtin registry while CPython 3.14 deterministically raises `TypeError: 'int' object is not callable`; after PR #132 the false success became an observable backend miscompile (`pycc run` silently called the shadowed function). Both `Call` arms in `crates/pycc_types/src/lib.rs` (`infer_expr_in` final validation, `collect_expr_constraints` private-helper inference) consulted the value environment only behind an `is_local` guard, so module bindings never shadowed call lookup. This entry is numbered D-110 because open PR #236 has already published claims on D-104–D-109; if that range shrinks before it merges, the gap stays documented here rather than being silently compacted.
- Decision: both arms consult the active value binding first — before the local-name check, the `print` special case, argument inference, and the function-registry fallback — and reject a bound callee with the existing `T0021` "name `X` is bound to a non-callable value" diagnostic (every value binding in the current subset is a primitive, so a shadowed target is always non-callable). "Active" means the net source-order binding: a `def` executes at its own position in the top-level walk and rebinds its name, so `helper = 1` followed by `def helper(): ...` leaves later `helper()` calls resolving the function exactly as CPython does, while a value assignment *after* the `def` shadows it again (this refinement comes from PR #252's own review, which caught the initial gate rejecting that valid, previously-compiling shape). The def-rebound fact is tracked *separately* from the value binding's representation record rather than erasing it: D-040's sticky-representation rule keeps consulting the original record, so `helper = 1; def helper(): ...; helper = "leaked"` still fails T0023 instead of reaching codegen with an `int`-allocated slot stored as `str` (the same review's round-4 blocker against a version that cleared the binding at the `def`). The def-rebound flag is cleared unconditionally at every value-assignment site — not only when a fresh binding is created — because a compatible-type reassignment of a name with a pre-`def` record never creates one; clearing only on fresh binds left the flag permanently stuck, so `helper = 1; def helper() -> int: ...; helper = 2; helper()` resolved the function where CPython raises `TypeError` (the review's round-5 blocker), and both environment walks now clear at the same points. Both environment walks — pass 2/pass 3's and the solver's accumulated globals — apply the same rebinding. Three deliberate consequences of that ordering, each pinned by a test: (1) under D-041's final-module-environment model for function bodies, a body call is rejected whenever the *net* source-order top-level binding for the callee is a value — including a program whose only call executes before the rebinding in CPython's dynamic order and therefore runs there; this is a knowingly stricter-than-one-dynamic-trace rule in D-086's spirit, made explicit here rather than left an accident. (2) Diagnostic order is callee-first: a shadowed callee with an additionally-invalid argument reports the non-callable callee, not the argument error — uniform with how the pre-existing local-shadow gate always behaved, though CPython's own evaluation order would surface the argument error first. (3) A bound value that shadows nothing (`x = 1` then `x()`) now reports non-callable instead of final validation's misleading "call to undefined function `x`" and instead of the solver path's dead-end "cannot infer return type of private helper" -- the constraint-collection mirror gate is load-bearing exactly when the bound callee is neither `print` nor any `def` (then, without it, the solver dead-ends before pass 3 ever runs); for a shadowed `print` inside an inference-signature helper the solver's `print` special case would otherwise resolve the call and pass 3's own gate would still reject the shadowing afterward, so there the mirror is fail-fast defense-in-depth rather than the only line of defense.
- Alternatives: keep #133's minimal framing without recording the body-semantics consequence (rejected — it rejects previously-compiling valid Python, exactly the class of strictness choice D-086 exists to record explicitly); gate pass-3 body calls on whether the binding is active at the call's own definition site (rejected — reintroduces #22's execution-order model, which that issue explicitly keeps separate, and contradicts D-041's uniform final-environment rule that plain name reads in bodies already follow); infer arguments before the binding gate to mirror CPython's argument-errors-first evaluation order (rejected — the pre-existing local gate already reported callee-first, and splitting the order by callee classification would make diagnostic selection depend on an implementation detail no user can see); introduce a callable type so bindings could shadow without erroring (out of scope — #133 defers callable values explicitly).
- Consequences: `tests/diagnostics/d0027`–`d0031` pin the five public-CLI shapes (function shadow, builtin shadow, annotated-body call, inference-helper call, inference-helper builtin shadow); in-crate tests pin the three ordering consequences above plus the preserved #22 boundary (a top-level call before the shadowing assignment still resolves the function). `tests/slice0.rs` pins that `pycc build` can no longer reach codegen for a shadowed call. When callable values arrive (v0.2+ surface), the gate's "always non-callable" simplification is the single place to extend.
