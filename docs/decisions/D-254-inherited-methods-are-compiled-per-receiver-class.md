## D-254: Inherited methods are compiled per receiver class when their behaviour depends on it

- Status: accepted ([#1337](https://github.com/rotnov/pycc/issues/1337))
- Context: pycc dispatches statically ([D-006](./D-006-generics-monomorphization-vtable-dispatch-only.md)) and lowered each method body once, with `self` typed as its defining class ([D-154](./D-154-class-instance-runtime-layout-stays-opaque.md)). A subclass `C` that inherits `D.g` without overriding it therefore ran `D`'s compilation of `g`, so a `self.m()` inside it called `D.m` even when `C` overrides `m`. It printed the wrong answer silently, and did the same for class-attribute reads, property accessors, classmethod calls through `cls`, `isinstance(self, ...)`, `cls(...)`, the class name a dataclass `__repr__` prints, and `super()` inside an inherited body, which followed the defining class's MRO rather than the receiver's ([D-160](./D-160-super-static-dispatch-no-runtime-polymorphism.md)'s documented diamond limitation). The template-method pattern is the most common shape in real code and the one the issue reports.
- Decision:
  1. **Invariant.** Every call to a user method runs the body that the receiver's static class resolves the member to, and that body makes every receiver-dependent decision (member bodies, class-attribute values, property accessors, `super()` targets, `isinstance(self, ...)`, `cls(...)`) for that class.
  2. **Copies.** `pycc_types` clones an inherited body into a new `HirItem::Function` with the receiver parameter retyped to the subclass, only when its behaviour can differ (the copy-needed rule in `crates/pycc_types/src/inherited_copies/plan.rs`: a least fixpoint over the *reach*, *super*, *identity* and *escape* arms and the differing set `Δ(C, D)`, including the `<identity>` pseudo-member). A body that cannot differ keeps using the original, with no new refusal and no code growth. The pass runs in the shared pre-pass both check entry points call ([D-245](./D-245-resolve-empty-container-element-types-in-a-pre-check-hir-pass.md)), after empty-container and attribute-slot resolution, so a copy inherits the resolved slot types. Static methods, abstract stubs, class-level hooks, and receivers that cannot have instances (abstract, protocol, generic, seeded builtin, or a user exception class without its own constructor) are never copied.
  3. **Names.** A copy is spelled as the receiver's own definition would be (`C.m`, `C.p.setter`, `C.k.classmethod`) when the origin is the receiver's first definer of the member, and `C.m.0super_D` (followed by the same kind suffix, `C.p.0super_D.setter`) when it is reached only as a `super()` target (the two can coexist in a diamond, so one spelling cannot serve both). `pycc_hir::inherited_copy_name` is the one producer and `pycc_hir::inherited_copy_origin` the one parser; no side table is kept, and a consumer that needs to know whether a copy *exists* checks its own item or scope table.
  4. **`super()`.** In a body compiled for receiver `C` whose source anchor is `D`, `super().x` selects the first class after `D` in `C`'s MRO that binds `x`, and runs that body's copy for `C` when one exists. For an original body (receiver equals anchor) this is D-160's rule unchanged; the diamond limitation D-160 documented is lifted. The type side reads the receiver from `self`'s type, as MIR does, so the checker and the lowering select the same override.
  5. **Diagnostics.** A diagnostic raised inside a copy is re-keyed to its origin item (so it maps to the origin's file), carries the help note ``while compiling `D.m` inherited by subclass `C` ``, and is dropped when it repeats one already reported for the same origin at the same place.
  6. **Escapes are refused, not guessed.** Where the receiver escapes a copy into a slot typed as the base class (`return self` from `-> D`, `helper(self)` with a `D` parameter, `x: D = self`) the copy fails to type-check and the program is refused with that `T0022`/`T0021`/`T0025`, carrying the note. A dataclass capability the subclass lacks (`print(self)` for a non-dataclass subclass, `self == o` against a different class) is refused the same way. Nothing is ever compiled for the base class instead.
  7. **Verification.** Every MIR routing site goes through `pycc_mir::receiver_exact::exact_callee`, the `--ext` driver through `src/ext_build/inherited.rs`, and a debug-build verifier (`crates/pycc_mir/src/verify_receiver.rs`) re-derives each user-method callee from the class tables alone and panics on a mismatch, so every test build checks the invariant over the whole corpus.
- Alternatives:
  - **Runtime class tags with closed-world dispatch.** They reverse D-006's "no runtime type tags" and D-154's opaque layout, need an override signature-compatibility rule pycc lacks, and touch every site and the runtime. They remain the long-term answer for escapes and `cast`, but are too large and project-wide for this fix.
  - **Copying every inherited member unconditionally.** It refuses programs that are correct today (`return self` where the subclass overrides nothing the base sees) and grows code for bodies that cannot differ.
  - **Pure refusal of overrides reached through `self`.** It needs the same reachability analysis as the chosen rule and refuses exactly the programs the rule fixes.
  - **Registering copies in `HirClassDef.methods`.** It would change the own-versus-inherited semantics other consumers read (for example `instance_hash`'s agreement check).
  - **Copies created on demand at call sites.** An inherited body is also reached from other inherited bodies, properties, constructors, `super()` and the ext boundary; the dependence rule already bounds growth.
- Consequences:
  - Inherited methods match CPython for `self.m()`, class attributes, properties, classmethods, `isinstance(self, ...)`, `cls(...)`, dataclass `__repr__`, inherited constructors and cooperative diamonds, natively and through `--ext`.
  - NEG, accepted cost: a program whose inherited body passes or returns `self` as the base type, and whose subclass changes something that body reaches, moves from silently wrong (or, when nothing observable differed, correct) to an honest `T0021`/`T0022`/`T0025`. Interprocedural parameter-dependence analysis or runtime tags would remove it.
  - NEG: [D-198](./D-198-cast-erasure-limits-cast-to-representation.md)'s `cast(D, c)` still widens a `C` value to `D` statically, and a later receiver-dependent call on it runs `D`'s body. This is the one remaining way a `C` value reaches a `D`-typed slot ([#1352](https://github.com/rotnov/pycc/issues/1352) tracks closing it).
  - Two exception-value holes found alongside this fix are closed without runtime class tags for user classes. `isinstance(e, T)` on a value typed as a seeded builtin exception class (a caught `PyExceptionObj`) reads the type tag that handler dispatch already reads, when `T` lies outside the static MRO (`MirExpr::ExceptionTypeTest`); every user-class value keeps the compile-time fold. A user exception class whose MRO resolves an instance-protocol dunder (`__str__`, `__bool__`, ...) to a user class is refused with `C0001` at its definition, since a raised exception value would never call it (Part 3 of [#541](https://github.com/rotnov/pycc/issues/541)).
  - Code size grows by one item per needed copy, bounded by the dependence rule. D-006's `0gen_` protocol specializations are the precedent for type-side copies; a protocol-parameter method's copy is specialized like any other item.
