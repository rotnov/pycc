## D-251: Link libpython statically into an embedded executable on request, with the whole archive loaded and its symbols exported

- Status: accepted (Part 1 of [#1227](https://github.com/rotnov/pycc/issues/1227), [#1271](https://github.com/rotnov/pycc/issues/1271); macOS and Linux hosts, standard-library embedded builds)
- Context: [D-248](./D-248-embedded-executable-artifact-layout-and-bridge-split.md) links an embedded executable against a shared libpython copied into `OUT.pycc/lib/`, and lists a static libpython as #1227. `docs/CLI_SPEC.md`'s manifest example already showed `[build] static = true` with no meaning behind it. A static link is only useful if the interpreter's C-API stays reachable: every `lib-dynload` extension the embedded interpreter imports is a `-bundle -undefined dynamic_lookup` image (macOS) or a shared object with undefined `Py*` references (Linux) that resolves them against the executable. A plain static link keeps only the archive members the launcher references and exports none of them, so the first such import fails. #1227 spans three seams, so it is delivered as three parts: #1271 (this entry), #1272 (static mode with a locked closure) and #1273 (an end-to-end oracle against a real static archive).
- Decision:
  1. **Spelling and precedence.** `pycc build --static-libpython` requests the static link. `[build] static = true` in a `pycc.toml` beside `PATH` requests it too, read like `[build] opt`: the flag wins, and a missing or unparseable manifest means no request. `static = true` means "statically link every library the artifact would otherwise load dynamically, where pycc supports it"; today that is exactly libpython in an embedded executable. An absent key means the artifact's own default: an embedded build links the shared libpython (D-248), and a native artifact keeps `docs/ARCHITECTURE.md`'s default. The request is a no-op for an artifact that links no libpython (a native build, `--pure`/`deny`, `--target`), so a project-wide key never breaks a native build. clap rejects the flag together with `--ext` (exit 2), because an extension module never links libpython; the key is ignored under `--ext` and under `pycc run`, which always links the shared library.
  2. **Archive discovery.** A separate static probe, whose script starts with `# pycc-static-probe`, runs only in static mode and prints the interpreter's `LIBPL`, `LIBRARY`, `LIBS` and `SYSLIBS`. The archive is `LIBPL/LIBRARY`. Its canonical path must be a regular file whose first eight bytes are `!<arch>\n`. A missing file, a directory, a thin archive (`!<thin>\n`), an empty file or any other content is refused with exit 2, naming the path and what was found (other content as its first bytes in hex). A universal (fat) file is refused with a note, never described as a shared library, because a fat archive and a universal dylib share the `0xcafebabe` header. The shared-mode requirement that the interpreter be shared (D-248 rule 4) is dropped in static mode; the version, free-threaded, `Python.h` and standard-library checks stay. The shared-mode probe and its output are unchanged.
  3. **Link recipe.** The archive replaces the bundled shared library as the first link argument. macOS: `-Xlinker -force_load -Xlinker <archive> -Xlinker -export_dynamic`. Linux: `-Xlinker --whole-archive <archive> -Xlinker --no-whole-archive -Xlinker --export-dynamic`. Then the `LIBS` and `SYSLIBS` tokens, which is `python3-config --ldflags --embed`'s own recipe. `MODLIBS` is excluded because it names build-tree paths that an installed interpreter does not have. The rpath and the vendored-native arguments are unchanged. A committed negative control links a two-member fixture archive and `dlopen`s an extension that needs the unreferenced member: the bare archive fails; on Linux `--whole-archive` without `--export-dynamic` fails; on macOS `-force_load` with `-dead_strip` fails without `-export_dynamic`. The full recipe resolves in every case. Exporting dynamically also exports `libpycc_rt.a`'s global symbols from the executable; nothing loaded into the process binds to them today.
  4. **Sidecar.** Static mode writes no libpython into `OUT.pycc/lib/` and sets no macOS install id. The standard library, `lib-dynload` and vendored native libraries are bundled as in D-248. The marker's `libpython-sha256` line carries the archive's digest, and a final line `libpython-link static` is appended; the shared-mode marker is byte-identical to D-248's and the header stays `pycc-bundle 1`, because a sidecar is fully restaged on every build.
  5. **A second libpython is refused.** In static mode any bundled image that depends on a libpython would load a second CPython into the process, so the build is refused with exit 2, naming the image and the dependency. The check runs before the shared-mode classification of each dependency and matches a file name starting with `libpython<major>.<minor>` or a `Python.framework` binary; on macOS a dependency the shared mode would rewrite to the bundled libpython, and on Linux one that resolves to the interpreter's source library under another name, are refused too.
  6. **Closure deferral.** A static build whose program consumes a `pycc.lock` closure is refused with exit 2 before the interpreter is probed, naming #1272, because closure extensions have not yet been checked for a second libpython.
  7. **Limitations.** Force-loading makes every archive member's own dependencies mandatory, so an archive whose built-in modules need libraries outside `LIBS`/`SYSLIBS`, or a non-PIC archive in a PIE link, fails in the linker (exit 1). Starting a real interpreter from a real static archive is not exercised by Part 1; #1273 adds that oracle.
- Alternatives: a `--static` spelling (rejected: ambiguous next to Rust's and the C toolchain's meanings); a `[build] libpython = "static"` key (rejected: it leaves the documented `static` key without meaning); linking the archive without whole-archive loading (rejected: the negative control shows an extension then fails with an unresolved symbol); using `LINKFORSHARED` (rejected: on a framework build it names the framework binary, which reintroduces the dylib); widening the shared-mode probe instead of a separate static probe (rejected: it would change the answer every fake interpreter in the test suite prints); silently falling back to the shared library when the archive is missing (rejected: it ignores an explicit request).
- Consequences:
  - **POS-001:** an embedded executable can run without a libpython in its sidecar, and the C-API it exports is the one its `lib-dynload` extensions bind to.
  - **NEG-001:** the request needs an interpreter whose `LIBPL` holds a regular, non-fat ar archive; on the development host the uv (python-build-standalone) 3.14 interpreter ships no archive and Homebrew's `libpython3.14.a` is a symlink to its framework binary, so both are refused with exit 2.
  - **NEG-002:** a static executable exports every libpython and `pycc_rt` global symbol, which enlarges its dynamic symbol table.
  - **NEG-003:** static mode and a locked closure cannot be combined until #1272.
- Amendment (2026-09-24, [#1272](https://github.com/rotnov/pycc/issues/1272), Part 2 of [#1227](https://github.com/rotnov/pycc/issues/1227)): rule 6 and NEG-003 are superseded, and rule 5 is widened. (a) *A locked closure*: a static build consumes a `pycc.lock` section as a shared build does. Its `libpython-sha256` is checked against the file that identifies the interpreter ([D-249](./D-249-pycc-lock-schema-environment-resolver-and-update-command.md)'s amendment of this date): the shared library when the interpreter is configured with one, else the archive. The closure is copied to `OUT.pycc/closure/`, and its natives are derived and compared as in D-249 rule 8. (b) *Second libpython*: rule 5's by-name match is now a file name starting with `libpython<major>.` of the interpreter's major version, any minor and suffix (so another minor's library and the stable-ABI `libpython3.so`, which itself loads the full library), or a `Python.framework` binary; it applies to a locked closure's images and natives as it does to the interpreter's own. A lock that is current for such an image does not hide it: `pycc lock` and the build derive the same natives for it, so the build refuses it as a second libpython, not as a stale lock. An image whose bytes changed since locking can instead meet the RECORD check first on macOS, where the closure is copied and hashed before relocation; on Linux the dependency walk, and so this refusal, runs before any closure file is hashed. (c) *No shared library to read*: on macOS, when the interpreter has no Mach-O shared library, the derivation and the relocation compare dependencies with no source-libpython names instead of running `otool` on a missing file. (d) *Order between the two refusals*: (b)'s refusal and the interpreter's own `libpython-sha256` comparison run in a platform-dependent order. When the interpreter's digest is also stale, macOS reports the stale lock first, because the digest is checked while the sidecar is populated and before relocation. Linux reports the second libpython first, because its dependency plan runs before the sidecar is populated. Either refusal exits 2, writes no new sidecar and leaves an existing `OUT.pycc` untouched.
- Amendment (2026-09-24, [#1273](https://github.com/rotnov/pycc/issues/1273), Part 3 of [#1227](https://github.com/rotnov/pycc/issues/1227)): rule 7's missing oracle now exists. `tests/issue_1273_real_static_archive.rs` links a real `LIBPL/libpython3.14.a` into embedded executables and runs them with no libpython in the sidecar or in the executable's dynamic dependencies. The executables import `_json`, `math`, `_random` and `_ssl` from the bundled `lib-dynload`, and one also bundles a locked closure. Each one's output matches CPython 3.14.7. The executable still runs after it is moved, and it fails with `ModuleNotFoundError` when the `lib-dynload` file for `math` is removed. The evidence comes from the Linux CI legs, x86_64 and aarch64. Their `actions/setup-python` interpreter is configured `--enable-shared` and still installs a genuine PIC archive, and the rule 7 linker limitations did not occur for it. On those legs the test fails if the archive is missing. On a host whose `LIBPL` has no genuine archive, such as the macOS legs and uv's standalone builds, it asserts the rule 2 refusal instead. So macOS `-force_load` is still not proven against a real archive.
