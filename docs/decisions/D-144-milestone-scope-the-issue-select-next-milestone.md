## D-144: Milestone-scope the issue-select/next-milestone autopilot loop

- Status: accepted
- Context: Issue #345 identified four independent gaps in the autopilot loop's milestone awareness: (1) no defined trigger for checking whether the active milestone's Accept criteria are met — the original design relied on "pool empty" which is unreliable when aged backlog persists indefinitely; (2) no milestone-at-filing convention, so issues accumulated without milestone tags; (3) `issue-select`'s scoring order let a smaller non-active-milestone issue silently outrank a same-priority active-milestone issue; (4) `next-milestone` was absent from the alpha-skill governance apparatus (`validate_agent_assets.py`, `run_alpha_skill_evals.py`, `docs/AGENT_TOOLING.md`) despite being an established alpha skill. Additionally, `docs/ROADMAP.md`'s "Current delivery status" section had drifted — still reading "Current milestone: v0.1" after v0.2's acceptance criteria were met — because `next-milestone`'s own step 6 never included refreshing that section.
- Decision: Two independent, low-risk mechanisms instead of a hard pool restriction. (a) Milestone membership becomes a scoring tie-break in `issue-select`'s step 5, not a pool filter: same priority tier, active-milestone issues rank above non-active-milestone issues, then size breaks remaining ties — every issue remains reachable, just not ahead of the active milestone's own same-priority work. (b) An explicit, unconditional evidence-check after every completed issue in `issue-select`'s Loop section: re-read the active milestone's `## vX.Y` section and verify cited evidence against the tree every cycle; if met, break to `next-milestone` step 6 regardless of pool state. Strengthen `AGENTS.md` D-021 step 9 to make milestone-at-filing the default (assign unless clearly cross-cutting, record reasoning either way). Add "Current delivery status" section refresh to `next-milestone` step 6's list of completion updates. Register `next-milestone` in `validate_agent_assets.py`'s `ALPHA_EVAL_RUNNERS` and `validate_alpha_skill_contracts` tuple, and in `run_alpha_skill_evals.py`'s `EXPECTED_RUNNERS` with its own contract tuple and eval cases. A hard pool restriction (the issue's own literal point 2 phrasing) was explicitly rejected: once the unconditional evidence-check replaces "pool empty" as the completion trigger, a hard restriction has no remaining job to do, and would remove the soft-defer judgment call `issue-select`'s step 4 blocker screen already exercises for later-milestone issues.
- Alternatives: Hard pool restriction to milestone-tagged issues only (rejected — all 26 non-v0.3 P1 issues are currently unassigned, so the issue's own proposal would not exclude them today; once the unconditional evidence-check lands, a hard restriction has no remaining job and would only remove an existing judgment call); mechanized "every issue must have a milestone" CI/Action gate (rejected — GitHub issues are not part of the PR-based CI surface this project gates; a soft convention backstopped by `issue-select`'s existing dynamic housekeeping is sufficient); gating the evidence re-check on "pool empty" (rejected — demonstrably unreachable with 26 non-v0.3 P1s in the tracker, and fragile even after the tie-break lands since aged backlog can persist indefinitely).
- Consequences: `issue-select`'s step 1 gains a self-sufficient milestone-determination read (same evidence rule as `next-milestone` step 2) so it works identically whether invoked directly or handed off from `next-milestone`. Step 5's scoring paragraph is rewritten to insert the active-milestone tie-break between priority and size, preserving the literal phrase "the repository's own priority markers rank first" required by `ISSUE_SELECT_CONTRACT`. The Loop section gains the unconditional post-cycle evidence check and a fourth stop condition. `next-milestone`'s step 6 gains the "Current delivery status" refresh. `docs/ROADMAP.md`'s stale "Current delivery status" section is corrected as a one-time fix. `run_alpha_skill_evals.py`'s `issue_select_higher_ranked` gains two defaulted parameters (`active_milestone`, `other_active_milestone`) so all existing call sites keep working unchanged. A new eval case asserts the tie-break; a new `next-milestone` eval suite with two cases exercises its own contract. `docs/AGENT_TOOLING.md` and `docs/ROADMAP.md`'s "Agent tooling" row update from "all five" to "all six" alpha skills. `.agents/skills/next-milestone/SKILL.md` (the thin Codex pointer) needs no change. Retroactive milestone migration of the 26 unassigned P1 backlog issues is explicitly out of scope — under the tie-break design, an unassigned issue and a past-milestone-tagged issue rank identically, so migration has no effect on scoring behavior; its only value is historical/dashboard accuracy (relevant to #336).
