## D-080: The conformance oracle's CI setup runs after the D-014 coverage gate, never inside its trusted boundary

- Status: accepted
- Context: Task 6 wires `tests/conformance.rs`'s CPython oracle (D-085) into all 5 Tier-1 CI targets, including `build-test-coverage` (macos-14), which also runs the D-014 100%-coverage gate under `scripts/check_roadmap_evidence.rb`'s security-reviewed `coverage_gate_present?` validation: a byte-for-byte match of the coverage job's step prefix (`TRUSTED_COVERAGE_STEPS`) and the coverage step's own script (`COVERAGE_SCRIPT`), plus a whole-file SHA256 pin (`REVIEWED_PERF_CI_WORKFLOW_SHA256S`) over `ci.yml` itself. A first pass at this wiring inserted `actions/setup-python` and an oracle-version-check step *before* the coverage step, and patched the coverage script itself to expose the oracle's directory on `PATH` inside the isolated `nobody` sandbox (via a new `ORACLE_PYTHON_DIR` lookup and `RUNNER_TOOL_CACHE` `chmod` calls). That correctly broke `check_roadmap_evidence.rb`'s structural checks — CI's `Workflow policy` audit rejected it three times running (`ruby scripts/check_roadmap_evidence.rb`: "evidence does not provide the exact 100% line and region gate") — because it silently expanded the coverage gate's reviewed trust boundary to include a live, network-installed interpreter, exactly what that boundary is reviewed to exclude. Separately, CI evidence from the same push showed `native-build-test`'s Windows leg failing too: `actions/setup-python` only produces a plain `python.exe` on Windows, never a version-suffixed `python3.14`, so the hardcoded oracle lookup in `tests/conformance.rs` (D-085) could not find it there.
- Decision: keep `build-test-coverage`'s coverage step's prefix and script byte-for-byte identical to `TRUSTED_COVERAGE_STEPS`/`COVERAGE_SCRIPT` — no oracle exposure inside the isolated sandbox at all. Mark both conformance tests `#[ignore]` by default (reason string on the attribute) so `cargo llvm-cov --workspace` — which the untouched coverage step still runs unparameterized — skips them cleanly; this costs nothing against the 100% gate because `tests/` files are already excluded from the coverage denominator (`docs/TESTING.md`'s "Code coverage" section predates this PR). The CPython oracle setup step and an explicit `cargo test --workspace -- --include-ignored` step move to *after* the coverage step — a region `coverage_gate_present?` does not constrain, since it validates only the step prefix through and including the coverage step, never what follows — so the conformance tests still execute for real, on every Tier-1 target, but never inside the coverage gate's reviewed, sandboxed boundary. `native-build-test`'s 4 legs (no coverage requirement, no structural step-prefix check) get the same oracle-setup-then-`--include-ignored` shape for consistency, plus a Windows-only step that copies the installed `python.exe` to a `python3.14.exe` alias immediately after `actions/setup-python`, so `tests/conformance.rs`'s one hardcoded lookup name keeps working uniformly across all 5 targets rather than special-casing the Rust lookup itself for one platform. That alias step resolves its source directory via `$pythonLocation` (the exact directory `actions/setup-python` itself exports and prepends to the real Windows `PATH`), converted with `cygpath -u` for bash's `cp` -- an earlier version used bash's own `command -v python` and failed in real CI, because Git Bash's own `PATH` view can be reordered relative to the real Windows `PATH` that the job's later `pwsh`-run steps (and the Rust test binary's own `Command::new` PATH search) actually search, so a bash-resolved "python" was not guaranteed to be the interpreter those later steps would find. The resulting whole-file digest is added to `REVIEWED_PERF_CI_WORKFLOW_SHA256S` as `D80_CONFORMANCE_ORACLE_CI_WORKFLOW_SHA256`, retiring `D62_REPLICATED_SOURCE_AWARE_PERF_CI_WORKFLOW_SHA256` the same way `D51`/`D56` were retired before it (comment marked, dropped from the active allowlist, its fixture and structural-acceptance test kept as a historical audit fixture); a matching `tests/fixtures/d80-conformance-oracle-ci.yml` snapshot and `scripts/test_check_roadmap_evidence.rb` updates ship in the same commit. The checker's own literal error string is corrected from "D-062" to "D-080" to keep naming the workflow content it is actually anchored to. **Addendum, confirmed by real CI evidence after the alias landed:** the `$pythonLocation`/`cygpath` alias alone was not sufficient. Both bash-run steps (the alias `cp` itself and "Verify oracle version") found and ran `python3.14` fine, but the Rust test binary's own `Command::new("python3.14")` still failed with "program not found" — because `std::process::Command` on Windows resolves a bare program name by searching `PATH` for that literal file name and does not append `.exe` when the name already contains a `.` (the version dot in "python3.14" reads as an extension marker to that resolver, unlike bash's own exec resolution, which does try appending `.exe`). Same file, same `PATH`, two different resolvers. `tests/conformance.rs::oracle_python_bin` therefore requests `python3.14.exe` explicitly under `cfg!(windows)` (D-080 addendum), leaving the alias step exactly as-is — it already produces that exact file name.
- Alternatives: install the oracle inside the coverage step's own script and update `COVERAGE_SCRIPT`/`TRUSTED_COVERAGE_STEPS` to match (rejected — the heaviest possible trust-anchor change, expanding the isolated sandbox's surface to include a live network-fetched interpreter, for a correctness check that has no need to run inside that specific measured boundary at all). Add a `--ignore-filename-regex` exemption for `tests/conformance.rs` to `docs/TESTING.md`'s coverage exemption table (rejected as redundant and still just as heavy — `tests/` files are already excluded from the denominator by existing project convention, so an explicit regex entry would be a no-op that only adds confusion, and it would still require editing `COVERAGE_COMMAND`/`COVERAGE_SCRIPT`, the exact change this decision avoids). Rely on the CI-side alias alone, keeping `tests/conformance.rs`'s oracle lookup as one hardcoded, platform-uniform name (originally rejected the per-platform-lookup alternative on exactly this uniformity ground) — **superseded by the addendum above**: real CI evidence showed the alias alone cannot work, because Rust's Windows program-name resolution does not perform the extension-appending search bash performs, so D-085's single-hardcoded-name ideal does not survive Windows regardless of what the CI alias does. The lookup now takes the platform-specific extension explicitly; the alias step is unchanged.
- Consequences: `scripts/check_roadmap_evidence.rb`'s `TRUSTED_COVERAGE_STEPS`/`COVERAGE_SCRIPT` constants and the coverage job's actual steps stay byte-for-byte aligned with the pre-PR-6 reviewed content; only the SHA256 allowlist gains one new active entry, with the prior one retired rather than deleted. `tests/conformance.rs`'s two tests require `-- --include-ignored` (or `--ignored`) to actually execute; a bare `cargo test`/`cargo llvm-cov` invocation silently skips them, matching the file's own doc comment. This PR's originally-planned D-080 slot (reserved in the implementation plan for Task 8's CLI_SPEC.md diagnostic-example fix) is renumbered to D-082, since this decision claimed D-080 first while resolving Task 6's CI failure, and a concurrent `main` PR claimed D-081 for its own unrelated iEvo-lifecycle hardening before this branch next merged it in. **Staging note:** `.github/workflows/workflow-policy.yml`'s `audit` job checks out `scripts/check_roadmap_evidence.rb` at `ref: ${{ github.sha }}` under `pull_request_target`, which resolves to the base branch's (`main`'s) HEAD, never the PR branch's — so a single PR that both edits `ci.yml` and teaches the checker its new digest can never pass its own audit, since the checker used is always `main`'s prior version, which does not yet recognize the new digest. This branch's digest was therefore first staged onto `main` alongside D-062 by a separate pull request (#159, following this project's established `a0a4c47`/`b6f5a29` two-PR stage-then-activate precedent for the D-062 transition), reverting the checker's error string to a generic non-decision-specific message on that stage branch; only after #159 merged did this branch's own commit retire D-062 and make D-080 the sole active entry, matching the digest #159 had already authorized.
