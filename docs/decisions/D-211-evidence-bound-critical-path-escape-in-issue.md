## D-211: Evidence-bound critical-path escape narrows D-191's in-scope marker-then-size order

- Status: accepted
- Context: Issue #733 recorded a structural starvation distinct from the one D-191 fixed. D-191 made active-milestone membership rank first, ahead of the priority marker, so an in-scope issue is always reached before an out-of-scope one. It left the ordering *inside* each group unchanged: "Inside each group (in-scope, and out-of-scope among themselves) the order remains marker-then-size." At the time #733 was filed, v0.3's Accept criterion could not be met without the exception chain #541 -> #703 -> #542 -> #543 landing — four unmarked issues carrying four of the five distinct PEP numbers the milestone still needed. All four are in-scope, so D-191's membership-first rule already puts them ahead of every out-of-scope issue; the starvation is entirely inside the in-scope group, where marker-then-size ranks every P1/P2/P3 issue in the milestone ahead of them regardless of whether those issues gate the milestone's own Accept criterion. The pool had enough marked in-scope issues that the unmarked tier was never reached. Retitling the four issues to add a priority prefix was considered and rejected in the issue itself: this repository has never added a priority marker to a previously unmarked issue (a scan of `renamed` events across #541, #703, #542, #543, #690, #698, #719, #720 found exactly one, and it updated a number inside an already-present prefix), and doing so here would rewrite the tracker's own priority semantics as a side effect of a scheduling problem — the same kind of shortcut D-191 itself rejected in favor of an ordering fix.
- Decision: Supersede D-191's Decision clause "Inside each group (in-scope, and out-of-scope among themselves) the order remains marker-then-size" for the in-scope group only; the out-of-scope group's internal ordering is untouched. Add one narrow, evidence-gated exception: an in-scope issue may outrank an in-scope issue carrying a higher priority marker when it comes with verified evidence that it gates the active milestone's own Accept criterion — a named Accept clause quoted from `docs/ROADMAP.md`'s current milestone section, plus the specific completion path that issue unblocks, checked against the current tree the same way step 6 verifies any candidate's premise. A bare claim of importance never qualifies: the priority markers already encode the repository's own judgment of importance, and admitting unverified importance claims on top of them would collapse that ordering entirely. The escape never reaches outside the scope and never changes what a `P1:`/`P2:`/`P3:` marker means (D-111's marker semantics stay exactly as recorded); it only recognizes that, occasionally, an unmarked or lower-marked in-scope issue holds the pen on whether the scope's own Accept criterion can be met at all. Invoking it is a reportable event, exactly like D-191's scope-departure record: step 8's hand-off report and the `## Output` section both carry it.
- Alternatives: Add a priority marker to the gating issues directly (rejected in the issue itself and here — no precedent for adding a marker to a previously unmarked issue, and it would silently rewrite tracker semantics as a side effect of a scheduling problem rather than fixing the ordering). Treat this as a step-4 blocker-screen judgment call instead of a step-5 ordering rule (rejected for the same reason D-191 rejected relying on step-4 judgment for its own starvation: the defect is structural across many iterations, not a single defensible pick, so a per-pick judgment call cannot catch it either). Let membership alone govern intra-scope order too, i.e. treat every in-scope issue as equally ranked (rejected — that discards the priority marker's own signal entirely inside the scope, which is far more disruptive than a narrow, evidence-gated exception, and it is not what #733 asked for).
- Consequences: `run_alpha_skill_evals.py`'s `issue_select_higher_ranked` gains two further defaulted parameters, `gates_milestone_accept` and `other_gates_milestone_accept`, both `False` by default and inert when neither side sets them — so every existing call site and eval case keeps working byte-identical to today. An eighth `issue-select` eval case covers the escape (an unmarked in-scope issue that gates the milestone's Accept criterion outranks an in-scope P1 that does not) and is registered in both `EXPECTED_RUNNERS` and `validate_agent_assets.py`'s mirror registry. A further literal, "gates the active milestone's own Accept criterion", is pinned in `ISSUE_SELECT_CONTRACT` alongside D-191's existing pinned phrases, so a future vague reword of the new rule fails the eval, matching D-111's and D-191's own precedent. `.agents/skills/issue-select/SKILL.md` stays an unmodified pointer: it already names only the two *arithmetic* D-192 gates as call-outs easy to miss by skimming, and the new rule is not arithmetic, so the existing "read the canonical file completely" instruction already gives full discovery on both platforms. Step 8's report checklist and the `## Output` enumeration both gain the escape-invocation record alongside the existing scope-departure record, so a session skimming either as its reporting checklist cannot miss surfacing an invoked escape.
