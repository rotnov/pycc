## D-088: Correct v0.2's acceptance criteria before any v0.2 PR starts

- Status: accepted
- Context: `/goal release v0.2` set v0.2 ("collections & generics") as the standing work target. Before writing an implementation plan, its three ROADMAP.md acceptance bullets were checked against the actual repository state, per this project's own "spec is law, but the agent verifies before building on a bullet" convention (the same discipline D-085/D-086 applied). Three problems surfaced, all from the same root cause: the bullets were written before the stdlib tier schedule (`STDLIB_PLAN.md`) and the real per-PEP conformance matrix (`PYTHON_STANDARDS.md`) existed in their current form, so nobody had re-verified them against that later, more detailed planning.

  **1. "Corpus Tier-1 (`tomli`, `packaging`, `more-itertools`) compiles" is unreachable at v0.2.** Empirically verified: `pip download --no-deps --no-binary :all:` for all three packages (`tomli` 2.4.1, `packaging` 26.2, `more-itertools` 11.1.0), then `grep` every `import`/`from` statement in their non-test source (`src/`, excluding `tests/`). Distinct stdlib modules imported: `re`, `typing`, `functools`, `collections`, `collections.abc`, `datetime`, `enum`, `abc`, `os`, `sysconfig`, `subprocess`, `struct`, `itertools`, `urllib.parse`, `email.*`, `dataclasses`, `contextlib`, `logging`, `keyword`, `operator`, `pathlib`, `ast`, `platform`, `warnings`, `types`, `bisect`, `heapq`, `decimal`, `fractions`, `statistics`, `queue`, `random`, `threading`, `importlib.machinery`. Cross-referencing `STDLIB_PLAN.md`'s Tier 1 table: the latest-scheduled module actually needed is `urllib.parse` (v0.8, listed as "`urllib` (subset)"); `subprocess`/`threading`/`queue`/`random` are v0.6; `os`/`pathlib`/`collections` are v0.4; `dataclasses`/`enum`/`typing` are v0.3. Worse, several needed modules (`ast`, `importlib.machinery`, `sysconfig`, `types`, `operator`, `platform`, `warnings`, `bisect`, `heapq`, `collections.abc`, `email`, `keyword`, `decimal`, `fractions`, `statistics`) are **absent from `STDLIB_PLAN.md`'s tier table entirely** — they have no scheduled milestone at all yet. `v0.2` builds only `math`/`sys` (per `STDLIB_PLAN.md`'s own Tier 1 v0.2 row). No version of "just add import resolution" closes this gap; the packages need stdlib breadth v0.2 does not and cannot have.
  - This also means `PYTHON_STANDARDS.md`'s corpus table entry ("Tier 1 ... must fully pass before v0.2") was never verified against these packages' actual surface. That table's tier-to-milestone gating is broader than this decision's scope to fix (re-deriving correct milestones for Tiers 1–4 against real import surfaces is real work of its own); tracked as a follow-up rather than solved here, so this decision does not silently leave the false claim in place for v0.3+ either.

  **2. Import support today is a deliberate, clean rejection, not a partial implementation.** Empirically verified: `pycc_ast` already recognizes `Stmt::Import`/`Stmt::ImportFrom` as AST variants (inherited from the vendored general-purpose parser), but neither `pycc_hir` nor `pycc_types` has any handling for them — `pycc check` on a file containing `import math` produces `error[C0001]: statement kind not supported yet`, the same honest-gap pattern used elsewhere in this codebase, not a panic or silent skip.

  **3. "Conformance ≥ 25 PEPs green" is not reliably reachable with v0.2's stated scope.** `PYTHON_STANDARDS.md` has 79 v1.0-scope conformance-matrix rows (after PR-13's split of PEP 695's row into a v0.2-scoped generic-functions fixture and a v0.3-scoped generic-classes fixture, both added by this PR) (`py30`-`py314`, counted directly by fixture path; the 11 `py315` rows are the post-v1.0 preview track and don't count). Itemizing which rows v0.1's shipped surface plus v0.2's stated scope (containers, comprehensions, slicing, methods, PEP 585/695 monomorphized generics, `--release`) can actually satisfy without adding new grammar features beyond that scope -- every "already true" claim below was verified empirically (`cargo run -p pycc -- check` against a minimal fixture), not assumed, after this decision's own first draft asserted PEP 526 and PEP 594 were free without checking and a review caught both:
  - Confirmed already true today: PEP 238 (true division), 3105 (`print()` as function), 3107 (function annotations), 3131 (non-ASCII identifiers -- verified via a plain, non-annotated assignment; an *annotated* one hits the same PEP-526 gap below), 414 (`u''` literals), 484 (type hints), 498 (f-strings), 515 (numeric underscores), 649/749 (deferred annotations, already true of v0.1's existing static-evaluation behavior) = 9 rows, no new work.
  - PEP 526 (variable annotations, `x: int = 1`) is **not** free: verified empirically that `pycc_hir` handles `Stmt::Assign` but has no `Stmt::AnnAssign` case at all, so an annotated local-variable statement produces `C0001` today. Reaching this row requires small, bounded new frontend work (recognizing `Stmt::AnnAssign` for a simple local variable, distinct from the class/instance-attribute annotations that need v0.3's class model) -- assigned to PR-9 as real scope, not claimed free.
  - PEP 594 (dead-battery stdlib removals) is **not** meaningfully testable yet either: verified that `import cgi` today produces the exact same generic `C0001: statement kind not supported yet` every import produces, since no import resolution exists at all -- there is no way to distinguish "this module was removed" from "imports aren't supported yet" until real stdlib-module resolution exists. Reassigned to PR-14 (which builds exactly that resolution for `math`/`sys`), where the distinction becomes meaningful, rather than counted as a free PR-9 row.
  - Container/generics work already in v0.2's scope: the `dict` insertion-order row and 585 (builtin generics), 709 (comprehension inlining semantics), 695 (generic functions + `type` statement, scoped per item 3 below), 613 (legacy `TypeAlias`, the same underlying alias mechanism as 695's `type` statement, piggybacking on that work at near-zero marginal cost) = 5 rows.
  - Total: 9 + 1 (PEP 526, new bounded work) + 5 + 1 (PEP 594, reassigned to PR-14) = 16 rows, encompassing 17 distinct PEP numbers (649/749 share one row). Reaching 25 literal rows would still require also implementing keyword-only parameters (3102), `nonlocal` (3104), extended unpacking (3132), unpacking generalizations (448), and `Final` (591) — none of which are "collections & generics" work; adding them would be undocumented scope creep to hit an unverified number, not a considered decision to broaden v0.2.

- Decision:
  1. Replace "corpus Tier-1 compiles" with a hand-authored container/generics differential corpus (list/dict/set/tuple literals, comprehensions, slicing, methods, generic functions), diffed against pinned CPython 3.14.6 on all 5 Tier-1 targets — the same fib/mandelbrot-ascii pattern D-085 already established for v0.1, extended to v0.2's own feature surface. The literal, unmodified `tomli`/`packaging`/`more-itertools` packages remain a real future target once the stdlib breadth they need actually exists, but citing them as a v0.2-binary gate was never achievable and is removed from that gate.
  2. v0.2 gets stdlib-module import support scoped narrowly: `import math`/`import sys` and `from math import ...`/`from sys import ...` resolve as compile-time intrinsic bindings against `pycc_std`'s own registry (the same category of special-case `infer_expr_in` already uses for `print`), not general filesystem/package resolution. Relative imports (`from . import x`), multi-file user modules, and namespace packages (PEP 420) remain v0.4 scope, unchanged from ROADMAP.md's existing milestone boundary — this decision does not pull any of that forward.
  3. PEP 695 in v0.2 covers generic functions (`def f[T](x: T) -> T`) and the `type` statement only. Generic classes (`class C[T]`) require v0.3's class model, which does not exist yet; the `py312/pep_0695_generics.py` conformance fixture is scoped to the function/type-statement subset for v0.2, with a second fixture covering generic classes added when v0.3 lands.
  4. Conformance target revised from ≥25 to ≥15 conformance-matrix rows green, backed by the itemized 16-row list above (encompassing 17 distinct PEP numbers). Reaching more than 15 during v0.2 is welcome but not required; the gate is set to what the stated scope can honestly deliver, not backfilled to justify a number nobody had verified.
  5. File a tracked GitHub issue (not resolved here) asking for `PYTHON_STANDARDS.md`'s full corpus tier table (Tiers 1-4) to be re-verified against real package import surfaces before any future milestone's acceptance criteria cite it as a binary gate, so this same defect doesn't recur at v0.3+.
- Alternatives: keep the original three bullets and treat them as aspirational rather than binary (rejected — ROADMAP.md's own milestone definition states "Milestone = shippable + demo-able. Acceptance criteria are binary," and this project's whole autonomy policy depends on binary, checkable gates; an unreachable "binary" criterion is worse than a corrected one). Pull a general multi-file import resolver forward into v0.2 so the literal corpus packages might compile (rejected — even with perfect import resolution, the packages still need stdlib modules scheduled through v0.8 and several modules scheduled nowhere; import resolution alone does not close the gap, and pulling it forward would substantially cannibalize v0.4's own defined scope for a criterion that still wouldn't pass). Expand v0.2's scope to add the extra grammar features needed to reach 25 PEPs literally (rejected — undocumented scope creep chasing a number that was never independently verified, contrary to this project's own "simplest correct thing for the stated scope" precedent, D-057).
- Consequences: `docs/ROADMAP.md`'s v0.2 accept line is rewritten to reflect all three corrections, citing this decision. The v0.2 implementation plan (written after this decision, in `docs/DELIVERY_PLAN.md`) is scoped to what this decision actually commits to: stdlib-intrinsic imports for `math`/`sys`, generic functions + `type` statement (not generic classes), a hand-authored container/generics corpus instead of the three named OSS packages, and a ≥15-PEP conformance target. The follow-up on corpus-tier re-verification for Tiers 1-4 against real package import surfaces is tracked in #183.
