## D-258: In an `--ext` module, `Any`, `object` and object-element container annotations are the opaque CPython object
- Status: accepted (planned contract, settles [#1285](https://github.com/rotnov/pycc/issues/1285) as "admitted"; no current compiler behaviour is claimed: `T0002` and the `C0003`/`C0001` refusals described below stand until the implementing pull requests land)
- Amendment (2026-10-05, [#1397](https://github.com/rotnov/pycc/issues/1397)): the Status line's "no current compiler behaviour is claimed" no longer holds. #1397 implements the decision. In every module of a `pycc build --ext` artifact, `Any`, `object`, a bare `list`/`dict`/`tuple`/`set` and a container with an object argument resolve to the opaque CPython object. A public signature carries that object across the export boundary as the `PyObject *` itself. A `native` build keeps `T0002` and the `C0001`/`T0034` refusals unchanged. Two cases are still deferred, each with its existing diagnostic: a list literal into an object slot (`T0003`/`T0034`) and `None` into an object slot (`T0022`, [#1387](https://github.com/rotnov/pycc/issues/1387)). A foreign-class parameter crosses the boundary without a run-time class check until [#1386](https://github.com/rotnov/pycc/issues/1386) decides on one.
- Amendment (2026-10-05, [#1409](https://github.com/rotnov/pycc/issues/1409)): an unannotated defaulted parameter in an `ext` module. The #1207 subject's `ParserState.__init__(..., state_stack=None, value_stack=None)` (line 40) and `ParserState.copy(self, deepcopy_values=True)` (line 59) are unannotated, and the compile-unchanged metric forbids editing them, so they met `T0001`. Under rule 1's scope, an unannotated parameter of a public function or method (`__init__` included) whose default is in the admitted literal subset now takes the type its default implies, and is checked exactly as if it carried that annotation. (a) A `None` default gives the opaque object of rule 2, that is, `x=None` is `x: Any = None`, on a method only. A module-level `def`'s default is spliced into in-module calls, where `None` at an object slot is still refused (#1387), so there `None` implies no type and the parameter stays `T0001`. (b) A literal `int`, `float`, `bool` or `str` default gives that **scalar type**, not the object. The resolution was made under D-127 after consulting an independent reviewer. The object alternative was rejected for three reasons. First, filling an object slot with a native literal is the boxing #1387 has not built, and today `x: Any = True` is itself a `T0021`. Second, a body using the value natively, such as `if deepcopy_values:` or `n + 1`, would depend on rule 5's incremental object operations instead of compiling as typed code. Third, the scalar is the type a reader of the default infers, and it is the annotation a D-252 addition would write; pyright infers the same declared type from such a default. The scalar choice is a deliberate deviation in the spirit of D-244 rule 7: at the host boundary the parameter refuses, with `TypeError`, exactly the values its annotated twin's boundary row refuses (`copy(0)` or `copy(None)` for the `bool` parameter; an `int` parameter still accepts a `bool`), where CPython, which checks nothing, would run. A parameter with no default, one whose default is outside the subset (`= []`), a private function's parameter (still inferred) and every `native` build are unchanged. The canonical statement is `docs/TYPE_SYSTEM.md`'s "No type is inferred from a default, except in an `ext` module" rule.
- Amendment (2026-10-05, [#1371](https://github.com/rotnov/pycc/issues/1371) Part 2d): the #1397 amendment's first deferred case, a list literal into an object slot, is now admitted for two sources. (a) An assignment annotated with a type rule 3 resolves to the opaque object (`object`, `Any`, a bare `list`, `List[Any]`) takes any list display, empty or not. (b) An unannotated empty `[]` takes the object when the target's other binding is the object, which is the #1207 subject's lines 94-101 (`s = value_stack[-size:]` / `s = []`, then `callbacks[rule](s)`). The semantics, decided under D-127: the display evaluates to a **fresh CPython `list`**, a new one per evaluation, with each element boxed in source order by the same packers a call argument uses, so elements may be `int`, `float`, `bool`, `str` or the object and may mix types. An element of any other type is `I0404`. The alternative of a native `list[T]` converted at the boundary was rejected: the slot is opaque, a mixed display has no native element type, and the callee may mutate the list, which a copy would hide. The list is leaked on the #1092 leak-only rule like every other produced object. Still deferred, each with its existing diagnostic: an attribute store (`self.s = [x]`, [#1421](https://github.com/rotnov/pycc/issues/1421)), a call argument (`f([])`), `return []`, a conditional-expression or `or` operand, a module-level statement, a non-empty unannotated display whose only object evidence is another binding (`T0023`), and dict, set and tuple displays (`{}` keeps `T0003`). `docs/TYPE_SYSTEM.md` ("Object slots") and `docs/RUNTIME.md` own the detail.
- Amendment (2026-10-05, [#1387](https://github.com/rotnov/pycc/issues/1387), Part 1): two narrow admissions, both needed by the #1207 subject. (a) **`None` at an object return.** In a function declared to return the object (`-> Any`, `-> object`, or a foreign class), a bare `return` and `return None` (the literal) return CPython's `None`. The subject's `feed_token(...) -> Any` has a bare `return` at line 89, which was `T0022`. The body hands back the borrowed `Py_None`, and the export wrapper's `pycc_ext_pack_object` takes the new reference the host receives. The rule keys on the declared type alone, so it holds wherever the object exists, a `native` program's foreign-class return included. Everything else the #1397 amendment deferred stays deferred with its existing diagnostic: a `None`-typed expression at an object return (`return g()` with `g -> None`, `T0022`), falling off the end of an object function (`T0022`), and `None` at every other object slot, namely an annotated binding (`T0025`), a call argument (`T0021`), an attribute, and a module-level `None` default (still `T0001`, as the #1409 amendment records). Only the literal is admitted because only the literal is CPython's `None` by construction; any other `None`-typed value needs the boxing #1387 has not built. (b) **The `__eq__`/`__ne__` operand.** In an `ext` module, the one unannotated, undefaulted parameter after the receiver of a regular `__eq__` or `__ne__` is the object of rule 2, not an inference variable. The subject's `def __eq__(self, other) -> bool` (line 51) has no call site to infer `other` from, so it was `T0021`, and `object` is the type Python's data model gives that operand. Every other dunder, an annotated or defaulted operand, a static method, and every `native` build are unchanged. This makes the operand typable only: dunder methods are still not exported to a host, so a host `==` on a pycc instance still compares identity where CPython would call `__eq__`, a divergence that predates this amendment ([#1427](https://github.com/rotnov/pycc/issues/1427)). Both choices were made under D-127 after consulting an independent reviewer. The canonical statements are `docs/TYPE_SYSTEM.md`'s `object` row and its "Call surface" section.
- Amendment (2026-10-05, [#1419](https://github.com/rotnov/pycc/issues/1419)): a CPython object flowing into a `bool` slot -- a `-> bool` return or a `b: bool = ...` binding of an object comparison such as `a == b` -- stays refused (`T0022`/`T0025`); pycc does not coerce it with an implicit `PyObject_IsTrue`. The resolution was made under D-127 after consulting an independent reviewer. Coercion was rejected for three reasons. First, CPython returns whatever the comparison returns (`numpy` arrays, a `__eq__` returning `'yes'`), and a `-> bool` annotation does not convert it, so an implicit truth test would silently change the value a caller sees. Second, rule 5 requires an explicit conversion out of the object type, and `bool(x)` is that conversion: it already lowers to `PyObject_IsTrue`, including its raising path. Third, the #1207 subject's `__eq__` does not need coercion once its `NotImplemented` return widens its result to the object ([#1418](https://github.com/rotnov/pycc/issues/1418)) and an object `and` operand is admitted ([#1423](https://github.com/rotnov/pycc/issues/1423)). The help of those two refusals (`T0022`, `T0025`) names the conversion for each scalar slot an explicit conversion produces (`bool(...)`, `int(...)`, `float(...)`, `str(...)`); the other refusals of an object in such a slot (`T0026` after a value-less declaration, `T0021` for a call argument) are unchanged and keep their generic help. A later need for coercion would take a run-time `PyBool_Check` under a new decision, not a silent truth test. The canonical statement is `docs/TYPE_SYSTEM.md`'s `object` row.
- Amendment (2026-10-05, Part 8 of [#1371](https://github.com/rotnov/pycc/issues/1371)): keyword arguments to a call on the opaque object. The #1207 subject's `lalr_parser_state.py` line 80, `raise UnexpectedToken(token, expected, state=self, interactive_parser=None)`, calls a foreign class with keywords, which met `C0001`. A method call, a direct call and a subscript-result call on an `object` now take keyword arguments under the same argument rule as positional ones, and every object call admits `None` as an argument. The call is made with CPython's `PyObject_Vectorcall` and a `kwnames` tuple rather than `PyObject_Call` with a keyword `dict`: a deviation in mechanism only, observably equivalent for every callable (CPython converts between the two conventions itself), chosen because it reuses the positional argument packing unchanged. The callee, arguments and keyword values follow the ownership rules `docs/RUNTIME.md` states for the positional call, and the result is leaked under the #1092 leak-only rule like every other producer. `**` unpacking and a pycc instance argument (`state=self`, `I0404`) stay refused, so line 80 itself still needs the instance boundary, and raising the call's `object` result is still `T0021`; `docs/TYPE_SYSTEM.md`'s `object` row owns the admitted shapes.
- Amendment (2026-10-05, [#1418](https://github.com/rotnov/pycc/issues/1418)): `return NotImplemented` in a comparison method of an `ext` module. The #1207 subject's `ParserState.__eq__` (lines 51-54) is annotated `-> bool` yet returns `NotImplemented` for an operand it does not handle, as CPython's rich-comparison protocol allows. Under rule 1's scope, a class's undecorated, non-`async` `__eq__`, `__ne__`, `__lt__`, `__le__`, `__gt__` or `__ge__` method whose body holds `return NotImplemented` at any block depth (outside a nested `def`, `lambda` or class) now returns the opaque CPython object of rule 2, whatever its annotation says, `-> bool` included. That is CPython-faithful: such a method really returns either a `bool` or the `NotImplemented` singleton, and the object is the one type that holds both. The rule reads the body rather than the annotation, so the subject's `return NotImplemented` (line 53) needs no edit; with Part 7 of [#1371](https://github.com/rotnov/pycc/issues/1371) admitting line 52's `isinstance` against the pycc class and [#1423](https://github.com/rotnov/pycc/issues/1423) typing line 54's `and` of a native `bool` with an object comparison as the object, the widened return also clears that line's `T0022` (an object into the `-> bool` slot, which the #1419 amendment above keeps refused rather than coerced), and the whole method now compiles. The admitted `return NotImplemented` yields CPython's own singleton. Every other spelling of `NotImplemented` in an `ext` module (an assignment, an argument, a module-level function, an ordinary method, a nested scope, a decorated or `async` comparison method, a method or class header) is refused with `C0001` naming the admitted form and #1418: the narrowest slice the subject needs. A `native` build is unchanged and keeps the unbound name's `T0021`. A native-typed return in a widened method, such as `return True`, stays `T0022` (expected `object`, found `bool`) with a help naming the widening and [#1387](https://github.com/rotnov/pycc/issues/1387), because boxing a native value into the object is #1387's work; an object-valued return, such as a comparison involving an object operand, passes. A widened method does not admit the native `==` between two pycc instances, which stays `T0021`; a future native `==` that dispatches through such a method owes CPython's fallback when it yields `NotImplemented` (the reflected method, then identity for `==` and `!=`). Publishing the comparison methods to the host as the class's `tp_richcompare` is a separate seam, [#1427](https://github.com/rotnov/pycc/issues/1427); until it lands the host sees `object`'s own comparison, and the compiled method is reached only from compiled code. The scope and the refusal code were settled under [D-127](./D-127-autonomous-agent-operation-model.md) with an independent reviewer rather than by asking the owner; `C0001` was chosen over `I0404` because the refused form is a missing capability, not an operation on a CPython object.
- Amendment (2026-10-05, Part 9 of [#1371](https://github.com/rotnov/pycc/issues/1371)): `raise o` with an opaque object `o` (rule 2) is admitted in an `ext` module and in an embedded (D-248) build, where it gave `T0021` before. Whether `o` is an exception is CPython's run-time decision, exactly as for CPython's own `raise`. An instance is raised as it is. A class is instantiated with no arguments. Anything else raises `TypeError: exceptions must derive from BaseException`. The raised exception enters the existing object error bridge, so `except Exception` and the builtin classes catch it through the tag map, and an uncaught one reaches the host as the identical object. Two shapes stay refused: `raise ... from ...` with an object on either side (`C0001`; `from None` is admitted, because HIR drops it for every operand), and an `except` clause that names a foreign class (`T0021`, unchanged). A `native` program never sees an object operand and is unchanged.
- Amendment (2026-10-06, [#1421](https://github.com/rotnov/pycc/issues/1421)): the Part 2d amendment's deferred attribute store and its deferred conditional-expression and `or` operand are now admitted, which clears the #1207 subject's lines 43-44 (`self.state_stack = state_stack or [self.parse_conf.start_state]`, `self.value_stack = value_stack or []`, both slots declared with rule 3 object annotations). A list display is built as the fresh CPython `list` of the Part 2d amendment, with the same packers, the same `I0404` for an unpackable element and the same leak, wherever it sits in a *value position* of an object slot. The slot is an assignment annotated with an object type, or an attribute store through a method's own receiver (`self`, or the parameter's other name) into a slot whose class layout type is the object: declared in the class body, inherited from a base, or established from an object value in `__init__`. The value positions are the stored value itself, either operand of `and`/`or`, and either branch of a conditional expression, nested to any depth. The test of a conditional expression, a truth-only `and`/`or` and the elements of a display are not value positions, so they keep their native typing. Decided under D-127: an operand is evaluated only when CPython would evaluate it, so `v or [1 // z]` with a truthy `v` builds nothing and raises nothing. The alternative of typing the display natively and boxing the `or`'s result was rejected, because it would convert at a boundary that the Part 2d amendment had already rejected. Still deferred, each with its existing diagnostic: a store through a name that is not the receiver (`a.s = [o]` keeps `T0034`), a display operand into an *unannotated* local (`s = v or [1]` keeps `T0021`), a call argument, `return []`, a module-level statement, and dict, set and tuple displays (`{}` keeps `T0003`).
- Amendment (2026-10-06, [#1442](https://github.com/rotnov/pycc/issues/1442), part of #1371): an attribute read on the opaque object that holds an instance of a class compiled in the same module. The #1207 subject's `ParserState.__eq__(self, other)` reads `other.state_stack` and `other.position` after `isinstance(other, ParserState)`; the read lowers to `PyObject_GetAttr` under this decision, and the published type carried no attribute for a slot or a property, so it raised `AttributeError`. Each constructible published class now carries a read-only `Py_tp_getset` table: one descriptor per instance-attribute slot and per `@property` whose declared type is `int`, `float`, `bool`, `str` or the object, packed by the D-244 return-type row and answering an unassigned slot with CPython's own `AttributeError`. `docs/RUNTIME.md` ("Reading a field through the published type") is the canonical statement. Three choices, settled by independent review under D-127. (a) *Descriptors, not `isinstance` narrowing*: narrowing `other` to the compiled class would read the slot natively and faster, but it changes the static type of an object-typed name, which is #1387's open scope, and it would not let host code read `obj.field`; the descriptor serves both readers through the one lookup CPython already performs, and narrowing remains open as a later optimization. (b) *Silently partial*: a field no return row packs from one machine word gets no descriptor rather than a `C0003`, because the table only widens what a host can observe of an object it already holds. (c) *Read-only*: a store through the published type -- from the host, or from compiled code through an object-typed name -- raises CPython's `AttributeError: attribute '<name>' of '<module>.<Class>' objects is not writable` where CPython would store the value. That is a recorded deviation; a setter must settle ownership of the replaced slot word and the conversion of the stored value, and [#1443](https://github.com/rotnov/pycc/issues/1443) tracks it. The compiled read keeps the object-operation temporary it produces, as every such read does until [#1092](https://github.com/rotnov/pycc/issues/1092) lands; the descriptor itself is reference-neutral. A non-constructible published type and an on-demand carrier type (#1435) wrap an instance too but carry no table yet; [#1448](https://github.com/rotnov/pycc/issues/1448) tracks them.
- Amendment (2026-10-06, [#1457](https://github.com/rotnov/pycc/issues/1457), Part 2 of [#1443](https://github.com/rotnov/pycc/issues/1443)): an attribute store `o.x = v` and an attribute deletion `del o.x` on the opaque object `o` are admitted in an `ext` module and in an embedded (D-248) build. They lower to `PyObject_SetAttr` and `PyObject_DelAttr`, so what happens is CPython's run-time decision, including a compiled instance's slot descriptor from Part 1 of #1443. The value may have any type a method-call argument on the object may have, is packed the same way, and is evaluated before the base, as in CPython; any other value type is `I0404`. A `del` of an attribute of any other base keeps a `C0001`, now located at the target. A store on a builtin value keeps `T0043`. A `native` program never sees an object operand and is unchanged.
- Amendment (2026-10-07, [#1448](https://github.com/rotnov/pycc/issues/1448)): the #1442 amendment's limitation that only a constructible published type carries the descriptor table, with a non-constructible published type and any other carrier left to #1448, is retired. The table is collected per carrier class (`collect_carrier_getsets` in `src/ext_build/getset.rs`) instead of per constructor, so every carrier type of an `--ext` module whose class has a descriptor carries it: a published type, constructible or not, on its own type object, and an unpublished class on D-244's #1427 hidden carrier type, registered at module exec. The #1442 rules hold unchanged -- the carried types, the silent partiality, the checked slot read, the namespace walk -- as do the slot setters (Part 1 of #1443) and the compiled property setters (#1458), so a host store into a slot of a hidden or non-constructible carrier converts by the parameter row exactly as on a constructible type. Classes no instance's run-time class can be (abstract, `Protocol`, a `0gen_` specialization) get no table, and neither does a class with a PEP 695 generic in its MRO, whose specializations share one carrier with different slot layouts: a field read through it still raises `AttributeError`, a silent partiality of the same kind as (b), not a `C0003`. The one exception is a constructible published generic template (`class G[T]` whose `__init__` the boundary carries): it keeps the table #1442 built for it from its constructor, so this amendment narrows nothing #1442 published. The existing hidden-type mechanism is generalized rather than giving the shim's on-demand type a second, runtime-built table, because the getters are generated per class and the hidden type already is the per-class slot array the issue asks for. `docs/RUNTIME.md` is the canonical statement, and `tests/issue_1448_carrier_getsets.rs` pins it against CPython.
- Amendment (2026-10-07, [#1475](https://github.com/rotnov/pycc/issues/1475), Part 2 of [#1387](https://github.com/rotnov/pycc/issues/1387)): boxing a native value into an `object` slot. In a module compiled with `ext` set (an `--ext` artifact or a D-248 embedded executable), an `int`, `float`, `bool`, `str`, `None` or pycc class-instance value that reaches a slot typed as the opaque object is boxed into a new CPython object, as CPython, which never checks the annotation, would pass the value itself. The seams are: a call argument of every call shape (a function, a private helper, a method, a constructor, `super().__init__`, a static or class method, an explicit `x.__eq__(y)`); an annotated binding or a plain `name = value` binding; a plain `name = value` rebinding of any object-typed name, annotated or inferred from a foreign producer, including in an embedded executable (only that binder boxes: a `for` target, a walrus, a `match` capture, a comprehension variable or a re-annotation of a name already bound stores its value unboxed and stays `T0023`, as does the reverse, a native-typed name rebound to an object); a `return`, including a native return in a method the #1418 amendment widens; an attribute store; and a property setter. A foreign-class annotation is the same object slot, so a native value boxes into it too, and crosses unchecked exactly as a foreign value does (#1386 owns the run-time class check). The value is packed by the export boundary's own packers and a `None` is the borrowed `Py_None`; a packer failure raises its CPython exception at the seam, and the boxed reference is leaked under the leak-only rule (#1092). One deviation is deliberate and pinned by a hosted test: an `int` outside the packer's inline range raises `OverflowError` where CPython keeps the integer (#1040). `is_assignable` is not widened, because the slot must know to emit the box; each seam asks one predicate, `pycc_types::object_box`, instead. The constraint solver, which has no class environment, defers a concrete non-object value returned into a declared `object` to the check phase, so such a refusal reads *expected return type `object`, got `list[int]`* rather than the solver's wording. Still refused: a container or `Optional` value at every seam (`T0021`, `T0022`, `T0023`, `T0025`), falling off the end of an object function (`T0022`), a value-less `x: object` declaration rebound natively (`T0026`), a native default for an object parameter (`T0021`), a class method's `cls` at every seam, including every call shape's arguments and a rebinding (`I0404`), a `native` program's `object` annotation (`C0001`), and an in-module comparison operator on pycc instances, which `pycc_types` types without user-dunder dispatch (`T0021`, deferred; the explicit `x.__eq__(y)` call is admitted). `isinstance` narrowing of an object back to a native type is Part 3 ([#1476](https://github.com/rotnov/pycc/issues/1476)). `docs/TYPE_SYSTEM.md`'s `object` row and `docs/RUNTIME.md` ("A native value boxed into an object slot") own the details; `tests/issue_1475_object_boxing.rs` matches CPython 3.14.7 on every seam.
- Amendment (2026-10-07, [#1476](https://github.com/rotnov/pycc/issues/1476), Part 3 of [#1387](https://github.com/rotnov/pycc/issues/1387)): `isinstance` narrows an object back to a native type. In a module compiled with `ext` set, a top-level `isinstance(name, C)` test on a name definitely bound to the opaque object, with the builtin `isinstance` and an unshadowed `C` that is `int`, `float`, `bool`, `str` or a regular class compiled in the module, narrows `name` to `C` in the region the test's polarity proves -- the guarded branch, and for a negated test whose body definitely terminates and whose `else` does not rebind the name the rest of the block -- with D-205's kills and joins and D-206's kill-prescan, in the check phase and the constraint solver alike. A native use of a narrowed read unboxes the object once (`MirExpr::ObjectUnbox` and the shim's `pycc_ext_obj_unbox_*`, which keep the closed D-244 rule-7 check); a use that would box it back (a return or binding into an object slot, a foreign call argument, an identity test) hands over the object itself, so identity and a `str` subclass survive. That holds only for a narrowed read that is itself the boxed operand: one inside a native expression (a conditional expression's arm, an annotated binding) is a native value and is packed anew, so a `str` subclass is flattened and identity is lost there. Extending the hand-over through such expressions was rejected: an arm that yields the borrowed object and an arm that yields a fresh native value have no common representation to merge, and every packing site would carry per-arm ownership, while the result is the flattening the fourth deviation below already states. A first binding from a bare narrowed read keeps an `object` slot; a first binding from any other narrowed expression (`y = o + 0`) is native, so a later binding of that local from the unnarrowed object is `T0023` where it compiled before (annotating the local `object` restores it). A class compiled in the module is consulted before the builtins, so a module-level `class int: ...` shadows the builtin in the guard and the narrowing alike, as in CPython; a module function spelled like `C` shadows it too, and the guard is refused (`I0404`) where CPython raises `TypeError`. A class another compiled class derives from does not narrow: pycc dispatches statically on the class a value is typed as (D-006, D-254), and the guard also admits a subclass instance, whose overrides a narrowed read would skip, so the operand stays an object and its method calls and attribute reads go through CPython's own lookup. Four deviations are deliberate and pinned by hosted tests: an `int` outside the inline range raises `OverflowError` at a native read (#1040); an uninitialized compiled-class carrier raises `TypeError` where CPython raises `AttributeError`; an object whose `__class__` property answers the guarded class without having its representation (a mock, a proxy) passes the guard, which is CPython's own `isinstance`, and raises `TypeError` at the native read where CPython runs the guarded body -- a loud refusal chosen over a guard that requires the representation, which would change the guard's truth value silently; and a native use of an `int`, `float` or `str` subclass instance runs the base type's operation, so an overridden dunder or method is not called and a `str` subclass handed to a compiled `str` parameter, or boxed back from a native expression, comes back a plain `str`. Everything else keeps the object: a tuple of classes, a container, enum, exception or foreign class, a class with a compiled subclass, a compound test, a maybe-bound name, and an unannotated parameter. `docs/TYPE_SYSTEM.md` ("Narrowing an object by `isinstance`") and `docs/RUNTIME.md` ("An object narrowed by `isinstance` is unboxed at each native read") own the details.
- Amendment (2026-10-07, [#1386](https://github.com/rotnov/pycc/issues/1386)): the run-time class check for a foreign-class parameter is decided as **none**. That check was deferred to #1386 by rule 2's second bullet, by the #1397 amendment and by the #1475 amendment. A parameter or return annotated with a foreign class, a subscripted foreign generic or a type variable crosses the boundary as the object itself, exactly as an `Any` one does. [D-244](./D-244-add-a-hosted-cpython-extension-module-artifact-mode.md)'s #1386 amendment records the decision, its narrowing of rule 7 and the rejected `isinstance` alternative. The interim behaviour those three passages describe is now the decided one, and nothing in this decision's rules changes.

    row).

  The #1207 kill-criterion subject is `lark` 1.3.1's `ParserState.feed_token(self, token: Token, is_end:
  bool = False) -> Any`, in `lark/parsers/lalr_parser_state.py`, annotated under
  [D-252](./D-252-admit-annotation-only-additions-to-a-kill-criterion-subject.md) and scoped to the subject
  module by [D-257](./D-257-kill-criterion-compile-scope-is-the-subject-module.md). It needs an answer for
  each of these:
  - its `-> Any` return, line 67. That return is `value_stack[-1]`, an arbitrary result of a user callback,
    so no honest concrete type exists. D-252 admits only annotation *additions*, so replacing `Any` is not
    an admissible fix;
  - `__eq__(self, other)`, line 51, whose only faithful annotation is `object`
    ([#1387](https://github.com/rotnov/pycc/issues/1387));
  - attribute annotations over CPython containers: `state_stack: List[StateT]`, `value_stack: list` and
    `states: Dict[StateT, Dict[str, tuple]]`. Each value is a list or dict that a `lark` caller built and
    passes in. Where the module creates one itself, it starts as `[]` or `[start_state]`.

  [#1285](https://github.com/rotnov/pycc/issues/1285) asked whether `Any` is admitted at the `ext` boundary,
  and how the value crosses it. The orchestrating session resolved the question under
  [D-127](./D-127-autonomous-agent-operation-model.md), after consulting an independent reviewer. This entry
  records the result.
- Decision:
  1. **Scope.** The rules below apply only to modules compiled into an `ext` artifact, that is, by `pycc
     build --ext` (D-244's hosted mode). They cover every module compiled into that artifact: the entry
     module, and any project module linked into it under
     [D-222](./D-222-project-modules-link-at-the-hir-level-into-one.md). The artifact mode is a property of
     the build, not of a module, and a second discriminator would only create a seam where the same source
     line means two things in one artifact. A `native` program (`pycc build` without `--ext`, `pycc run`,
     `pycc check` of such a program) is unchanged: `Any` remains `T0002`, with the same code and message,
     and `object` stays unspellable there unless #1387 decides otherwise for that mode.
  2. **`Any` is the opaque object.** In an `ext` module, `typing.Any` lowers to the type a foreign import
     binds (D-244 rule 3, `Ty::Object`). This holds in a parameter, return, attribute (class-body or
     `self.<attr>`) or local annotation, and as a type argument (rule 4). A value of that type is a strong
     `PyObject *` reference. Its ownership follows `docs/RUNTIME.md`'s rule for `object`, including the
     release protocol [#1092](https://github.com/rotnov/pycc/issues/1092) tracks. At the export boundary it
     crosses **unchanged**, with no conversion in either direction:
     - an `Any` parameter receives the host's object, and an `Any` return hands the host a new reference
       to the object the body produced. So `-> Any` on `ParserState.feed_token` returns the very CPython
       object `value_stack[-1]` holds;
     - every value conforms to `Any`, so D-244 rule 7's non-conforming `TypeError` can never fire on such a
       parameter, and pass-through is the only behaviour available. This decides nothing about a parameter
       annotated with a foreign *class* (`token: Token`). Whether the thunk passes that through or checks
       `isinstance` remains [#1386](https://github.com/rotnov/pycc/issues/1386)'s to decide;
     - the wrapper slot that carries an object, which `collect_exports` refuses today with `C0003`, is one
       mechanism shared with #1386. Whichever pull request lands first builds it, and the other reuses it.

     This settles #1285 as **admitted**.
  3. **`object` means the same type.** In an `ext` module the builtin name `object`, used as an
     annotation, lowers to the same opaque type as `Any`. The two spellings are interchangeable there. This
     answers the spelling question #1387 asks for the `ext` mode only. #1387's implementation is unchanged:
     boxing a native `int`, `float`, `str`, `bool`, pycc instance or container into an `object` slot, and
     `isinstance` narrowing back out of one.
  4. **Object containers are the CPython container.** In an `ext` module, the following annotations also
     lower to the opaque object:
     - a container annotation whose element, key or value type is the object type of rules 2 and 3
       (`list[Any]`, `dict[str, object]`, `tuple[int, Any]`);
     - an unparametrised `list`, `dict`, `tuple` or `set` annotation;
     - `List[...]`, `Dict[...]`, `Tuple[...]` or `Set[...]` (or the lower-case forms) over a foreign class or
       a foreign type variable (`List[StateT]`, `Dict[StateT, Dict[str, tuple]]`).

     One object-typed argument anywhere in the annotation makes the whole value opaque: `tuple[int, Any]` is
     one CPython tuple, not a native struct with one object field. The value is the CPython container
     itself, for example the stacks and the parse table a `lark` caller passes in, so aliasing is preserved:
     a mutation through it is visible to every other holder, as in CPython. A list, dict, tuple or set
     literal assigned to such a slot (`[]`, `[x]`, `{}`) builds a CPython container (`PyList_New`,
     `PyDict_New` and so on), not a pycc-native one. A native container whose element types are all
     native, including a pycc class (`list[int]`, `dict[str, int]`, `List[MyPyccClass]`), is unaffected
     and stays under [D-105](./D-105-v0-2-s-list-t-thin-slice-scope-cuts-and-runtime.md)
     and [D-122](./D-122-dict-k-v-set-t-key-element-types-are-scoped-to.md). Those decisions govern native
     containers, and this rule neither lifts nor contradicts their element-type scopes. A pycc-native
     container value passed where an object container is expected has no conversion, and it is refused at
     compile time. Copying it into a CPython container would break the aliasing this rule exists to keep.
  5. **Operations lower to the C-API.** Every operation on a value of the opaque type lowers to the
     corresponding CPython C-API call, and CPython's own exceptions propagate. The operations are:
     - identity, `is` / `is not` (`Py_Is`);
     - rich comparison, `==`, `!=`, `<` and the rest (`PyObject_RichCompare`);
     - subscript load, store and delete, slices included (`PyObject_GetItem` / `SetItem` / `DelItem` with
       a slice object);
     - a call with positional and keyword arguments (`PyObject_Call`), including a call on a subscript
       result (`callbacks[k](v)`);
     - `isinstance` (`PyObject_IsInstance`) and `type(x)` (`Py_TYPE`);
     - truth testing, iteration and method calls;
     - `raise` of an object that is an exception instance.

     A pycc-native operand of such an operation (an `int` index, a `str` key, a native argument) is boxed
     with the existing boundary conversions. In the other direction an object reaches a native-typed slot
     only through an explicit conversion (`int(o)`, `float(o)`, `str(o)`, `bool(o)`, D-244's Part 4
     amendments) or through `isinstance` narrowing (#1387). Assigning it to a native slot directly stays
     refused (`I0401`/`I0404`), as D-244 rule 3 states. The list is implemented incrementally:
     [#1371](https://github.com/rotnov/pycc/issues/1371)'s series, and the issues the #1207 subject-module
     frontier table in `docs/TESTING.md` links (#1095, #1255, #1333, #891 and others). An operation not yet
     implemented keeps its current diagnostic until its part lands.
  6. **Implementation seam.** `pycc_hir` has no artifact-mode awareness, as the comment on the
     `memoryview` arm next to `T0002` in `crates/pycc_hir/src/func.rs` records. The implementing pull
     request therefore follows the `memoryview` precedent: the annotation lowers unconditionally, and the
     mode-dependent refusal lives where the mode is known (`src/memoryview_mode.rs`, `src/ext_build.rs`).
     For `Any` that means a `native` build must still report `T0002` with its current code, message and
     span. The refusal moves to the mode-aware layer, and its meaning does not change. Any other shape
     that keeps `native` output byte-identical is admissible.
- Alternatives:
  - *Refuse `Any`, and record #1285 as a standing blocker at the 2026-10-22 deadline.* Rejected.
    The subject returns an arbitrary callback result, so no honest concrete type exists, and D-252 admits
    only annotation additions, so the annotation cannot be replaced. The opaque object already exists for
    foreign imports. Refusing to spell it in an `ext` module would record a by-choice refusal as a verdict
    on the compiler, which is the attribution error D-247 and D-257 rule 2 were written to prevent.
  - *Admit `Any` on returns only.* Rejected. The same opaque representation already exists for foreign
    imports, so a return-only rule saves no machinery. The subject's containers and `__eq__(self, other:
    object)` need the same answer for parameters and attributes. A position-limited rule would only move
    the refusal one line down.
  - *Lift D-105/D-122 to object element types inside native containers* (a native `list[object]` holding
    boxed references). Rejected for this sprint. The subject's containers come from CPython callers, so a
    native container would require a copy at every ingress. That copy is slower than operating on the
    CPython container, and it is unfaithful: a callback that mutates the list it was handed would mutate
    the copy, not the caller's list. A native object-element container may still be decided later for
    containers pycc itself creates and never shares. That would be a separate decision.
  - *Treat `Any` as PEP 484's gradual type* (assignable to and from every type without a check).
    Rejected. It would let an object flow silently into a native `int` slot, which D-244 rule 3's `I0401`
    forbids, and pycc's typed lowering has no representation to receive it. `Any` here is a top type
    with an explicit way out (rule 5), not a hole in the checker.
- Consequences:
  - **Deviations.** Code typed with the object type gets no static checking beyond the type itself.
    Misuse is whatever CPython raises at run time (`AttributeError`, `TypeError`, ...), exactly as the
    interpreter would raise it. Unlike mypy's gradual `Any`, an object value does not pass silently into a
    native-typed slot; it needs rule 5's explicit conversion. That is stricter than CPython, which does not
    enforce annotations at all, and it is recorded as a deliberate deviation in the same spirit as D-244
    rule 7.
  - **Performance and the kill criterion.** Object-typed code runs at C-API speed: each operation is a
    call into CPython, with no typed lowering to gain from. `feed_token`'s loop body works almost entirely
    on objects pycc does not own, as D-257 rule 6 already records, so under this decision it runs almost
    entirely on that path. This bears directly on D-244 rule 6's ≥ 5× kill criterion, which is judged on
    2026-10-22 and is not changed here. D-244's 2026-09-16 amendments also bar evaluating the criterion on
    a hot function containing foreign loads until #1092's release protocol lands, and an object-typed
    `feed_token` is exactly such a function. A compile under this decision makes a timed run *possible*;
    it does not predict that the bet is won.
  - **D-257's scoping stands.** Under rule 1, the two `T0002`s inside `lark/utils.py` become admissible
    in an in-tree `--ext` build once this decision is implemented. D-257's subject-module reading still
    stands, because the two `T0001`s in that closure module keep the whole-closure reading unreachable on
    their own (D-257 rule 2).
  - **Documentation and diagnostics.** The implementing pull request updates these together with the code:
    - `docs/TYPE_SYSTEM.md` strictness rule 3 and its `object` row;
    - `docs/DIAGNOSTICS.md`'s `T0002` row and `pycc explain T0002` (`crates/pycc_diag/src/explain.rs`),
      which must then describe `T0002` as a `native`-mode refusal;
    - `docs/PYTHON_STANDARDS.md`'s `Any` row;
    - the #1207 frontier table in `docs/TESTING.md`.

    Until then `docs/TYPE_SYSTEM.md` and `docs/TESTING.md` mark the rule as decided and not yet
    implemented.
  - **What becomes harder.** The `ext` mode now has two container representations behind similar
    spellings: `list[int]` is native and `list[Any]` is a CPython list. A diagnostic that mixes them
    (for example a native `list[int]` passed to a `list` parameter) must name both, so the reader can see
    which one was meant.
