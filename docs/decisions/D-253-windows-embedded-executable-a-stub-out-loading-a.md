## D-253: Windows embedded executable: a stub OUT loading a program DLL from OUT.pycc

- Status: accepted (Part 1 of [#1226](https://github.com/rotnov/pycc/issues/1226), [#1286](https://github.com/rotnov/pycc/issues/1286); Windows hosts, standard-library embedded builds; Part 2, [#1287](https://github.com/rotnov/pycc/issues/1287), adds a locked closure, `pycc lock` and a PE dependency scan)
- Context: [D-248](./D-248-embedded-executable-artifact-layout-and-bridge-split.md) rule 1 refused every CPython-backed import on a Windows host with `I0403`. Its POSIX artifact finds libpython through an rpath relative to the executable, which Windows has no equivalent of: an executable's static imports resolve from the application directory, the system directories and `PATH`, never from a subdirectory. Putting `python314.dll` beside `OUT` would break D-248 rule 2's two-entry layout. `python314.dll` also exports data symbols the compiled module imports, so it cannot be delay-loaded. On Windows CPython's `sysconfig` reports `LDLIBRARY = python314.dll` (the loaded DLL's basename), `LIBDIR = <installed_base>\libs` (the import libraries) and no `Py_ENABLE_SHARED` or `LIBPL`, so D-248 rule 4's shared-library check and D-251's archive probe do not apply; the standard library is `Lib\` and the extension modules are `DLLs\`, whose `PLATLIBDIR` is `DLLs`, not D-248 rule 7's `lib`.
- Decision:
  1. **Artifact.** On a Windows host `OUT` is a **stub** executable (`src/embed/pycc_embed_stub_windows.c`) linked with the static CRT, whose import table names only the system DLLs `KERNEL32.dll` and `ntdll.dll` (the static CRT references the latter), both resolved from System32 and never from `PATH` or the sidecar. `OUT.pycc\` holds `pycc_program.dll` (the **program DLL**: the launcher, the unchanged shim, the compiled module and `pycc_rt`, linked `-shared` against `libs\python314.lib` with no import library written), `python314.dll`, `python3.dll`, `vcruntime140.dll` and `vcruntime140_1.dll` when the interpreter's `base_prefix` has them, a filtered `Lib\` and `DLLs\` (without `site-packages`, `__pycache__`, `test` and the Tcl/Tk files), and the `PYCC-BUNDLE` marker. There is no `lib\`. The program DLL's name is fixed; the stub and the build spell it alike.
  2. **Loading.** The stub takes its own path from `GetModuleFileNameW`, replaces the file name with the sidecar name baked into it, calls `SetErrorMode(SEM_FAILCRITICALERRORS)` and loads `<sidecar>\pycc_program.dll` with `LoadLibraryExW(..., LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_DEFAULT_DIRS)`, so the program DLL's imports resolve from the sidecar root and the system directories and never from `PATH`. It calls the DLL's exported `pycc_embed_main(argc, argv, sidecar)` and exits with its result. If the load or the lookup fails it prints `pycc: cannot load <path> (error N)` to stderr and exits 121, next to the launcher's 1 (an uncaught exception) and 120 (a failed finalization).
  3. **Interpreter start.** `pycc_embed_main` starts an isolated interpreter as D-248 rule 7 does (no `site`, no bytecode writes, unbuffered stdio), with `home` set to the sidecar and `sys.path` set explicitly (`module_search_paths_set`) to `<sidecar>\Lib` then `<sidecar>\DLLs`; nothing is taken from `getpath`'s derivation. `platlibdir` is left at its default. `sys.executable` and `sys.argv[0]` are the stub's path as it was spawned.
  4. **Probe.** The default interpreter is `python3.14.exe`. The probe keeps D-248 rule 4's version, free-threaded, header and standard-library checks, drops the shared-library check, and requires `libs\python314.lib`, `libs\python3.lib` (named by `PC/pyconfig.h`'s `#pragma comment(lib, ...)`), `<base_prefix>\python314.dll`, `<base_prefix>\python3.dll` and `<base_prefix>\DLLs`, each missing one an exit-2 failure naming the path.
  5. **Refusals and their order.** A root outside the standard library is `I0403` naming #1287, after the `--target` and excluded-root reasons. `--static-libpython` or `[build] static = true` is refused at exit 2 before the probe: CPython for Windows ships no static library ([D-251](./D-251-static-libpython-link-for-embedded-executables.md)). A `pycc.lock` section the build would consume is refused at exit 2 naming #1287. When both apply, the static refusal wins. `pycc lock` stays an exit-2 refusal on a Windows host, now naming #1287.
  6. **Link order.** D-248 rule 3's existing-sidecar check, staging directory and check-then-swap are unchanged. After the swap the program DLL is linked into the sidecar first and the stub at `OUT` second. A failed program-DLL link leaves a marked sidecar without `pycc_program.dll` (a stale `OUT` beside it then exits 121); a failed stub link leaves a complete sidecar beside a stale or missing `OUT`. Both are exit 1 from the link step, as on POSIX.
  7. **What D-248 still governs.** Rule 3 as above, the marker format, rule 6 widened by one Python-free C file (the stub), and rule 1 with its Windows-host reason narrowed to roots outside the standard library.
- Alternatives: the interpreter DLLs beside `OUT` (rejected: files outside `OUT` and `OUT.pycc` break D-248 rule 2's layout and rule 3's overwrite safety, and two programs built into one directory, or a user's own files there, would collide on `python314.dll`); a side-by-side manifest with a private assembly (rejected: an assembly identity per build tied to the sidecar name, every transitive DLL listed as an assembly file, opaque "side-by-side configuration is incorrect" failures, and `.local` redirection ignored for manifested applications); delay-loading `python314.dll` from the sidecar (rejected: the data imports cannot be delay-loaded); relying on `getpath` for `sys.path` (rejected: on Windows it appends the executable's directory); resolving symlinks in the stub as POSIX's launcher does with `realpath` (rejected for Part 1: creating a symlink needs privilege on Windows and the stub is not the place to handle `\\?\` paths).
- Consequences:
  - A standard-library-only program builds and runs on a Windows host; the pair `OUT` plus `OUT.pycc\` is relocatable together, like D-248's.
  - The stub does not resolve symlinks, unlike the POSIX launcher: a symlink to `OUT` looks for the sidecar beside the link.
  - `LOAD_LIBRARY_SEARCH_*` requires Windows 10 or later in practice (earlier systems need KB2533623).
  - NEG: whether the artifact runs on a machine without the VC++ redistributable is not proven by CI, because the runners install it system-wide. CI proves the stub imports only `KERNEL32.dll` and `ntdll.dll` and that the vendored runtime DLLs are byte-identical to the interpreter's.
  - NEG: relocation is not fail-closed on Windows in Part 1. D-248 rule 5 classifies every dependency and refuses one outside the system or the prefix; Part 1 does no PE import scan and copies `DLLs\` wholesale, so a `.pyd` or DLL depending on a library outside `DLLs\`, the sidecar root and the system directories builds without error and fails only after the pair is moved. #1287 closes the gap with a scanner.
  - Every Windows arm is a pure function unit-tested on every host against a Windows-shaped fake interpreter; the real artifact is exercised only on the Windows CI leg by `tests/issue_1286_windows_embedded_executable.rs`, which fails rather than skips there when CPython 3.14.7 or `llvm-readobj` is missing.
- Amendment (2026-09-24, [#1296](https://github.com/rotnov/pycc/issues/1296), Part 1 of [#1287](https://github.com/rotnov/pycc/issues/1287)): a Windows embedded build consumes `pycc.lock` under [D-249](./D-249-pycc-lock-schema-environment-resolver-and-update-command.md)'s #1296 amendment. Rule 1: when the section locks at least one package, `OUT.pycc\` also holds the locked closure in `closure\`. Rule 3: `sys.path` is `<sidecar>\Lib`, `<sidecar>\DLLs`, then `<sidecar>\closure` when the launcher is compiled with `PYCC_EMBED_CLOSURE`. Rule 5: the `I0403` reason for a root outside the standard library, the lock-section refusal and the `pycc lock` refusal are lifted; `--static-libpython` is still refused first, before the probe, and a closure holding a PE image is refused at exit 2 after the payload is planned and before anything is staged, naming #1297. Rule 7: rule 1 of D-248 no longer has a Windows-host reason at all. The relocation NEG consequence narrows: the closure is fail-closed by that refusal, and only `DLLs\` is still copied without a PE import scan until [#1297](https://github.com/rotnov/pycc/issues/1297). The real closure is exercised on the Windows CI leg by `tests/issue_1296_windows_locked_closure.rs`.
- Amendment (2026-09-24, [#1305](https://github.com/rotnov/pycc/issues/1305), Part 1 of [#1297](https://github.com/rotnov/pycc/issues/1297)): Rules 2 and 3: before initializing the interpreter the launcher calls `AddDllDirectory(<sidecar>)`, failing with a one-line error and exit 1 if it cannot, so a `DLLs\` image that imports a root DLL the program DLL's own import graph does not load (such as `vcruntime140_1.dll`) finds it in the sidecar, as it finds it beside `python.exe` on the host; the sidecar root is already the program DLL's search root, so no trust root is added. Rule 1: the `DLLs\` copy also skips extension images of another ABI (a `.cp3NNt-` free-threaded name, a `_d.pyd` or `_d.dll` debug name). Rule 5: after the probe and before staging, every PE image the sidecar bundles from the interpreter (the root DLLs and the kept `DLLs\`) is parsed by an in-tree import reader (`src/embed/pe.rs`), and the build is refused at exit 2 when an image is not an x86-64 PE32+ DLL, cannot be parsed, or has a static import that is none of an API set (`api-ms-`/`ext-ms-`), a root DLL, a kept image in its own `DLLs\` directory, or a file in the build host's system directory; a delay import must be an API set, a system file or the interpreter's DLL, because delay loading uses the standard search order. A kept file under `Lib\` that Windows would load as a PE image is refused too, since nothing there is scanned. NEG, extended: a system-directory file is accepted whatever it is, so a third-party DLL the build host installed in System32 is trusted and must also exist on the target, as the VC++ redistributable must. NEG, narrowed: relocation is now fail-closed for the root DLLs and `DLLs\`; only a closure PE image stays refused wholesale, until [#1306](https://github.com/rotnov/pycc/issues/1306) scans it.
