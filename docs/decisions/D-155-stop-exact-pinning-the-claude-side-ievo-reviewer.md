## D-155: Stop exact-pinning the Claude-side ievo reviewer to a commit

- Status: accepted
- Context: D-068 required verifying the Claude-side `ievo@ievo-skills` reviewer against an exact `sha` recorded in this repository's own `.claude/settings.json`, on the premise that the pin was actually enforced at install time. It is not: Claude Code's plugin marketplace registry is a single global, name-keyed file (`~/.claude/plugins/known_marketplaces.json`), not per-project state any repository pull request can control. Once any project on a machine, or a manual `/plugin marketplace add`, registers the `ievo-skills` marketplace name unpinned, that global entry governs resolution for every project referencing the same name -- this repository's own declared `sha` included. On a real, non-isolated machine the installed plugin routinely resolves to whatever commit last won that global registration, not the pinned one; only a from-scratch, isolated `CLAUDE_CONFIG_DIR` ever actually observed the pinned commit. The exact pin was, in practice, unenforced and gave a false sense of a verified supply chain.
- Decision: drop the `sha`/`ref` pin from `.claude/settings.json`'s `ievo-skills` plugin source; the source tracks the upstream default branch by design. `scripts/validate_agent_assets.py` now rejects a `sha` or `ref` key on that plugin source outright instead of requiring one. Replace the exact-digest comparison in the CI-safe `scripts/check-claude-marketplace.sh` with a structural well-formedness check: the deep-review entrypoint and deep-reviewer agent artifacts are non-empty, and the plugin manifest's `version` field is semver-shaped -- CI only ever sees a clean install, so this is the check CI can actually make good on. Add `scripts/check_claude_reviewer_binding.py` as the local, non-CI half of the contract: it hard-fails only when no structurally intact `ievo@ievo-skills` install can be found at all for the current project (falling back to a user-scope install), and otherwise prints an advisory freshness note against the latest upstream release tag that never blocks dispatch of the D-068 review loop.
- Alternatives: reconcile the exact pin across every machine and project that shares the global marketplace registry (rejected -- the registry is machine-local, out of this repository's control, and shared by unrelated projects; there is no mechanism to enforce one repository's pin against it); keep the exact pin as documentation-only, unenforced intent (rejected -- an unenforced security control that looks enforced is worse than an honest structural check, since it invites false confidence); drop local verification entirely and rely only on the CI-safe check (rejected -- the local review loop D-068 established still needs its own presence/freshness signal, since CI's clean-install assumption does not hold for a developer's already-populated machine).
- Consequences: the Claude-side reviewer pin table in `docs/AGENT_TOOLING.md` no longer claims an exact-commit guarantee it was not actually providing; the local and CI-safe checks both narrow to what each can actually verify from where it runs. Reviewer updates no longer require a documented digest-comparison security review before every version bump -- structural well-formedness plus the advisory freshness note is the new bar. If a future incident shows structural-only verification is insufficient (a compromised upstream release that is still well-formed), that is a new decision, not a reason to silently re-add an unenforced pin here.
