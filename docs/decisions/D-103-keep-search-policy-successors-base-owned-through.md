## D-103: Keep search-policy successors base-owned through a complete two-merge manifest

- Status: superseded by D-172
- Context: the prospective search-visibility audit executes only trusted base code under `pull_request_target`, but its first activation would make the successor workflow, policy scripts, self-tests, and their repository inputs authoritative for later pull requests. Pinning only the workflow digest during that one activation is insufficient: a candidate could preserve the approved workflow bytes while replacing a future checker with a no-op, omit a transitive self-test input, change a protected path into a symlink or submodule, or add `.gitattributes` rules that make checkout materialize bytes different from the Git blobs the trusted audit reviewed. The same circularity recurs on every later policy revision if the pull request that changes an active target may also authorize its own replacement bytes.
- Decision: the active search-policy trust anchor reads a complete `tests/fixtures/policy-successor-manifest.json` from the trusted base. The manifest binds every protected workflow, checker, self-test, fixture, and transitive repository input to a base-staged source path and SHA-256 digest. Every candidate must keep existing protected targets byte-identical to those base-owned sources, preserve exact `100644 blob` Git entries for protected and proposed files, retain every existing target, and contain no root or nested `.gitattributes`. A policy-bundle revision requires two merges: the first adds inert proposal files and a complete non-shrinking next manifest while active targets stay unchanged; only a later pull request may activate those exact, now-base-owned bytes. The activation may then point each manifest source back to its active target for the next cycle. Initial activation is governed by the same principle through the still-active predecessor checker's deterministic activation bridge, which validates the candidate successor bundle and requires every candidate workflow entry to remain a regular non-executable blob before the predecessor anchor is retired.
- Alternatives: let a policy pull request update active targets and their manifest digests together (rejected because candidate-controlled authorization makes the base-owned audit circular); protect only executable scripts and workflows (rejected because omitted fixtures and transitive inputs can change what trusted self-tests prove); rely on Git blob SHA values without constraining modes or `.gitattributes` (rejected because symlinks, submodules, executable-bit changes, or checkout filters can change materialization without changing an approved regular-file blob); require manual repository review instead of a mechanical transition protocol (rejected because repository policy treats pull-request content as untrusted and requires the trust boundary to fail closed).
- Consequences: search-policy maintenance has a deliberate two-merge latency and the manifest cannot shrink in place; removing a protected target requires a future superseding decision and checker protocol rather than an ordinary bundle update. In return, no single pull request can both alter a protected policy input and make that alteration authoritative after merge. The workflow-policy checker and its mutation suite mechanically enforce the manifest schema, source digests, Git modes/types, no-`.gitattributes` rule, non-shrinking target set, deterministic initial activation, and exact-base staging requirement described in `docs/TESTING.md` and surfaced in `docs/ROADMAP.md`.
