## D-032: Branch protection requires one aggregate `ci-gate`, not per-matrix-leg checks

- Status: accepted (PR-3 is the PR that depends on it)
- Context: PR-3's own Codex review (on the head commit that added the Tier-1 matrix) flagged that branch protection required only `build-test-coverage` and `audit` (confirmed via `gh api repos/rotnov/pycc/branches/main/protection`) -- none of `native-build-test`'s four Tier-1 legs, `cross-compile-build`, or `cross-compile-verify` were required checks. A pull request could therefore merge with a broken Windows, Linux, or macOS native build, or a broken cross-compile proof, as long as the two originally-required checks passed -- leaving SPEC.md's invariant 5 ("a feature doesn't exist until it's green everywhere") unenforced for exactly the jobs added to prove it.
- Decision: add a single `ci-gate` job to `ci.yml` that `needs: [build-test-coverage, native-build-test, cross-compile-build, cross-compile-verify]` and fails unless every one of those four results equals `'success'` literally, checked per job name rather than via `contains(needs.*.result, 'failure' | 'cancelled')`: `cross-compile-verify` has no `if:` of its own, so when its dependency `cross-compile-build` fails, GitHub marks `cross-compile-verify` itself `'skipped'`, not `'failure'` -- a failure-only blocklist would miss that cascade and let the gate pass. Checking each name for literal `'success'` catches `skipped`/`cancelled`/`timed_out`/`failure` alike without enumerating every non-success state.

  Branch protection's actual required-checks switch (from `build-test-coverage` to `ci-gate`) is **deliberately not done in this same step**: flipping it while `ci-gate` exists only on this PR's branch would immediately affect every other currently-open pull request against `main` (confirmed several are in flight in parallel), each waiting on a required check (`ci-gate`) that doesn't exist in their own tree yet -- a shared-governance change with a real blast radius beyond this PR, surfaced to the user rather than applied unilaterally (the same category of call as the mid-review `origin/main` divergence earlier in this arc). The switch happens once `ci-gate` exists on `main` itself, i.e. after this PR merges.
- Alternatives: add each `native-build-test` matrix leg plus `cross-compile-build`/`cross-compile-verify` directly to branch protection's required-checks list (rejected -- a matrix job's GitHub-generated check name bakes in its matrix values verbatim, e.g. `native-build-test (ubuntu-latest, x86_64-unknown-linux-gnu)`; renaming an `os` value, changing a `target`, or adding a new Tier-1/Tier-2 leg later would leave the old name permanently required-but-nonexistent -- silently blocking every future merge with no clear cause -- while the new leg goes unenforced. A single job whose own name never depends on the matrix avoids this class of staleness entirely). Flipping branch protection to require `ci-gate` immediately, in the same PR (rejected for the blast-radius reason above).
- Consequences: adding, removing, or renaming a `native-build-test` matrix entry (or any other job this PR's Tier-1 work added) needs no branch-protection change -- only `ci-gate`'s own `needs:` list, reviewed the same way as any other workflow edit. `ci-gate` runs on `ubuntu-latest` and needs no elevated permissions (it only reads `needs` context, never checks out or executes code), so it passes the existing CI permissions checker (D-020) unchanged. Until the required-checks switch happens (tracked, not silent -- see TESTING.md), a failing or pending `native-build-test`/`cross-compile-build`/`cross-compile-verify` does not by itself block a merge into `main`. (The switch has since happened -- see D-033, a new entry rather than an edit to this one.)
