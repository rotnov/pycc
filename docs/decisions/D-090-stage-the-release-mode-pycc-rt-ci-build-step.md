## D-090: Stage the release-mode `pycc_rt` CI-build-step digest alongside active D84 (superseded before activation)

- Status: accepted; superseded before activation by D-091 -- this digest was never live
- Context: PR-8, Task 5's `nbody` benchmark harness (`tests/nbody_bench.rs`) needs `pycc build --release` to actually link an optimized `pycc_rt` static library, not the always-`target/debug` build `src/main.rs::find_pycc_rt_lib_dir_in` unconditionally resolved regardless of the `--release` flag (a real bug, found and fixed during that task's own root-cause investigation of a benchmark ratio far short of its required gate). Exercising the fix in CI needs a new "build `pycc_rt`, release profile" step added to `build-test-coverage` and every `native-build-test` leg (5 Tier-1 targets), alongside each leg's existing debug-profile build step. Same mechanism as D-080/D-084: `.github/workflows/workflow-policy.yml`'s `audit` job checks out `scripts/check_roadmap_evidence.rb` at `ref: ${{ github.sha }}` under `pull_request_target`, which resolves to `main`'s HEAD, never the PR branch's — so a single PR that both edits `ci.yml` and teaches the checker its new digest can never pass its own audit.
- Decision: stage `tests/fixtures/d90-release-pycc-rt-ci.yml` (the target content: D84's own reviewed content, unchanged, plus a release-profile `pycc_rt` build step added to `build-test-coverage` after its `cargo build --workspace` step, and to every `native-build-test` leg after its own `cargo build --workspace` step) and authorize its digest (`D90_RELEASE_PYCC_RT_CI_WORKFLOW_SHA256`) alongside active D84, then activate those reviewed bytes in a fresh pull request (part of v0.2 PR-8) and retire D84's digest.
- Alternatives: build `pycc_rt --release` lazily inside `tests/nbody_bench.rs`'s own Rust test code (e.g. shelling out to `cargo build --release -p pycc_rt` at test-run time) instead of a dedicated CI step — rejected: this would make the ignored benchmark test itself responsible for a build side effect unrelated to what it measures, paid on every invocation of that one test rather than once per job, and would leave the release-mode build undiscoverable from the job log the way every other Tier-1 leg's existing debug-profile `pycc_rt` build step already is.
- Consequences: this staging commit does not change live CI behavior. `scripts/check_roadmap_evidence.rb`'s `TRUSTED_COVERAGE_STEPS`/`COVERAGE_SCRIPT` constants and every job's actual steps stay untouched pending activation; the reviewed-workflow allowlist temporarily holds two active entries (D84, D90) until activation retires D84.
- **Correction before activation**: opening PR-8's own pull request against `main` (the step that would have exercised this content for real) surfaced that this staged fixture was incomplete: `build-test-coverage`'s own "Hard coverage gate" step builds `pycc_rt` inside an isolated `nobody` sandbox for its cross-compile target and in debug profile, but never in release profile — this decision's release-profile build step ran only later, outside that sandbox, after coverage measurement. `tests/pycc_toml_release_default.rs`'s non-ignored test needs a release-built `pycc_rt` to exist, so the coverage gate would have failed the moment this digest activated. D-091 folds the missing coverage-sandbox build into its own composed digest alongside an unrelated, independently-discovered fix (relaxing `frontend-perf-measure`'s manifest contract) and supersedes this one. `D90_RELEASE_PYCC_RT_CI_WORKFLOW_SHA256` and its fixture are removed from the reviewed allowlist entirely rather than kept as retired-but-once-live evidence (unlike D51/D56/D62/D80's own retirement pattern) — this content was never activated, so there is no "this was once the real approved workflow" fact to preserve.
