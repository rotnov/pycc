## D-159: Add cumulative run statistics and per-model defect attribution to the `ultra-review` checkpoint

- Status: accepted
- Context: D-147's checkpoint (issue #355) held only a single-snapshot, three-line body — `Last reviewed commit`, `Reviewed at`, `Last run: <N findings, M filed, K deduped-as-existing>` — that each run's own write fully replaces. This has no way to answer "how many findings has `ultra-review` filed in total" or "which AI model's commits produce the most filed findings" without manually reconstructing history from every past edit to issue #355's body, which GitHub does not expose as structured data. #430 asked for both a running cumulative total and a per-model breakdown, attributing each filed finding's `git blame`d commit to the `Co-Authored-By` trailer(s) it carries. #430's own worked numbers (a `Co-Authored-By` trailer census over `git log`) did not fully reproduce against a refreshed baseline, but the qualitative shape held: most commits carry no trailer at all, a handful of named models/agents account for the rest, and squash-merge concatenation means a single landed commit can repeat one contributor's trailer line several times without that meaning several distinct contributors.
- Decision: Extend the checkpoint body (delimiters unchanged) with three new lines — `Counting started: <sha> at <timestamp>` (written once, never rewritten), `Cumulative: <R> runs, <F> findings, <M> filed, <K> deduped-as-existing` (only a run whose write actually lands increments it), and `Cumulative by model: <name>: <count>, ..., unattributed: <count>, ambiguous: <count>` (bucket shown only once nonzero, sorted alphabetically case-insensitive with the two fixed buckets always last). `SKILL.md` step 2's parse routine tolerates the old three-line format by treating every cumulative field as absent/zero; the very next write — bootstrap or migration — converges on the identical new steady-state shape, so there is no third transitional format. A new `SKILL.md` step (inserted between the existing "Publish" and "Advance the checkpoint" steps, renumbering the latter from 8 to 9) attributes each *filed* finding: `git blame -L <line>,<line> --porcelain <default-branch-tip>` (no `-w`, no `-M`/`-C` — copy-detection would credit whoever wrote a line's text first, not whoever is responsible for it landing in its current flagged form) resolves the blamed commit; `git merge-base --is-ancestor <blamed-sha> <checkpoint-sha>` decides whether that commit predates the reviewed range (bucket `unattributed`, crediting no model) or falls inside it, in which case `Co-Authored-By` trailers are parsed with `re.compile(r'^[Cc]o-[Aa]uthored-[Bb]y:\s*(.+?)\s*<', re.MULTILINE)` and deduplicated: zero distinct names is `unattributed`, exactly one is that model (unless the name contains a literal `,` or `:`, which cannot serialize into the `Cumulative by model` line and folds into `ambiguous` instead — it was resolved, just not safely serializable), two or more distinct names is `ambiguous`. The renumbered checkpoint-write step gets two independent concurrency mitigations for this project's documented concurrent background actor (D-078): a fresh `gh issue view` read immediately before `gh issue edit`, with this run's own delta added to that fresh read rather than to step 2's stale read (narrows, does not eliminate, the lost-update window); and a sha-comparison abort — if the fresh read's `Last reviewed commit` no longer matches what step 2 read, a concurrent run's write has already landed, the reviewed ranges may overlap, and this run does not write the checkpoint at all, leaving it exactly as found.
- Alternatives: splitting this into "Part 1: cumulative counters" / "Part 2: per-model attribution" (rejected — both additions share one delimiter pair, one parse routine, one write routine, and #430's own wording asks for the breakdown inside the same cumulative block, so Part 1 could not ship a stable body format without already knowing Part 2's line shape); a local tracked checkpoint file instead of continuing to extend the GitHub-native issue (rejected for the same reason D-147 already rejected it — this project's ephemeral-worktree lifecycle does not survive a local file, and a commit-per-run under protected-`main` is unwanted churn); falling back to a commit's own `%an`/`%cn` author/committer identity when no trailer is present (rejected — most commits on this repository carry no trailer at all, so this would silently attribute the majority of defects to the repository owner rather than reporting them as genuinely unattributed); backfilling attribution for the three pre-existing findings #430 itself cited (#422/#423/#424) or any run before this feature's own first write (rejected — `git blame` on their cited lines today would attribute them to whoever last touched an already-stale citation, not to the actual root cause, which is actively wrong rather than merely missing; and even where backfill would be attribution-correct in principle, the historical blame result *at filing time* is not preserved anywhere and cannot be soundly reconstructed from today's tree); a true compare-and-swap checkpoint write via a conditional `If-Match` header (rejected — `gh issue edit` exposes no conditional-write flag today, and a bespoke raw-`gh api` PATCH path is a larger, separately-justifiable change this issue did not ask for).
- Consequences: a concurrency-aborted checkpoint write is a **permanent, accepted undercount** of the `Cumulative` counters, not merely a delayed sha advance — no later run recovers a declined write's own contribution, because no later run knows those numbers once this step declines to record them. This is deliberate: the alternative (guessing at a possibly-overlapping merge and risking double-counted findings) is worse, and a future reader who notices `Cumulative: M filed` reading lower than `gh issue list --label ultra-review --state all`'s true count should read that gap as the mitigation working as designed, not as a defect to silently "fix" by reconstructing the missing numbers after the fact. `SKILL.md` grows one new step (per-model attribution) and gains new prose in the parse/write steps and the `## Output` section; `.claude/skills/ultra-review/evals/evals.json` grows from four cases to six; `scripts/run_alpha_skill_evals.py`'s `EXPECTED_RUNNERS["ultra-review"]`, `ULTRA_REVIEW_CONTRACT` (three phrases to five), and `run_ultra_review_case`'s dispatch table, plus `scripts/validate_agent_assets.py`'s `ALPHA_EVAL_RUNNERS["ultra-review"]`, all gain the same two new runner names — mirroring D-147's own registration pattern unchanged. `scripts/test_run_alpha_skill_evals.py` gains direct unit tests for the two new oracle functions; its existing generic contract-phrase and unknown-runner tests need no change. This introduces no new public-write authorization boundary: `ultra-review`'s writes remain exactly what D-147 established — GitHub issue-body edits and GitHub issue creation, no repository commit, no pull request. D-147's own "a four-case `evals.json`" phrase is an accurate historical record of D-147's own Consequences at the time it was accepted and is intentionally left unedited here, per this project's "never silently rewrite an accepted decision" rule.
