## D-142: `issue-implement`'s step 4 implementation runs in a dispatched `Agent`, not the orchestrating session's own context

- Status: accepted
- Context: `issue-select`'s standing autopilot loop is meant to carry many issues through `issue-to-plan` -> `issue-implement` -> merge in one continuous session, per D-127's own lifecycle-ownership framing and `.claude/skills/gha-watch-ci-pr/SKILL.md`'s closely related rule that a dispatched orchestrator must not stop-and-wait for its own sub-dispatches. Before this decision, `issue-implement`'s step 4 (write the code and tests, run builds, run the full local gate set) executed directly in the orchestrating session's own context — every file read, every edit, every `cargo build`/`test`/`clippy`/`llvm-cov` invocation and its output accumulated there. One real run of issue #181 (`float(x)` as a builtin) demonstrated the cost directly: the implementation step alone, plus a coverage-gate root-cause investigation (comparing baseline-vs-diff `cargo llvm-cov --json` output, several failed HTML/lcov-parsing attempts) and a full D-068 review fix cycle, consumed the large majority of that session's context, leaving comparatively little headroom for the loop's own next iteration. D-127's own prescribed mitigation for exactly this — agents "compact the session... proactively" at task checkpoints — turned out not to be an available capability at all; the correction appended to D-127 above (recorded as part of this same change) documents the direct research (Claude Code's hooks documentation, this environment's own `CronCreate`/`ScheduleWakeup` scheduling primitives) confirming no hook, setting, CLI flag, or SDK call can trigger `/compact`/`/clear` or spawn a fresh session from inside a running one. The one primitive genuinely available from inside a running session that isolates context per unit of work is agent dispatch: a freshly-spawned `Agent` gets its own clean context, and only its final report — not its own tool calls and their output — returns to the dispatching session.
- Decision: `issue-implement`'s step 4 dispatches the actual implementation (reading and editing source, writing tests, running the full local gate set) to a freshly-spawned `Agent`, working inside the same task branch and worktree the orchestrating session already created in step 1's D-021 preflight — so the dispatched agent's commits are the orchestrating session's own committed work, not something foreign to it. The dispatching session gives it a self-contained brief (the plan's own text or issue-comment URL, the task branch/worktree, which D-080/D-103 staged-pattern branch applies if any — a classification the orchestrating session itself makes while reading the plan in step 3, since it decides how many pull requests the run opens — and the exact gate commands/thresholds) and expects a compact report back (files changed, gate results, plan deviations), not a full transcript. Step 5's D-068 review fix rounds resume that same dispatched agent (`SendMessage` to its own agent id, which resumes it with full context of the code it just wrote) rather than fixing findings in the orchestrating session's own context or re-dispatching a stateless fresh agent each round; a fresh dispatch is the fallback only once the original agent's run has already ended and cannot be resumed.
- Alternatives: rely on Claude Code's own automatic context compaction as the sole mitigation (rejected as insufficient alone — it already runs transparently regardless of this decision, per the harness's own stated behavior, but it compacts by token-size threshold, not at clean task boundaries, so it does not by itself bound how much of a single task's own grind — file reads, build/test output, a multi-round review-fix cycle — lands in the orchestrating session's context before that threshold is even reached); end and externally restart the session at each task boundary (rejected as the only mechanism that would give a genuinely fresh context per task, but confirmed to require action outside the running session's own agency — no session can restart itself with a clean context from the inside — making it unusable as a fully autonomous, unattended loop mechanism); route the review loop's fix rounds through fresh, stateless agent dispatches each round instead of resuming the same one (rejected as needlessly discarding the original implementer's own working knowledge of the code it just wrote, forcing every fix round to re-derive context an already-running agent already has).
- Consequences: `issue-implement`'s own workflow text (`.claude/skills/issue-implement/SKILL.md`, step 4 and step 5) and `docs/AGENT_TOOLING.md`'s summary paragraph both describe this dispatch pattern explicitly. No new authorized-write, stop condition, or eval oracle is introduced — this is process guidance for how the existing steps 4/5 are carried out, not a new decision the skill makes, so `scripts/validate_agent_assets.py`'s `validate_alpha_skill_contracts` (which checks eval-set completeness, not literal-phrase coverage of every paragraph) needs no change. The orchestrating session still owns everything that genuinely requires its own git/GitHub state directly: re-fetching and rebasing, pushing, opening and monitoring the pull request, invoking and reading the D-068 pinned reviewer itself, and merging. A future session finding this pattern insufficient (e.g. the dispatched agent's own report still grows unmanageably large for very big implementations) should record that finding and its own resolution as a correction to this entry, not silently revert to direct in-session implementation.
