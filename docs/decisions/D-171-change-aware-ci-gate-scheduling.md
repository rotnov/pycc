## D-171: Change-aware CI gate scheduling
- Status: accepted; the exact reviewed checker and self-test are active as of 2026-08-15, while the CI workflow successor remains staged and does not activate change-aware scheduling yet.
- Context: D-014 made 100% line and region coverage a hard merge invariant and expressed its scheduling as `cargo llvm-cov` gating every pull request. The same complete compiler, cross-platform, performance, and Pages topology consequently runs for documentation and other changes whose exact paths cannot affect those gates. That delays feedback and consumes runner capacity without adding evidence, while trigger-level path filters cannot be used because they would omit the required `ci-gate` context. The skip decision therefore needs an always-run, reviewable, fail-closed authority inside CI rather than at workflow-trigger level.
- Decision: Supersede only D-014's sentence that schedules the coverage gate on every pull request. An always-run classifier may mark the compiler, Pages, and agent-heavy categories irrelevant from the pull request's exact changed paths; unknown, empty, malformed, or unsupported input selects the complete topology. A selected heavy job must succeed, and an unselected heavy job must be skipped. The always-run required `ci-gate` fails closed unless the classifier and governance jobs succeed and every conditional job matches that truth table. Compiler-relevant pull requests still run the coverage job at exactly 100% lines and 100% regions over the entire workspace, inside the isolated `nobody` sandbox, with the same pinned tools and documented whole-file exemptions. The Tier-1 native matrix, cross-compilation build and verification, paired frontend performance measurement and gate, and both Pages quality gates remain required whenever their reviewed inputs can change. Pushes to `main` always select the complete topology so post-merge evidence retains every gate. The base-owned `audit` check remains required and unchanged.
- Alternatives: GitHub Actions trigger-level `paths` filters were rejected because a filtered pull request would never emit the required `ci-gate` context. Moving the full topology only to `main` or a schedule was rejected because compiler changes would reach `main` before coverage, Tier-1, cross-compilation, and performance evidence existed. Treating any skipped job as success was rejected because classifier failure or condition drift could then silently suppress a required gate.
- Consequences: Documentation-only and other exactly classified pull requests may receive faster feedback after the staged CI successor is activated through D-103's base-owned sequence. Changes to the workflow, classifier, classifier tests, or an unknown path select every heavy category. Every compiler input also selects the offline alpha skill evals because they execute the freshly built compiler and bind its current diagnostics/backend boundaries, including D-072. This decision does not lower either coverage threshold, narrow the workspace denominator, weaken the `nobody` boundary, change tool pins or exemption rules, remove a Tier-1 target, relax cross-compilation or performance evidence, change a Pages budget, weaken the fail-closed required gate, or reduce the full topology executed on `main`. The exact checker and self-test are active; until CI workflow activation, the live workflow continues to run its existing every-pull-request topology.
