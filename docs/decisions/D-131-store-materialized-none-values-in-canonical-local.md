## D-131: Store materialized `None` values in canonical local and module slots

- Status: accepted (closes issue [#242](https://github.com/rotnov/pycc/issues/242); D-130 is reserved by concurrent PR #313)
- Context: the frontend accepts ordinary Python assignments whose right-hand side has `Ty::None`, including `y = xs.append(2)`, `result = values.add(2)`, and the result of a user function declared `-> None`. Codegen already preserves each operation's side effects and materializes D-075's canonical LLVM `i8 0` unit carrier, while name loads and printing retain the static `Ty::None` distinction from `bool`. Storage alone remained incomplete: `collect_stmt_bindings` excluded `Ty::None`, so a function-local assignment reached `emit_assign` without a predeclared slot and panicked; adding it there alone would make the equivalent module assignment reach `declare_module_globals`, whose type match also lacked `Ty::None` and would panic. D-074's consequence that general nested `None` values remained outside D-072 described that earlier backend limit, while D-075 named only parameter ABI and parameter entry slots.
- Decision: use the existing canonical LLVM `i8 0` unit carrier for ordinary function-local and module-global `Ty::None` assignment slots. Collect `Ty::None` assignment targets with the other storable MIR types; allocate module globals as zero-initialized `i8`; and retain each slot's separate initialized flag so the carrier's zero value can never make a read-before-assignment look valid. The MIR expression and `StorageSlot` static type, not the physical width or `Scalar::Bool` carrier variant, controls Python-visible `None` behavior. This decision supersedes only D-074's broad statement that general nested `None` values remain outside D-072 and extends D-075's parameter-only storage scope. D-072 itself remains accepted unchanged: using `print()`'s own result as a nested expression still takes its explicit named rejection and does not reach the storage path.
- Alternatives: reject every `None` assignment with a new spanned frontend diagnostic (rejected because it would introduce a pycc-only restriction after the backend already implements the value carrier and observable behavior); special-case only `list.append` (rejected because user-function and `set.add` results have the identical checked type and carrier, so storage policy belongs at the type boundary); add a heap singleton, pointer representation, or new tagged union (rejected because `None` carries no payload here and identity/optional-union work is outside this issue); relax D-072 and lower nested `print()` too (rejected because that separate accepted boundary is unnecessary to fix any currently materialized non-`print` result).
- Consequences: assigning, reading, returning, testing, and printing an already-materializable `None` result can now use ordinary local or module storage without an internal compiler panic; `list.append` and `set.add` side effects occur before the zero carrier is stored, and printing the stored name renders `None`, not `False` or `0`. Local/global read-before-assignment safety remains governed by D-074's independent initialization flags. `None` still has no heap object, optional/union representation, general identity/equality surface, or `dict.get` no-default support, and `value = print(...)` remains D-072's deliberate exit-101 boundary.
