## D-150: Hand-authored `EXPLANATIONS` const slice as `pycc explain`'s content source, not a runtime `docs/DIAGNOSTICS.md` parser (#366, Part 1 of #338)

- Status: accepted
- Context: `pycc explain CODE` (`Command::Explain` in `src/main.rs`) previously fell into the same generic "not yet implemented" stub arm as `test`/`clean`. Implementing it for real required choosing where its long-form content (a summary, a longer explanation of the real trigger condition, and a worked example) comes from. `docs/DIAGNOSTICS.md`'s "Initial registry" table only carries a `Code | Severity | Message (short form)` row per code — there is no existing long-form prose or worked example anywhere in the repository to parse; any content source has to be authored from scratch regardless of mechanism. At the time this issue was planned, the registry held 41 codes; by implementation time, open PR #360 had merged and added a 42nd (`T0041`, definite-assignment tracking, issue #118 Part 1), which this PR's `EXPLANATIONS` table and completeness test cover too — re-verified against `docs/DIAGNOSTICS.md` immediately before this ADR was written, after rebasing onto that merge.
- Decision: a hand-authored `const DiagnosticExplanation` slice, `EXPLANATIONS`, in a new module `crates/pycc_diag/src/explain.rs`, looked up by `.iter().find(...)` (`find`) — not a runtime parser over `docs/DIAGNOSTICS.md`. This mirrors `pycc_std::REGISTRY`/`resolve_symbol` (D-136), which already resolved the identical design question — "a small hand-authored table, looked up by exact string match" — for stdlib symbol resolution: that registry's own doc comment states the reason explicitly, "fewer than two dozen entries, so no `HashMap`/`OnceCell`/macro-generated dispatch table is warranted, and a linear scan keeps every branch trivially unit-tested (D-014's 100% line/region coverage gate applies to this crate too)." The same reasoning applies here at a larger but still small scale. Concretely, under D-014's `--fail-under-regions 100` gate: a `match code { "T0001" => ..., "T0002" => ..., ... }`-shaped dispatch table compiles to one region per arm, so covering it would require one test execution per code (41, and growing) before even asserting content; a `const` slice linear-scanned by `find` has exactly two regions regardless of table size — "found" and "not found" — both already required for functional correctness (a real code, and an unrecognized one), so the coverage gate imposes no proportional cost as the table grows. A markdown parser's own failure modes (a missing code cell, a malformed severity word, a row with the wrong column count, an unreadable file) would additionally be new regions in this repository's own source that D-014 would then require dedicated malformed-fixture tests to exercise — disproportionate surface for a Part 1 CLI-subcommand issue, and avoided entirely by not having that code path at runtime.
- Drift prevention: a test-only completeness check (`explain::tests::completeness_test_covers_every_registered_code_and_severity`), not a runtime mechanism. It reads `docs/DIAGNOSTICS.md` at test time via a `CARGO_MANIFEST_DIR`-relative path (the same pattern `tests/conformance.rs` already uses for fixture paths), extracts each registry row's code and severity cells with a line-oriented scan scoped to the "## Initial registry" section (the "## Code ranges" table above it also has a backtick-quoted first cell and would otherwise be mistaken for registry rows), and asserts both directions: `EXPLANATIONS`'s code set exactly equals the documented registry's code set, and every shared code's severity matches, after normalizing the documentation's severity cell to its leading word before any `"→"` (so `"warning→error"` compares as `"warning"`) — written generically, not as a single hardcoded `E0106` special case, so a future PR adding another escalating-severity code needs no matching special case in this test. The parsing lives entirely in `#[cfg(test)]` code and uses `.expect()`/indexing directly on this repository's own known-good file rather than a fallible helper with an `Err`/`None` arm the test itself never exercises, so there is no dead branch for D-014's coverage gate to require a fixture for (the same pattern `tests/slice0.rs` already uses `.unwrap()`-ing `serde_json::from_str` inside a test body). `E0106`'s registry entry is documented as `warning→error` (a future PR is expected to escalate it to a hard error; the `Severity` enum has only `Error`/`Warning`, no third state) — its `EXPLANATIONS` entry carries `severity: Severity::Warning`, its current, initial documented state, and its `explanation` text says so explicitly.
- **Ongoing obligation this decision creates**: every future PR that adds a new code to `docs/DIAGNOSTICS.md`'s registry table must add a matching `EXPLANATIONS` entry (summary, explanation, worked example) with the correct severity in the same PR, or the completeness test fails CI immediately. `docs/DIAGNOSTICS.md` itself carries a pointer sentence to this effect next to the registry table, so a contributor editing that table sees the obligation from the doc they are already changing, not only from `explain.rs`'s own source. This is why the decision is recorded as an ADR rather than only as a code comment (contrast `pycc_std::REGISTRY`, whose own equivalent doc comment cites D-014/D-136 inline without a dedicated ADR — that registry has no drift-guarded sibling document requiring synchronized edits the way `explain.rs` now does against `docs/DIAGNOSTICS.md`).
- Forward compatibility with #337 (not a prerequisite): #337 proposes a canonical Rust-side source for diagnostic *codes*. `DiagnosticExplanation { code, severity, summary, explanation, example }` is a strict superset of what such a canonical registry would need for its own `code`/`severity` fields, so #337, if and when it lands, can either subsume `EXPLANATIONS` directly or keep it as a satellite next to whatever canonical registry it introduces — no schema break either way.
- Output shape: `pycc explain CODE [--format human|json]` — a new `--format`/`OutputFormat` flag on `Command::Explain` (`src/cli.rs`), deliberately not reusing `check`'s `--error-format`/`ErrorFormat`, since `explain`'s output is never an error. JSON output (`render_explanation_json`) adds a `"kind": "diagnostic_explanation"` field that `check`'s own diagnostic-occurrence JSON schema does not have and must not gain here (that schema's codes and JSON structure are intentionally stable per `docs/DIAGNOSTICS.md`'s own quality bar) — the two schemas both happen to start with `"format_version": 1` but describe unrelated things (an occurred diagnostic with spans vs. a code documented in the abstract), and `"kind"` is the disambiguator for a consumer holding a bare JSON blob with no side channel. Exit `0` on a recognized code in either format; exit `2` with a plain stderr message on an unrecognized code, regardless of `--format` — an unrecognized code is an out-of-band invocation failure, not a diagnostic occurrence, matching how `check`'s own out-of-band `FrontendFailure::Input` class is never subject to `--error-format` either. Lookup is an exact, case-sensitive string match (every registered code is always uppercase).
- Alternatives: a runtime parser over `docs/DIAGNOSTICS.md` (rejected — see Decision above: strictly more work and more D-014-relevant surface than the same content authored directly as Rust data, for no benefit since the prose still has to be authored somewhere either way); ship `EXPLANATIONS` with only a handful of domain-representative codes and file a follow-up issue for the rest (rejected — `docs/DIAGNOSTICS.md`'s own opening line already states the target contract, "documented via `pycc explain`," for every registered code, not a sample, and the completeness test makes "populate all of them" and "populate a sample" the same amount of *mechanism* work, so a follow-up issue would not be an independent code seam — exactly what AGENTS.md's decomposition rule says not to split); reuse `check`'s `--error-format`/`ErrorFormat` flag name and type for `explain` (rejected — `explain`'s output is never an error; reusing the name would be actively misleading, and reusing the type would make an `explain`-specific field named `error_format` hold a value that is never an error either).
- Consequences: `crates/pycc_diag/src/explain.rs` is a new module (`pub mod explain;` in `crates/pycc_diag/src/lib.rs`) with `DiagnosticExplanation`, `EXPLANATIONS` (42 entries at this PR, one per code currently in `docs/DIAGNOSTICS.md`'s registry, including `T0041`), `find`, `render_explanation_human`, `render_explanation_json`, and their own unit tests plus the completeness test above. `src/cli.rs` gains `OutputFormat` and `Command::Explain`'s new `format` field; `src/main.rs`'s `explain` function replaces `Command::Explain` in the stub arm (leaving `Command::Test | Command::Clean` there). `tests/slice0.rs` gains integration tests covering one domain-representative code per `docs/DIAGNOSTICS.md` range in both formats, plus the unrecognized-code exit-2 path in both formats. `docs/CLI_SPEC.md` documents the new `--format` flag and a new "`pycc explain` output contract" section cross-referencing the existing diagnostics-output-contract section. `docs/DIAGNOSTICS.md` gains a pointer sentence to `explain.rs`'s obligation. `docs/ROADMAP.md`'s CLI status row drops `explain` from its "not yet implemented" clause and gains a sentence describing the new capability (also correcting an adjacent, pre-existing error in `.claude/skills/pycc/SKILL.md`'s own not-implemented sentence, which incorrectly listed `init` there too — `init` has been implemented since #237/#256). `docs/SPEC.md`'s `docs/DECISIONS.md` summary line extends to include this entry.
