## D-121: dict[K, V]/set[T] v0.2 representation is a dense insertion-ordered array with linear-scan lookup, not a hash table

- Status: accepted
- Context: `docs/RUNTIME.md` (line 11) and `docs/TYPE_SYSTEM.md` (line 56) both already say "swiss table" for `dict`, and the v0.2 design doc's own PR breakdown (item 4, `docs/superpowers/specs/2026-07-28-v0-2-collections-generics-design.md` §3) explicitly names `set[T]`'s representation as PR-11's own ADR to record. Neither doc ever elaborates what "swiss table" means beyond the name -- no open-addressing scheme, probe sequence, or group-metadata layout is specified anywhere in this repository.
- Decision: v0.2 ships `dict[str, int]`/`set[int]` as a dense, insertion-ordered array (`Vec`-backed) with **linear-scan** lookup, using the equality-comparison primitives `pycc_codegen` already has for each scalar type (`pycc_rt_str_cmp` for `dict`'s `str` keys, raw `i64` equality for `set`'s `int` elements). No hash function, no probe sequence, no load factor, no resize/rehash logic exists in this PR's own runtime objects. `dict`'s insertion-order guarantee (`docs/PYTHON_STANDARDS.md`'s dict-insertion-order row) is trivially true of a dense array by construction. `set`'s CPython-matching non-guaranteed iteration order is likewise trivially satisfied -- our own array happens to iterate in insertion order, which is *a* legal order Python permits, not necessarily *the* order CPython's own hash table would produce for the same literal (see D-123 below for why no fixture may assert on this).
- Alternatives considered:
  - A real open-addressed hash table (the literal "swiss table" the docs name) -- rejected for v0.2: this PR's own scope is small, fixed-arity literal construction plus at most one post-construction mutation operation (`dict`'s `d[k] = v`); a full hash table's probing/resize machinery is pure implementation risk for a data-structure property (O(1) amortized lookup) that no v0.2 fixture or benchmark actually measures. Per D-057's "simplest correct thing" precedent (already cited by D-089), the dense-array-plus-linear-scan design is strictly simpler, is trivially correct, and defers zero user-visible guarantee -- `dict`'s insertion order and `set`'s membership behavior are identical either way at the scale this PR's own fixtures exercise.
  - Reusing `pycc_rt`'s existing per-scalar comparison functions generically via some kind of type-erased "compare any two `Scalar`s" runtime function -- rejected: pycc is statically typed end-to-end, and codegen already knows a given `dict`/`set`'s key/element type at every call site, so a type-erased runtime dispatch would add an indirection this static information makes unnecessary.
- Consequences: `docs/RUNTIME.md`'s "swiss table" wording gets a "Current state (through PR-11, D-121)" caveat (Task 10 of this plan), mirroring `list[T]`'s own "Current state (through PR-10, D-105)" pattern at line 10 -- the real hash-table design remains the v1.0 target, not silently abandoned. A future PR that needs true amortized-O(1) lookup (a `dict`/`set` used at a scale where linear scan is a real cost) replaces `PyDictObj`/`PyIntSetObj`'s internals without changing either type's own public FFI surface (`pycc_rt_dict_get`/`_set`/`_len`, `pycc_rt_int_set_add`/`_len`), so callers in `pycc_codegen` do not need to change.
