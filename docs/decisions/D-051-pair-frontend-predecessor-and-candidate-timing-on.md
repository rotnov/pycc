## D-051: Pair frontend predecessor and candidate timing on one hosted runner

- Status: accepted (staged successor to D-048's cross-run timing transport and D-042's mean estimate; D-044's greater-than-2% hard merge threshold and isolated review boundary remain unchanged)
- Context: D-048 correctly made baseline provenance exact and fail-closed, but its absolute Criterion estimate comes from a prior `main` runner while the pull-request estimate comes from a different hosted runner. That leaves machine-to-machine scheduling and host variation indistinguishable from compiler work. PR #107 exposed the defect with a documentation-and-Ruby-test-only head that changed no Rust source, benchmark, manifest, lockfile, or active workflow. Against the exact-base estimate of `7673.79 ns`, three complete workflow attempts measured `13875.91 ns` (`+80.82%`), `8657.32 ns` (`+12.82%`), and `8233.64 ns` (`+7.30%`). The third run's narrow 95% confidence interval (`8160.75`–`8316.24 ns`) shows that Criterion was internally stable on that host while still far from the predecessor host. Re-running until one sample happens to fall below 2% would select a convenient machine rather than prove the patch fast enough.
- Decision: supersede D-048's cross-run artifact comparison with a paired measurement, using the same two-phase workflow trust process as other byte-exact CI changes. The staging phase authorizes both the active D-048 digest and the inert full-workflow fixture `tests/fixtures/d51-paired-ci.yml`; it does not change `.github/workflows/ci.yml`. A separate fresh-base activation pull request must replace the active workflow byte-for-byte with that reviewed fixture and retire the D-048 digest and fixture. The paired `frontend-perf-measure` job resolves the predecessor exclusively from `pull_request.base.sha` or `push.before`, rejects missing, zero, and unsupported-event inputs, checks out both that exact SHA and `github.sha` with pinned actions and no persisted credentials, and verifies both revisions. Before executing untrusted benchmark code it requires the benchmark-definition and build-configuration contract to be identical: `benches/`, the root `Cargo.toml` and `Cargo.lock`, both supported root toolchain filenames (`rust-toolchain.toml` and `rust-toolchain`), root `.cargo/`, every workspace-member `Cargo.toml`, and every tracked local `build.rs`. It runs the predecessor Criterion benchmark first on `macos-14` and uploads that one JSON file through the pinned v4 artifact action before candidate code runs. It then benchmarks the candidate on the same runner with a separate Cargo target directory and uploads its one JSON file separately. The isolated `frontend-perf-gate` checks out the comparator from the exact predecessor, hash-verifies the dedicated reviewed median comparator and its tests, binds each download to the exact artifact ID returned by its trusted upload step so deletion or replacement fails closed, requires exactly two regular-file estimates with no symlinks or extra files, and applies the unchanged greater-than-2% threshold. This statistic is part of the reviewed transition because a local paired validation of identical Rust and benchmark code produced a `-2.94%` mean difference when one side accumulated 15 severe high outliers, while the medians differed by only `-0.56%`. Both jobs remain literal-success dependencies of `ci-gate`.
- Alternatives: keep re-running the existing job until a favorable host passes (rejected as selection bias); increase Criterion's within-run sample or measurement duration (rejected as insufficient for the observed between-host shift, whose confidence interval was already narrow); lower or average away the 2% threshold (rejected because D-044 defines it as a hard product invariant); compare against the newest convenient `main` artifact (rejected because it loses exact-predecessor semantics); require a self-hosted benchmark machine (deferred because the repository has no reviewed, available self-hosted runner or operating procedure).
- Consequences: the staging commit still runs and documents the active D-048 artifact gate; the paired workflow is inert until its separate byte-exact activation merges. Activation needs no administrative variable or missing-baseline bootstrap because every run carries its own exact predecessor/candidate pair. After activation, old cross-run artifacts remain historical audit evidence but no longer determine merge outcomes; each run's sealed `frontend-perf-previous` and untrusted `frontend-perf-current` artifacts retain the two same-run inputs for 90 days. Measuring two revisions adds benchmark time, removes cross-machine variance, and makes isolated high outliers less able to decide the gate without weakening the threshold or comparator isolation. A change to any bound benchmark-contract path is deliberately fail-closed, even when a manifest or lockfile change is otherwise a legitimate implementation dependency update: it requires its own reviewed gate transition instead of silently redefining the performance test inside an implementation pull request.
