## D-244: Add a hosted CPython extension-module artifact mode and pull the C-API interop core ahead of v0.5/v0.6

- Status: accepted (owner direction of 2026-09-12 on #1014; planned contract, no current compiler behavior is claimed)
- Amendment (2026-09-12): for the `ext` mode only, rule 7's clause that an integer of any magnitude conforms is narrowed, and with it rule 4's "rule 4 applies unchanged" for that case: an `int` argument or result outside the inline-integer range [-2^62, 2^62-1] (D-061/D-141) raises `OverflowError` at the wrapper until #1040 gives `pycc_rt` a bigint boundary. Rule 1 is unchanged.
- Amendment (2026-09-13): two narrowings for the `ext` mode only, both from Part 2 of #1037 (#1049), which widened the boundary to `str`. First, rule 7's "for a conforming call rule 4 applies unchanged" is narrowed the same way the 2026-09-12 amendment narrows it for magnitude: a `str` argument that has no UTF-8 encoding -- a lone surrogate, which `PyUnicode_AsUTF8AndSize` refuses -- raises CPython's own `UnicodeEncodeError` at the wrapper, propagated verbatim rather than translated into a `TypeError`, because the condition is a property of the value and not of the annotation. The `str` return direction needs no narrowing: a `PyStrObj` provably cannot hold invalid UTF-8, every constructor taking already-valid Rust input. Second, the reference a `str` argument's ingress creates is consumed by the compiled callee's own parameter slot and is never released, so an exported function taking a `str` leaks one `PyStrObj` per call. This is not new to hosted mode: it is D-074's boundary and D-180 residual 2, whose *scope* hosted mode extends from bounded-by-process-exit (a `native` program leaks it once per call until the process ends) to trip-count-linear (a long-lived interpreter accumulates it without bound). The wrapper must not "fix" it with a post-call release: the callee's slot owns the reference, and `decref_str_slot_before_store` already releases it on any reassignment, so a wrapper-side release is a use-after-free. Closing it is callee-side work under v0.5's `pycc_own`, tracked by #1054. Rule 1 is unchanged.
- Amendment (2026-09-13): one narrowing for the `ext` mode only, from Part 3 of #1037 (#1050), which widened the boundary to a `tuple` of `int`/`bool`/`float` elements. Rule 7's admissibility is stated over the *elements*, not over the container: a `tuple` argument conforms when it is a `tuple` (or a `tuple` subclass -- rule 7 is closed against duck typing, not against subtyping, the same reading that admits a `str` subclass) of exactly the declared arity whose every element conforms at its own declared type. Admissibility is over D-116's three element types only: a `tuple` whose declared element type is a container, a nested `tuple`, or `str` is not carried at all -- `str` is carried at a top-level position under the amendment above and is still not a carriable element. Each element carries its own row's narrowings unchanged, including the 2026-09-12 `OverflowError` amendment in both directions. The narrowing proper is to identity, extending the `str` half of the amendment above: the elements are copied out by value, so a returned `tuple` is always an exact `tuple` and identity never survives a crossing -- for a subclass argument, and for an exact `tuple` handed to an identity export alike. #1043 covers this the same way it covers `int`, `float` and `str`. The artifact contract of rule 3 gains one generated symbol per `tuple`-carrying export, `pycc_ext_thunk_<name>`, which exists because pycc's aggregate calling convention is not the platform C struct ABI and so no C declaration of the compiled function could be written: the thunk presents scalars and out-pointers only and the aggregate never leaves the LLVM side. It is an implementation detail of the generated artifact, not a public surface. Rule 1 is unchanged.
- Amendment (2026-09-13): one ownership clarification to the rule-3 artifact contract, from the review of Part 3 of #1037 (#1050). A returned `tuple`'s element words arrive at the generated wrapper *borrowed*, not owned: D-180 rule 6 retains at a `return` only for a scalar value, and the `pycc_ext_thunk_<name>` seam copies each field out of the aggregate without transferring a reference. An export returning a stored tuple whose `int` element is a heap bigint (`saved = (2 ** 62,)`; `return saved`) therefore hands the wrapper a word the module global still owns, and `pycc_ext_pack_int`'s `OverflowError` path releases it -- a refcount underflow, and on the next call a use-after-free inside the host interpreter. The `tuple` egress accordingly takes its own reference with `pycc_rt_bigint_retain` immediately before each `int` element's packer, which is where the pairing stays balanced on every classification. No rule's admissibility or narrowing changes; rule 1 is unchanged.
- Amendment (2026-09-13): two rule-4 deviations from Part A of #1038 (#1063), which converts the four numeric-operator `**` abort paths into D-173 raises. Rule 4's oracle requires an `ext` function to produce the same exception types as the pinned CPython for a conforming call; two of the four converted sites cannot, because for them CPython raises no exception at all and returns a value pycc has no type for. `int_pow` with a negative exponent raises `RuntimeError` where CPython evaluates `2 ** -1` as `0.5`, and `float_pow` with a negative base at a non-integer exponent raises `RuntimeError` where CPython returns a `complex`. Both are pre-existing `pycc_types::numeric_result_type` simplifications (#1068) that were previously process aborts; Part A makes them observable as exceptions without narrowing or widening the domain either one covers, so the deviation is newly *visible* rather than newly introduced. `RuntimeError` is chosen precisely because it is not a class CPython would raise here, so no program can mistake it for conformance. The other two converted sites are conformant and need no deviation: `float_pow` raises `ZeroDivisionError` for a zero base at a negative exponent with CPython's own sentence, and `OverflowError` for a finite pair whose result leaves `float` range. Rules 1, 3 and 7 are unchanged; this amendment is not `ext`-scoped in the sense the four above are -- it states a deviation of the compiled semantics themselves, which the `native` mode carries identically.
- Amendment (2026-09-13): one scope statement from Part A of #1038 (#1063), recorded because it is a deliberate non-change rather than an omission, and because — unlike the four amendments above — it is **not** `ext`-scoped. `Pow` stays in `pycc_codegen::exception::expression_can_set_exception`'s infallible arm, so generated code emits no exception check immediately after a `**`; the raise is observed at the next enclosing D-173 checkpoint instead, and an expression with no following checkpoint inside a `try` body can reach the handler a statement late or, at the top level, let the `0.0`/`0` sentinel be printed before the exception is reported at exit. The `ext` mode narrows this residual but does not remove it. What it guarantees is the *uncaught* direction: the wrapper epilogue emits `if (pycc_rt_ext_pending_type() >= 0) { pycc_ext_raise_pending(); return NULL; }` ahead of every return arm, so an export that does not handle the exception itself can never return a sentinel to the host as if it were a result -- rule 3's artifact contract holds exactly for that direction, with no codegen change. What it does not change is the *late-observation* direction inside the export's own body, which is identical to `native` mode and was measured through a real artifact at this commit. A `try` suite's own end is a checkpoint, so `try: x = a ** b` with the raise as the suite's last statement does reach its handler; but a statement following the `**` *within* the same suite runs first (`x = a ** b` then `y = 1.0`, handler observed with `y == 1.0`), and a second raise before the next checkpoint relabels the first, so `a ** 1024.0` followed by `0.0 ** -1.0` in one suite selects the `ZeroDivisionError` handler rather than the `OverflowError` one. Both are the D-173 checkpoint semantics applied to an expression the classifier calls infallible, not an `ext`-specific defect, and both are strictly better than the process abort they replace. The residual stays open on measurement, not oversight: `tests/fixtures/nbody.py` runs ten `Pow` nodes per hot-loop iteration, and D-084/D-095/D-140 wire per-target speedup floors of 12x/15x/18x/20x into CI, so making `**` a checkpoint adds a thread-local load and a branch to the innermost loop of the benchmark those floors are measured on. Closing it belongs with #1031's removal of the per-call exception TLS check, which changes the cost of a checkpoint rather than paying the current one ten more times per iteration.
- Amendment (2026-09-13): two statements from Part B of #1038 (#1064), which converts the list, set and float-formatting abort paths. First, a rule-4 deviation of the same shape as the 2026-09-13 Part A amendment above, for the `ext` mode only: `int_list_slice`'s three rejected bounds raise `ValueError` (`slice start must be non-negative`, `slice stop must be non-negative`, `slice step must be positive`) and `float_to_str` outside its `1e-4 <= |x| < 1e16` positional window raises `RuntimeError`, where the pinned CPython raises nothing at all for those programs -- it addresses a negative slice bound from the end, reverses on a negative step, raises `ValueError` only for a zero step, and formats any float in scientific notation. These are the pre-existing D-108/D-118 and float-formatter scope cuts, unchanged in substance and only now observable as a catchable exception instead of a process abort; the conformance work is tracked as [#1070](https://github.com/rotnov/pycc/issues/1070) (slice bounds and steps) and [#1071](https://github.com/rotnov/pycc/issues/1071) (float scientific notation). `int_list_pop` on an empty list (`IndexError: pop from empty list`) and `check_set_len_unchanged` (`RuntimeError: Set changed size during iteration`) are conformant and need no deviation. Second, the "sentinel printed before the exception is reported" class this decision's 2026-09-13 Part A amendment already accepts extends to two more observable shapes, both measured on this branch in the `native` and `ext` modes rather than derived: `print(1e20)` writes a bare newline to stdout (the empty-`str` sentinel) before the `RuntimeError` reaches stderr, and because `.pop()` is not itself a `pycc_codegen::exception::expression_can_set_exception` checkpoint, a statement following an empty-list `.pop()` prints its `tag_smallint(0)` sentinel before the enclosing suite's checkpoint observes the pending `IndexError`. Neither is guarded: a `print`-side guard would be a half guard, since an f-string reaches `float_to_str` through the interpolation path instead, and the checkpoint classifier is out of scope for #1038 in the same way Part A recorded. Every sentinel is a *valid* value of its return type (`tag_smallint(0)`, a fresh empty list from `pycc_rt_int_list_new()`, `new_pystr(b"")` -- never a raw `0`, which is not a valid D-141 encoded word, and never `NULL`), which is what makes touching it before the checkpoint safe rather than undefined.
- Context: Every artifact pycc produces today is a whole program: a self-contained native executable whose only runtime is `pycc_rt`, with no libpython and no way to be loaded by a CPython process. D-128 defines the project's only planned interop mode, and it is the mirror image of what a library author needs: pycc stays the host, bundles a pinned CPython 3.14 runtime plus a locked package closure, and owns the whole process. The repository owner's reference use case is the opposite shape — a fully annotated (mypy `--strict`) proprietary library whose hot numeric loops run *inside* an existing CPython process next to numpy, VTK, and torch, imported by code the library author does not control. A one-day probe on that codebase (barycentric point-in-triangle loop, 2M triangles, the same annotated source for every variant) measured CPython 3.13 at 5.2 s, Cython 3.1.6 in pure-Python mode with `annotation_typing` at 3.5 s (1.5×), pycc `--release` at 0.40 s (13×), and C `-O2` at 0.07 s (75×). pycc wins on strictly typed scalar and tuple code because it trusts annotations — native `i64`, stack tuples — where Cython silently falls back to `PyObject*` whenever a type is not one it can specialize; pycc's strict typing turns the same situation into a diagnostic instead of a slow path. The probe also showed that none of that speed is reachable from the reference codebase: pycc can neither *be imported* by CPython nor *import* CPython packages, and natural strictly-typed code still failed on `and`/`or`, `list[float]` (T0034), and tuple-unpacking assignment (tracked by #1017/#1018). A profile of the pycc binary put roughly 35 % of samples in `pycc_rt_exception_active` (the thread-local pending-exception check after every runtime call) and `_tlv_get_addr`, with integer operations routed through `pycc_rt_int_*` runtime calls — headroom that matters once the artifact is a library called from a foreign host. Product sprint 1 (milestone `product-sprint-1`, parent issue #1014, due 2026-10-22) was therefore redirected from the competitive-programming corpus metric to closing this one gap: the owner-direction comment on #1014 records the redirection, and #1025–#1028 are its new parts.
- Decision:
  1. **Two artifact modes.** `native` is today's artifact, unchanged: a self-contained executable linked against `pycc_rt` only, with no libpython dependency. `ext` is new: a CPython extension module (`.so` on Linux/macOS, `.pyd` on Windows) exporting `PyInit_<mod>` for the compiled module, with typed export wrappers that unpack `PyObject*` arguments into native representations and pack native results back. Which functions get a wrapper follows the repository's existing public/private contract rather than a new one: every public module-level function of the compiled module is exported, and a private helper is not exported and is not reachable from the host. That discriminator is not restated here — `docs/TYPE_SYSTEM.md` rule 1 and its v0.1 local-inference subsection own it (a module-level function whose name starts with `_` is a private helper under D-038, which is also what `crates/pycc_hir` already implements), and `T0001` binds exactly that public set to full parameter and return annotations, which is what makes a typed wrapper constructible at all. A module that needs a currently-private function callable from CPython renames it public; `__all__` is deliberately not consulted, because a second export selector could disagree with the one `T0001` enforces and would leave the artifact's CPython API undefined where they differ. An `ext` artifact never bundles or embeds an interpreter and never binds to a specific host installation: on Linux and macOS it leaves its CPython symbols undefined and resolves them from the host interpreter at load time, exactly as every wheel's extension does; on Windows, where PE/COFF cannot leave references unresolved, it links the stable-ABI import library `python3.lib` so those references bind to the host's `python3.dll`, which is the standard wheel practice there too. In both cases the artifact is built against the stable ABI (`Py_LIMITED_API`) at the lowest CPython version the runtime supports, so one artifact serves every later GIL-enabled host version on the target it was built for. The stable ABI removes the host-version axis, not the CPU-ABI one, so an artifact is per Tier-1 **target** — the target triples `docs/ARCHITECTURE.md`'s "Cross-platform (hard requirement)" section enumerates as Tier 1, which are not restated here — and not per operating system: an x86_64 ELF shared object or Mach-O dylib cannot be loaded by an arm64 interpreter on the same operating system. Whether the two macOS triples ship as one universal binary or as two artifacts is a packaging choice #1025 makes; this decision requires every Tier-1 target to be covered, not a particular file count. Free-threaded hosts are out of scope: their stable ABI is the separate `abi3t` contract (PEP 803, the item `docs/PYTHON_STANDARDS.md` defers to the interop boundary), so an `ext` artifact targets GIL-enabled builds only, `#1025` fails a free-threaded host at import time with a clear error rather than loading, and supporting `abi3t` is a later decision that adds a second artifact contract instead of widening this one. What a wrapper does with an argument the host passes that does not conform to the export's annotations is rule 7, which is not restated here.
  2. **One C-API bridge in `pycc_rt`.** The `PyObject*` ↔ native unpack/pack layer, the `object` type that holds a CPython-owned value, and the reference-count discipline at the boundary live in `pycc_rt` and are shared by the `ext` mode and by D-128's embedded mode. Neither mode gets a private bridge.
  3. **Import classification.** The resolver classifies every import as a project module (compiled with the artifact), a `pycc_std` registration (D-128's "native pycc" class), or a foreign module. A foreign import lowers to a runtime `PyImport_ImportModule` call and binds an opaque `object`; attribute access, method calls, and the standard-Python scalar/tuple conversions at the boundary are the supported surface, and an untyped value leaking into typed pycc code remains `I0401`. In `ext` mode D-128's `auto`/`allowlist`/`deny` policies and `--pure` do not apply: the host interpreter owns the environment, and whatever it can import, the artifact can import. Those policies, `pycc.lock`, and the bundled closure remain the embedded mode's contract, unchanged.
  4. **The oracle is unchanged.** The CPython byte-for-byte oracle of `docs/TESTING.md`'s conformance harness (D-242 rule 4; D-097/D-098 for the benchmark-equality lineage) governs the `ext` mode too, at the pinned interpreter version that harness names rather than at whatever version a host happens to run: an `ext` function must produce the same values, exception types, and observable effects as the same source executed by that pinned oracle. Rule 7 scopes that requirement to calls that conform to the export's annotations and defines what the boundary does with a call outside that domain. A later GIL-enabled host is a supported *loader* under rule 1, not a second oracle; raising the conformance language level still requires the versioned gate and superseding decision `docs/SPEC.md` demands, and this decision does not raise it.
  5. **Sequencing.** The interop core — #1025 (extension-module output, typed export wrappers, stable ABI, no bundled interpreter under rule 1's per-platform link contract) and #1026 (foreign imports as opaque `object`) — is pulled ahead of roadmap v0.5 (generators and ownership) and v0.6 (threads); the buffer-protocol bridge (#1027) follows once #1026 shows where the boundary cost really is; the embedded-interpreter executable (#1028, D-128's bundled mode) follows the hosted mode on the shared bridge. `pycc build --lib`'s C-ABI library (v0.9) is unaffected: it remains a third output whose consumers are C/Rust/Go, not a CPython host.
  6. **Sprint metric and kill criterion** (from the #1014 owner-direction comment). The metric is the number of functions of the reference annotated codebase that compile unchanged, plus the speedup of its hot loop versus CPython and versus Cython; the codebase is proprietary, so only numbers are published. The kill criterion, at the unchanged 2026-10-22 date: the reference hot function compiles unchanged as an extension module and runs ≥ 5× faster than CPython when called from CPython.
  7. **The host call boundary.** Rule 1's typed export wrappers face code pycc does not compile, so the hosted mode is the first place in the project where a value no `T0001`-checked call site produced can reach typed pycc code at run time; in `native` mode every caller is inside the compiled program, which is why rule 4's oracle needed no scoping until now. Rule 4's oracle is therefore scoped to **annotation-conforming calls** — those whose arguments satisfy the export's own parameter annotations under the boundary rules `docs/TYPE_SYSTEM.md` already owns, which decide what "conforming" means and are not restated here: its rule 1 (annotations are binding, `T0001`), its rule 4 (no implicit `Optional` and no implicit numeric widening, so an `int` argument at a `float`-annotated parameter does *not* conform), and its type table's `int` row (arbitrary precision, accepting `bool` as a subtype at checked boundaries, D-061/D-141 — so an integer of any magnitude and a `bool` at an `int` parameter both do conform). For a conforming call rule 4 applies unchanged. For a non-conforming one the wrapper raises `TypeError` before the compiled body runs, with no argument mutated and no partial effect left behind — the convention `PyArg_ParseTuple` and every C-API converter already follow, and the only behaviour a wrapper that unpacks into native representations can implement safely. This deviates from CPython deliberately: CPython does not enforce annotations at all (`def f(x: int) -> int: return x + 1` returns `2.5` for `f(1.5)`), while pycc treats an annotation as binding, and reproducing the non-enforcement would need the `PyObject*` fallback path this decision's Context rejects as the Cython shape. The boundary is closed for every way a host call can fail to conform, not only an argument's type: an argument whose type does not satisfy its parameter's annotation, too few or too many positional arguments, `None` at a parameter annotated `T` rather than `T | None`, and — until [#884](https://github.com/rotnov/pycc/issues/884) gives the compiled call surface default values and keyword parameters — any keyword argument, are each that same `TypeError` raised at the wrapper. The exception's message text is not fixed here; #1025 owns it, and NEG-004's CPython-driven harness is where each of these shapes is pinned.
  Relationship to existing decisions: this decision does **not** supersede D-128 — it adds a second mode beside D-128's embedded one and reuses its import-classification and typed-boundary rules (D-128 rules 1 and 4) for the bridge. It narrows every accepted statement that pycc's artifact is always a self-contained executable with no libpython: D-128 POS-003 ("pure artifacts retain the no-libpython guarantee") and its Context sentence that pycc "uses its own unboxed/native representations and no libpython", `docs/RUNTIME.md`'s opening ("the static library linked into every binary ... pure Rust with no libpython"), and `docs/ARCHITECTURE.md`'s "Pure/native-only artifacts use static linking by default" rule. Each of those stays true for the `native` mode and for every `deny`/`--pure` embedded artifact; the `ext` mode explicitly does not carry it, because an extension module is by construction loaded into, and resolves symbols from, a CPython process. The public website's projection of that statement — the canonical pages under `site/`, their Markdown projections, and the prose those pages' checkers pin verbatim — is deliberately **not** updated by this decision: it describes the embedded arm correctly and is incomplete rather than false, and rewriting it requires the four-pin rotation `docs/WEBSITE.md` mandates for every canonical page. #1033 owns that rewrite, and `docs/WEBSITE.md` moves with them: its Purpose section is not one of those projections but the specification that owns the canonical pages, enumerating the claims they make, so narrowing it while the pages still carry the old wording would make the specification describe content that does not exist. #1033 therefore rewrites that section's interop bullet in the same change as the pages it describes. No accepted decision file is edited (D-240); the scoping is recorded here and in `docs/RUNTIME.md`.
- Alternatives: generate C and let Cython or clang compile it (rejected: it discards the LLVM backend and the typed lowering that produced the 13×, and inherits Cython's build-tool coupling); static libpython embedding only, i.e. keep D-128's bundled mode as the sole interop shape (rejected for the reference use case, where another interpreter is the host and pycc cannot own the process; kept unchanged as the embedded mode, #1028); keep the competitive-programming corpus direction (rejected by the owner: no demand was found for whole-binary stdin/stdout programs, and a compile-rate metric does not close the one gap the reference use case has); a version-specific ABI instead of `Py_LIMITED_API` (rejected: it multiplies artifacts per host version and buys nothing the typed export wrappers need); apply D-128's `allowlist`/`deny` policies to `ext` artifacts too (rejected: the host interpreter, not pycc, owns the environment an extension module runs in, so a policy there is unenforceable theatre).
- Consequences:
  - **POS-001:** Annotated code that already compiles with pycc becomes usable from CPython without a source rewrite, and CPython packages become usable from pycc code through ordinary `import`, on the same shared bridge.
  - **POS-002:** The `native` mode and its no-libpython guarantee are untouched; existing conformance, benchmark, and distribution evidence stays valid as-is.
  - **POS-003:** The stable ABI makes one `ext` artifact per Tier-1 target serve every later host CPython version (rule 1: per (operating system, architecture) triple, since the stable ABI removes the host-version axis and not the CPU-ABI one), and the absence of a bundled interpreter (rule 1: undefined symbols on Linux/macOS, the `python3.lib` import library on Windows) removes the interpreter-bundling, licensing, and loader-path work of D-128 NEG-002 from the hosted path.
  - **POS-004:** Building the bridge once in `pycc_rt` means #1028's embedded mode starts from working marshalling code instead of a second implementation.
  - **NEG-001:** `pycc_rt` gains a CPython C-API surface (headers, refcount rules, GIL discipline at the boundary), and every `ext` build depends on the host's CPython headers being available at compile time.
  - **NEG-002:** Foreign values are opaque `object`s: attribute access and calls on them go through the C-API at CPython speed, and the buffer-protocol bridge (#1027) is required before numpy or VTK arrays cross the boundary without a copy.
  - **NEG-003:** Roadmap v0.5 and v0.6 move behind the interop core; `docs/ROADMAP.md` and `docs/DELIVERY_PLAN.md` record the reordering, and `docs/RUNTIME.md`'s interop section must be rewritten when #1025 lands to describe both modes instead of the embedded one alone.
  - **NEG-004:** An `ext` artifact's correctness now also depends on host state pycc does not control — the interpreter version, the GIL, the loaded packages — so conformance for the hosted mode needs a CPython-driven harness in addition to the whole-binary oracle.
  - **NEG-005:** The hosted mode carries a deliberate, enumerable deviation from CPython at exactly one point (rule 7): an `ext` export enforces its annotations where the same source run by the interpreter does not. A host that today passes a non-conforming value to an annotated function gets a `TypeError` from the compiled module where the interpreter returned a value, so replacing a module with its `ext` build is not transparent for callers that rely on CPython's non-enforcement.
