## D-132: Measure the D-084 throughput floor as a median of 3 samples

- Status: accepted
- Context: PR #313 hit a one-off `FAIL: exceeded 50ms threshold (measured 54.55ms)` on `scripts/check_frontend_throughput.rb`'s D-079/D-084 `pycc check` throughput-floor gate; a bare rerun passed. Before treating this as either a regression or accepting indefinite reruns, a dedicated investigation gathered historical evidence: ~209 sampled `build-test-coverage` runs on `main` and active PR branches (2026-08-01 through 2026-08-03) whose throughput step completed successfully showed a stable 14.60-31.92ms range against the 50ms threshold (mean 19.03ms, median 17.88ms), with zero passing runs within 10% of the threshold and zero historical failures of this specific step across the entire sample. The 54.55ms spike does not reproduce anywhere in that record. This matches classic single-wall-clock-sample noise on a shared GitHub-hosted runner (scheduler jitter, co-tenant contention, cold cache) rather than a systemic regression — the check has a wide, stable margin, not one it normally runs close to. D-126/D-129 already established that migrating a similar gate (nbody) from wall-clock to CPU-time measurement did not reduce variance on Ubuntu x86_64 and made it worse on Windows, so switching D-084 to CPU-time was ruled out without re-testing that already-answered question.
- Decision: change `measure_and_check` in `scripts/check_frontend_throughput.rb` to run `pycc check <fixture>` `samples` times (default 3, must stay odd) and gate on the median wall-clock elapsed time rather than a single sample, keeping the same 50ms absolute-floor threshold and the same immediate hard failure if any individual sample's `pycc check` invocation itself exits non-zero. This directly cancels a single-draw noise spike (an outlier can only win if it is not the middle value) while still catching a genuine, sustained regression, which would raise all three samples together. No CI workflow or threshold change is needed — `.github/workflows/ci.yml`'s invocation (`ruby scripts/check_frontend_throughput.rb target/debug/pycc tests/fixtures/pr6_1000_loc_bench.py 50`) is unchanged; neither this script nor `ci.yml`'s job definition is D-103-manifest-protected, so no propose/activate sequence was required.
- Alternatives: switch to CPU-time (rusage) measurement (rejected — D-126/D-129's own evidence on the structurally similar nbody gate already showed this does not help and can hurt cross-platform variance; re-deriving that result here would waste the exact CI time this ADR exists to stop wasting); raise the 50ms threshold for headroom (rejected — the historical data shows headroom is already large and stable, so a higher threshold would only mask a future genuine regression sooner, unlike D-114's frontend-perf-gate threshold raise, which responded to a gate that genuinely ran close to its line); do nothing and rely on manual reruns (rejected — this is what already cost the session real time and prompted the investigation; an unattended median-of-N measurement removes the need for a human or agent to notice and rerun); use hardware performance counters (`perf_event_open`) (rejected without implementation — often unavailable or restricted on hosted GitHub Actions runners and has no cross-platform equivalent for the Windows/macOS legs this same job's matrix also runs; issue #297 already scoped profiler tooling to a local, non-gating diagnostic workflow, not a CI gate mechanism).
- Consequences: `scripts/check_frontend_throughput.rb` now invokes `pycc check` up to 3 times per CI run instead of once, adding a small constant runtime cost (roughly 2 extra ~15-30ms invocations) that is negligible next to this job's multi-minute build-and-coverage steps. A future sustained regression must clear the median of 3 runs, not just avoid one unlucky sample, which is a strictly stronger signal than the prior single-sample design. If historical evidence later shows the median-of-3 design itself still flakes, escalate the sample count or revisit CPU-time measurement citing fresh evidence, but do not do either preemptively without new data.
