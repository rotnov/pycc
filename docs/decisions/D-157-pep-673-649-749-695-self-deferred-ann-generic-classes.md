## D-157: PEP 673 Self, PEP 649/749 self-referential deferred annotations, PEP 695 scoped generic classes
- Status: accepted
- Context: Issue [#387](https://github.com/rotnov/pycc/issues/387) asks for three PEPs that all touch the class-model scope: (1) PEP 673 `Self` as a method return/parameter annotation, (2) PEP 649/749 self-referential deferred annotations (a class name used as a type annotation within its own method bodies), and (3) PEP 695 scoped generic classes (`class C[T]:` with a single type parameter and scalar-only instantiation). All three are v0.3-scope and build on PR-15's class-instance model (D-154) and PR-13's generic-function monomorphization infrastructure (D-133/D-134).
- Decision: Implement in three parts.
  - **Part 1 (Self):** Thread the class name into `annotation_to_ty` (and its callers in `lower_method`/`lower_class`) so that `Self` resolves to `Ty::Instance(class_name)` at HIR-lowering time. No new `Ty` variant is introduced — `Self` is a pure HIR-lowering alias, mirroring how `type` aliases (D-135) are compile-time-only name-to-`Ty` substitutions with no runtime representation.
  - **Part 2 (self-referential deferred annotations):** Make the class name resolvable as a type annotation within the class's own method bodies. This mirrors PEP 649/749's deferred-evaluation semantics for the class-model scope: at HIR-lowering time, the class name is already in scope (it was registered before method bodies are lowered), so `annotation_to_ty` can resolve it to `Ty::Instance(class_name)` without any new deferred-evaluation machinery.
  - **Part 3 (generic classes):** Add `class C[T]:` with a single type parameter and scalar-only instantiation (`C[int](args)`). A new `HirExpr::GenericClassInstantiate` variant is lowered at HIR time when the parser produces a `Subscript` expression whose value is a class name and whose call arguments follow. `pycc_types::monomorphize` pre-scans the entire HIR for all `GenericClassInstantiate` expressions, collecting unique `(class_name, type_arg)` pairs, then monomorphizes each generic class's methods by substituting `T` with the concrete scalar type — reusing PR-13's `substitute_ty`/`substitute_body`/`mangle_generic_instantiation` infrastructure (D-133/D-134). A new `substitute_ty_with_class`/`substitute_body_with_class` pair also rewrites `Ty::Instance("C")` to `Ty::Instance("0gen_C__T_int")` in method signatures and bodies, so MIR/codegen resolve attribute slots against the monomorphized class's substituted attribute types. The monomorphized class definitions are added to `HirModule.class_defs` so `pycc_mir`'s `classes` HashMap can find them. `is_assignable` accepts `Ty::Param` as matching any concrete scalar type during type checking, because `monomorphize` will substitute the type parameter before MIR/codegen.
- Alternatives:
  - **A runtime `Self` type:** Rejected — pycc's static, eager `Ty`-resolution model has no runtime type representation, and `Self` is always resolvable to a concrete `Ty::Instance` at HIR-lowering time.
  - **A new `Ty::Self` variant:** Rejected — would require threading and resolving it through every `Ty`-matching site for no benefit, since the class name is always known at lowering time.
  - **Full PEP 649 deferred-evaluation machinery:** Rejected for this scope — pycc's static model already resolves all annotations eagerly; the only gap was that the class name was not in scope during method-body lowering, which Part 2 fixes by registering the class name before lowering method bodies.
  - **A separate generic-class monomorphization pass (distinct from PR-13's function monomorphization):** Rejected — the existing `substitute_ty`/`substitute_body`/`mangle_generic_instantiation` infrastructure is directly reusable; only the `Ty::Instance` rewrite needed a new helper (`substitute_ty_with_class`).
  - **Vtable/dynamic dispatch for generic classes:** Rejected — pycc's class model is static-dispatch (D-006/D-154), and monomorphization is the consistent approach for generics (D-133).
- Consequences:
  - **Easier:** `Self` and self-referential annotations are now first-class in class method signatures, unblocking patterns like builder methods that return `Self` and linked-list/tree nodes that reference their own class type. Generic classes with a single scalar type parameter compile to real native code.
  - **Harder:** The monomorphization pass now handles both generic functions and generic classes, increasing its complexity. Each unique `(class, type_arg)` pair produces a new class definition and a full set of specialized methods, so code size grows with the number of distinct instantiations (the same tradeoff as PR-13's function monomorphization).
  - **Irreversible:** The `HirExpr::GenericClassInstantiate` variant and the `HirClassDef::type_param` field are part of the HIR contract; removing them would require a coordinated change across `pycc_hir`, `pycc_types`, `pycc_mir`, and `pycc_codegen`.
  - **Remaining gaps:** Two or more type parameters, container-position type parameters (`class C[T]: ... list[T]`), non-scalar instantiation (`C[MyClass]`), `Self` in standalone functions (not method annotations), and PEP 696 defaults all remain unimplemented — tracked as v1.0-target follow-ups.
