## D-089: `Ty` becomes a recursive, heap-boxed enum for v0.2 generics

- Status: accepted
- Context: v0.2 ("collections & generics," see D-088 for its corrected scope) needs `pycc_types`/`pycc_mir`/`pycc_codegen` to represent parameterized types (`list[int]`, `dict[str, float]`, generic function type parameters). Read `crates/pycc_hir/src/lib.rs`'s actual `Ty` definition before assuming a shape: `pub enum Ty { Int, Float, Bool, Str, None, Infer }`, derived `Debug, Clone, Copy, PartialEq, Eq` — a flat, fixed-size, six-variant enum with no recursive/parameterized case, re-exported and consumed 729 times across `pycc_types` (258), `pycc_mir` (87), `pycc_codegen` (352), and `pycc_hir` itself (32). None of that code holds a "generic container type" case today; `list[int]` cannot be represented as a `Ty` value at all in the current design.
- Decision: `Ty` becomes recursive: `Ty::List(Box<Ty>)`, `Ty::Dict(Box<Ty>, Box<Ty>)`, `Ty::Set(Box<Ty>)`, `Ty::Tuple(Vec<Ty>)`, plus whatever case PR-13 needs for a generic function's type parameter (a placeholder/parameter marker distinct from `Infer`, resolved to a concrete `Ty` at each call-site instantiation during monomorphization — this decision does not fully design that case; PR-10/PR-13's own implementer resolves the exact shape against the actual constraint-solving code in `collect_expr_constraints`/`infer_expr_in`). `Copy` is dropped from the derive list (a `Box`/`Vec`-containing enum cannot implement `Copy`); every one of the ~729 call sites that relied on implicit-copy semantics needs an explicit `.clone()` where the borrow checker flags it. `PartialEq`/`Eq` continue to derive correctly (both are implemented for `Box<T>`/`Vec<T>` whenever `T` implements them), so structural type-equality (`list[int] == list[int]`, `list[int] != list[str]`) requires no new logic.
- Alternatives: an arena/interning scheme (`Ty` stays a `Copy` index into an interner that stores the actual recursive structure, the `rustc`-style approach) — rejected for v0.2: it requires threading an interner/arena through every function that currently takes `Ty` by value (a larger, more invasive change than the `Box` version across the same 729 call sites) and buys hash-consed cheap comparisons/copies that this project has no evidence of needing yet — no profiling has shown `Ty` cloning to be a bottleneck, and D-057's "simplest correct thing for the stated scope" precedent argues against building the more complex mechanism speculatively. If a future milestone's profiling shows type-value cloning is actually a hot path (plausible once `pycc_own`'s v0.5 escape analysis or a much larger generic surface exists), interning can replace this representation then as its own superseding decision — the recursive-enum shape does not foreclose that later migration. Keep `Ty` flat and represent generic containers as a separate side-table keyed by some other identifier (rejected — this splits "what type is this expression" across two different lookups depending on whether the type is a container, which every one of the 729 existing call sites would need to learn to check, for no benefit over just extending the enum itself).
- Consequences: the mechanical migration (adding recursive variants, dropping `Copy`, fixing every compile error the borrow checker surfaces from the dropped `Copy` impl) is PR-10's own first task, before any monomorphization logic — it is large in call-site count but low in risk, since the compiler itself enumerates every location needing a fix and the change is behavior-preserving for all six existing scalar variants. `docs/TYPE_SYSTEM.md`'s existing representation table (`list[T]`/`dict[K,V]`/`set[T]`: native vec/swiss-table; `tuple`: inline struct) already specifies the runtime layout PR-10/PR-11 target; this decision is specifically about the compile-time `Ty` value's own shape, not the generated code's runtime layout, which is unchanged. `set[T]`'s exact swiss-table variant (with vs. without CPython's own non-guaranteed ordering) is PR-11's own decision to record, not resolved here.
