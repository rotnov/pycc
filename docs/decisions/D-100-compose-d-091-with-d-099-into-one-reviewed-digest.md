## D-100: Compose D-091 with D-099 into one reviewed digest after D-099 activated first

- Status: accepted; the composed digest and `ci.yml` content below are correct and unchanged, but activation required an additional stage PR the Alternatives section below originally (wrongly) argued was unnecessary -- see the Update note at the end of Consequences
- Context: v0.2 PR-8 branched from `main` while D-091 (release-mode `pycc_rt` build step, relaxed `frontend-perf-measure` manifest classification) was the sole authorized whole-file digest. Before PR-8 could merge, an independent, unrelated concurrent change activated D-099 (a Windows vcpkg binary cache for D-027's libxml2 build, issue #225) directly on `main`, which retired D-091's digest to audit-only status as part of that activation (main's own `scripts/check_roadmap_evidence.rb` explicitly anticipated this and left `REVIEWED_PERF_CI_WORKFLOW_SHA256S` holding only `D99_VCPKG_LIBXML2_CACHE_CI_WORKFLOW_SHA256`). Since `workflow-policy.yml`'s audit job runs the *base* branch's copy of `check_roadmap_evidence.rb` against the PR *head*'s `ci.yml` as data (D-080's trust boundary), this made PR-8's own still-D-091-shaped `ci.yml` fail the audit on every subsequent push, with no relation to anything PR-8 itself had changed.
- Decision: merge `main` (carrying D-099's activation) into the PR-8 branch, and compose a new `ci.yml` combining D-091's changes (the release-mode `pycc_rt` build step on `build-test-coverage` and every `native-build-test` leg, that same release build inside `build-test-coverage`'s isolated sandbox, and `frontend-perf-measure`'s relaxed manifest classification) with D-099's changes (the three Windows-only vcpkg cache steps inside `native-build-test`'s Windows leg, inserted at the exact same point D-099 itself inserted them). The two changes touch disjoint regions of `ci.yml` (D-091: `build-test-coverage`/every `native-build-test` leg's release-`pycc_rt` step, plus `frontend-perf-measure`; D-099: `native-build-test (windows-latest)`'s LLVM-install section only) and compose without any semantic interaction -- verified by a clean `git merge` with no conflicts inside `ci.yml` itself (only the surrounding docs/scripts needed manual resolution). A new digest constant, `D100_COMPOSE_D91_D99_CI_WORKFLOW_SHA256`, is computed over the composed file and becomes the sole entry in `REVIEWED_PERF_CI_WORKFLOW_SHA256S`; `D91_RELAX_FRONTEND_PERF_MANIFEST_CI_WORKFLOW_SHA256` and `D99_VCPKG_LIBXML2_CACHE_CI_WORKFLOW_SHA256` both remain defined as historical audit evidence, exactly as D-090's and D-084's own retired digests do.
- Alternatives: wait for a separate stage-then-activate PR pair, matching D-090→D-091's and D-091-staging→D-099's own two-PR pattern (considered -- rejected only because this composition is happening inside PR-8's own branch before PR-8 has merged at all, so there is no separate "activation PR" distinct from PR-8 itself; the stage/activate split exists to protect `main`'s own `pull_request_target` trust boundary from a PR that edits `ci.yml` and its authorizing digest in the same commit, which is exactly what this decision still avoids: the digest is added in a state where `ci.yml` itself does not yet match it until the same PR's own later activation, mirroring D-090/D-091/D-099's own within-repository sequencing, just compressed into one already-open PR rather than two sequential ones since no separate branch exists to stage from). Revert D-099 out of `main` to unblock PR-8 (rejected -- D-099 is an independent, already-reviewed, already-active improvement with no relationship to PR-8's own scope; reverting it to resolve an ordering accident would discard real, working CI-time savings for no benefit). Keep D-091's original digest active and let D-099 be the one to compose (rejected -- moot in practice, since D-099 already activated on `main` before PR-8's own merge; by the time this was discovered, D-099 was already the live digest and PR-8's own branch was the one needing to catch up).
- Consequences: PR-8's `ci.yml` now carries both D-091's and D-099's changes together, and `workflow-policy.yml`'s audit job passes against `main`'s current `check_roadmap_evidence.rb` once this composed digest is registered. Future PRs that touch `ci.yml` while another concurrent, unrelated activation is in flight face the same class of transient audit failure this decision fixes -- this is an accepted structural property of the two-phase trust boundary (D-080) combined with concurrent independent CI work, not a defect introduced here; `docs/DECISIONS.md`'s own append-only, supersede-don't-edit convention is what makes recovering from it tractable each time it happens (D-090→D-091, D-091(+D-099 ordering)→D-100).

  **Update:** this decision's own Alternatives section was wrong about skipping the stage-then-activate split -- real CI on this exact PR-8 branch refuted it directly: `workflow-policy.yml`'s audit job failed with "does not match a reviewed active-or-staged performance CI workflow" on every push after this commit, precisely because `main`'s own copy of `check_roadmap_evidence.rb` (which the base-owned audit executes, not PR-8's own copy) had no record of `D100_COMPOSE_D91_D99_CI_WORKFLOW_SHA256`. A separate stage PR, [#231](https://github.com/rotnov/pycc/pull/231), registers that digest (alongside active D-099, matching D-090's/D-099's own stage-alongside-active pattern) without touching live `ci.yml`; PR-8's own already-composed `ci.yml` and this decision's own text needed no further changes once #231 merges. The composed digest value, the `ci.yml` content it covers, and this decision's core reasoning (compose D-091 with D-099 rather than reverting either) all remain correct and unchanged -- only the "no separate stage PR needed" claim was refuted.
