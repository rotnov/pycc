## D-040: Function bodies resolve sibling calls against the module's shared function registry

- Status: accepted (PR-4 Task 9 follow-up, `pycc_types`) -- supersedes D-039's "Alternatives" deferral of sibling-to-sibling calls
- Context: D-039 deliberately deferred sibling function calls, reasoning that no fixture exercised the case. That reasoning didn't hold up: `def helper(x: int) -> int: return x + 1` plus `def main() -> None: print(helper(5))` plus `main()` is ordinary, valid Python -- and, verified directly against the built `pycc` binary, it was rejected with `T0021: call to undefined function `helper``. The root cause is exactly what D-039 flagged as a known gap: `check_function` (called from `check()` for every `HirItem::Function`) built its own `Environment::new()` from scratch, so only a function's *own* signature (self-registered for recursion) was ever visible inside its body -- a sibling's signature, even though already present in `check()`'s module-level `env`, was never threaded through. A compiler that rejects one ordinary function calling another is a correctness defect in a PR-4 headline feature (function definitions and calls), not a documented scope boundary.
- Decision: `check_function` is split into a thin public wrapper (unchanged signature, still seeds a fresh, self-only `Environment` -- so its own existing unit tests keep testing exactly what they tested before) and an internal `check_function_in(module_env: &Environment, function: &HirItem)`, which starts from `module_env.child_for_function()` -- a new environment with empty local bindings but the *module's full function registry* cloned in. `check()` now calls `check_function_in(&env, item)` (its own module-level `env`, already populated by D-039's pre-registration pass) instead of the old `check_function(item)`. `Environment::child_for_function` is a private helper (`bindings: HashMap::new(), functions: self.functions.clone()`) -- local variables never leak into a function body's scope (correct, since Python functions don't see their caller's or the module's locals without `global`/`nonlocal`, which v0.1 doesn't support), but the function registry does, in both directions (a function can call one defined earlier or later in the file, matching D-039's own forward-reference reasoning).
- Alternatives: keep `check_function` fully isolated and special-case `main`-only top-level calls (rejected -- this is exactly the "doesn't generalize" alternative D-039 already rejected, and it would leave the newly-confirmed sibling-call bug unfixed); thread the whole module `Environment` (including top-level bindings) into every function body (rejected -- would incorrectly let a function body read module-level variables as if they were closures, which isn't real Python scoping and isn't in TYPE_SYSTEM.md's rules).
- Consequences: any module-level function can now call any other module-level function, regardless of definition order, closing the gap D-039 left open. `check_function`'s public behavior (self-only visibility, used by its own pre-existing unit tests) is unchanged and covered by `check_function_the_public_api_still_has_no_sibling_visibility`. New regression tests `a_function_can_call_a_sibling_function_defined_before_it` and `a_function_can_call_a_sibling_function_defined_after_it` cover both directions at the `pycc_types` level; an end-to-end CLI test isn't added because D-035 keeps PR-4 frontend-only -- lowering a function body with a `Return(BinOp(...))` isn't wired up in `pycc_mir`/`pycc_codegen` until PR-5, so the fixture above type-checks cleanly but still panics at the documented "codegen lands in PR-5" boundary if actually built.
