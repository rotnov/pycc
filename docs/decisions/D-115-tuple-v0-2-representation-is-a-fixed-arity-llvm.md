## D-115: tuple[...] v0.2 representation is a fixed-arity LLVM struct-of-scalar-fields, held as an SSA aggregate value — no heap object, no refcounting question

- Status: accepted
- Context: `docs/TYPE_SYSTEM.md` (line 55) already says tuple's representation is "fixed heterogeneous ... inline struct (stack when non-escaping)". `Ty::Tuple(Box<Vec<Ty>>)` already exists as a stub (`crates/pycc_hir/src/lib.rs:54`); `pycc_codegen::ty_to_basic_type` currently panics for it (`crates/pycc_codegen/src/lib.rs`, locked in by `ty_to_basic_type_panics_clearly_for_tuple`). Unlike `list[int]`/`dict[str,int]`/`set[int]` (all heap-allocated, pointer-referenced `pycc_rt` objects), every v0.2-accepted tuple element type (`int`/`bool`/`float`, per D-116) is a fixed-width scalar with a compile-time-known count — LLVM's own aggregate (`struct`) value type models this directly, with no allocation needed at all.
- Decision: `ty_to_basic_type` maps `Ty::Tuple(elems)` to `context.struct_type(&field_types, false)` (not packed — ordinary field alignment). `pycc_codegen::Scalar` gets a new `Tuple(StructValue<'ctx>)` variant holding the whole aggregate **by value** — an SSA register, not a `PointerValue` to a heap or stack allocation, unlike every existing container variant. Construction uses `struct_type.get_undef()` followed by one `Builder::build_insert_value` per element (LLVM's `insertvalue`); reading `t[k]` for a literal, in-range `k` uses `Builder::build_extract_value` directly on the already-loaded `StructValue` (LLVM's `extractvalue`) — neither operation needs a pointer, so `Builder::build_struct_gep` (the facility this PR's original research assumed would be needed) turns out to be unnecessary for this slice: nothing here ever addresses a struct field through a pointer, only whole-value insert/extract on an SSA aggregate. Storage for a tuple-typed local needs no special-casing: `declare_module_globals`/`storage_slot_at_entry`/`emit_assign` already generalize over any `BasicTypeEnum`/`BasicValueEnum` via `Builder::build_store`/`build_load`, and `inkwell`'s `BasicValueEnum`/`BasicMetadataValueEnum` both already include a `StructValue` variant (verified against the installed `inkwell = "0.9.0"` source, `src/values/enums.rs:70-73`), so an alloca's store/load, an argument-marshalling site, and a function's return value all accept a `Scalar::Tuple`'s payload with a plain `.into()`, identically to `Scalar::Str`/`List`/`Dict`/`Set`'s own pointer payloads.

  Refcounting has no question to answer here (unlike D-124's extension of D-107 for dict/set): D-116 excludes `Ty::Str` from tuple's v0.2 element types specifically so that no tuple ever contains a refcounted field, so `compile_to_object`'s `Ty::Str` exit-time decref loop (`crates/pycc_codegen/src/lib.rs`, iterating `module_globals.values()`) is correctly untouched by this PR — a plain enum equality check that structurally can never match a `Ty::Tuple(_)`-typed slot regardless of that tuple's own element types. A tuple containing a `str` field would need real per-field teardown logic this project has never had to write for any type (a struct's fields need individual inspection, unlike every existing container, which is a single opaque pointer) — deferred to whichever future PR widens the element-type gate to include `str`.
- Alternatives considered:
  - A heap-allocated `pycc_rt` runtime object (`PyTupleObj`), pointer-referenced like `PyIntListObj`/`PyDictObj`/`PyIntSetObj` — rejected: a heap allocation buys nothing for a fixed-arity, fixed-layout aggregate of scalar fields known entirely at compile time, and would reopen D-124's leak-only-refcounting question for a fourth heap type where D-116's own element-type gate makes the question moot for an SSA-value representation.
  - `Builder::build_struct_gep` plus a stack alloca, mirroring the original research's assumption — rejected once `build_insert_value`/`build_extract_value` (operating directly on an SSA `StructValue`, no pointer or alloca required) were confirmed present and sufficient for this slice's read-only, whole-tuple-construction scope; kept as the natural upgrade path if a future PR needs field mutation (which Python's own tuples do not support anyway) or a tuple large enough that by-value passing becomes a real cost.
- Consequences: `ty_to_basic_type`'s `Ty::Tuple` arm and its own dedicated test (`ty_to_basic_type_panics_clearly_for_tuple`) both change in Task 5 of `docs/superpowers/plans/2026-08-01-v0-2-pr11-tuple.md` — the test's very name asserts a panic that Task 5 replaces with real struct-type construction. A future PR widening tuple's element types to include `str`/any container needs to revisit this ADR's "no heap object" premise for whichever field types are refcounted or themselves pointer-sized-and-owning.
